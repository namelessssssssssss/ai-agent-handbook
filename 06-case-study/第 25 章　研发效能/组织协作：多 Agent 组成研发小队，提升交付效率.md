# 组织协作：多 Agent 组成研发小队，提升交付效率

## 一、痛点：编码快了 10 倍，需求上线为什么只快了不到两天？

团队拿一个复杂 Feature 的典型排期算过一笔账：从提出需求到上线一共约 **20 个工作日**，其中真正写代码只占约 **2 天**。就算 Coding Agent 把写代码效率直接拉高 10 倍（从 2 天压到 0.2 天），端到端总周期也不过从 20 天降到 **18.2 天**。

原因很简单：研发从来不是纯写代码，真正吃掉剩下 18 天的，是需求与规格反复对焦、对照存量架构定方案、等测试和 Code Review 反馈、拉跨模块环境联调，以及发现方向错了之后整条链路打回重来。

所以提效的重点不再是继续压榨那 0.2 天，而是让一支 **AgentTeam** 接管并跑通整条协作链路——省掉角色之间反复转述上下文的损耗，让测试和审查结果直接驱动下一步返工，人只在目标、架构和风险拍板时出手。

---

## 二、AgentTeam：由 15 个角色组成、AgentCore 统管的研发小队

这套体系不是放一群 Agent 各自自由发挥，而是把 **15 个面向不同工序的 Agent** 放进能力池，由 **AgentCore** 当 Leader 统筹拆解任务、调度角色、维护状态与共享上下文，代表性角色分工如下：

| 角色 | 核心职责 | 关键产物 |
| --- | --- | --- |
| **Researcher** | 吃透需求和老代码，画出问题证据地图 | 相关模块、约束与历史变更 |
| **Explorer** | 在代码库里找同构老实现，拟出候选方案 | 参考锚点（Reference Anchor）与方案对比 |
| **Spec** | 把目标、边界和验收条件落成结构化契约 | 可执行规格说明（Spec） |
| **Code Worker** | 在独立分支和会话里写代码实现方案 | 代码变更 |
| **Test / Harness** | 跑编译、单测和端到端验证 | 可复现的测试证据 |
| **Judge / Verify** | 独立做多方案选优、语义验收与对抗审查 | 审查结论与失败反馈 |
| **Deploy** | 准备环境并执行发布验证 | 发布与回滚证据 |

任务从 Issue（或聊天补充信息）进门后，AgentCore 根据失败性质决定往哪退：单测或编译没过，就保留当前代码会话上下文继续修；方案方向就错了，带着失败证据退回给 Researcher 和 Explorer 重选路径；连续几轮不收敛，立刻触发人工闸门（Human Gate）叫工程师介入。最终交出来的不止是一份 PR，还有测试报告、审查证据、进度状态和全链路 Trace。

## 三、双层 Coding Loop：内层保“跑得通”，外层保“没改偏”

多 Agent 能不能真正干成活，不取决于堆了多少个 Agent，而在于反馈闭环怎么接。核心 **Coding Loop** 拆成内外两层：

1. **前置锚定**：Researcher 先建问题证据地图，Explorer 翻出仓库里最像的现有实现做参照，产出一条或多条候选路线。
2. **内层循环（代码能不能跑）**：每个候选方案进独立分支和独立会话，Code Worker 改完交给 Test / Harness 编译验证，挂了就带着报错原地续修，直到绿灯或确认卡死。
3. **外层循环（方案是不是对）**：独立的 Judge / Verify 登场，不光看单测全绿没有，还要严查有没有满足原始需求语义、有没有违背既有架构——专抓“测试跑通了但实现方向歪了”的隐患。边界小毛病保留代码局部修补；方案级失误直接退回 Research / Explore 重来。

支撑这套循环的四个硬设计：

- **参考锚定**：先找现有同构代码和约束再动笔——老代码未必完美，但往往比文档更真实新鲜。
- **生产与验收分离（Produce / Verify 分离）**：写代码的和做 Judge 验收的绝不共用同一个会话，防止同一个 Agent 拿自己定的尺度证明自己没错。
- **带失败记忆迭代**：返工续接原会话并带上前面每一轮的踩坑记录，不用每退回一次就从零重读代码。
- **分级放行**：正确性、安全与架构偏离一票否决必须改；非阻塞小优化记档即可；持续不收敛果断转人工。

## 四、用 AgentLoop 数据飞轮让小队持续长本事

跑通一次只能证明链路能动。业务和代码天天在变，今天调好一个 Prompt，明天可能顺手把别的任务调坏。因此团队用 **AgentLoop** 接住 AgentCore 的运行底座，采集全量 Trace、会话和执行轨迹，并跑两条数据飞轮：

- **离线 Meta-Loop**：拿人类工程师的历史 Commit 反向抽题，把标准答案藏起来让 AgentTeam 独立解题；跑完后拿它的 Diff 和轨迹去跟专家原解对照，反查是哪个 Skill、工具还是状态流转拖了后腿，改完再用原题和留出盲测题做回归验证。
- **在线 Experience Loop**：从真实线上成功与失败轨迹里自动提炼 SOP、有效工具链、修复规则和反模式；经过来源、适用范围和效果核验后，下次碰到同类任务时按语义召回，动态塞进 Researcher、Explorer 或 Code Worker 的上下文里。

## 五、阶段性真实账本：先跑通闭环，再谨慎评估提效

目前公开数据保持克制，先看两个已跑通真实上线闭环的生产任务：一个是修复 Trace2Trajectory 的非标轨迹清洗 Bug，另一个是给数据处理管线新增算子——两者都走完了改代码、测试、审查到正式上线全流程。

在离线盲测校准中，团队从内部整理了 24 道基线题，拿其中 **19 道未参与调优的新题**做盲测，逐题对照人类专家代码：

| 盲测结果分类 | 题数（共 19 题） |
| --- | --- |
| 与专家方案等价 | 10 道 |
| 接近专家方案 | 5 道 |
| 部分完成 | 4 道 |
| 方向性错误 | 0 道 |

这个结果说明流程和机制已经能有效拦住“改偏方向”的硬伤（0 道方向错误），但它属于内部题集测试，不等同于任意生产任务的直接通过率。线上交付侧，少量 Feature 样本观察到的平均交付节奏约一周左右，由于样本还少且没按复杂度分桶，目前只作阶段性观察参考。后续会继续紧盯独立验收通过率、人工 Review 耗时、单位交付成本和上线缺陷率这四项硬指标。

说到底，AgentTeam 不是为了把程序员赶下场，而是把人从“传话、跑测试、等反馈”的机械劳动里拔出来——**可执行、可验证、可回放的交给 Agent 团队跑，目标、架构、风险和最终放行权牢牢留在工程师手里。**
