# 组织协作：数据库领域，从报警到自动修复的端到端实践

## 一、痛点：分布式数据库修 Bug，最耗时的不是写那几行代码

云原生分布式数据库 PolarDB-X（高度兼容 MySQL、支持水平扩展和 HTAP）对稳定性和正确性要求极高，因此修 Bug 从来不是最容易的那种任务。

![image](../../assets/imgs/chapter-25/image-009.png)

_图 1：PolarDB-X 整体架构_

团队把日常研发拆成两类，采用完全不同的人机协作姿势：

- **新功能与深度优化**（如改分布式事务、做新数据压缩）：方案需随测试不断打磨，采用**研发定方案把关 + Agent 跑编码测试**的模式。
- **报警、工单与缺陷修复**：这才是团队最头疼的效率瓶颈。最终改代码往往只有几行，但之前研发得自己捞实例版本、扒监控和海量日志、对照源码猜原因、搭环境造条件复现，改完还要对照验证加全量回归。**前面查现场、后面搞复现占了绝大多数时间，只让 Agent 写那几行修复代码根本省不下多少精力。**

但这类任务有个天然优势——它有具体故障现象，可以靠“能不能稳定复现”和“修前必挂、修后必过”作为铁打的验收尺子。于是团队决定把 Agent 的起点直接往前推：从接到一条报警或工单开始，自己查现场、自己跑环境验证、自己写复现用例和修复代码，研发只留在最后审一遍证据和 Diff。

## 二、PolarDB-X Loop：如何把“靠猜”变成“可复现的自动化闭环”

![image](../../assets/imgs/chapter-25/image-010.png)

_图 2：PolarDB-X 缺陷自动修复流程。验证结果决定下一步继续推进，还是返回分析与修改。_

整个自动闭环叫 **PolarDB-X Loop**：Agent 吃进报警或工单，自己拉现场信息 → 提假设并动手复现 → 跑不通就拿新证据修正假设 → 稳定复现后改代码并把复现步骤固化成测试用例 → 过完修前修后对照和全量回归才准提 PR。

团队在实战中摸出一条最关键的判断：**对于缺陷修复，最值钱的一步不是写代码，而是“稳定复现”**——因为分析阶段靠它证伪假设，修复阶段靠它固化验收标准，代码评审时研发也靠它先核对“是不是真修中了靶心”。要让这三步全由 Agent 自己走通，必须补齐三套硬能力。

## 三、三大核心实战：取证 CLI、运行时调试与复现门禁

### 1. 现场取证：把零散网页端操作封装成 Agent 顺手的 CLI

早期工程师得手动截监控图、剪日志片段喂给 Agent，Agent 想换个节点或拉长十分钟时间窗就只能干等。

![image](../../assets/imgs/chapter-25/image-011.png)

_图 3：CPU 使用率监控截图。_

第一步是集中管理分散在各生产节点上的日志，并用结构化接口或 CLI 替代手工截图。比如通过阿里云 CLI，Agent 一行命令就能拉回指定时段两个计算节点的 CPU JSON 数据，自己顺藤摸瓜继续深挖：

```bash
aliyun polardbx DescribeDBNodePerformance \
  --RegionId cn-hangzhou \
  --DBInstanceName pxc-xxxxxxxxx \
  --DBNodeIds "pxc-i-xxxxxxx,pxc-i-yyyyyyyy" \
  --CharacterType polarx_cn \
  --Key Cpu_Usage \
  --StartTime 2026-09-03T03:51Z \
  --EndTime 2026-09-03T03:53Z
```

简化返回示例（标识与数值仅作演示）：

```json
{
  "PerformanceKeys": [
    {
      "DBNodeId": "pxc-i-xxxxxxx",
      "Measurement": "Cpu_Usage",
      "Points": [
        { "Timestamp": 1788407460000, "Value": "92.6" }
      ]
    },
    {
      "DBNodeId": "pxc-i-yyyyyyyy",
      "Measurement": "Cpu_Usage",
      "Points": [
        { "Timestamp": 1788407460000, "Value": "28.3" }
      ]
    }
  ]
}
```

但很多老内部平台根本没人写 CLI。团队从阿里内部一位普通研发在没源码的情况下写出“抢会议室 CLI”受到启发：

```bash
ali meeting book -r <roomId> -s <start> -e <end>
```

他们干脆让 Agent 自己去点浏览器使用存量监控/拓扑平台、抓取网络请求和认证方式，参考已有工具源码把这套功能封装出来。前后只用了**约一周时间**，Agent 就把常用监控、日志、拓扑查询打包成了自建的 `polardbx` CLI。

![image](../../assets/imgs/chapter-25/image-012.png)

_图 4：自建 PolarDB-X CLI 的命令分组。_

在此基础上，诊断方法、指标字典、日志查询模板和采集脚本一并打包成 `polardbx-diagnostics` Skill，Agent 碰到报警不再需要人手把手喂图，而是自己顺着线索一查到底。实际上手后团队甚至发现，在整理海量日志时间线和跨节点找隐蔽线索这件事上，Agent 往往比人工更细、更不易漏。

### 2. 实战转折点：一桩悬了 5 年的 MDL 锁泄漏，逼出运行时调试能力

光会查日志和看源码，照样会在复杂并发 Bug 前面翻车。

团队遇到过一个**悬了五年的元数据锁（MDL）泄漏老案**：线上低概率发生，一旦泄漏就会把后续所有改表结构（DDL）卡死。之前结合现场与源码，Agent 很快“推理”出一份看起来头头是道的并发时序报告：

| 时序 | 主线程（ServerExecutor） | KillExecutor 线程 |
| --- | --- | --- |
| 1 | 获取第一把 MDL 锁，写进当前连接的锁记录集合 | — |
| 2 | 准备拿第二把锁，拿到同一个锁记录集合但还没写入 | — |
| 3 | — | 响应用户 KILL 操作，开始关连接 |
| 4 | — | 释放第一把锁，把已清空的锁记录集合从连接索引移除 |
| 5 | 继续获取第二把锁，写进了已脱离索引的集合 | — |

Agent 据此断言第二把锁脱链泄漏了。结果工程师搭环境花了约两小时真跑了一遍，**发现这套推测压根不成立**——只静态读源码漏掉了状态守卫和多处释放路径，把“理论上可能”当成了“实际上会跑”。Agent 连着改了好多版报告，始终隔靴搔痒。

![image](../../assets/imgs/chapter-25/image-013.png)

_图 5：Agent 在多轮分析中生成的报告和测试文档。_

这次踩坑让团队顿悟：**不给 Agent 下断点、控线程和查内存的工具，每次推理出错就得靠工程师亲手去证伪。** 于是他们给 Agent 补齐了三样运行武器：

- **可保持会话的 JDB CLI**：JDK 原生 jdb 是给人在终端交互用的，Agent 每次调用进进出出留不住断点现场。团队基于 JDI 重写了一版——后台守护进程一直维持调试会话，前台命令行随时进出下断点、看变量、步进恢复；更关键的是支持**指定线程断点**，命中时只暂停目标线程，其余线程照常跑，让 Agent 能精准摆布线程并发交错时序。

![image](../../assets/imgs/chapter-25/image-014.png)

_图 6：前台命令独立调用，后台持续保留调试会话。_

- **大内存 ECS 上的 Heap Dump OQL 查询接口**：Java 堆快照动辄几十上百 GB，团队直接把快照挂在大内存云服务器上集中加载，暴露 HTTP OQL 查询接口让 Agent 自己去翻锁对象和引用链（该平台已累计处理两千多份 Heap Dump 任务）。

![image](../../assets/imgs/chapter-25/image-015.png)

_图 7：大内存 ECS 加载 Heap Dump，Agent 通过 HTTP 接口发起 OQL 查询并获取结果。_

- **两套按需选择的复现环境**：

| 环境 | 适合场景 | 用法 |
| --- | --- | --- |
| **PolarDB-X Zero 临时实例** | SQL 报错、普通功能异常快速复现 | 起最新版临时实例，验完即销毁 |
| **K8s 完整复现环境** | 依赖特定老版本、多节点拓扑或并发时序控制 | 按原故障实例版本拓扑拉起，挂上 JDB CLI 精细调度 |

工具齐活后，Agent 自己上 K8s 复现环境试那个 MDL 锁泄漏。头几次没触发，它就对着真实运行路径改断点位置，几轮之后竟然自己抓到了人当年也没盯住的真正条件：**必须在连接刚建立、还没进入语句执行状态之前发起 KILL，再卡准后面关连接与拿锁的交错顺序。**

![image](../../assets/imgs/chapter-25/image-016.png)

_图 8：Agent 通过指定线程断点控制执行顺序，复现 MDL 锁泄漏及后续 DDL 阻塞。_

一个依赖随机调度才会冒头的 5 年疑难并发 Bug，就这样被 Agent 转化成了每次必现的确定性操作步骤。

### 3. 交付门禁：先审复现证据，再看修复代码

找到了确定性时序，Agent 直接通过特殊 Hint 在代码关键点注入延迟，把这组并发交错固化成可反复运行的自动化测试用例，并踩实一条硬门禁：**这个用例在修前必须能复现原故障，修后必须稳过，再加上全量回归全绿，才允许提合并请求。**

PR 里一并附上代码 Diff、复现用例、修前/修后对照截图日志与全量回归报告。工程师 Review 时顺序反过来了——**先看复现用例是不是真还原了线上那个 Bug，确认打中靶心再看代码改动**。

## 四、云端沙箱运行半年实绩与三条经验

为了让这套闭环 7×24 运转，团队在云端沙箱搭建了 **PolarDB-X Agent**，兼顾环境隔离（搞坏沙箱不污染研发本机）和最小权限管控（只开放任务必需权限）。

![image](../../assets/imgs/chapter-25/image-017.png)

_图 9：PolarDB-X Agent 云端平台，承载 Loop 的持续运行。_

在文中所记录的**半年生产实践中**：团队**所有线上报警已全部先由 Agent 完成首轮分诊与分析**；累计从**上万次报警中揪出两百多个真实代码缺陷**，其中**超过 70% 成功实现了稳定复现，并由 Agent 完成修复提交代码评审**。

对于其他想跟进的团队，三条可直接抄走的经验是：

1. **先把系统能力变成 Agent 调得动的接口**：集中日志、给常用查询包上 CLI（哪怕没源码让 Agent 自己抓包封装），再把排查套路写成 Skill。
2. **让 Agent 自己能在真环境里证伪自己**：复现环境、调试器、内存快照接口必须开放给它；用“修前必现、修后必过”卡死评审入口。
3. **放进云端隔离沙箱长跑**：配合最小权限，挑验收条件清晰的任务（如报警排查修复）切入，从头跑到尾打通整个 Loop 再向外扩展。
