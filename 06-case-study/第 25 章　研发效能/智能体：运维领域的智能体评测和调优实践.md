# 智能体：运维领域的智能体评测和调优实践

阿里云 STAROps 是基于大模型和智能体打造的 Agentic Ops 平台，已服务上千家客户。本文拆解 STAROps 在构建生产级运维评测集与调优闭环时的实战经验：为什么公开数据集直接拿来测会失真、一条可信的运维评测数据到底长什么样、如何用四个专门 Agent 流水线批量造题和验题，以及这套体系在真实投入和质量把控上的取舍。

---

## 一、背景：从“考场做卷子”到“真实猎场抓故障”

### 1. 运维评测集的演进

![运维评测集的快速发展](../../assets/imgs/chapter-25/aiops-agent-evaluation-01.png)

判断大模型或 Agent 的能力上限，大家习惯看评测报告。公开评测集适合横向对比，但企业要验证自己的运维 Agent，必须有贴合自身拓扑和业务特征的私有评测集。

上图整理了 30 多项运维相关评测资源，可以明显看出三个趋势：

- **数量集中爆发**：绝大多数评测集是近两年密集出现的。
- **领域不断外扩**：早期集中在遥测数据和少数可执行环境，后来延伸到专门考核因果推理的根因分析，并覆盖网络、数据库和 AI 基础设施。
- **考核方式剧变**：以前多半拿静态离线日志和指标出题，只比对最后答案对不对，像是在考场里填试卷；现在越来越多评测把 Agent 直接丢进可执行的真实运维环境里，像放进猎场看真本事——不仅看结论，还查它找了什么证据、有没有查对时间窗、能不能真把问题修好。

### 2. 一次根因分析到底要考什么？

![一次根因分析过程](../../assets/imgs/chapter-25/aiops-agent-evaluation-02.png)

拿 STAROps 的一次真实根因分析（RCA）来看：左边输入是下单错误、商品查询错误、前端异常三条告警；右边输出是根因实体、传播链、影响面和处置建议；中间核心是一轮又一轮**“判断 → 调用工具取证 → 调整假设”**的循环：

- 每轮先圈定可能受影响的服务和时间段；
- 列出嫌疑根因假设；
- 调工具查指标、日志、调用链、事件、拓扑和变更记录，否定不成立的假设；
- 带着剩余线索进入下一轮，历史排查经验还会决定“先查什么、后查什么”。

因为中间隔了这么多轮推理，**结论碰巧对了，不代表过程可信**。评测必须回答三个问题：这套分析套路换个故障还能不能用？如果错了，是工具没查到还是查到了没用对？有没有大量无效工具调用把上下文越塞越乱？

更隐蔽的一类翻车是图下方标的**时间窗查错**：Agent 工具调通了、拿到的也是真实数据、推理链前后完全自洽、甚至结论碰巧蒙对了——唯独它查的那段时间根本不是故障发生的时间窗。单看输出根本看不出破绽，所以评测数据里必须把故障的真实时间窗和告警锚点钉死，拿去对照 Agent 实际传给工具的时间参数。

## 二、一条靠谱的运维评测数据，必须满足什么条件？

### 1. 公开评测集的三大硬伤

![对评测集的一些需求](../../assets/imgs/chapter-25/aiops-agent-evaluation-03.png)

任何评测数据都要守住三条底线：**覆盖广、能重复跑、每条都证明自己真有效**（图中三栏数字来自外部公开研究，非 STAROps 自测统计）：

- **覆盖不足**：某个公开运维根因数据集在三套系统上覆盖了 27 类注入机制、500 个可评测实例，但放到真实生产环境里，故障花样远不止这些。
- **波动剧烈**：大模型随机性加上环境波动，同一 Agent 跑同一场景 10 次可能只成功 6 次——只跑一次、或者只挑成功那次记录根本作数不了。
- **因果悬空（有效性差）**：有些数据集往服务里注了个 CPU 故障，看到服务报异常就把 CPU 写成标准答案，却没证明异常真是这次注入引起的；另一项研究从 9,000 多次初始故障注入里按标准筛选，最后真正造成可感知异常、保留下来的只有 1,430 条。**命令执行了故障注入，不等于造出了一条有效考题。**

### 2. 一条运维评测数据的标准结构

![一条运维评测数据的构成](../../assets/imgs/chapter-25/aiops-agent-evaluation-04.png)

为了让每次评测能查错、能复现、跨版本可比，一条评测数据不能只存一个标准答案，而要打包存下完整快照：

- **五步分析轨迹**：**目标**（从哪几条告警出发）、**观测**（指标/日志/调用链/事件/拓扑/变更）、**工具**、**动作**（每轮判断和取证调用）和**结果**（根因实体、传播链、影响面、处置建议）。轨迹不强求 Agent 按死板路线走，但关键证据和关键判断必须能对上号。
- **两个绑定附件**：**配套条件**（当时的环境、工具版本与观测手段）和**核验依据**（固定不变的评分标准）。不存这两样，新版本 Agent 换了环境或换了判分尺度重跑同一题，分数涨跌就成了糊涂账。
- **四项运维特有约束**：
  - **环境绑定**：故障脱离真实服务和流量就不存在，数据必须和产生它的环境配置一起存；
  - **时间绑定**：调用链和日志过几天就会过期清理，线上问题回流必须第一时间保全时间窗与现场证据；
  - **完整因果链**：原因、传播链、影响面必须逐环挂证据；
  - **低频高风险**：生产事故不能反复往线上炸，要能在隔离评测环境里用故障注入按同一机制稳定复现。

## 三、十二步造题流水线：注入只是其中一小步

![STAROps 评测集的构建流程](../../assets/imgs/chapter-25/aiops-agent-evaluation-05.png)

构建一条根因分析评测数据，实际要走过四个阶段共十二步，真正耗时的大头不在执行故障注入命令，而在前后的准备、取证和两道严查：

1. **设计（Agent 主导）**：从能力地图空缺或线上真实回流问题里选题；结合架构设计注入什么故障、注在哪里、按什么路径传播。
2. **注入、验证与恢复（工具确定性执行）**：先核验未注入时的基线必须干净、流量正常、观测可用；执行注入后，还要分别确认“信号真的异常了”和“告警真的触发了”；最后把环境恢复干净。
3. **取证与写答案（Agent 主导）**：故障发生当场保全告警、信号和调用链，环境恢复后再拉取全程指标与日志，拼出完整因果，整理成七字段标准答案。
4. **检查与入库（程序 + 人工把关）**：先过**程序门禁**（字段是否齐全、每个数字附带的查询重跑是否一致），再过**准入复核**（先由独立 Agent 审因果链通不通、相似嫌疑排没排除干净，最后人工终审放行）。

数据入库后，被评 Agent 拿到相同输入去诊断，输出与标准答案逐字段比对。前面任何一步掉链子——比如故障根本没生效、证据过期没保住、门禁没拦住假数字——都会直接把评分带偏。

## 四、持续造题的四个核心难题与 Agent 分工

![构建评测集的四个核心问题](../../assets/imgs/chapter-25/aiops-agent-evaluation-06.png)

单条跑通只是开始，要长期批量造题并维持质量，绕不开四个互相咬合的问题：**题目从哪来、环境怎么搭、怎么保证题真有效、题库怎么持续防退化**。

![评测集构建中 Agent 分工](../../assets/imgs/chapter-25/aiops-agent-evaluation-07.png)

纯靠人工逐条梳理，产能很快见顶。STAROps 把这条造题流水线也交给了四个分工明确的 Agent，人对重复劳动退居二线，只抓三件核心决策：**定目标（补哪块短板）、定验收（答案和证据到什么标准）、终审（数据入库最后拍板）**。

| 负责 Agent | 对应环节 | 核心动作 |
| --- | --- | --- |
| **ScenarioAgent** | 选题目 | 对照能力地图找缺口、分析业务变更与架构风险、把线上真故障回流成题 |
| **EnvironmentAgent** | 搭环境 | 构建服务依赖拓扑、业务仿真链路、打入持续流量、接通指标/日志/链路/告警观测 |
| **BuildAgent** | 造题与复核 | 执行故障注入、捕获六项信号、提取七字段证据写答案；**注意**：准入复核时必须清空构建上下文，独立重查证据 |
| **SupervisorAgent** | 管质量 | 做五项体检、下架失效题目、在 Agent 修复后跑回归复测、在满分扎堆时主动加难 |

造评测集这件事本身，就是对一个组织 Agent 工程成熟度的压力测试——如果连找题、搭环境、取证据、交叉复核都还得靠人手工拼接，那说明基础设施、工具标准化和质量治理远没有到位。

## 五、题目设计、环境扩展与标准答案生成细节

### 1. 用“能力地图”主动规划覆盖面

![按能力域和难度规划场景](../../assets/imgs/chapter-25/aiops-agent-evaluation-08.png)

第一类出题来源是主动规划。团队拉了一张**能力地图**，横轴是 8 个能力域（代码与变更、应用运行时、数据库、容器、中间件、云产品、主机、网络），纵轴是 4 档难度（不是互斥分类，而是代表**要拨开多少干扰才能抓住根因**）：

- **单点故障**：一条异常一根线，例如配置改错、接口内部报错、慢查询、容器反复重启、队列积压、CPU 打满、磁盘写满、丢包。
- **有传播链**：顺着调用往回追，例如发布引发报错、依赖超时堆积、锁等待传导为调用方超时、节点驱逐降级、缓存击穿压垮数据库、主备切换断连。
- **多故障并发**：多个机制同时发作得拆清楚，例如发布叠加限流、限流叠加超时。
- **告警风暴**：十几个信号同时炸屏，真根因藏在噪音里（图中右上角作为下一批重点建设格子）。

地图上哪个格子空着，人定好优先级，就派 Agent 去补齐。

### 2. 线上真实故障回流：先保全，再还原

![线上问题还原成评测集](../../assets/imgs/chapter-25/aiops-agent-evaluation-09.png)

第二类来源是线上真实事故。它可能落进已有格子里充当真实样本，也可能揭露了地图上没登记过的新故障机制。处理顺序铁律是**先保全，再还原**：

1. **先保全现场**：出事当下立刻把轨迹、调用链、时间窗存下来，晚了日志链路就被清理了；
2. **机制还原（Agent）**：弄清故障触发的必要条件和因果机制，不能只照着报错表象瞎仿造；
3. **等价重放（工具）**：在评测环境里用同一机制重演一次；
4. **重建验证（程序）**：比对线上与重放信号的时序，出现先后顺序列对不上说明传播路径还原错了，直接打回重做；
5. **统一入库**：交由 BuildAgent 按同一套七字段标准生成答案并复核。

### 3. 按需扩展评测环境：先保观测，基线不清零不开工

![按需扩展评测环境](../../assets/imgs/chapter-25/aiops-agent-evaluation-10.png)

环境不为规模而扩，只在能力地图出现空白、线上出现新机制或需要隔离干扰时才扩。演进路径从最初一个单链路开源微服务样板，逐步补齐主机层注入与主机指标、云产品观测告警，再到做跨集群与多故障并发时克隆出第二套集群，并把流量拆成两层：

- **常态流量**：让系统像生产一样持续跑请求，故障一来立刻有业务受影响；
- **场景化流量**：专门打向目标传播链路，并用历史数据回放校准告警阈值，保证该响时响、平时不误报。

每次扩展走五步：读依赖与环境规划 → 按模板部署或克隆集群 → 接通两层流量与观测并固化注入/恢复配置 → **程序检查干净基线** → 产出可一键复刻的环境配置代码。基线检查卡得极严，观测缺失更是绝对一票否决——**宁可少测几类环境，也必须优先保观测**，因为看不到信号就无法证明故障真的发生过。

### 4. 构建循环与“七字段标准答案”

![基于故障注入的评测集构建循环](../../assets/imgs/chapter-25/aiops-agent-evaluation-11.png)

环境就位后，BuildAgent 沿着四步循环出题，任何一步不过立刻退回：

1. **故障注入**（复用固化脚本 / 改配置 / 改代码）：注入完绝不默认生效，必须用信号证明。
2. **信号捕获六必查**：告警源头是不是注入对象、同时期有无别的环境变更、根因指标是否真异常、异常是否沿调用链传播、上下游影响面是否匹配，以及最致命的**噪音干扰**（同时间窗撞上别人的故障，数据直接作废）。
3. **提取七字段标准答案**：
   - **根因实体**：写死到具体服务或资源；
   - **故障类型**：写明可验证的机制，不写表面现象；
   - **因果链**：原因、传播、影响三段分开写；
   - **鉴别点**：写清为什么排除了长得像的其他嫌疑对象；
   - **告警锚点**：锁死实际触发的事件和时间窗（专治“查错时间窗”）；
   - **关键数字 + 原查询**：**写不出可执行查询的数字，一律不准进标准答案**；
   - **按字段独立评分规则**：根因猜对但传播链猜错时能如实拆开扣分。
4. **独立准入复核**：重开干净上下文独立取证核对，再交人工终审。

这里有一个真实踩坑案例：某条答案原本写着“错误率约 25%”，人工肉眼审读觉得挺合理；结果上工具重跑连续五个时间窗一查，错误数全为零。还有些接口受返回条数上限截断、或者拿不同长度的基线窗与故障窗直接作比，看着合理其实全错。从此团队定下死规矩：**程序只认重跑查询出的真实数值，不认文字写得像不像。**

## 六、上线之后怎么防退化？五项体检、规模与真实账本

### 1. 评测集的五项持续体检

![评测集的质量检查](../../assets/imgs/chapter-25/aiops-agent-evaluation-12.png)

基础镜像、告警规则一改，昨天还好好的题今天就可能跑不通。团队用五项短板检查持续盯住题库质量（按最弱那项打分，不能拿平均分掩盖漏洞）：

1. **质量**：七字段全不全，每个数字附带的查询重跑对不对得上；
2. **覆盖**：对照能力地图还有哪些域和难度空着；
3. **区分度**：强弱版本模型/Agent 跑出来能不能拉开分差；
4. **规模**：样本量够不够支撑置信结论；
5. **新鲜度**：**不看题建了多久，只看抽样原样重跑还能不能跑通**。

发现失效数据立刻下架，绝不让“坏考题”误导研发去修不存在的 Bug；被评 Agent 修复缺陷后，也只在仍然有效的题目上跑回归复测。

针对最容易被忽略的**区分度**（图右侧曲线）：当强弱两条能力曲线双双摸到满分天花板时，分不出到底是 Agent 变强了还是题太简单。做法是在中间竖虚线处**主动加难**——把单点故障换成有传播链、多故障并发或叠加告警风暴。如果分差重新拉开，说明原有题库确实失去区分度；加难后分数下滑是正常的，不能误读成 Agent 能力退步。

文中也对照了外部研究的同向验证：PAIChecker（2026 年 8 月）查出 SWE-bench Verified 500 题中一成多描述与修复不对齐（质量）；CORE-Bench（2026 年 6 月）头部方案逼近满分（区分度）；2026 年 7 月研究按置信区间定样本量（规模）；ICML 2026 的 MMBench-Live 限定只抓一年内新图出题（新鲜度）。

### 2. 当前规模与自建理由

![STAROps 评测集规模](../../assets/imgs/chapter-25/aiops-agent-evaluation-13.png)

截至 9 月，STAROps 累计沉淀 **1,400 多条**评测数据（含在建与已复核）。其中通过复核的有效**根因分析题 838 条**，覆盖 100 多类故障（相比 3 月时的 58 条，半年涨了 10 倍以上），另有**取数能力评测 500 多条**。坚持自建核心原因有三点：自己的服务拓扑和告警规则别人没有、线上不断冒出的新故障机制公开集里没有、环境变了需要能立刻重跑自证。

### 3. 真实成本结构：总花销未必降，省下来的是重复人工

![构建评测集的成本投入](../../assets/imgs/chapter-25/aiops-agent-evaluation-14.png)

上图展示了投入结构的相对变化（示意曲线，非实测账单）：

- **起步期**：人工占绝对大头，手工跑通少数场景，环境刚搭一套，模型调用很少；
- **补齐环境与判据期**：要把业务流、观测、告警补全，环境开销急追上来，人工在反复试跑修判据时见顶；
- **成熟复用期**：环境配置能一键复制、校验规则能复用，人退到维护标准和处理异常，重复劳动大幅回落，模型调用量随后超过人工，但**最贵的一块变成常年运转的集群、流量与观测环境**。

换句话说，用 Agent 造评测集**不一定让总账单变便宜**——环境算力、Token 和审核都在持续花钱，它真正替代的是把资深工程师按在椅子上做重复造题与核对的体力活。（外部两项 2026 年夏季研究也印证了自动化建题需保留人工把关，其中一项实测每条合格任务约 40 美元、耗时 1–2 小时。）

### 4. 开放生态与下一步

![开源开放共建](../../assets/imgs/chapter-25/aiops-agent-evaluation-15.png)

开放侧沿着三个方向推进：**开源**（RCA100、RCA200 已开放，后续陆续放出更多数据集与评测方法）、**共建**（接更多团队真实环境）和**重建**（把公开场景描述搬进真实环境重构，后两项仍在规划方向阶段）。自动化侧的下一步，则是把缺口探测直接接上造题管线——地图空了、某类分数摸顶了、线上出了新故障，系统自动拉起下一批造题与难度升级。

---

## 小结：三条拿得走的铁律

回头看，STAROps 评测工程之所以转得起来，靠的是三条硬原则：

1. **标准答案只能长在可重跑的证据上**（没查询的数一概不认）；
2. **复核的独立性靠清空上下文重查来保证**（不让出题人顺着旧上下文批卷子）；
3. **评测集自己也是活软件，必须持续体检、下架坏题、主动加难**。

判断一个运维团队够不够 AI Native，不妨拿造评测集做块试金石：理想状态不是人肉把几百个 Agent 串成工坊，而是**人定目标与标准，Agent 自主拆解协作，底座提供可复刻环境与标准工具，系统自动校验，人只留给异常和终审**。
