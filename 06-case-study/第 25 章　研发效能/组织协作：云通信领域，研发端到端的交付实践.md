# 组织协作：云通信领域，研发端到端的交付实践

## 一、痛点：代码产量翻了 N 倍，需求交付周期却没变短多少

阿里云通信研发团队在 AI Coding 上走过三段路：2024 年铺开代码补全和对话编程；2025 年把研发规范和领域知识沉淀成项目宪法和 Skill；2026 年开始转向全流程 Agent 协同的端到端交付。

![fig1-1-三段演进.png](../../assets/imgs/chapter-25/image-018.png)

_图 1-1　AI Coding 三段演进_

前两段跑完后，团队遇到一个很现实的尴尬：AI 写出的代码量翻了几倍，可一个需求从提出到上线，总交付周期只缩短了一小截。回头一拆整条链路才发现：**编码提效根本不等于交付提效**。真正把吞吐卡死的，是编码前后仍然得靠人肉衔接的三个节点：

1. **需求澄清卡在人**：PRD 要素缺胳膊少腿，Agent 开不了工，还得研发和产品来回对齐补上下文。
2. **代码评审卡在人**：Agent 动辄一口气吐出上万行代码，最后还是得工程师一行一行看，审不过来直接堵死。
3. **测试排期卡在人**：编码产出猛涨，人力测试队列瞬间爆仓。

只要交付链路上还留着“人工中转站”，那几个站的吞吐上限就是整条链路的上限。但要把整条链路交给多 Agent 协同自动跑起来，又有三个硬问题绕不过去：**Agent 之间怎么交接才不丢上下文？Agent 的权限和出事责任算谁的？怎么安全接入现有生产体系而不炸线？**

![fig1-2-编码与交付对比.png](../../assets/imgs/chapter-25/image-019.png)

_图 1-2　编码与交付对比_

团队没有在“怕出事干脆不用”和“跳过底座建设纯靠大模型硬抽卡”两个极端里打转，而是拿出了三件套解法：**标准化流水线 + 数字分身 + 渐进式门控落地**。

## 二、核心架构：为什么用“数字分身”，而不是招一个“独立 AI 工程师”？

很多团队喜欢把 Agent 当成一个独立的“虚拟员工”来建账号、分配权限，但研发工作一旦出错就是线上事故——独立 AI 账号立刻引出三个麻烦：权限到底给多大、代码出 Bug 谁背锅、谁来负责维护它的经验库？

云通信团队选择了**数字分身**模式，把 Agent 定位成研发负责人在数字世界里的延伸：

- **权限直接复用负责人**：人在公司系统里能看哪些库、能改哪些代码，分身就在同一套边界里干活，不用另搭权限体系；
- **责任直接锚定负责人**：系统里看到的提交人、审批流始终挂在人名下，谁的分身干了什么、改了哪行代码一清二楚；
- **谁受益谁维护**：负责人亲手喂养应用物料和领域知识，分身顺手把杂乱经验沉淀下来，反过来帮人把知识库补扎实。

### 1. 7×24 小时自动作业闭环

![fig2-1-作业闭环.png](../../assets/imgs/chapter-25/image-021.png)

_图 2-1　作业闭环_

数字分身同时充当需求总入口和路由器。产品或业务方直接把需求发给负责人的分身；分身接单后先对照当前能力等级裁决——接得住就一路跑完需求对焦、技术方案、编码、自检、测试整条流水线；接不住就立刻转交研发负责人走人工开发。

### 2. 四层架构与“2–3 天”快速装载

![fig2-2-四层架构.png](../../assets/imgs/chapter-25/image-022.png)

_图 2-2　四层架构_

整套体系从下往上分四层：

1. **工具层**：以钉钉机器人做 IM 交互入口（收需求、澄清需求、关键点请求人类拍板），配合云端 Agent 执行平台（独立代码工作区与构建部署）和状态图编排引擎。

![fig2-3-工具层.png](../../assets/imgs/chapter-25/image-023.png)

_图 2-3　执行链路_

2. **应用物料层**：把藏在老员工脑子里的隐性规矩显性化成六类可加载物料——规则、项目宪法、应用描述、架构文档、历史经验、编码规范——并做统一索引，供不同工序按需加载。物料越全，分身能承接的需求风险等级就越高。
3. **流水线层**：把交付切成九道责任明确的工序，由产品、研发、测试、质检、审计等不同数字分身和可插拔 Skill 配合推进，技术负责人 Agent 负责统筹收口。
4. **知识库与审计优化层**：每跑完一单，审计平台从数据、产物、过程三个维度扫描复盘，把发现的漏洞沉淀回物料或知识库台账，形成“越跑越强”的反哺循环。

只要前置条件齐备，给一位负责人装载并初始化这套分身只需要 **2–3 天**：接入钉钉机器人 → 拉起云端独立执行空间 → 补齐目标应用物料与知识库。装好之后，负责人的日常重心从“逐个需求写代码”退到了“维护物料和 Skill + 只在需求确认、方案确认两个节点拍板”。

![fig2-7-分身装载.png](../../assets/imgs/chapter-25/image-024.png)

## 三、防止多 Agent 跑偏的三项硬设计

要让全流程无人盯着也能稳跑，必须防住三个经典翻车点：上下文越传越失真、Agent 自查“王婆卖瓜”、系统跑久了经验退化。团队用三套机制堵死了这三个口子。

### 1. 契约链：拿不出正式交付物，休想往下流转

多 Agent 协作最怕上游自己觉得交差了，下游拿到的却是缺斤少两的口头总结（行业里叫“上下文丢失”）。团队把整条链路切成九道工序，并定死每一步必须交出结构化产物：

1. **需求门控**：比对需求风险等级（R）和分身能力等级（L），决定接不接单。
2. **需求对焦**：圆桌对焦补齐要素，输出结构化规格文件 `spec.md`。
3. **技术方案**：生成实现计划 `plan.md`，经独立评审和人工确认后才锁定。
4. **编码实现**：按 `tasks.md` 拆成可控小批次编码提交，并自动部署到测试环境。
5. **研发自检**：四个独立视角交叉审查，产出 `check_reports`。
6. **自动测试**：自动写用例、搭环境、跑测试，输出执行报告。
7. **平台质检**：按平台级合规要求做旁路复核。
8. **审计归档**：三层正交扫描整单过程，回流知识库。
9. **人工放行**：研发负责人最终核对产出物，合并上线。

![fig3-1-契约链.png](../../assets/imgs/chapter-25/image-025.png)

_图 3-1　契约链_

契约链靠两条硬门禁撑住：**强制交付物**（上一步交不出合格产物就卡死，绝不往下推进）和**运行时三重校验**（卡住标签格式、修饰符、发送者身份，杜绝 Agent 口头宣布“我干完了”蒙混过关）。而且契约链是跟着审计反馈长大的——团队曾发现某类需求在方案环节反复打回、对话轮次飙高，一查原来是物料里的规则模板漏了对应章节，补齐模板后返工率立刻掉了下来。

### 2. 交叉质检：互相不共享上下文，技术负责人 Agent 收口

![fig3-2-交叉质检.png](../../assets/imgs/chapter-25/image-026.png)

_图 3-2　交叉质检_

大模型天生有“自查护短”的毛病，自己审自己写的代码十有八九给通过。因此自检阶段拉了四个彼此隔离的分身——**产品、研发、测试、安全**——各自开独立会话和独立工作区，互不共享聊天历史，只加载代码 diff、规格文档、规则和知识库，分别盯着需求完成度、代码健壮性、安全合规性和功能测试结果独立出报告。

最后由**技术负责人 Agent** 拿着四份报告逐条对声明式检查点拍板：全部过关才放行；只要有一处打回，立刻退回编码分身返工，直到四个视角全都签字通过。

### 3. 渐进式门控 + Loop 归因：先做简单单，边跑边长本事

![fig3-3-需求门控.png](../../assets/imgs/chapter-25/image-027.png)

_图 3-3　渐进式需求门控_

每次接单前，系统根据模块跨度、是否核心链路、性能要求、是否涉及资金等维度算出需求风险等级（R），再对照物料完备度算出分身能力等级（L）：**只有 R ≤ L 才接单，R > L 直接转人工**。更关键的是 L 会动态升降——连续几次高质量交付就自动升级放开更多需求；一旦多次交付偏离预期就立刻降级收紧闸门。

![fig3-4-Loop闭环.png](../../assets/imgs/chapter-25/image-028.png)

_图 3-4　Loop 闭环_

每一单收尾的审计不做笼统打分，而是从数据层（规格与方案产物齐不齐）、产物层（跨文件协作是否对得上）、过程层（从日志算 Token 消耗与人工干预次数）做三层扫描，并精准归因到三条整改通路：**规则模板缺了改物料、工具掉链子改工具链、业务知识有盲区进知识库补齐**。改完经验证全局生效，下一单就不再踩同一个坑。

## 四、真实需求走一遍：一单简单需求的端到端之旅

![fig4-1-全链路.png](../../assets/imgs/chapter-25/image-029.png)

_图 4-1　端到端全链路_

下面是一个已脱敏的真实简单需求（单模块、非核心链路、可自测）在流水线里的完整跑法：

1. **钉钉下单与门控接单**：业务方在钉钉向分身发需求，分身核对 R ≤ L 后判定接受，拉起流水线。

![fig4-2-钉钉发送需求.png](../../assets/imgs/chapter-25/image-030.png)

_图 4-2　钉钉发起需求_

![fig4-3-需求门控.png](../../assets/imgs/chapter-25/image-031.png)

_图 4-3　需求门控_

2. **对焦与方案锁死**：圆桌对焦生成 `spec.md`，方案阶段产出 `plan.md`，先让测试角色独立审一遍，再交由人类技术负责人重点确认三件事：是否覆盖 spec 承诺边界、架构中间件是否合规、风险与回滚路径清不清楚。这一关把方案级偏差提前锁死在写代码之前。

![20260916150322.jpeg](../../assets/imgs/chapter-25/image-032.jpg)

_图 4-4　技术方案确认_

3. **分批编码与“被抓回重做”的自检**：编码按 `tasks.md` 控制单批上下文复杂度。进入四视角自检后，**这一单还真被打回过一次**——研发分身在改代码时顺手越界动了 `tasks` 范围之外的代码，当场被拦下打回重做，绝不让超范围的半成品溜到下一道工序。

![fig4-4-研发自检.png](../../assets/imgs/chapter-25/image-033.png)

_图 4-5　研发自检_

![fig4-5-自检打回.png](../../assets/imgs/chapter-25/image-034.png)

_图 4-6　自检打回_

4. **全自动测试与审计入库**：测试分身自动建用例、搭环境跑通全量测试（若接口报错会自动定位回传研发分身修完重跑），最后经审计三层扫描把这一单的经验写进知识库，整套分支处于“待人工放行交付”状态。

## 五、下一步：向复杂需求、成本控制与人机混编演进

简单需求跑通之后，团队接下来瞄准三个方向：

1. **能力外扩**：靠物料和知识库持续积累，把原本接不住的跨模块、跨应用复杂需求拆解成子任务逐步接管进来。
2. **成本红线**：守住“AI 端到端做一个需求不能比人更贵”的底线，靠模型分档、上下文瘦身和错峰调度压低单位交付成本。
3. **人机混编小团队**：一位工程师带着几套专业数字分身组成作战单元，让团队研发吞吐不再被纯人头数死死按住。

![fig5-1-组织形态.png](../../assets/imgs/chapter-25/image-037.png)

_图 5-1　人机混编的小团队_

通用大模型能把公开编码知识背得滚瓜烂熟，但它不可能天生懂你公司内部的历史遗留、架构暗坑和行业黑话。**真正靠得住的从来不是单次模型抽卡，而是围绕模型建起来的契约流水线、私有物料与自进化反馈系统。**
