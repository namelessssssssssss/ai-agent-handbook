# 智能体：提升内核补丁交付效率的实践

## 一、痛点：上游补丁进下游，卡的从来不止是 Git 冲突

把Linux内核上游的修复补丁合入下游产品版本时，很多时候不是跑个 `git cherry-pick` 解几行冲突就完了。真正让内核工程师头疼的是下面这些暗坑：

- 同一个函数在下游已经被重构过，表面没冲突，位置却早就变了；
- 结构体字段或函数签名已经演化，原补丁照抄进来编译都过不了；
- 这个修复依赖的某几个前置提交，压根还没进到下游目标分支里。

过去全靠资深内核工程师逐个翻日志、对上下文、捞依赖提交、改代码再反复验证。补丁量一大，交付速度就卡死在少数专家身上，处理过程也很难复盘。

问题的关键其实不在于“模型能不能吐出一段代码修改”，而在于：**能不能把一次补丁移植变成过程可追踪、结果可验证、失败能积累经验的工程流水线。**

PatchPilot 就是为此设计的内核补丁交付智能体。它把整个合入过程拆成多阶段工作流——从拉取补丁、冲突分类、意图理解，到可行性分流、依赖分析、AI 解冲突、语义审查，再到最后的交付回检——每一步都有明确输入、产物和持久化状态，方便观测、暂停、恢复和复盘。

## 二、核心机制：不把大模型当万能生成器，而是放进带校验的工程闭环

PatchPilot 刻意限制大模型的自由发挥空间，而是把它嵌入五个确定性机制构成的工程框架里：

| 机制 | 具体做法 | 解决什么问题 |
| --- | --- | --- |
| **可行性分流** | 先用启发式规则快筛，只把拿不准的任务交给 LLM 精判 | 省下昂贵推理算力，集中火力打硬仗 |
| **依赖分析** | 结合补丁意图、目标分支代码状态和前置提交，递归找必要依赖 | 避免只按缺失符号机械找依赖，把依赖链越滚越大 |
| **AI 解冲突** | 按代码块（hunk）逐块推理，记录每一轮尝试的方案、失败原因和改动范围 | 让下一轮重试避开已经踩过的死路 |
| **质量守护** | 自动查残留冲突标记、代码漂移和语义偏差 | 防止把“刚好能合进 Git”误当成“代码能交付” |
| **人机协同** | 证据充分、低风险的任务自动推进；拿不准或高风险的自动升级给工程师 | 既保住了自动化吞吐，也守住了工程责任边界 |

## 三、三个最关键的工程实践

### 1. 失败任务先过“快筛 + 精判”双层漏斗

一次 cherry-pick 失败，可能是缺前置依赖，可能是上下文变了，也可能是真实逻辑冲突。如果全靠人先看一遍“值不值得修、能不能修”，光分诊就耗掉大量时间。

PatchPilot 的做法是**先规则后模型**：先用轻量级启发式规则评估冲突规模、缺失符号、高危改动范围和复杂度；把显然能做和显然太危险的两头直接分走，只把处于模糊中间地带的任务送进 LLM 做精细评估。

这里隐含一条重要原则：**自动化不是无边界自治**。高风险改动在动手解冲突之前就被拦下并走人工升级通道，让 Agent 专心啃高确定性、可验证的硬骨头，工程师则把精力留给架构差异和风险拍板。

### 2. 解冲突前先对齐意图，并用 Git 工具锁死依赖事实

大模型直接解 Git 冲突最容易犯的错，是“表面看似合进去了，实则改丢了原意”——留下半截冲突标记、漏改关联分支，甚至脑补出上游根本不存在的函数或提交。

PatchPilot 用三招把模型按在铁轨上：

- **State-First（状态优先）依赖分析**：不光盯着报错信息里“缺了哪个符号”，而是对比函数实现、结构体字段和函数签名的演化状态。因为很多依赖缺失不会报错缺符号，却会导致运行时逻辑对不上。
- **Git 工具约束推理**：严禁模型凭记忆或猜想补全前置提交，所有依赖提交的 commit SHA 必须通过 Git 命令真实枚举出来，以工具返回值作为唯一事实依据。
- **结构化失败记忆**：大模型多轮重试时经常反复撞同一堵南墙。PatchPilot 把每一轮尝试的方案、失败原因、修改范围存成结构化记录传给下一轮，迫使 Agent 换思路而不是原地打转。

改完之后，流水线还会按顺序过三道门：**查残留冲突标记 → 查无关代码漂移 → 查原补丁语义偏差**，过关才往下走。

### 3. 用“端到端是否可交付”代替“命令是否跑通”

如果只统计“解冲突命令成功了多少次”，很容易产生虚假繁荣——表面合入成功，到了编测、PR 检查或回检环节照样挂。

PatchPilot 直接把成功标准锚定在最终交付物上：冲突解完后自动创建 PR、触发构建和检测轮次、生成回检报告，把任务、日志、审查结论和最终产物串成同一条记录。同时依靠持久化任务状态机管理调度和断点恢复，哪怕中途超时或进程挂掉，任务也能接续重试，不会悄无声息地卡死在半路。

## 四、可复用的五条方法论

回过头看，PatchPilot 的效果并不只是因为接了大模型，而是把**轻量规则、昂贵推理、质量门禁、持久化调度**拧成了一套生产级系统。这套模式同样适用于 SDK 大版本升级、跨分支移植、Fork 仓库同步等代码迁移场景，具体可以复用五条经验：

1. **从高频、证据链清晰的场景切入**：优先挑日志、代码 diff、任务状态都摆在明面上的活，别一上来就追求端到端拍脑袋决策。
2. **先搭状态机和工作流，再往里填 Agent**：没有持久化状态、上下文传递和回检闭环，Agent 进了生产环境早晚失控。
3. **用自动化门禁卡住生成质量**：每个自动操作都得配明确的可验证输出和人工兜底条件。
4. **用全链路交付指标做验收**：不能只看单步成功率，要同时盯着耗时、成本、最终合入率、人工升级率和返工率。
5. **把失败经验沉淀成系统资产**：每一次失败的原因、试过的路径和人的最终裁决都要结构化存下来，反哺给规则、提示词和评测集。
