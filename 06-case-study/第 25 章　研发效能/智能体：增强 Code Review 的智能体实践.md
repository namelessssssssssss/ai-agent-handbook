# 智能体：增强 Code Review 的智能体实践

## 一、背景：代码越写越快，评审人手不够了

AI 编程普及以后，写代码的速度暴涨，但有能力做评审的资深工程师并没有变多，研发瓶颈正快速从“写代码”转移到“审代码”。

先看几组行业和开源社区的一线数据：

- **漏洞压力在涨**：Linux 内核上游修复 CVE 的数量从 6.9–6.19 版本的四五百个，跳升到 7.0 版本的约 1,250 个、7.2 版本的近 1,900 个，7.3 版本预计会超过 2,000 个。放大到全行业，CVE 总量同比增长 394%，高危漏洞同比增长 811%（数据来源：Linux Foundation《The CRA Readiness Reality: What Changed and What Didn't Between 2025 and 2026》）。
- **PR 量与评审耗时都在飙升**：以龙蜥社区 ANCK 内核仓库为例，引入 AI Agent 后，两个主流版本分支合入的 PR 数量持续攀升。Google Cloud 旗下 DORA 年度报告《State of AI-assisted Software Development》（受访约 5,000 人，相关性口径）也显示，AI 深度介入开发的同时，代码 Bug 率上升 9%，代码评审时间拉长 91%，平均 PR 体积膨胀 154%。

![image.png](../../assets/imgs/chapter-25/image-001.png)

龙蜥社区正在把传统持续集成升级为智能化持续集成（Agentic CI），整条流水线包含四环：AI 协同编程、智能化代码评审、智能化测试、社区审核合入。AI 评审卡在中间承上启下的位置：上游代码产量暴涨，如果评审这一关守不住，要么把漏洞放进下游测试甚至主干，要么让 Maintainer 被 PR 洪流彻底淹没。

Kitta 就是为这个场景打造的**领域定制 Code Review Agent**。它在龙蜥社区线上运行至今，已累计审查超 7 万个补丁，门禁准确率 97%，代码合入率稳定在 62%；其领域定制方法也在操作系统内核、编译器、云原生平台等六大领域完成验证，带来 17.0%–31.6% 的审查质量提升。

## 二、为什么通用 AI Review 工具在核心仓库里“不好用”？

通用 AI Review 工具对基础语法错误和表面坏味道效果不错，但一进到内核、编译器这类复杂核心仓库就容易掉链子。问题出在两层：

**第一层是工程约束不够**。PR 稍微大一点，模型就只挑一部分文件看，漏审严重；指出问题的代码行号也经常对不上；甚至稍微换句提示词，审查结果就大幅波动。

**第二层是检查深度不够**。通用工具把所有仓库当成同一种代码去扫，不理解具体项目的门道，具体表现为三个痛点：

- **缺领域知识**：通用模型见过大量公开代码，但不一定懂特定内核子系统的锁语义、编译器的中间表示约定——而这些往往才是决定一段代码会不会出大事故的关键。
- **缺业务语境**：开源社区、企业内仓、商业发行版对“什么算问题、有多严重”的尺度完全不同，通用规则抓不准轻重。
- **缺信任闭环**：没有客观的评测基准，也没有根据研发真实修改动作反馈进化的机制。用户客气说句“不错”不代表真好用，Agent 自己觉得审得挺好更不可信。

一句话概括：**通用 AI 看得懂代码语法，却看不懂你的项目规矩。**

## 三、Kitta 的三步领域定制方案

为了解决“看不懂项目”的问题，Kitta 把通用智能体拆解成三步做领域化定制。

### 第一步：把老师傅的评审经验变成可验证资产

领域知识不是拍脑袋总结的，而是从真实历史里洗出来的。Kitta 从项目 GitHub/社区仓库的历史评审记录与缺陷记录出发，经过采集关联、去噪规整、语义解析，以及**隔离复现**（保证每条缺陷模式和预期结论都能被独立复现验证，不是把历史噪音当经验），沉淀出两类项目级专家资产：

- **评判标准**：项目特有的评审原则、常见缺陷模式和工程惯例，解决“按什么标准判”。
- **验证样本**：真实问题样本、正常样本和预期结论，解决“怎么衡量判得准不准”。

换一个新项目时，这套管线可以直接把新项目的历史记录重跑一遍，快速提炼出新项目的专家资产。

### 第二步：双轮驱动定制——流程决定“看哪里”，知识决定“怎么判”

有了专家资产，接下来要分别定制审查流程和领域知识库。以龙蜥社区 ANCK 内核仓库为例：

**轮子一：定制审查流程，确保不漏项。** 针对语义一致性、回合完整性、发行版规范、集成风险四个维度建规则。其中，下游内核维护最高频也最头疼的工作是**补丁回合（Backport）**——把上游社区的补丁移植到下游老版本内核时，常要配合上下文改代码，稍不留神就会漏掉关键修复或改偏语义。Kitta 为此专门加了两项检查：

- **补丁语义一致性检查**：先微观比对回合补丁和上游原补丁的代码差异，再宏观评估整体功能意图有没有走样，避免“逐行看似都改了，整体逻辑却不对”。
- **补丁完整性检查**：沿着上游依赖链自动追查对应的 `Fixes` 修复补丁，用四阶段检索排查有没有漏带前置或后续修复，防止已知漏洞在下个版本回归。
- **流程上下文检查**：一并覆盖 PR 描述规范性、描述与实际改动是否一致等外围门禁。

**轮子二：定制领域知识，确保看得深。** 仅仅查表还不够，Kitta 做了三件事把审查深度拉上去：

- **内核数据工程**：对多源内核知识做筛选、合成与均衡处理，生成领域知识库和 Benchmark 题集。
- **按子系统拆知识库**：内核不同子系统的禁忌和惯例差别极大，拆分后按子系统精确加载。
- **深度审查思维链**：强制走一遍“有罪推定 → 全栈调用链分析 → 自我辩论”的推理流程——先假设代码藏着问题，沿着完整调用链追踪语义，再自己反驳和校验结论，专治隐藏在深处的并发与生命周期风险。

同时，Kitta 收集三类数据建成了 Benchmark 横向评测集：**LKML**（Linux 内核邮件列表的真实评审过程，问题分布自然）、**sashiko benchmark**（单个提交与单个 issue 精确对应，方便聚焦改进方向）以及**龙蜥社区真实数据**，并拉来 sashiko、review-prompts、qoder 等主流方案同台对比，用评测分差直接指导 Skill 的迭代优先级。

### 第三步：在线离线协同进化，越用越准

领域知识是活的，模型和工具也在变，Kitta 用两套闭环保证不退化：

- **离线侧**：定期拿验证样本做隔离回测，根据失分点反思和更新审查 Skill 与阈值。
- **在线侧**：上线后持续统计评审意见的真实采纳率——**不听用户嘴上怎么夸，只看开发者后续到底有没有照着意见改代码**，结合评估框架自动校准知识库和拦截阈值。

## 四、线上实战：龙蜥内核的五阶段流水线与效果

在龙蜥社区真实流水线里，开发者提交 PR 或在评论区回复 `/check-code-review`，就会触发 Kitta 的五阶段审查流水线，从轻到重层层过滤：

1. **Stage 1：PR 分类**。检查 Commit 中是否带有类似 `commit xxxx upstream` 的上游来源声明。纯自研补丁会直接跳过回合专属检查，省去不必要的开销。
2. **Stage 2：PR 与 Commit 规范检查**。对照社区规范检查标题、Commit 信息和 PR 描述，无问题静默通过，有问题给出修改建议，把沟通成本拦在最前面。

![image.png](../../assets/imgs/chapter-25/image-003.png)

3. **Stage 3：补丁完整性检查（回合补丁专用）**。顺着“检索上游 Fixes → 检查是否在当前 PR 内 → 检查是否已合入下游仓库”的路径排查，输出“无遗漏 Fixes”“已合入的 Fixes 补丁”或“遗漏的 Fixes 补丁”，直接阻止带已知漏洞的半成品合入。

![image.png](../../assets/imgs/chapter-25/image-004.png)

4. **Stage 4：补丁回合一致性检查（回合补丁专用）**。拉取上游原补丁做三层对比：改了哪些文件/代码块、引用符号与上下文适配是否合理、整体功能语义是否一致。输出从 `consistent` 到文本不一致、语义不一致、完全不一致的分级结论，帮 Maintainer 一眼定位差异性质。

![image.png](../../assets/imgs/chapter-25/image-005.png)

5. **Stage 5：代码质量审查**。最后真正审代码，按严重程度输出 `Critical` 与 `Medium / Low` 级别问题；高危问题以内联评论精准标到具体代码行，要求作者处理或说明误报；没发现风险就给 `LGTM`。

![image.png](../../assets/imgs/chapter-25/image-006.png)

## 五、三条经验底线：AI Code Review 的信任边界

跑了这么多真实仓库后，团队沉淀出三条关于人机分工的共识：

1. **红线要硬，提示要克制**：安全漏洞和破坏性变更坚决在 CI 门禁拦死；其余非致命建议做好分级提示，不要满屏刷评论，把开发者的注意力淹没掉。
2. **用代码修改说话，不搞“自我感觉良好”**：开发者沉默无视不代表同意，必须盯住意见发出后代码到底改没改，用真实修改行为和置信度熔断来驱动迭代。
3. **AI 做探照灯，人握方向盘**：AI 负责把可疑点照亮、把证据摆出来，但最终合不合入、争议怎么拍板，必须由 Maintainer 兜底。
