# 塔斯汀万店连锁的智能运维闭环实践

## 一、背景：不到十人的 SRE 团队，怎么扛住上万家门店？

塔斯汀在全国已经开出超过一万家门店，支撑它的 SRE 团队却不到十人，管着门店 POS、供应链、会员营销、线上点餐等数十条核心服务链路。雪上加霜的是，AI Coding 让研发上新微服务的节奏从按周变成按天，可排障经验依然锁在少数老 SRE 脑子里——小团队的人效快被业务扩张甩开了。

在落地智能运维前，团队卡在三个互相咬合的现实难题上：

1. **告警分散在四个台子里，值班群被刷屏淹没**：应用监控靠 ARMS、基础设施水位靠 CMS 1.0、日志查 SLS、容器指标靠 Prometheus。四套系统各自配规则、各自往飞书群发消息。晚高峰一旦遇到数据库慢查询拖垮连接池，四个产品各自按自己的口径炸出十几二十条独立消息，值班人员得同时开四个控制台肉眼对时间线，才能猜出“这十几条其实是一件事”。
2. **新服务天天上，排障经验全靠翻聊天记录**：上次订单服务 OOM 是因为堆外内存参数没配对，三个月前支付超时是因为下游限流加熔断阈值太低——这些关键结论全散落在当时值班群的文字回复里。新人半夜接班碰到同款告警，只能从头自己摸三个平台。
3. **试过直接上 AI 做根因分析，但结论常常“说了等于没说”**：查“过去 1 小时 Redis 命中率低于 90% 的实例”这种明确取数活，Agent 做得很稳；可一到复杂根因分析就频频跑偏——比如上游发券流量翻倍拖慢下游，AI 却怪下游数据库慢；或者 Nacos 推配置引发服务重启抖动，AI 建议“扩容实例数”；而且对错了谁也没地方记，系统根本没法越用越准。

## 二、四步搭建可控闭环：事件归并 + 飞书卡片 + 反馈三元组 + 数字员工

基于阿里云云监控 2.0（CMS 2.0）和 STAROps，塔斯汀没有一上来空谈“全自动自愈”，而是老老实实搭了四层扎实底座。

### 1. 统一告警入口：四源合一，按“Group Key + Incident ID”收敛刷屏

第一步是把 ARMS、CMS 1.0、SLS、Prometheus Alertmanager 的告警通过 Webhook 全部收拢到 CMS 2.0 事件中心，统一划成 P1–P4 四级，再按业务线路由进对应飞书群（P1/P2 直接 @ 值班人员）。

核心设计在两条标识字段：

- **分组标识（Group Key）** = `告警等级 + 资源标签组合（服务名/集群/命名空间）`。在同一个收敛时间窗内，相同 Group Key 撞进来的告警自动归成同一个事件——不同等级（比如 P1 和 P3）绝不混并。
- **生命周期标识（Incident ID）**：同一次事件一旦全部告警恢复并关闭，下午再犯就算另一个新的 Incident ID，单独记认领、时间线和复盘，不把两场事故搅成一锅粥。

一次事件严格走完四个状态阶段：**首次触发**（发一张飞书卡片到群里）→ **持续触发**（同源新告警不发新消息，只**原地更新卡片上的活跃告警计数**）→ **部分恢复**（只更新恢复计数，继续标“处理中”，绝不提前误关）→ **全部恢复**（流转为“已恢复”，但强制保留 **72 小时复盘窗口** 用来补录根因和给 AI 打分——业务恢复不等于复盘结束）。

同时团队把 Java、Redis、MySQL/PolarDB、K8s 的通用规则做成开箱模板，新服务上线一键绑定就能跑。

### 2. 飞书一张卡片全闭环：认领、带上下文追问、精确查统计

推送到飞书群的不是死文本，而是一张带操作按钮的交互卡片（含事件 ID、等级、时间、关联服务、活跃/恢复数、状态、认领人）：

- **一键认领**：点完按钮卡片立刻改成“已认领 by @xxx”，杜绝多人重复抢着查，后续更新只精准 @ 认领人。
- **引用卡片直接追问 AI**：值班人在群里直接回复这张卡片向 STAROps Bot 提问，系统自动把事件 ID、关联的**全部告警明细、最近 15 分钟 ARMS 调用链和指标趋势快照、以及该服务的历史根因记录**打包塞进上下文。新人再也不用在提问里手打“我在查哪个服务哪个时间段”。
- **自然语言查统计绝不让大模型心算**：群里常问“今天 P1 告警有多少”（含已恢复）和“当前活跃 P1 有多少”（不含已恢复），口径差之毫厘谬以千里。实现方式很克制——**Bot 先把问题解析成查询条件去调事件中心结构化 API 拿精确数字，AI 只负责把数字顺成自然语言回复**，绝不让模型翻原始列表自己数数，确保每个数字都能溯源到明确 API 调用。

### 3. 反馈闭环：把每一次人工排查变成“（上下文，人工根因，评价）”资产

为了治好“AI 瞎猜还没地方纠错”的老毛病，塔斯汀把评价直接嵌进了值班卡片里：

1. **AI 先出诊断**：按固定格式输出“一句话推测根因 + 引用的指标/日志依据 + 建议操作”。
2. **人工填实际根因**：事件恢复后，值班人点卡片“填写根因”录入真相（例如：“上游营销发券流量突增 3 倍打满下游交易连接池，已调大 maxActive 到 200 并加限流”）。
3. **给 AI 判个准不准**：紧接着弹出只有两个按钮的打分——“AI 准”或“AI 不准”，选不准时顺手补一句错在哪。

系统把每一次处置存成一条标准反馈记录：

```plaintext
{
  incident_id: "事件ID",
  ai_diagnosis: "AI输出的诊断结论全文",
  human_root_cause: "值班人员填写的实际根因",
  ai_accuracy: "准/不准",
  accuracy_note: "不准时的补充说明（可选）",
  service: "关联服务名",
  alert_type: "告警类型分类",
  timestamp: "反馈时间"
}
```

这组三元组攒起来立刻产生两大复利：一方面下次同一个服务再炸，AI 会优先读取历史根因库，相当于直接继承了上一任 SRE 的排障经验；另一方面团队能按“服务 + 告警类型”算出 AI 准确率。**2026 年 6 月，塔斯汀正是拿着这批带错例样本的精确统计，直接向产品侧定位并推动修复了那三类典型误判**：级联故障甩锅给下游、配置推变更抖动误判扩容、以及笼统回复“系统负载高”。

### 4. STAROps 数字员工：把老兵 SOP 写进 Skill，用 Mission 定时巡，用“一键 RCA”救火

最后一步是把资深 SRE 脑子里的排查套路编码成可调度的 **Skill**——写明触发条件、按什么顺序查指标日志、满足什么条件算什么根因、按什么格式输出：

| 已沉淀 Skill | 采集哪些现场 | 区分哪几种典型根因 |
| --- | --- | --- |
| **Redis 缓存异常诊断** | 命中率、内存水位、慢日志 Top10、连接数趋势 | 大 Key/热 Key 拖垮命中率 vs 内存淘汰触发 Key 被清 |
| **数据库连接池诊断** | RDS 活跃连接、慢查询 Top SQL、应用侧 HikariCP/Druid active/idle/pending | 慢查询阻塞占满连接 vs 上游突发流量撑爆连接池 |
| **Java 服务 OOM 诊断** | 堆/堆外/Metaspace/DirectMemory 曲线、Full GC 频率与暂停、24h 增长斜率 | 堆泄漏 vs Metaspace 无上限被反射撑爆 vs DirectMemory 超限 |
| **支付链路超时诊断** | 到银行/第三方支付网关成功率与 P99、Sentinel 熔断状态、重试队列深度 | 下游限流 vs 网络抖动 vs 本地处理慢 |

围绕这些 Skill 搭出两套实用用法：

- **Mission 定时巡检矩阵**：把多个 Skill 编进长期定时任务——**交易链路巡检**在午晚高峰（11:00–13:00、17:00–21:00）每 15 分钟跑一轮、其余时段每小时一轮；**基础设施巡检**全天每 30 分钟一轮；**中间件巡检**（RocketMQ 堆积、Nacos 健康、Sentinel 流控）全天每小时一轮。每天自动生成折叠正常项、标红异常项的体检报告，SRE 不用干盯大屏了。
- **卡片“一键 RCA”**：真告警来了，值班员点一下“一键 RCA”，系统按服务标签和告警类型自动并发拉起匹配的多个 Skill（比如交易服务延迟告警 → 并发跑数据库连接池 + Redis + Java OOM 三个 Skill），合成一份资深 SRE 级别的初判报告。新人头一回值班，就算还不熟这个服务的 Redis 集群在哪、监控怎么查，照样能接住第一波排查。

## 三、落地后的真实变化

跑通这套体系后，不到十人的 SRE 团队撑住了万店级系统日常运行，变化主要体现在三件事：

- **告警噪音降噪超七成，值班群安静了**：同一次数据库级联故障，群里不再炸出 17 条来自四个产品的红字消息，而是收敛成 **1 张原地刷新“当前 17 条活跃告警”的事件卡片**。
- **排障路径从“切三个台子拼时间线”变成“一张卡片里点一下”**：从收到通知到看到第一份带全链路上下文的排查报告，路径极大缩短，新人也能独立兜住首轮响应。
- **排障经验留在了系统里，不随人员流动清零**：每一次处置留下的三元组和新增 Skill 让团队能力可以持续积累复用，不再因为核心 SRE 休假或离职瞬间腰斩。

## 四、下一步往哪走？

在交易链路跑稳之后，团队接下来的规划聚焦三件事：

1. **防患于未然**：接通 Jenkins 发布节点和 Nacos 配置推送事件，在发布或改配置前先用 Agent 跑一遍风险预判。
2. **把技术告警翻译成生意损失**：把告警事件关联到受影响订单量、波及区域和持续时长，让业务和管理层直观看到稳定性投入对高峰期点餐和支付成功率的保障价值。
3. **横向复制到全业务线**：把已经验证通的告警归并、Skill 编排和反馈闭环直接铺向供应链（仓储调度、门店补货、冷链温控）和会员营销（发券核销、积分一致性）等链路，做到业务版图扩大而运维人力不用线性加人。
