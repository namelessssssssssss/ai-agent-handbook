# 第 29 章　GOAI Agent Infra 赛道：多 Agent 协同的前沿实践探索

前面第 25–28 章看的是企业真实生产线上已经跑通的项目。这一章换个视角：把一批开发者放进同一道高风险命题里，逼着他们拿多 Agent 系统去碰企业最核心的流程——**这帮一线选手最后到底会交出什么样的架构选择？**

2026 年 GOAI 世界人工智能开源大赛“Agent Infra 新智基座”赛道定下的命题很硬核：**面向企业级复杂任务搭建多 Agent 基础设施与协同系统，推动 Agent 从 Demo 走向 Production。** 硬要求摆在桌面上：系统里至少有三个不同职能的 Agent，基于 AgentTeams 设计协同，必选 Skill 封装能力，还得一路贯通从任务拆解、上下文传递、工具调用、结果验证、审批回滚到经验沉淀的完整链路；评审盯住场景价值与可复制性、多 Agent 协同闭环、Skill 复用、安全审计验证和开源贡献五个维度。

赛道自 **2026 年 7 月**开赛，共吸引 **7,802 支队伍、8,346 名选手**报名，收到 **847 个作品**，覆盖全球 **38 个国家/地区**；经初赛复赛层层筛下来，**9 月**有 **15 项作品**闯进决赛。本章复盘的，正是这 15 项作品挑了什么场景、怎么划权限、以及在赛道规定之外不约而同做出的那些清醒判断。

## 一、参赛画像：高手不分出身，四成决赛队跨单位凑局

15 支决赛队伍一共 30 位选手，来自 11 所高校和 7 家企业及科研机构（高校队 7 支、企业与科研机构队 5 支、个人开发者队 3 支，比例约 5:3:2）。有意思的两个现象是：

1. **做不做得好，真不看机构光环**：三类队伍平均分咬得很紧，前五名里高校、企业、个人开发者各占席位；三支个人开发者队全部打进决赛，挑的全是 IT 运维、金融数据治理、跨平台故障恢复这类没十年一线踩坑经验根本提不出的真痛点。
2. **跨单位联手成了常态**：15 支队里有 6 支是跨组织组队（占四成）——比如“逐光”由浙江吉利控股与 OPPO 工程师跨厂组队，“星河引擎”横跨昆山杜克大学、深圳大学和上海大学，“helloworld”则是高校 + 科研院所 + 独立开发者搭伙；产业侧的 8 位选手分布在 7 家单位，除了浙江移动创新研究院是两人小队，其余全是工程师单枪匹马带着本职工作的真实痛点下场打比赛。

## 三、9 项代表性作品拆解：场景痛点与硬核设计

下面这 9 项作品覆盖了全部 5 个垂直行业，外加财务结算、数据工程、安全运营和 IT 运维四条横向线，能最直观看出这一批开发者的工程取舍。

### 1. EnergyMesh-Agents：给园区能源调度加上“独立审计 + 确定性优化器”

- **团队与领域**：超境创新｜李如枫（深圳维境拟生）、夏超｜能源电力
- **痛点**：工业园区和算力中心要协调光伏、储能、分时电价和生产负荷，既有能源管理系统（EMS）和确定性优化器已经很强，但在生产计划和电价动态跳变时，缺一层跨状态核实、独立审计和安全授权调度。
- **关键设计**：在原有 EMS 和确定性优化器上面加了一层 Multi-Agent 治理层——感知角色确认现场、规划角色调用优化器算计划、审计角色独立核查安全约束并有权毙掉失效计划、执行角色只跑已获批准的版本。**实际的功率曲线和电费全由确定性优化器算**，BMS/PCS 和底层保护设备不动，模型绝不瞎算电流功率。
- **验证情况**：跑通状态快照、计划版本、独立审计、人工审批、模拟执行、回读与回退全链，用公开园区数据与原策略做对照组完成数字孪生验证。

### 2. FinFlux：抓出“接口没报错、口径却悄悄变了”的金融数据漂移

- **团队与领域**：dovic\_cn｜李瑞（独立开发者）｜金融
- **痛点**：金融交易和行情字段最凶险的故障不是接口挂掉，而是返回码 200、JSON 格式全对，业务统计口径却暗地改了——这种语义漂移会顺着数据血缘一路污染风控和结算，等炸雷时根本查不清波及多广。
- **关键设计**：三类 Agent 分别负责证据采集、影响面评估与结论签署，配合资产画像、血缘追溯、口径比对等五个 Skill。准入结论不是粗暴的是/否二选一，而是**放行、暂缓、拦截三条路径**，且每条路径必须附带完整证据链与模型调用记录。
- **验证情况**：在期货行情资产上完整跑通三条路径，审批签署和中间证据支持全链路回放。

### 3. 总工之眼：工程图纸多专业会审，有分歧绝不“和稀泥求平均”

- **团队与领域**：晨之初晞｜李博（北京伯禹规划设计）、王娜（独立开发者）｜建筑工程设计
- **痛点**：出图会审最坑的地方在于，结构、暖通、给排水各专业单独看都合规，合到同一堵墙或同一根梁上就打架。
- **关键设计**：协调角色把可追溯事实分派给各专业审查角色，再汇总跨专业碰撞关系交由独立证据核验角色复查。最清醒的一条设计是**跨专业分歧不做平均折中**——一旦两家专业意见撞车或证据不够，系统绝不代替人拍脑袋和稀泥，而是把两边依据原封不动摊开交给真人总工程师裁决留痕。
- **验证情况**：已跑通真实 AgentTeams 运行记录，覆盖多专业并发审查、跨专业碰撞、异常恢复与人工终审留痕。

### 4. 店巡 Agent：冷柜温度恢复了，不代表里面的肉还能卖

- **团队与领域**：逐光｜夏志强（浙江吉利控股）、马荣（OPPO）｜零售连锁 / Agent Infra
- **痛点**：门店冷柜半夜报警后，经常出现“维修工单关了、设备温度回来了，但停电化冻过的那批货早变质了却被照常上架”的食安隐患。
- **关键设计**：异常触发后先强制停售遏制，再走维修处置；更关键的是**设备恢复与商品安全拆成两条必须同时过关的独立校验路径**，而且执行维修的角色不能自己给自己签完结，必须由独立 Auditor 重新查设备状态、商品批次和审批单，缺一不可。只要证据不足或仍有风险，系统把状态锁死在停售不关单——**在这里，卡住不放行才是正确结果。**
- **验证情况**：验证了正常流程以及设备故障、传感器误报、审批超时、维修查询异常等六类正反向场景。

### 5. SceneGuard：三维资产受控修复——原件只读，验证不过宁可零发布

- **团队与领域**：星河引擎｜顾梓洋（昆山杜克大学）、刘志豪（深圳大学）、王峥睿（上海大学）｜数字内容
- **痛点**：游戏、XR、电商批量导出的 3D 模型常在上线后才爆出网格、贴图或材质问题，靠技术美术手工进 DCC 工具改，既慢又完全没法留痕复现。
- **关键设计**：协调角色拆解任务，审计、出修复计划、改资产、回归验证四个角色权限严格隔离，严守三条底线：**原始资产绝对只读**、修复动作锁死在白名单操作内、每一步留检查点；高危动作停下来等人批，回归验证没过立刻自动回滚并保持“零发布”。
- **验证情况**：代码层面已打通缺陷检出、白名单受控修复、回归复验到内容寻址证据留痕与发布闭环。

### 6. RevGuard：渠道佣金异常核算——金额绝不让大模型算

- **团队与领域**：helloworld｜任宇帆（西安工业大学）、宋传承（中科院信工所）、乐达（独立开发者）｜财务与渠道佣金结算
- **痛点**：渠道返佣算错账，多数不是加减乘除算错，而是套错了政策版本、卡错了渠道等级生效时间点，或者漏算了一条激励项——少付挨投诉，多付追不回。
- **关键设计**：1 名 Leader 带 9 个 Worker 分工受理、取证、匹政策、写台账、核账。最核心的工程克制是**金额绝不让大模型生成**：所有钱的计算全权交给专用十进制规则引擎按条款精算，大模型只管串流程、比对政策版本和用人话解释差额。写入台账必须凭单次审批令牌，失败走反向冲销，最后独立角色复核。
- **验证情况**：用 8 个覆盖政策版本错配、等级时点冲突、漏算激励的用例完成验证，审批、写账、回滚全链路可追溯。

### 7. DataFlow-Agent：先去算子库里找现成的，找不到再让 AI 写新脚本

- **团队与领域**：PKU-DCAI｜强美伊、梁昊、徐畅（北京大学）｜数据工程
- **痛点**：算法和数仓团队让 AI 从零写一次性 Python 数据清洗脚本，跑起来凑合，但难沉淀、难单步改、难稳定复跑，一旦某步挂了说不清哪坏了。
- **关键设计**：立了一条非常正确的复用优先级——**先检索平台已有成熟算子拼装，实在缺能力才针对性生成新算子**，避免每次重造脚本。Agent、可视化编排画布和后端共用一份流水线状态，任何增删前后自动过校验，交出来的不是一段聊天代码，而是一条可编辑、可重跑、状态透明的数据流水线。
- **验证情况**：已打通可视化编辑、算子管理、流水线保存运行和结果追踪。

### 8. CyberGuard：安全封禁“宁慢勿错”，单次审批绑死具体对象，复测有权翻案

- **团队与领域**：逆律成调｜吴林斌、陈培琛（杭州电子科技大学）｜网络安全运营
- **痛点**：线上封 IP、断网、禁账号动手太重，一旦封错直接把正常生产业务打趴。
- **关键设计**：分诊、情报、取证、遏制、验证、恢复、审计七大角色分工，踩实两根红线：**一是每次人工审批只绑死当次具体提案和具体目标对象**，执行角色半步不许越界扩杀伤面；**二是独立复测角色有权推翻上一轮处置结论**，发现封错对象立刻退回重新走规划审批，并支持把误封动作回滚掉。
- **验证情况**：跑通串起七角色与四次人工审批的完整轨迹，演示了模型服务故障自愈、改目标重批、回滚误操作与两轮复测结案。

### 9. OpsKeeper：防修错机器，工单、提案、目标、指令四码合一才放行

- **团队与领域**：奔悦智维｜蒋幸（独立开发者）｜IT 运维与故障恢复
- **痛点**：救火时诊断在飞书群、审批在工单系统、敲命令在跳板机，经常发生“看准了 A 库连接满，手滑重启成 B 库”或者“命令跑通了、业务其实还挂着”的二次事故。
- **关键设计**：控制层和执行层硬拆——调查只读、修复受控、验证独立。授权校验把安全锁死到**“故障工单 + 处置提案 + 目标对象 + 具体指令”四项标识必须严丝合缝全匹配**，错一个字直接拒执行；验证角色也绝不拿“命令返回 exit code 0”当恢复，而是拿真实业务健康探针结果说话。
- **验证情况**：完整演示了一起数据库连接池耗尽事故——故意派错目标对象被系统当场拒掉，人工批准正确目标后执行并确认连接归零与探针恢复绿灯。

## 四、比赛没规定，但高手们不约而同选了同一条路

虽然主办方规定了“多角色、审批、回滚、留痕”这些必答题，但最值得研究的，是**比赛题目里压根没要求，这批队伍却自己做进了同一套工程共识里**的五个选择：

1. **自己干的活，自己绝不准签字验收**：虽然规则只说要“验证环节”，但 MergePilot（修复不能自签）、店巡 Agent（维修不能自认安全）、CodeNotary（作者看不到盲测题、测试者不碰实现源码）、OpsKeeper、RevGuard 全部把验证权从执行者手里拿走——**自证清白的检查在工程上等于没查。**
2. **授权不再发“长期通行证”，而是“一单一批一次有效”**：CyberGuard 绑死具体提案目标，OpsKeeper 卡死四项标识全匹配，RevGuard 写入带单次令牌，把权限最小化真正写进了运行态校验。
3. **要算死数、碰物理边界的，把大模型请出去**：EnergyMesh-Agents 把电网调度交还确定性优化器，RevGuard 把返佣算账交还十进制规则引擎——**让模型管语义理解与流程组织，让确定性程序扛数值责任。**
4. **把“拒绝执行 / 维持阻断”设计成正儿八经的成功终态**：店巡 Agent 宁可继续停售、SceneGuard 宁可零发布、MergePilot 对高危 MR 直接永久阻断、FinFlux 把拦截路径做到和放行一样完整——不再逼着 Agent 没证据也必须挤出一个“通过”答案。
5. **证据链跟同一次运行生死绑定，绝不事后补日志**：从协作消息、工具入参返回值、人类点批按钮到最终状态，全在运行期自动挂到同一条可回放时间线上。

## 六、这批前沿探索留下了什么？

这 15 个作品大多还处于参赛工程原型阶段，离企业大规模日用还有距离，但它们共同踩实了三件事：

1. **多 Agent 真正的难度不在通用通信协议，而在具体场景怎么定义“什么叫对”**：放在 11 个截然不同的行当里马上现出原形——电网难在安全物理约束，佣金难在政策生效时点，连锁生鲜难在设备好≠货没坏。
2. **高风险核心流程敢不敢上 Agent，不靠等下一个更聪明的模型，靠重新拧紧工程权限**：执行与验证隔离、授权细到单次动作、精确计算移出模型、允许合理拒答——这四条今天拿现有模型就做得到。
3. **一批可跨行业直接搬运的工程套路已经成型**：像 OpenXnet 用同一套控制面底座只换插件接管三个平台、SceneGuard 的“原件只读 + 白名单受控写 + 不过即零发布”、FinFlux 的“放行/暂缓/拦截”三路带证据裁决，放到任何高敏场景都能直接复用。
