# 从 Personal Agent 到企业智能体：AgentScope 的 Agent as a Service 架构

## 一、共同死穴：一旦任务活得比单次对话久，绑定在进程里的 Agent 就会崩

做个人助手（Personal Agent）和做企业智能体，看起来面对的是两拨完全不同的人，其实一进生产环境，撞上的工程死穴一模一样：

- **个人助手场景**：用户在电脑上刚让 Agent 开始整理调研资料，合上盖子出门了；后台必须接着跑，用户拿手机能看进度、点审批，回到电脑前还要由本地 Harness 无缝接手同一份上下文和记忆继续干。
- **企业智能体场景**：监控告警或工单来了，Agent 在云端拉起排查，需要跑二十分钟压测或者进企业内网查日志，中途还要挂起等研发点确认；执行节点换了、浏览器断了，任务不能从头再来。

两类场景压在底层只提出同一条硬要求：**Agent 的身份、任务进度、长期积累和文件工作区，绝不能跟某一台电脑、某一个客户端窗口、或者某一个死扛内存的进程绑死。**

把这件事服务化，就是本文讨论的 **Agent as a Service（AaaS）**——把 **Agent 定义**（长期复用）、**用户会话**（跨多个任务）、**单次推理实例**（按需拉起、等工具时就释放）和**执行沙箱**（按文件与进程需要保留或回收）这四条生命周期彻底拆开。

## 二、核心架构抉择：先看“构建入口”，更要拍板 `Agent IN Sandbox` 还是 `Sandbox as Tool`

谈服务化之前，先顺手把“从哪起步搭 Harness”跟“代码跑在哪”这两个维度分开。正如[第 03 章《Harness 的主流构建方式和责任边界》](<../../02-build/第 03 章　范式：Harness 的主流构建方式和责任边界.md>)里梳理过的，构建入口有四条路可以组合着用：用高代码框架自己拼（如 AgentScope）、直接嵌入成熟产品化的 CLI/SDK（如 Qoder/Coding Agent）、把模型和指令托管给平台跑、或者用云产品界面低门槛装配。

选完怎么搭，**真正决定服务架构长相的，是这一刀怎么切：负责推理循环的 Harness，到底放不放进执行生成代码的 Sandbox 里面？** 行业里由此劈出两条路线：**`Agent IN Sandbox`** 和 **`Sandbox as Tool`**。

| 具体构建方式 | 推理循环（Harness）跑在哪 | 归属部署模式 |
| --- | --- | --- |
| 高代码框架自研 Harness，跟任务环境打成一片塞进同一沙箱 | 沙箱内 | **Agent IN Sandbox** |
| 复用产品化 Harness，在沙箱里直接拉起 CLI 或 SDK 主进程 | 沙箱内 | **Agent IN Sandbox** |
| 平台直接在任务沙箱里运行完整 Agent 组件 | 沙箱内 | **Agent IN Sandbox** |
| 高代码框架把 Harness 跑在服务端，调工具再去远程沙箱执行（本文 AgentScope 方案） | **沙箱外的服务端** | **Sandbox as Tool** |
| 复用支持远程执行的产品化 Harness，只把文件与命令操作甩进独立沙箱 | **沙箱外的宿主或服务端** | **Sandbox as Tool** |
| 平台在服务端跑 Harness，沙箱只老老实实承接工具执行 | **沙箱外的平台服务端** | **Sandbox as Tool** |

**判定标准极简单，别被“用了哪个 SDK”绕晕：只看 Agent Loop 到底在哪条隔离边界里转。** 哪怕 SDK 从外面发起调用，只要它真干活的完整 Harness 进程蹲在沙箱里，它就依然是 `Agent IN Sandbox`。

![Agent IN Sandbox 与 Sandbox as Tool 部署模式对比](../../assets/imgs/personal-agent/agentscope-aaas-01.png)

### 两种模式的工程取舍对比

- **`Agent IN Sandbox`**：好比把开发人员直接装进工位电脑。本地依赖多、重度吃既有 CLI 工具链时最顺手、起步最快；但缺点是推理跟环境死绑，升级、进程重启恢复、防容器里的恶意代码偷窥模型访问凭据，都得费劲自己拆。
- **`Sandbox as Tool`**：把大脑和手彻底物理隔离——**Harness 安安稳稳蹲在服务端组织上下文和决策，真正要动文件或跑不可信代码时，再通过工具协议去叫远程 Sandbox**。模型访问密钥和用户权限审批全部留在沙箱外头，天然建立起安全边界。**它的代价也很明确**：多出了一截跨网络远程调用，你必须老老实实处理网络超时、结果丢包、半截重启怎么接上的工程问题。

| 架构观察点 | Agent IN Sandbox | Sandbox as Tool（本文选用） |
| --- | --- | --- |
| **任务怎么承载** | 容易整套绑定在一个完整 Agent 环境里 | 推理实例和执行沙箱天生分开管理 |
| **长期状态放哪** | 得特意从沙箱环境往外抠并持久化 | 直接围绕服务侧独立任务账本组织 |
| **资源怎么扩缩容** | 推理算力和沙箱容器紧耦合，一起占资源 | 等沙箱跑 20 分钟单测时，推理内存可以先放掉 |
| **权限怎么守** | 得在沙箱内部死防代码越权偷凭证 | 凭证全扣在服务端，在远程工具边界集中卡死 |
| **故障处理难点** | 进程和沙箱环境缠在一起，两头都要查 | 必须说清“远程工具到底跑没跑成、结果怎么交接” |

## 三、AgentScope AaaS 怎么落地：四层拆解与挂起恢复机制

基于 AgentScope 搭这套服务，思路很干脆：**用 AgentScope 里的 Harness 把模型、工作区、记忆、Skill 和子任务循环管起来，在外面包一层统一的服务调度与持久账本，再把文件/命令/业务系统接成受控工具端（Hands）。**

### 1. 总体运行链路与六层职责分工

![AgentScope Agent as a Service 总体架构](../../assets/imgs/personal-agent/agentscope-aaas-02.png)

先看懂这张总图里的四个核心编号（实线是任务、状态和工具结果流转；虚线是执行权交接）：
- **① Harness 远端托管**：推理循环跑在服务端，网页关了照样推；
- **② 本地与远端执行交接**：用户在本地电脑和手机端切来切去，谁拿到当前执行权就由谁推进；
- **③ 云端状态服务**：把 Context、Memory 和检查点全托管到云端；
- **④ Brain / Hands 分离**：服务端 Brain 通过统一工具协议按需路由到云沙箱、用户本地电脑或企业内网执行端（Hands）。

整条链路切分出六个干净的职责层：

| 服务职责层 | 实际落地干什么 |
| --- | --- |
| **定义与资源管理** | 管好 Agent 用的模型、指令、工具集、Skill、配置版本和资源授权范围 |
| **请求与事件接入** | 验身份、接会话和任务，吐出实时进度订阅、补充要求入口和人工审批弹窗 |
| **任务调度与执行控制** | 持久化排单、管会话串行与预算上限，**控制谁抢到执行权以及故障怎么拉起恢复** |
| **Agent 推理执行** | 由 AgentScope Harness 拼装当前上下文、调模型、派发工具、落盘推进记录 |
| **工具执行层（Hands）** | 真正去调沙箱、MCP 或企业接口，带稳定执行标识跟踪进度，支持查状态和取消 |
| **状态与工作区存储** | 落盘会话日志、检查点、待办、工具记录、交付物及工作区文件持久化 |

### 2. 怎么做到“状态与推理分离”且“可随时组合”？

要把这套骨架做活，关键靠四项工程安排：

1. **身份和状态彻底外置**：每次调用带稳健的用户与会话标识把日志和检查点落盘。哪怕执行节点半路挂掉，新节点只需要先抢下当前任务的执行权，再从库里捞出最后提交的检查点接着推，不依赖旧进程内存。
2. **推理资源和工具资源按需拆开省钱**：模型推理占昂贵算力，耗时测试占普通沙箱，等人工审批只需要数据库里一条待办。**等待期把推理实例放掉**；回收沙箱前先核对有没有活动进程或未存文件，绝不让等审批的任务白白霸占推理槽位。
3. **四层可组合架构，支持“跨端接力”和“换手执行”**：
   - **第一层（远端托管 Harness）**：解决断网断连后台照跑；
   - **第二层（本地与远端 Harness 交接）**：保证同一时刻只有一个执行者握着执行权——在检查点或轮次边界交接时，先确认上一任已退场或撤权，另一端再读状态接盘；
   - **第三层（Context 与 Memory 云端化）**：当前会话摘要/计划（Context）和跨会话事实/偏好（Memory）全存在云端权限边界内，不管本地还是远端 Harness 都能按授权拉取；
   - **第四层（Brain / Hands 路由分离）**：Brain 不动，工具可以按数据在哪路由到云沙箱、个人 PC 或公司内网。**换 Hands 时一条铁律：已经发出去的在途工具继续找原执行端按原标识结算，只有新派发的才切到新执行端**，避免同一操作两头重干一遍。
4. **行为配置与运行环境版本各自管牢**：每条任务记死当时用的模型、指令、Harness 配置和环境镜像版本，升级只管新任务或做兼容验证，防止改一版配置把跑了一半的老任务带歪。

### 3. 核心难题实操：长工具任务怎么安全挂起、唤醒，还不重复下单？

拿一个最常见的研发场景走一遍：**让 Agent 调查线上故障并跑一轮耗时测试**。

1. **受理留底**：校验身份授权，把输入、会话/任务 ID 和版本落库（网络超时重试沿用同一个请求号防建重单）；
2. **拿权开推**：调度层授予当前执行权，加载工作区与检查点开跑；
3. **派发耗时工具**：模型决定跑测试，过权限检查后先把调用参数和**稳定执行标识**记进账本，再发往沙箱；
4. **落盘挂起、释放算力**：发现工具短时间回不来，把继续干活所需的上下文、等待清单和检查点持久化确认安全后，任务挂起、**推理实例立刻释放**；
5. **收到回调唤醒续跑**：沙箱跑完写回结果并通知调度层；新节点抢到执行权，核对等待条件全齐后把结果喂回模型，继续下一步（**必须处理一种并发竞态：万一挂起写入和结果回调几乎同时到达，唤醒前重检就绪条件，避免结果早就到了任务却永久睡死**）；
6. **交付验收**：落盘终态产物，浏览器断了也不影响。

做挂起恢复最容易栽在**两类隐蔽状态**上：
- **第一类：工具到底处在哪一步？** 光看聊天记录根本分不清工具是“模型刚想调还没发出去”“正在沙箱里跑着”还是“结果早回来了但还没进下一轮模型输入”。检查点必须显式存好这三态。
- **第二类：外部副作用的 `unknown` 未知态。** 比如建工单或发通知时网络超时了，对端可能已经办成！系统必须把它标为 `unknown`，先拿着稳定执行标识反查外部状态，或者转给人拍板，**严禁不核对就直接自动重发一次**；如果业务系统支持幂等键，把同一个键从头传到尾。

## 四、同一套底座，怎么同时扛起 Personal Agent 与企业事件智能体？

跑通了受理、挂起、恢复和交接，个人助手和企业智能体其实是共用同一套服务发动机，只在入口适配和业务边界上拧不同的开关：

![Personal Agent 与企业智能体共用服务架构](../../assets/imgs/personal-agent/agentscope-aaas-03.png)

| 对比维度 | Personal Agent 怎么配 | 企业事件驱动智能体怎么配 |
| --- | --- | --- |
| **服务对象** | 个人用户及跨天持续目标 | 团队、具体岗位或自动化业务流 |
| **常见触发** | 网页/手机对话、定时提醒、邮箱日历事件 | 监控告警、文档上传、工单更新、超时回调 |
| **长期资产** | 个人偏好、项目草稿与日常记忆 | 业务规则库、历史排障经验和验收规范 |
| **人的介入** | 用户自己补充要求或点授权确认 | 按岗位角色和合规流程做复核与审批 |
| **最终交付** | 个人能直接看能直接改的文件和答案 | 带证据链、可写回业务系统的结构化产物 |

### 场景 1：Personal Agent 的跨端接力与后台守望

用户通过统一网关把网页、手机、桌面和聊天软件绑成同一个后台身份。早上用户在手机上交代：“继续整理上周调研并出一份对比报告。”远端 Harness 立刻读出云端进度接上活——查公开数据直接丢给云沙箱 Hands 抓；需要翻用户电脑里没上传的私有文件时，在授权范围内把读文件工具路由到刚好在线的本机 Hands；报告吐出来放回网页。晚上用户回到电脑前，本地 Harness 一键把执行权和云端上下文接回来继续精修。

另外，记忆与技能增长也要有边界：把临时上下文、长期偏好和事实分开放，提供给人查看、修改和删除的入口，防止错误记忆带偏后续任务。

### 场景 2：企业事件驱动任务的闭环写法

![企业事件驱动任务的执行与恢复链路](../../assets/imgs/personal-agent/agentscope-aaas-04.png)

放到企业生产环境（如故障排查、文档合规核验、客户经营方案生成），重点在于**事件适配器与版本防串台**：
1. **进门先去重和定版**：监控告警或文档上传进来先按事件去重（重发复用同一任务 ID）；如果文档传了新版，开出关联新版本的新任务，**最后写回业务库时强核对版本号，绝不让旧任务的慢结论覆盖新文档事实**。
2. **安全路由**：远端 Brain 读完日志后，复现与测试按权限分别发进企业内网执行端或隔离沙箱；结果存为待审产物，走企业既有审批流发布。
3. **确定的卡点交给代码工作流**：别让大模型去裁决钱和最终权限审批！用工作流或业务代码把“确定性步骤、审批流和写库幂等事务”卡死，让 Agent 专心啃它最擅长的“读懂杂乱材料、调查异常、按反馈调整动作”。

## 五、平台承载与工程取舍边界（基于阿里云 AgentCore 实践）

用 AgentScope 把上面这套服务框架搭好之后，怎么放到云上长期稳定托底运行？本文实践使用阿里云 [AgentCore](https://help.aliyun.com/zh/agentcore/agentcore-product-overview) 来承载应用与接入（当然企业也可以对照这套职责清单接入自研底座）。

如果你想保留自己用 AgentScope 精细打造的 Harness、状态协议和业务逻辑，走 AgentCore 的[高代码 Agent 部署入口](https://help.aliyun.com/zh/agentcore/high-code-agent-deployment-guide)最对路，四步接通就行：
1. **打包应用镜像**：把 AgentScope Harness、工具适配和服务入口打进容器，暴露对话和健康检查接口；
2. **配资源与网络角色**：配好启动命令、端口、角色权限及模型/内网系统的网络连通性；
3. **接好外部持久存储和沙箱**：接通会话日志、检查点、工作区与独立代码沙箱；
4. **挂进统一观测**：声明调用协议路径、配置身份鉴权和链路观测，把进度、待办和产物送回前端入口。

当然，如果团队不想自己维护一套循环和编排代码，也可以直接用 AgentCore 的[托管 Harness 入口](https://help.aliyun.com/zh/agentcore/agent-instructions-managed-harness)，围绕内置的 QwenPaw 或 Qoder 配模型、角色、工具和 Skill 即可。**关键是双方边界写清楚**：平台负责实例拉起、流量接入和基础托管；应用团队照样要对自己的任务恢复协议、工具幂等键和业务验收负全责。

### 最后的架构选型取舍：这套重底座什么时候才值得上？

1. **别一上来搞“过度解耦”**：如果只是个单轮问答或跑在开发者自己电脑上的轻量脚本工具，`Agent IN Sandbox` 甚至单机进程最香——直接拿现成环境跑，省掉一套分布式挂起、心跳、Outbox 和跨网络工具协议的运维账单。
2. **只有踩中“跨端接力、长等待省算力、企业级凭证不进沙箱”至少两项，才值得切 `Sandbox as Tool` AaaS 架构**。
3. **这套架构真正成立的生死线在协议兼容性**：当本地和远端 Harness 交接、或者服务升级迭代时，必须提前做在途任务的检查点兼容测试，并把 Context、Memory 与工具状态协议定死——否则一升级就把昨天还没跑完的任务全弄炸了，所谓“持续服务”也就成了空谈。
