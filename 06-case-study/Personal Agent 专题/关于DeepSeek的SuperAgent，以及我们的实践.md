# 关于DeepSeek的SuperAgent，以及我们的实践

> *DeepSeek 的 SuperAgent 发布之后，业内普遍有个共同感受：Agent 的底层工程架构正在快速趋同。我们自己做协同空间时踩出来的不少设计，回头一对照几乎撞在了一起。这篇文章除了拆解 DeepSeek SuperAgent 的原理解法与源码判断，也会重点摊开我们做的企业级协同空间 Flock 的真实踩坑和思考。*

## 一、DeepSeek 到底想解决什么痛点？

先看一个很多研发天天都在过的下午——你开着三个窗口让 Agent 同时干活：一个修 Bug、一个写方案、一个跑数据：

![DSH-SuperAgent-首图-IM版-动画.svg](../../assets/imgs/personal-agent/deepseek-superagent/superagent-01.svg)

图 1 · 同一个下午的两种过法

左边累死人的根源根本不是 Agent 本事不行，每个窗口单拎出来干得都挺漂亮；**真正把你拖垮的，是“项目经理”这个调度摊子全压在了人身上**——谁卡着等你拍板、哪条报错属于哪个任务、群里改过的结论在哪扇窗口里，全靠你脑子硬记。DSH 团队观察得很准：**一个人脑子同时跟进 3 到 5 个活跃会话就到极限了**。他们总结出那句极其精辟的话：**单任务的上限取决于模型，多任务的上限取决于人的注意力。**

于是 Super Agent 要啃下来的核心命题压成一句话：**让对面的人感觉始终只对着“一个 Agent”说话，而背后它能同时把一堆事稳稳推进完。** 为此得满足四个要求：
- **连续**：群里刚拍板改用方案 A，转头在代码评论里改成方案 B，它自己接得上，不用你操心信息散在哪个窗口。
- **高效**：不用干等手头这件跑完才能接下一件。
- **主动**：自己盯着环境动态，该出手才出手，没必要就安静闭嘴。
- **持久**：全天候在线，进程挂了能自己捡起来接着跑，不因为你合上笔记本就断气。

DSH 内部举了个很带劲的真实例子：群里根本没人 @ 它，它自己捕捉到异常定位了根因还顺手提了修复：

![image.png](../../assets/imgs/personal-agent/deepseek-superagent/superagent-02.png)

图 2 · 群里没人 @，Super Agent 主动定位根因并提交修复（来源：DSH 原文）

### 在 DeepSeek SuperAgent 之前，大家各解决了哪一段？

这些卡点行业早发现了，只是一直各管一头：Cursor 的 Background Agents 把执行搬到云端免得人干瞪眼，可什么时候发起、怎么调度还是人盯着；LangChain 的 [Ambient Agents](https://blog.langchain.com/introducing-ambient-agents) 靠事件触发省掉了人手动起头，可多任务协调还是得自己拼；今年 9 月集中登场的 Muse、dots、Grok Bot 拆掉了“人必须在线”的墙，偏偏对团队协作里的责任追认着墨不多。

## 二、核心原理：把“一个 Agent”拆成一套前后台小团队

DSH 原文列了六个模块，绕了一圈概念，其实扒开看非常直白。先放原文架构图，再看我们抽出来的简化版：

![dsh-arch.jpeg](../../assets/imgs/personal-agent/deepseek-superagent/superagent-05.jpeg)

Super Agent 原文架构

把它当成一家小公司里的前后台就秒懂：**常驻的 Router 是前台总机**，接待所有人、接收所有新消息并决定把活交出去；**Worker 是各干各活的专业工程师**。前台不亲自写代码，专员不直接跑去前台瞎聊天。外面环境冒出来的消息叫 **Trigger（触发事件）**，进门前先过一道规则筛子。

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-06.png)

图 5 · Super Agent 的简化理解架构

本质上它就在干一件事：从现实世界乱七八糟涌过来的海量事件里，用最省成本的办法滤出真正该管的那一小撮，平衡好大事件流和有限上下文窗口之间的关系。下面拆开每一招看它到底解决了啥问题。

### 2.1 双层架构：连续性和并发吞吐为什么必须分家？

做 Agent 架构有个天然死结：**连续性 vs 吞吐量**。所有事都挤进同一个 Session 串着跑，前后记忆最连贯，但单个循环只能排队处理，一个长耗时工具直接卡死后面所有新事；如果来一件事就新开一个 Session，并发是上去了，可十几个窗口互不认识，还会一起弹窗烦你。

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-07.png)

图 6 · 连续性和吞吐量在单会话里只能二选一，拆成两层才能兼得

DSH 干脆把两件事拆开：**Router 专职扛连续性**，所有对人的沟通和跨任务协调过它这一关，当全局序点和总管；**Worker 专职扛并发**，一件事一个隔离 Session，配最强模型把推理和工具死磕关在自己屋里，干完活只向 Router 交结果，再由 Router 统一跟人对话。Router 因为不用干重活（DSH 甚至连 Bash 都不给它配），用轻一点的模型完全够使。

至于大家老问它跟“Agent Team 里的 Team Lead”有啥区别——Team Lead 要一头扎进单任务内部拆子步，而 **Router 只管任务和任务之间的外层关系**；Worker 自己想在内部再拉子 Agent 对 Router 完全透明。原文也直言，如果你拿提示词死锁住主会话不准亲自干活，其实也能看成这套双层思路——**核心在职责边界划分，不在组件叫什么名字**。

### 2.2 事件驱动加直通订阅：别让噪音白白烧掉模型钱

真实工作环境是“高噪音、低有效触发率”——群里刷几百条水群消息、PR 里一堆格式提示，真要问一次大模型，又慢又烧钱。

DSH 搭了个漏斗：**简单情况走 Fast Path（硬规则过滤）**——比如优先盯死重点群、重点人（产品经理或老板的发言重点监听）——**只有漏斗最底下少部分真拿不准的才走 Slow Path（调模型判断）**。实验负载里大约 300 条原始消息过完漏斗，真正变成工作请求的只有约 20 条：

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-08.png)

图 7 · 把昂贵的模型放到漏斗最末端（300 与 20 来自 DSH 实验合成负载）

更巧的是**订阅直通机制**：同一个 PR 或群聊话题的一串往返事件归成一条 **Thread**。Worker 一旦接了活并订阅这条 Thread，后续相关回复由代码直接推到它手里，**不用再去惊动 Router！** 而且多个 Worker 可以同时订阅同一条 Thread，彼此能看见对方进展，顺手解决了“干活时不通气互相踩脚”的麻烦。

消融实验数据非常诚实：砍掉订阅直通后，任务总完成时间几乎没变，但 **Router 要多做约 30% 的判断，读缓存 Token 暴涨约 37%**——这招省的是前台大脑的负载和账单，不是单个专员干活的绝对速度。

### 2.3 上下文怎么放：Inline、Spill 和链式召回

窗口塞太满既贵又容易让模型分心，塞太少模型又得来回调工具找历史。DSH 把上下文窗口当成 CPU Cache 来管理，借了编译优化的两个概念：
- **Inline（内联）**：近期大概率马上要用到的紧邻信息直接拍进窗口，省一轮工具调用；
- **Spill（溢出）**：超出预算或低频老材料踢出窗口，只留一行摘要或引用 ID。

把这套引用顺手嵌进 Trigger、Thread 和 Worker Session 里，它们就自动连成了一张引用图——每个节点都指着下一跳的 ID。Router 根本不用硬背三个月前的所有对话，遇到人重提旧事，顺着 ID 一跳一跳往回捞就行，这就是**链式召回（Chain of Recall）**：

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-09.png)

图 8 · 链式召回示意：顺着对象引用一跳跳翻回历史

当然原文也坦诚划了边界：这套召回打理近期交办非常顺，一旦跨度拉到好几个月，长期记忆照样是个没完全解透的硬骨头。

### 2.4 全双工：跟 Codex 的“运行中插话”有什么不一样？

用过 Codex 的同学熟它的 `steer` 插话能力——能往正在跑的轮次里塞一句新提示。但问题在于，传统循环是“思考 → 调同步工具 → 干等 20 分钟跑完测试 → 下一步思考”，**只要卡在等同步工具返回，你在外面喊一百句“先停下”，模型也要等 20 分钟后才能看见！**

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-10.png)

图 9 · 插话 vs 全双工的区别在于：“先停下”到底要等几分钟才被模型看见（示意）

DSH 说的**全双工**专治这个阻塞：所有耗时命令和子任务全部改造成**异步启动（start）加主动叫停（stop）**——调用立刻返回“已启动”，推理步飞快收尾；工具在后台闷头跑，出结果再当新事件投递回来。这样每个推理步都很短，人随时插话随时下一秒就生效（原型代码里干脆卡死：**前台命令跑超 5 秒自动转后台**）。模型本身依然是一步步串行推理，只不过把阻塞等待拆出了推理环外头。

### 2.5 把计算、状态和执行环境拆成三件独立的事

传统本地 Agent 把思考循环、会话记录和你的本机环境死绑在同一台电脑上，合上笔记本全停摆。DSH 这套原型拆了整整两刀：

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-11.png)

图 10 · 跨周末长任务示意：本机中途离线也不丢进度（间歇在线设备接入思路来自原文）

- **第一刀：计算和状态分离**：Agent Loop 跑在云端无状态容器里，Session 进度落进数据库，容器随时挂了重起也不丢账；
- **第二刀：计算和环境分离（BYOM 思路）**：开发者电脑里满是未提交代码、私有密钥和公司内网权限，想在云上完美复刻一台一模一样的沙箱太费劲还容易漏。DSH 反其道而行之：**不折腾复刻环境，直接把不存状态的轻量 daemon 装到本机原地干活**，云端大脑需要用本机环境时把指令发下去，设备睡了就原地挂起等它上线再接着推。（当然凡事有代价：必须容忍设备离线时这一步干等着；像 Cursor Background Agents、Codex 云端任务走另一条路，在云上重造干净沙箱——不靠你开机、并发 isolates 也好，代价就是每次复刻环境极重。两条路只是各自用不同成本换不同东西。）

![Picture 11](../../assets/imgs/personal-agent/deepseek-superagent/superagent-12.jpg)

图 11 · Anthropic 的“脑手分离”思路同源：Session、Harness、Sandbox 拆成独立接口；DSH 的特色是优先兼容间歇在线的个人机器（来源：[Anthropic Engineering](https://www.anthropic.com/engineering/managed-agents)）

顺带提一句极实在的排障设计：**Agent 最常见的死法不是进程崩掉，而是进程活蹦乱跳，模型却在原地死循环打转**——普通心跳探针根本抓不出来。于是 DSH 在外围单独设了个独立的 **Watchdog 会话**，定时巡查每个 Worker 有没有真推进、方向有没有跑歪。

### 2.6 看懂原文实验账本：多花 3.8 倍读缓存到底买了什么？

很多人瞄一眼原文只记得“快了将近一倍”，其实把完整数据表摊开看更有意思：

<div class="superagent-table">

| **实验方案** | **P50（中位完成时间）** | **P95（慢长尾完成时间）** | **读缓存 Token 消耗** |
|---|---|---|---|
| **Super Agent** | 12.4 分钟 | 15.7 分钟 | 2,323 万（基准的 3.8 倍） |
| **单会话 + 提示词要求优先委派** | 13.8 分钟 | 29.0 分钟 | 1,082 万（基准的 1.8 倍） |
| **单会话 + 中性提示词** | 20.4 分钟 | 29.5 分钟 | 605 万（1 倍基准） |

</div>

看清这组对比：**光靠在单会话里加一句提示词，中位耗时就已经追到只差 11%，Token 花费还不到 Super Agent 的一半！** 那整套双层架构究竟贵在买到了什么？**买到了稳稳当当的 P95 下限（15.7 分钟 vs 29.0 分钟）！** 靠提示词约束的单会话，模型总有那么几次一拍脑袋觉得“这活不大我自己干算了”，直接把最慢那批任务拖回 29 分钟——这种随机性靠写提示词永远按不住。另外注意：这组测试用耗时空跑工具模拟编码，测的是纯粹的并发调度，不能直接外推成真实团队开发速度翻倍。

## 三、把原型源码扒开看：写进代码里的五条工程铁律

DSH 开源了一个约 1.6 万行代码的[原型实现](https://github.com/deepseek-ai/dsh-superagent-prototype)。翻完代码，这几个核心对象先对上号：

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-13.png)

图 12 · 原型核心数据对象关系

- **Trigger 与 Thread**：外面发生了什么事，以及哪些事件归同一条讨论线；
- **Ticket（工单）**：一份获准开工的工作，是全场最硬的稳定对象——聊天可断、Worker 可换，Ticket 永远在那；
- **Policy（规则）**：团队规矩（谁能派活、啥时候允许主动插手），支持版本迭代；
- **Mandate（授权）**：写死这张工单凭什么开工、谁拍的板、管多大范围、依据哪版规则。

把 Ticket 和 Mandate 拆成两个对象非常聪明：假如上周修复合并完 Ticket 已经关闭，一周后突然有人在旧 PR 下面补了一句“这还有个小问题”。系统既不用傻傻重新过一遍审批流程，也不会鲁莽无授权乱改——**拎出当初那份 Mandate 对照最新 Policy 验一遍还生不生效，就能决定让不让工单原地复活**。一件事“做到哪了（状态）”和“凭什么还能动（授权）”，本就是两码事。

再走一遍一条消息进门到开工的流水线：

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-14.png)

图 13 · 一条消息进门到开工的五步链路（整条链只有第 4 步叫了一次模型）

1. **进门先 Append-Only 落盘去重**，保证重启不重放、事后能追踪去向；
2. **查现有归属**：若消息落在某张进行中 Ticket 订阅的 Thread 上，直接甩给对应 Worker，连 Router 都不用找；
3. **代码硬门禁（Gate）**：先按硬规则查发信人有没有资格；
4. **实在拿不准才问 Router 模型**；
5. **原子开单**：生成 Ticket、Mandate、订阅和确认回复一次落库提交，绝不留“单开了却没人认领”的半吊子态。

这套 1.6 万行代码里，最值得抄走的工程判断有五条：

### 1. 模型只负责“提议”，代码程序才是最终裁决者

整个系统里只有一个确定性的程序核心能改写 Ticket 状态。Router 说“我要接单开工”，**技术上只是向程序交了一张申请单**，核心代码逐项核对权限、规则、参数合法性和当前状态，不合格直接打回。模型哪怕抽风或被注入了，最坏也不过是递了一份被门卫挡回去的废纸（Router 不准亲自跑耗时操作也是直接写死在代码校验里的，绝不靠提示词自觉）。

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-15.png)

图 14 · 模型提议的灵活性与确定性代码的铁闸门

### 2. 先在数据库记完账，再去干外部副作用（Outbox 模式）

最怕状态刚写成“已接单”，确认消息还没发出去服务器崩了。DSH 彻底执行分布式经典 **Outbox 模式**：启动 Worker、发消息、投 IM 通知，全部作为待办动作和状态变化打包在同一个数据库事务里提交，再由后台协程逐条发往外部；万一崩溃重启，未执行的动作接着发，同时提醒 Worker 重启后先看一眼磁盘代码和 PR 现状，别把刚干完的活又傻傻重做一遍。

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-16.png)

图 15 · 外部副作用先跟状态一起进事务账本，提交后再异步兑现

### 3. 外部文本永远只是不可信数据，且严防“传话走样”

整天读群聊和 PR 评论，迟早撞见恶意提示注入。代码死死卡住“系统策略永远压过用户指示、外部消息只能蹲在最底层当纯数据”；而且还有一个特别细微的设计：**Router 派单给 Worker 时，备注最多只准写 30 个词，绝不许替 Worker 擅自定实现方案和验收标准**，Worker 必须亲自去翻原始消息——彻底堵死人类团队里最常翻车的“一层层传话失真”。

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-17.png)

图 16 · 指令权限优先级金字塔：外部消息永远压在最底层

### 4. 主动干活的能力，必须先开“影子试运行”灰度

自动乱提 PR 的机器人一天之内就会被团队拔电源。原型把“判断该不该干”和“真去干”拆开：新规则先放影子模式试跑，模型照常推理并必须逐条引用规则和消息原文留痕写明“如果放开我会接这个单”，但不真执行——等团队翻记录点头觉得靠谱，再切开真实执行闸门。

### 5. 永远把“人的注意力”摆在最高优先级

代码里落了三处极其务实的细节：看板排序永远把“正在等谁拍板”且卡在人身上的排最顶；哪怕 Worker 并发槽位全打满了，也必须死留一个特权通道给人的新插话；而且严格区分**“消息送进队列”和“模型真读进历史”**——万一 Ticket 关单那一刻发现人刚发了一句“等一下别合！方案有变”还没被 Worker 读到，立刻退回重评重开，绝不瞎关门。

### 原型的坦诚局限

当然，这毕竟是一个 1.6 万行代码的研究原型，本身也有明显妥协：状态蹲在单机数据库里、一个部署只绑一套账号和一个代码仓；Worker 直接拿运维者宿主权限跑（文档明说命令包装不算安全沙箱）；文中夸过的 Watchdog 和投机执行在开源原型里其实并没有找到实现；更重要的是**研发天然有 PR 合并、CI 绿灯这种客观完结信号**，可换到企业非研发通用业务上，完成判定远没那么痛快——而这些缺口，刚好就是我们自己下场做企业级协同空间补上的地方。

## 四、反思“数字员工”与我们的五个核心判断

### 1. 先给“数字员工”卸妆：别拿聊天框加知识库糊弄人

这两年满大街产品都自称数字员工，点进去十有八九还是“对话框 + RAG 知识库 + 几个 MCP 工具”，窗口一关前情清零，下次来还得再讲三遍前情提要。算不算真数字员工，我就问四个朴素问题：

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-18.png)

图 17 · 我对“数字员工”的四级划分（个人观点）

- 用不用每次重讲一遍背景？（真同事不该让你每次先点“新建会话”）
- 你出门开会之后，它自己还能接着往下推吗？
- 上游完事了、CI 挂了、到点了，没人催它能自己醒来吗？
- 捅娄子了，查得出当时谁指使的、为什么这么干吗？

答案全部是“能”，才够格叫数字员工，这恰好就是 Always-on 与 Super Agent 指向的同一终点。不过落地到企业协同空间里，在具体设计上我们走了几步跟 DSH 不太一样的路。

### 2. 不一定要常驻大管家 Router，Coordinator 按需唤醒也很香

大家读 DSH 时目光全盯在中心 Router 上，可拆开了看它其实一人兼了三份差事：前台接待、路由分发、全局记忆。我们自己动手时把这三份活彻底拆开了：

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-19.png)

图 18 · 同样的三项职责，我们在协同空间里的拆分落点

人机共享的频道（Channel）时间线本身就是前台；谁该唤醒靠程序盯着账本状态直接算；需要动脑拆解和汇总的时候才唤醒频道里的普通成员 **Coordinator（协调者）**——它的死规矩是只准拆单、盯进度和收口，绝不亲自下场干脏活；记忆全沉进任务单（Quest）和文件里。**这样换的好处是协调者不用 24 小时常驻，窗口极干净、权限好画圈**；吃亏的地方是少了常驻大管家积攒一波事件“顺便批处理打包解决”的红利——这也是我们下一步准备找 DSH 偷师的点。

### 3. 别照搬人类公司层层汇报的科层架构来设计 Agent

人类团队天然害怕“所有事全找同一个人”，因为人脑带宽只有那么一点宽，才逼出了总监、经理、周会逐级压缩。可 Agent 没有这条人体限制！DSH 的 Router 压测出了一个极其反直觉的数据：事件密度从每分钟 1 条涨到 40 条，单次路由决策的平均思考时间不升反降——**从 6.4 秒暴跌到 1.6 秒！** 原因就在思考间隙堆起来的事件被下一轮一口气合并批处理了。

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-20.png)

图 19 · 同样是中心化结构，人类和 Agent 的成本曲线截然相反（右侧数据引自 DSH 压测）

![Picture 20](../../assets/imgs/personal-agent/deepseek-superagent/superagent-21.jpg)

图 20 · Router 批处理压测：在一定吞吐内事件越密，单次决策反而越省时间（来源：DSH 原文）

给我们的最大启发就一句：**千万别按公司组织架构图照猫画虎去设一堆层级汇报的 Agent 角色**。人类组织的科层是为人类窄带宽打的补丁，在 Agent 系统里，扁平集中反而是最不费劲的高效拓扑。

### 4. 但中心化的四个瓶颈没消失，只是搬了家

当然那个压测 Worker 用的是假桩且只冲到每分钟 40 条，中心架构的四个真瓶颈依然摆在台面上：

| **瓶颈点** | **为什么会撞墙** | **DSH 原型的招** | **我们协同空间的招** |

我们在企业场景里宁愿先牺牲一点全局大一统，也要优先把按 Channel 切分的安全边界立住。

### 5. “只管验收结果”什么时候成立？只有能独立验收的活才配拆分

中心协调者一旦插手“具体怎么做”，马上重新退化成又肥又慢的瓶颈。

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-22.png)

图 21 · 中心只下达契约与验收口径，执行过程对中心黑盒化，结果回来再复场验收

我们在协同空间里派发任务单，只写死目标、验收标准、唯一责任人和前后置依赖，绝不代写实现计划；怎么调子 Agent 或走什么工具流全归执行者管，做完醒来交差就行。相比之下，研发因为有 PR 和 CI 充当硬裁判，DSH 甚至连验收标准都不让 Router 写；但企业业务往往没有现成裁判，必须把验收标准写进任务契约。

由此也刚好能回答去年行业里那场著名论战：一边 Anthropic 演示了多 Agent 并行搜资料的 Research 系统大杀四方，同一时间 Cognition 写长文《Don't Build Multi-Agents》拿一起画 Flappy Bird 举例（一个画了超级玛丽背景，另一个画了格格不入的鸟）劝大家别乱拆。其实两边都没说错——**调研搜集可以拆，统一美术风格拆不开！多 Agent 该不该拆，只看一条准则：这项子工作能不能离开全局上下文被“独立验收”。**

## 五、我们的企业级实战：协同空间 Flock 踩出来的七个教训

如果说 DSH 回答的是“怎么让一个人同时稳稳驾驭好几个后台 Agent”，我们做协同空间 Flock 要啃的是企业里更现实的问题：**一群不同部门的人加上一群各司其职的 Agent，怎么共同把同一件事扛到底、还要能交差审计？**

### 1. 架构先立骨：控制面和执行面彻底拆开

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-25.png)

图 24 · 协同空间四层架构与流转过程

最核心的一刀是**业务事实的控制面，和跑模型调用、断点恢复的执行面彻底分家**。谁背锅、做到哪一关、现在是第几版交付物，全躺在控制面的硬账本里；执行面哪怕挂机十次、半途换了另一台机器接着跑，业务责任和进度永远稳稳留在控制面。

### 2. 一张由 Channel 拼起来的协作网（含本地机器接入）

不像 DSH 一个超级中心管全局，我们按项目和业务边界建了好多彼此隔离的 Channel：人、协调者、云端 Agent 甚至开发同事电脑上的本地 Qoder 都坐进同一个频道共用同一条时间线，默认上下文和权限不出墙。需要跨部门配合时，不是把外人拉进来看私密历史，而是在对方 Channel 下正式发一张单，由对方在自己权限域里干完把交付物送回来——**我们还立了条防扯皮熔断规则：同一条跨频道交互链来回推诿超过 6 轮直接锁死并弹窗建议“你们俩合并空间算了”**。至于本机上的 Qoder，我们干脆把它当成频道里的一个普通实名成员领任务、交成果，和云端 Agent 吃完全同一套验收体系。

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-26.png)

图 25 · 多 Channel 空间隔离与受控跨边界建单协作

### 3. Sessionless：把“会话”藏进抽屉变成一次性的耗材

你找老同事交代工作，绝不会每次先点个“新建一个同事”。我们的系统里用户根本找不到“新建会话”按钮——底层当然还是有会话，但它彻底沦为一次性耗材：**平时聊天靠几个事实维度（含空间、成员集合等）自动算出一个会话键，人不变就接着聊，频道一旦进出成员立刻自动隐式切换防泄密；正式干活每轮尽量开干净新会话防止老垃圾越滚越胖；最后验收环节每次必开全新纯净会话，不让裁判带着运动员的草稿记忆判分！** 为了藏住会话之后依然能查账，9 月专门补了一张全链路血缘表，顺着人发的那句 @ 一次查清背后长出了几串任务和会话。

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-27.png)

图 26 · 前端只看到一条连贯时间线，背后系统已按职责自动切出多段独立会话

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-28.png)

图 27 · 会话边界由系统事实计算决定（成员变动自动保护隐私隔离），不用人手动选

### 4. Quest（责任状）：没有甲方点“验收通过”，就不算干完

会话成了用完即扔的耗材，真正扛住长周期跨度的稳定内核叫 **Quest（建表备注就三个字：责任状）**。目标、验收标准、唯一责任人全钉死在上面。

这里卡得最狠的状态叫**“待验收”**：**Agent 报错没出现、代码跑完了，在企业里根本不叫任务结束，它只算交了一版初稿！** 必须由真人或者指定的独立验收 Agent 对照标准点认可，才算完事；不满意直接打回留在原单重做，上一版留痕存档。比如在线上协同空间里，经常是研发 PM Agent 刚在频道立完 Quest 单，本地 Qoder 认领完把代码产物提交上来，最后乖乖停在“待验收”等研发负责人拍板。

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-29.png)

图 28 · Quest 任务生命周期：增加刚性的“待验收”与打回机制

### 5. 任务链 DAG 不是开局画出来的，是干着活“长”出来的

复杂事情开局根本列不全流程图，我们立了三条简单规则：**干活途中自己拆单默认挂成当前任务的子单；建单写明依赖谁，上游过验收才自动唤醒下游；所有子单闭环自动唤醒父单汇总交付。** 就像下面这个提货任务里，“失败订单复核”就是执行者在干活途中发现异常自己临时拆出来的，开局压根不在大盘里。为了防任务脱离监管变孤儿，系统唯一卡死的铁规是：新建子单说不清归属父任务直接拒绝创建。

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-30.png)

图 29 · 一个提货任务干着干着自然长出来的 DAG 任务树

![image.png](../../assets/imgs/personal-agent/deepseek-superagent/superagent-31.png)

图 30 · 协同空间真实生产环境长出来的全景任务执行链路

### 6. 顺着任务链找两周前的老账 & 防住“互相 @ 死循环”

有了任务链这张带血缘的工作关系图，连回忆历史都省心多了——问一个两周前为什么出异常的复杂问题，线索在第二版批注里、证据在上游失败单里、解释在业务人员一句回信里，Agent 不用硬背两周上下文，顺着 Quest 链路走过去就全捡起来了：

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-32.png)

图 31 · 沿 Quest 责任链反向捞取跨周证据（场景与数字为示意）

至于主动推进，压根不需要有个大模型 24 小时坐在那儿冥想“我今天干点啥”——**任务状态全躺在账本里，状态一变代码直接算出该唤醒谁，有真变化才拉起模型**。

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-33.png)

图 32 · 状态变化算唤醒、执行产出再变状态的主动推进闭环

但这地方我们踩过最惊悚的一个线上坑：**多 Agent 互相疯狂唤醒！** 预发上有个简单的“点名报数”任务，本该 3 次执行收工（协调者点两个成员、各自回一句、汇总），结果一眨眼跑了 10 多次生出 8 个执行实例，甚至还有 Agent 自己在那儿 @ 自己。查下来发现压根不是模型傻，而是平台把“群里点名聊天”和“派发责任单”绑在了一条触发链上——被 @ 的 Agent 拿到的死命令是“完事必须交正式交付物”，于是老老实实不断拆单发通知循环引爆。

解法极简单粗暴：**在代码协议层把语义彻底劈开——`@` 只算聊天口头打招呼，正经 `Quest` 才算派发执行权**；外加抄送不准唤醒、Agent 之间连续相互唤醒默认最多连跳 3 次立刻锁死，人一插手再清零计数。和 DSH 一样的血泪结论：**管住并发灾难，平台硬约束永远比写一百遍提示词管用。**

### 7. 跨会话长期记忆：被线上问题逼着“从推改成拉”（MDC）

早期我们也图省事，每次唤醒都把成员表、当天消息、最近动态全一股脑塞进窗口生怕它漏；结果就是窗口越来越肥、废话越来越多。后来一刀全砍光，逼出了和 DSH Inline/Spill 如出一辙的思路：**别硬塞，给它一个带索引和引用路径的文件接口，需要哪段它自己按需翻！** 顺便修了一个小细节：超长工具输出再也不粗暴砍半截，而是留住头尾、折叠中间并注明翻页参数，免得每次全新醒来的 Agent 拿了半截信息误以为是全部。

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-34.png)

图 33 · 从“一股脑硬推”被逼成“给线索按需拉”

![](../../assets/imgs/personal-agent/deepseek-superagent/superagent-35.png)

图 34 · MDC 思路：把记忆变成可审计、可引用、换模型也能带走的文件接口（目录为规划示意）

## 写在最后：两个越来越清晰的工程趋势

看完 DSH 源码再对照我们自己的泥坑，两个大趋势已经摆在桌面上了：

**第一，Agent 底层架构正在快速收敛。** 并不是谁抄谁，而是约束条件把可行解空间挤得越来越窄：模型已经足以干完单个孤立任务，人的注意力成了稀缺品，逼出了统一入口；任务跑得比窗口和单台电脑更久，逼出了无状态执行与外置稳定任务单；任务状态必须跨断点活下来，逼出了 Ticket / Quest 这种核心数据模型。就像当年数据库全部走向预写日志（WAL）、操作系统全部走向进程和调度器一样，答案天然在往同一个方向长。

**第二，Agent 正在大规模回归经典系统工程。** 一旦 Agent 从“聊天机器人”变成“长周期跑在网上的服务进程”，进程挂掉、网络抖动、消息重放、副作用不能执行两遍这些分布式系统的老祖宗问题一个也躲不过。你看今天无论 DSH 还是我们代码里，满眼全是最经典的工程手艺：**预写日志、Outbox 事务外发箱、执行权租约（Lease）、幂等键和可回放账本**。

模型永远是系统里唯一充满概率不确定性的部件，而工程师的全部使命，就是造一套极其确定的钢壳把它稳稳包在里头。可靠不再只靠“求着模型每次都一次做对”，而是靠“做歪了、半路断了，外面的系统也能兜住并收敛回来”。未来的 Agent 会越来越像一门硬核的系统工程：**Model 是 CPU，而包在它外头的 Harness 脚手架，就是操作系统加数据库。**
