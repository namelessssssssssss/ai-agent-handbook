# 第 30 章　从 Agentic Application 到 Agentic OS

当一家公司只跑一两个 Agent 时，谁都可以自己在脚手架里顺手写套超时重试、建个临时目录、塞几行权限判断和日志埋点。可只要同时上线十几个 Agent、团队之间用着三四种不同框架、背后还要隔离几十个业务租户，灾难就来了——**前面每一篇提到的所有工程硬要求，都会在每个应用里被重写一遍，而且每家的实现口径、ID 命名、沙箱规格和账单算法完全对不上。**

这不是某个团队代码写得懒，而是因为所有应用底下缺了一个**共享的系统层**。

本书把这一正在成型的公共系统层称为 **Agentic OS**。先说死一个前提：**它目前还不是市面上能直接买到的成熟商业软件，也不必然意味着非要重写一个操作系统内核**；它更像一组正在迅速收拢的系统级职责，专治多应用、多框架并发跑起来之后的重复造轮子和互相不信任。

## 30.1 前 29 章已经确立的共识，与放量后避不开的六类痛点

### 30.1.1 五项底座级共识

前六篇拆了构建、运行、治理、调优和一线案例，剥开技术细节后，其实收束到了五条站得住的共识：

1. **设计对象是整套系统，不是单次模型调用**：第 01 章把 Agent 拆成大脑（Model）和外层任务控制脚手架（Harness），第 02 章把整个系统切出五个责任域——模型升级不该逼着重写应用，任务逻辑也不该绑死在某台机器的 Runtime 上。
2. **任务是长周期管理对象**：第 04、05、07、08 章反复证明一件事，一个 Agent 任务的寿命远长于一次 HTTP 请求和单个进程，它必须外置状态、随时能挂起等审批、随时能换机断点续跑。
3. **能看见工具 ≠ 有权执行工具**：第 05、06、09 章把能力发现和权限授予彻底拆开。模型脑子里知道某个 MCP 工具存在，绝不代表它有资格把参数发过去改线上数据。
4. **放多大权，就配多大隔离和撤回能力**：第 07、09、14 章划死一条线，自主性不是靠信任模型给的，而是靠可撤销的爆炸半径和审计证据兜出来的。
5. **拿不出可复现的评估证据，就不算发版**：第 13、16、21、22 章把“线上 Trace → 黄金数据集 → 离线/仿真回归 → 灰度准入”连成硬门槛，改动不管落在 Prompt、Skill、工具还是脚手架上，都得拿同一套评估证明真变好了。

### 30.1.2 多应用并跑后炸出的六类重复造轮子

这五条在一个应用里咬牙都能做完。真正卡脖子的是**组织规模化之后**，六个硬骨头在每个业务线反复重演：

1. **“一次运行”各自起名，算账排障对不上号**（第 04、05、07、08 章）：有的框架按 Session 算一次任务，有的按图（Graph）执行节点算，有的按进程算。财务想跨业务汇总一次任务的真实花费、SRE 想拉全链路限流，第一步全卡在“先把各家 ID 强行对齐”。
2. **执行环境成了烧钱大户，波峰波谷直接决定并发上限**（第 07、08 章）：Agent 干活的特点是“等模型思考 10 秒空转，然后集中 2 秒狂跑编译测试”。按峰值给每个任务常驻容器，90% 的算力都在睡大觉；按均值压密度，几十个任务同时醒来调工具瞬间堵死。沙箱的冷启动、空载占用和挂起恢复速度，直接卡死了平台能养多少并发。
3. **工具描述太穷，出事根本不敢自动重试**（第 06、23 章）：现有工具描述最多写清入参出参，但生产里最缺三句实话——**这接口改不改外部状态（有没有副作用）、重发一次会不会扣两遍（是否幂等）、挂了能不能安全重试**。缺这三项声明，第 23 章的自愈闭环根本不敢碰写操作，只能转人工。
4. **对话一压缩，State 就被偷偷污染**（第 05 章）：理论上 Context 和 State 必须分家，但写代码图省事时，摘要和续行逻辑经常把“残缺的聊天历史”直接当成“可恢复的任务事实”。单应用靠 code review 还能盯住，接入多个异构框架时根本管不住。
5. **父任务掐死了，派生出去的子任务凭证还在外面裸奔**（第 09、14 章）：主 Agent 会派生子 Agent、后台作业和工具调用，授权得跟着传递下去；可当人工喊停主任务时，由于任务中止、网关策略和凭证注销分散在不同代码里，“任务显示已终止”和“它的子凭证真的作废”往往不同步。
6. **各自埋点，指标打架**（第 13、21 章）：模型、工具、状态、审批各自吐各的日志格式，跨团队根本没法比“哪个 Agent 更稳、单位任务成本谁更低”。

这六件事没有一件是单个应用写错了 Bug，它们共同指向同一个事实：**应用底下缺一个公共系统层。**

## 30.2 什么该下沉成公共层，什么必须死守在应用里

### 30.2.1 三条下沉判据

千万别把“大家都要用”的东西一股脑全塞进系统层——把业务规则和任务语义塞进去，只会造出一个谁都嫌难用的大泥球框架。本书只给一条硬杠杠：**必须同时满足“判据一”，且至少满足“判据二”或“判据三”之一，才配下沉。**

- **判据一：复用性**——多个应用都在重复实现，而且各家实现得不一样并不产生任何业务差异化价值（比如工作区打快照、轻量沙箱启停、底层 Trace 采集属于此类；任务的业务完成标准和终止条件则绝对属于应用自己）。
- **判据二：强制性**——只有卡在被约束方外面，规矩才真的算数（比如权限校验、网络出站白名单、预算熔断、审计留痕；写在 Prompt 里劝模型“请别越权”，或者让 Agent 代码自觉调一下检查函数，全都不算强制）。
- **判据三：可验证性**——需要独立于干活那一方的旁路证据，才敢信它没撒谎（比如宿主机关联出的真实调用链、独立核对工作区变化；Agent 自己汇报“我改完了且测试全过”不算独立证据）。

拿这三条尺子回头量上面六个痛点，落点立刻清晰：
- **明确该下沉的**：环境资源与并发承载（痛点 2）、随任务派生的可撤销授权（痛点 5）、统一口径的旁路证据采集（痛点 6）。
- **靠跨厂商标准对齐的**：统一的 Run 对象标识（痛点 1）、副作用与幂等性元数据（痛点 3）。
- **接口下沉、策略留应用**：Context 与 State 的隔离边界可以下沉成 Runtime 接口规范，但具体每轮怎么挑上下文依然归应用自己管（痛点 4）。

### 30.2.2 Agentic OS 的窄定义与三条底线

按三条判据收口，我们给 **Agentic OS** 下一个极窄、极实操的定义：

> **Agentic OS 是为各类 Agent 任务提供公共运行对象、公共能力接入、可强制边界与统一证据的系统层。它只管任务、环境、能力、授权和证据，绝不掺和具体的任务语义。**

定义里的三条否定红线，比正面描述更重要：

1. **绝不替代 Harness**：这一步怎么拼上下文、循环何时算完、按什么业务规则验收（第 02 章定义的 Harness 脚手架核心），是业务语义，必须留在应用侧。系统层管的是“任务运行对象的生老病死”，不管“任务本身怎么干”。
2. **不是又一个 Agent 框架**：框架靠 SDK 规范你的写法，不用那套 SDK 约束就没了；系统层靠接口和物理强制点管住运行行为——哪怕接入的是第 11 章讲的黑盒第三方 Agent、对方压根不配合修改代码，照样能拦得住、查得清。
3. **不等于非要重写操作系统内核**：下沉的真正目的是“把控制点移到被约束方够不着的外面”，而不是比赛谁的代码离硬件更近。放平台控制面、宿主机守护进程、容器运行时还是内核模块，只看两件事：**在该层能不能真拦住**、**开销划不划算**。这与第 02 章“最低充分架构”的逻辑一脉相承。

### 30.2.3 它和业界说的“AI 操作系统”四种路线是什么关系

行业里聊“AI 操作系统”常把四类完全不同的东西混为一谈，表 30-1 帮你在 10 秒内分清它们和本书的关系：

| 产品形态 | 到底改了什么 | 典型长相 | 和本书主线的关系 |
| --- | --- | --- | --- |
| **1. 交互层重构（系统之外）** | 外部助手透过现有桌面/命令行操控 OS | 命令行助手、Computer Use 桌面代理 | 对应第 06 章环境接口，宿主系统自身几乎零改动 |
| **2. 内核与服务增强（系统之内）** | 专门针对 AI 和 Agent 负载改造内核、驱动和运行底座 | 异构算力适配、缓存管理、沙箱高密调度 | 正是第 07–09 章的物理托盘，直接决定并发成本上限 |
| **3. 功能层融合（系统之内）** | 把模型、上下文、工具与任务管理融入系统级服务 | 系统智能服务、系统级 Agent 账户、任务管控 | 和第 09、10 章及治理篇的控制面职责高度重叠 |
| **4. 底层架构颠覆** | 推倒重来重构计算、保护与状态的基础机制 | 全新 AI 原生内核、专用执行域研究原型 | 对应 30.7 节前沿探索，目前尚无通用成熟商用底座 |

表 30-1　“AI 操作系统”四类产品路线的工程定位

看懂表 30-1 就会发现，Agentic OS 根本不是凭空空想出来的概念，而是**两条已经开跑的工业演进线，正在同一组管理对象上迎头撞上**：

- **自上而下，平台能力往系统接口下沉（第 3 类）**：openEuler Intelligence 把本地知识库、语义接口、MCP 服务和运维工作流做成了系统级智能服务；Red Hat 推出 RHEL MCP Server 把系统诊断命令直接暴露为标准工具接口（开发者预览）；Microsoft 把 Agent 独立标准账户与 Agent Workspace 放进了系统能力（相关 Copilot Actions 处于实验预览）。
  在这条线上，阿里巴巴开源的 **ANOLISA** 是组织方式最贴近本章模型的公开样本，因此后文会多次拿它对照：它把面向 Agent 负载的操作层拆成三个域——**Agent 入口**（cosh-ng 终端、OS Skills、ktuner 内核调优）、**上下文效率**（Token-less 工具输出压缩、Agent Memory 跨会话记忆、AgentSight 轨迹与 Token 可见性）、**运行与安全**（ws-ckpt 工作区检查点回滚、SkillFS 技能视图、Agent Sec Core 沙箱校验、Blaze 沙箱生命周期）。关键在于它的边界声明：**保留用户原本的 Shell、Agent 框架和沙箱，每个模块可单独启用**，既不强迫换框架也不要求魔改内核。同时必须如实说明成熟度：截至 v1.1（2026-08-08），除 copilot-shell 外其余组件多处于 0.x 版本，这里只作为架构组织样本参考，不作为直接照搬的生产基线。
- **自下而上，Linux 宿主机和内核为 Agent 负载增肌（第 2 类）**：传统 Linux 用 PSI（压力停滞信息）和 cgroup v2 做资源观测与配额微调，如今沙箱轻量冷启动、模板预热、写时复制、空闲瞬时回收已成标配诉求，连 CPU 厂商都开始把“单机能同时塞多少 Agent 沙箱、每秒批量拉起多少个”当成核心基准场景。

两条线最终会师的点，正好就是前面撞上的“环境、授权、证据”。这也划清了现实边界：**第 4 类原生重构目前还在学术和实验室阶段，当下工业界真正能落地的 Agentic OS，本质上是“第 2 类 + 第 3 类”在既有 Linux 底座上的组合演进——叫它“操作系统”，讲的是系统级责任归属，不是非得换内核。**

## 30.3 Agentic OS 到底管什么：九个核心对象与三层结构

### 30.3.1 传统 OS 管进程文件，Agentic OS 管这九个对象

操作系统长什么样，归根结底看它把什么东西当作一等管理对象。把前面 29 章散落各处的抽象收拢起来，Agentic OS 需要直面表 30-2 里的九类对象：

| 核心管理对象 | 一句话语义 | 寿命跨度 | 既有系统里的土办法近似物 | 缺了它必然踩的坑 |
| --- | --- | --- | --- | --- |
| **Agent 身份** | 可被单独授权和追责的执行主体 | 长于单次任务 | 服务账号、独立标准账号 | 出了事分不清是用户点错了还是 Agent 擅自干的 |
| **Run（任务运行）** | 一次有目标、可暂停、能换机恢复的执行 | 分钟到数天 | 进程组、Job、工作流实例 | 跨框架算不清账、限不了流、挂了没法接 |
| **Session** | 交互连续性与对话上下文载体 | 与 Run 交叉但不等价 | 长连接、会话记录 | 把残缺对话历史误当成唯一任务事实 |
| **Workspace** | 任务可读写的隔离文件与产物空间 | 随 Run 派生并回收 | 临时目录、卷、容器可写层 | 并发任务互相踩脏文件，改坏了回退不了 |
| **Skill** | 经过校验、可发布可回滚的标准化做法 | 独立版本化 | 脚本包、软件包 | 沉淀的能力被偷偷篡改也发现不了，改崩了没法回退 |
| **Tool 与 MCP 端点** | 可被发现、按策略授权调用的外部能力 | 独立注册与授权 | 系统调用、API 网关 | “模型看见工具”直接等价于“模型有权调用” |
| **Budget Lease（预算租约）** | 带额度上限、有效期和撤回钩子的复合授权 | 随 Run 派生并级联吊销 | 配额、cgroup 限额 | 预算花穿，或者主任务砍了子任务还在外面猛调接口 |
| **Policy** | 不容绕过的强制安全与成本红线 | 集中定义，分布判定 | ACL、seccomp、网络策略 | 安全规矩全写在 Prompt 里，一遇注入形同虚设 |
| **Evidence（证据）** | 计划中、已发出与已确认结果的不可篡改账本 | 长于 Run，供审计与恢复 | 应用日志、审计流水 | 没法证明新版本真的变好了，故障恢复还可能重复扣款 |

表 30-2　Agentic OS 的九类核心管理对象

这里面有三个对象和传统操作系统长得最不一样，必须单独划重点：

- **Run 绝对不是进程**：一个 Run 可以横跨好几台物理机上的不同进程，中间还可以休眠三天等审批。判断一个 Run 对不对，看的是**任务事实账本完不完整、一不一致**，而不是看某个容器 PID 还在不在。
- **Budget Lease（预算租约）是可控自治的开关**：过去第 09 章管配额、第 14 章管最小权限，两套系统经常打架。租约模型把“能动哪些资源、能调哪些动作、最多花多少钱、几分钟后自动过期、随子任务怎么派生、喊停时怎么一刀全废”拧成一张可撤销凭证。
- **Evidence（证据）必须拆清三态，否则恢复必闯祸**：每一条动作记录都要死死区分**计划中（Planned）、已发出（Dispatched）、已确认结果（Confirmed）**。举个最实在的例子：“Agent 改完本地配置并重启远程服务”——如果你直接把本地 Workspace 快照回滚，本地文件确实还原了，**但远程服务早就带着旧错配置重启过一次了**；如果那次重启请求“已发出但没收到回执”，你闭着眼睛重放一遍，就会把刚恢复好的服务再重启搞挂一次。所以 Evidence 根本不只是事后审计看的，它是故障恢复时查账补偿的核心输入。

### 30.3.2 三层架构与图 30-1 深度解读

拿着第 30.2.1 节的三条判据，可以把这九个对象落到图 30-1 的三层架构里。读这张图有一个极关键的视觉信号：**顶部灰色虚线框**是留在应用侧绝不下沉的业务领地，中间那条**红色虚线**就是全书守死的那条**任务语义边界**，下面实线大框才是真正独立于业务代码之外的 Agentic OS。

![image](../assets/imgs/chapter-30/image-001.png)

图 30-1　Agentic OS 的三层结构与责任边界

顺着图左侧的三条判据，三层分工各管一摊：

1. **Agent 运行服务层（对应判据一：复用性）**：只提供 Run 的创建、挂起、恢复与终止，Session 与 Workspace 的派生回收，Context 与 State 的隔离读写，Skill 与 MCP 的标准挂载，以及挂上 Budget Lease 租约——**接口语言是任务和状态，绝不掺和函数调用细节**。
   学术与工业界已经走出了清晰样本：AIOS 把模型调度、上下文、记忆、存储和访问控制抽成多个 Agent 共享的公共内核服务（位于宿主操作系统内核之上）；IBM 研究团队在《Towards an Agent Operating System》里同样主张由平台统一托住动态执行的生命周期、上下文和恢复规则。工业开源里，ANOLISA 把 Agent Memory（跨会话记忆）、SkillFS（只露出当前需要的技能视图，其余按需发现）、ws-ckpt（工作区断点回滚）以及 Token-less 做进了这一层。其中 Token-less 的摆位极有代表性：**它插在 Agent 和模型之间做工具 Schema 与大返回值的可逆压缩**（扔掉的数组项留好检索标记可随时取回），完全不用改各个 Agent 框架自己的代码——既满足全生态复用，又卡在调用必经之路上强制生效，证明连“省 Token”本身都可以下沉成系统能力，而不必靠在应用里苦哈哈调 Prompt。
2. **系统承载层（对应成本与密度上限）**：管的是“同样 SLA 下能并发扛多少个任务、一个任务单次空转花多少钱”，覆盖轻量沙箱模板共享与秒级回收（如 ANOLISA 的 Blaze）、基于 Linux PSI 和 cgroup v2 的混部反馈调优（如 ktuner）、模型前缀缓存（KV Cache）分域加速以及可信机密执行。这里有个绕不开的真实代价：**模板共享、挂起唤醒和激进回收自己也要吃开销**。大批闲置任务同时醒来会抢 CPU、过度回收会把下次冷启动拖成龟速、邻居任务一爆内存可能拉低整机尾延迟——所以绝不能只看“单机能塞进多少个容器”这种实验室数字，得拿真实混合负载下的完成时间和尾延迟一起压测。
3. **治理与证据层（对应判据二/三：强制性与可验证性）**：这是唯一能确保“哪怕被管的 Agent 代码抽风或者被注入，也掀翻不了桌子”的硬防线。它集中定身份和策略、把 **fail-closed（故障即拒绝）** 的拦截点焊死在请求必经之路上、旁路采集关联证据并支持幂等补偿。
   业界已有多种落地路径：NVIDIA OpenShell 把策略独立放到 Agent 之外，用沙箱、声明式策略、Landlock、seccomp 和网络代理卡住文件、进程和出站流量（目前文档标注 alpha，部分控制带兼容降级配置）；Windows 365 for Agents 直接把专用执行桌面绑进任务生命周期，任务一结束整套环境重置。对照回 ANOLISA，这层有两个机制非常值得抄作业：一个是 **AgentSight**，用 Linux eBPF 旁路抓取用户输入、模型调用、工具执行、Token 消耗和子 Agent 分支并自动串起来——完全不改 Agent 代码，实现了真独立于执行方的客观证据；另一个是 Agent Sec Core 的 **Skill Ledger** 状态机，只要已签名的 Skill 文件在本地发生了未经授权的改动，再次使用前立刻标成 `drifted`，重新扫描发现阻断风险直接记为 `deny` 拒绝放行——这才是“Skill 可校验”在代码里的真实长相。

### 30.3.3 哪些归宿主机/内核，哪些归平台控制面，哪些死守应用侧

把三层再往工程团队的职责表里落一次，并加上一条经济底线：**跨层拦截带来的性能与研发开销，不能大过它换来的安全性收益。**

- **适合沉进宿主机与内核机制的**：沙箱和工作区的高密快速启停、基于压力信号的资源混部调节、文件/进程/网络的强制内核级拦截、可信启动、以及像 eBPF 这样对业务零侵入的旁路观测。核心特征是“必须靠物理隔离卡在被管代码外面”。
- **适合留在平台控制面的**：Run/Session 统一语义、组织级评估基线与准入门禁、人工审批流、跨租户预算分摊、Skill 和 MCP 的中心化注册与版本灰发。核心特征是“得和企业组织架构、审批权限和跨集群治理对齐”。
- **必须死死留在应用侧 Harness 的**：终止条件、这一步到底喂哪些上下文、业务验收标准、以及具体业务规则。第 02 章说过编排层不能耦合 Runtime 内存；反过来也一样，**系统层一旦开始插手规定“任务具体该怎么干”，它就瞬间从操作系统退化成了一个又重又难用的框架。**

## 30.4 四个解耦面与解耦的真实代价

### 30.4.1 四个解耦面：哪里成熟了，哪里还在打架

Agentic OS 能不能站得住，要看应用和底座之间那四个接缝处的接口稳不稳——**真正稳定的接口，能让你在不重写业务逻辑的前提下换掉底层实现，还能用同一套回归评测证明换完效果没退化。**

| 解耦面 | 稳定接口管什么 | 已经基本定型的 | 还没收敛踩坑最多的 | 最典型的毁解耦操作 |
| --- | --- | --- | --- | --- |
| **1. Model ↔ Harness** | 请求/响应、工具调用与结构化输出格式 | Tool Calling 与 JSON 输出协议基本互通 | 长上下文里的指令遵循和多步稳定性没法写进协议 | 把专治某个旧模型毛病的诡异 Prompt 和死循环补丁写死进业务主流程 |
| **2. Harness ↔ Runtime** | Run、Session、Checkpoint、Workspace 状态契约 | “状态必须外置”已成行业共识 | 各框架对“一次运行”的边界和生命周期定义还各唱各的 | 编排逻辑直接读取某个 Runtime 的内存变量或线程模型 |
| **3. 能力 ↔ 协议** | 工具描述、发现、调用和错误返回格式 | MCP 已经基本接管工具发现与调用协议 | 操作有没有副作用、是否幂等、风险几级还缺机读字段 | 把“协议调通能发现工具”直接当成“有权执行”，省略权限设计 |
| **4. Runtime ↔ 承载环境** | 沙箱契约、文件网络边界、快照与恢复接口 | 多后端可插拔已有成熟实践（如 OpenSandbox 支持配 gVisor 或 Kata） | 内部快照和跨系统外部副作用的联动语义没人写死 | 天真地以为回滚了容器文件系统，发出去的数据库写和发出的消息也会跟着撤回 |

表 30-3　四个核心解耦面的现状与雷区

四个接缝里最容易让人大意的是第一、第三和第四个：
- **协议兼容 ≠ 能力等价**（第 02 章提过的致命坑）：把主模型降级成便宜模型，工具调用的 JSON Schema 百分之百合法，可多步执行中途偷偷忘了业务前置约束，最后安静地办了一件错事。所以换模型绝不能只测接口通不通，必须带着完整 Harness 跑回归集。
- **描述清楚 ≠ 授权正确**：Windows App Actions 让应用声明可复用动作及其入参出参，服务器端用 MCP 和结构化命令把日志查询、服务管理包得非常清晰——这确实能大幅减少模型猜错参数，但依然回答不了“这个用户今天有没有权重启这台机器”，权限还得客户端、服务端和宿主三道把关。

### 30.4.2 别光听“解耦”好听，这三笔账必须算清

解耦从不是免费的，它只是把代码里的耦合复杂度，搬到了**版本矩阵、隐式漂移和验证成本**上：

1. **版本组合矩阵爆炸**：模型版本、Harness 框架版本、MCP 协议实现、Runtime 与底层驱动各自独立升级，能跑稳的组合验证量呈指数级增长。传统基础设施早已交过学费：NVIDIA 必须围绕 DGX 硬件严格列出驱动、通信库和 OS 的配套白名单；Red Hat 把追求新硬件快速适配的专用组件做成“只保最新、不沿用标准发行版超长支持周期、不保证跨版向后兼容”的独立通道。做 Agent 平台也一样，**明确写出“哪几版模型配哪几版脚手架和协议经过压测可用、怎么平滑升级”，本身就是硬交付能力。**
2. **接口一行没改，行为悄悄漂移**：传统 API 只要签名和返回值类型不变，升级一般不出大事；可大模型或系统级内置模型一升级，输出风格和指令遵循尺度全可能变。Apple 在 Foundation Models 的更新说明里专门提醒开发者，系统更新带来模型变动后必须重新验证既有提示词——这说明**Agent 时代的兼容性，早已没法靠接口定义保证，只能靠评测集兜底。**
3. **验证成本成倍抬高**：要证明把框架 A 换成框架 B、把沙箱 X 换成沙箱 Y 之后“能力等价”，必须在完全一致的并发负载、权限设置和 SLA 目标下重跑同一套评估。缺了第 21、22 章的可复现评估，所谓“架构解耦”其实只是把炸雷从写代码阶段推迟到了线上生产。

因此判断一次解耦成不成立，只有一个硬标准：**能不能不改任务语义就把底座替换掉，并用同一套评估证明替换后的质量、成本和安全都在可接受区间内。**

## 30.5 怎么形成行业标准：先对齐六类接口，拒绝裸百分比

### 30.5.1 别闭门造标准，先补齐这六类接口公约

真正管用的标准从来不是在 PPT 里画出来的，而是从多家跑通的产品共性里榨出来的。当前最成熟、最该统一的是这六类接口：

1. **任务与运行对象模型**：统一 Run、Session、Checkpoint、Workspace 的状态机和生命周期边界，解决跨框架算账、限流、排障对不上账的问题。
2. **身份与委派链**：统一 Agent 身份表达、跨组织委派凭证的传递校验以及级联撤销语义。
3. **能力副作用与幂等声明（最缺、收益最直接）**：在现有工具 Schema 上补齐“是否有外部副作用、是否幂等、风险等级与前置条件”的机读字段——有了它，网关和运行时才能自动化重试补偿，审批策略也能直接按风险等级配置而不是人工维护一长串工具黑名单。
4. **可观测事件最小字段**：约定模型调用、工具调用、状态变更、审批四类事件的最小必填字段和因果关联 ID，让不同框架的 Trace 能拼进同一张大图。
5. **评估与门禁口径**：统一数据集格式、Evaluator 接口和质量门禁写法，让各家拿出的评测分数具备可比性。
6. **执行环境与快照契约**：说清工作区、网络出站、文件隔离怎么声明，更要白纸黑字标明“**打快照到底能回退哪些状态、绝对回退不了哪些外部系统**”。

### 30.5.2 标准怎么长出来：三条路径与“三段式数据披露”

参考操作系统生态的演进，形成标准靠三条路：**一是上游贡献**（像龙芯把矩阵乘、卷积、转置向量优化直接推进 ONNX Runtime 1.17.0 上游，省去各发行版各自打补丁），对应到 Agent 就是把统一 Run 和观测字段推进主流开源框架；**二是多方共建**（如清华、月之暗面、阿里云、华为存储联合推进 Mooncake，龙蜥社区用 SysOM 整合各家运维能力）；**三是同台可复现测评**。

这里特别要拎出 **ANOLISA 对 Token-less 省流效果的数据披露写法**，建议全行业直接抄成默认规范：它把效果拆成组件级基准（分别标出工具响应、工具 Schema 与全链路的压缩率及耗时开销）和单次真实编码任务实测（节省约 **31.7 万 Token**，压缩比例约 **40.5%**，明确标明**由 AgentSight 测得**），更关键的是紧跟着写死三条适用边界——**节省只覆盖喂进上下文的工具响应，不等于整场会话账单；效果随负载变化；估算方法另有文档可查。** 这种“**具体数字 + 明确适用范围 + 独立测量来源**”的三段式披露，才是严肃的工程指标；丢掉适用条件甩出一句“提效 50%”的裸百分比，没有任何横向参考价值。

### 30.5.3 从“调得通”到“敢换底座”的生态三层阶梯

判断一个方向标准化走到哪一步，对照这三层就行：
- **第一层：协议兼容**（大家按同一种格式互相发请求，比如 MCP 在工具接入上已经做到这一步）；
- **第二层：语义一致**（同样的错误码、重试策略和状态变更，换一套实现跑出来的外部后果一样——这一层因为缺副作用与幂等声明，目前普遍还没过关）；
- **第三层：证据可比**（不同厂商、不同框架吐出的运行账本和评估分能直接放一起比好坏，做到这一步，企业才算真正摆脱单厂商绑架）。

同时记住别搞“过早标准化”：在语义还没摸透的领域，先强制统一可观测字段让各家差异变得可度量，远比拍脑袋写死一份没人遵守的行为规范务实得多。

## 30.6 从“能跑起来”到“敢放权”：自治阶梯、硬隔离与补偿兜底

### 30.6.1 自治阶梯：放多大权，看“能不能撤、能不能查”

把第 04 章的完成验证和第 06 章的权限审批合并，就能得到表 30-4 这条 L1—L5 自治阶梯。它的用处不是催着你赶紧往 L5 冲，而是清清楚楚告诉你：**每往上放一档权，必须同步补齐哪两样硬配套。**

| 自治级别 | 系统干什么活 | 必须新增的边界卡点 | 必须新增的证据要求 |
| --- | --- | --- | --- |
| **L1 建议** | 生成命令或修改建议，由人亲自执行 | 无需真实执行权限 | 建议生成来源可追溯 |
| **L2 单步获准执行** | 每动一次外部状态，先弹给人批准 | 操作对象与资源一一对应授权 | 每次动作的入参、出参和审批人记录 |
| **L3 有界自主** | 在限定目录、预算和工具清单内连续自主跑 | Budget Lease 租约、目录白名单、读写分离 | 完整工具调用轨迹与真实预算消耗 |
| **L4 长任务自主** | 跨会话跑几小时到几天，随时可暂停恢复 | 可级联吊销的派生授权、可回退的工作区快照 | 账本严格区分“计划中 / 已发出 / 已确认结果” |
| **L5 组织级自治** | 跨系统、跨团队委派子 Agent 协同交付 | 第三方可验证的委派链凭证、跨域强制拦截点 | 跨组织可审计的清晰责任归属证据 |

表 30-4　Agent 自治阶梯与对等边界要求

表里藏着一条硬逻辑：**一个业务到底敢放多少自主权，上限从来不由模型有多聪明决定，而由“做错了能不能撤回”和“事后能不能拿出独立证据”决定。** 如果一件事既撤不回、事后又查不清到底发生过什么，那就算模型跑分 99.9%，把它放出去全自动执行在工程上也是不负责任的。

### 30.6.2 别把“看见了”吹成“管住了”：强制边界 vs 观测边界

纳管多个不同来源的 Agent 时，工程团队和厂商最容易玩文字游戏：把“我能监控到越界行为”，说成“我把权限管住了”。架构评审时务必把这两件事劈开：

- **强制边界**必须同时过三条死门槛：第一，**全路径兜底**（任务入口、凭证获取、网络与 DNS、进程间通信、子进程派生、原生工具、后台作业、交互控制台无一漏网）；第二，判定组件挂了或超时，默认采取 **fail-closed（失败即拒绝，宁可中断绝不放行）**；第三，**拿真实的负向绕过测试打过靶**，证明绕路尝试确实被拦死了。少任何一条，都只能老实叫作**观测边界**（出事能告警、事后能抓人，但当时拦不住）。
- 同样地，**“只读接入”不是你在设计文档里写上“只读”两个字就成立的**——只有跑完“写路径不可达”负向测试才配叫只读接入；没测过之前，严谨的说法永远是“暂未观察到写操作”。

接入外部不可改代码的第三方框架或 CLI 工具时，平台的管控真实成色只有四档：
1. **外部边界强制**：在被接入方完全碰不到的外围建好强制点（注意写清楚到底覆盖了哪几条已验证路径，且策略来源和证据采集来源必须独立互证）；
2. **包装器中介**：靠替换入口、设代理或挂 Hook 拦截，效果高度依赖被接入方是不是真的绕不开这层包装；
3. **仅观测**：只能旁路采集行为和告警，必须用负向测试确认它没偷偷留写通道；
4. **不支持**：既拦不住又看不明白，只能直接划进禁区，绝不能对外宣称“已纳管”。

用前面提到的 ANOLISA 当样本一照就明白为什么不能笼统喊“某产品已控住”：它的 Agent Sec Core 通过 Hook 接进 Qoder CLI、Qwen Code、Codex，在提示词、工具和输出层套策略，这属于**包装器中介**——规矩确实定在 Agent 外面，但到底绕不绕得开 Hook，得靠负向测试一条条验证；而它的 AgentSight 靠 eBPF 旁路取证，零侵入、证据极其扎实，但它本身不拦请求，属于**仅观测**。同一个系统里的两个组件落在完全不同的级别上，因此回答“管没管住”，永远只能拆成四个维度逐项交底：**是强制还是观测、覆盖什么操作语义、封死了哪些执行路径、证据靠不靠谱。**

### 30.6.3 不可逆操作、补偿与“过期记忆毒化”

最后一块硬骨头是失败收拾残局。一定要打破一个幻想：**Workspace 快照只救得了本地文件，救不了已经发出去的跨系统副作用。** 数据库已经落盘的扣款、已经发进群里的通知、已经创建的客服工单、已经重启的远程实例，绝不会因为你把沙箱文件系统回滚了就跟着撤销。

所以长任务恢复必须三样齐抓：
1. **带三态区分的操作记录 + 幂等键 + 显式补偿**：一旦发现某个动作“已发出但没等到结果”，先去目标系统查现状，查实没生效再决定重试，查实生效了就决定继续还是跑反向补偿——绝不盲目重放。
2. **提防“脏记忆”在恢复时指错路**：软件刚升过级、配置刚迁过库，以前 Memory 或共享知识库里攒下的“正确经验”可能已经彻底作废。任务恢复重新上路时，涉及环境现状的一定重新实时查一遍，别直接轻信老记忆；同时印证第 05 章的要求，记忆底座必须原生支持精准更新、删除和访问控制。
3. **把网页、日志和工具返回永远当“不可信数据”**：哪怕诊断日志或网页正文里藏着诱导模型“顺手执行某条高危命令”的间接注入文本，执行端的工具网关依然只认调用方的真实身份和最小权限硬核验，绝不因为模型读了段外部文本就给它放大权限。说到底，Agent 并没有发明全新的漏洞，它只是把老问题——**权限开太大、配置漏缝、危险接口缺幂等**——用自动化和百倍并发放大了无数倍。

## 30.7 留给未来一两年的七个开放问题

前面讲的都是已经看清方向、甚至已有开源原型的部分。下面这七个硬问题，全行业都还没有标准答案。我们为每个问题写下了**未来一两年内的验收坐标**，方便你在跟进技术演进时自己打分校准：

1. **Run 对象到底该归哪一层管？** 是留在平台控制面，沉进宿主机守护进程，还是融进执行域基础机制？**验收标志**：出现被主流多框架共同认账的 Run 状态机语义，且即便框架代码不配合，宿主机照样能观测和叫停。
2. **Agent 身份和委派链怎么跨公司、跨系统传递？** **验收标志**：出现能被独立第三方验真的委派凭证标准格式，以及全链路的瞬间吊销机制。
3. **副作用和幂等性能否写成工具协议的机读字段？** **验收标志**：主流 MCP/工具协议正式把“有无副作用、是否幂等、风险等级”列为标准元数据，且网关和 Runtime 真能按这些字段自动切换重试或人工审批分支。
4. **Agent 负载下沙箱的成本与隔离最优点在哪？** 进程隔离、用户态应用内核（如截获系统调用的 gVisor）、TEE 内库操作系统（如 Occlum）、缩小可信计算基的 Rust framekernel（如 Asterinas）各有利弊。**验收标志**：行业内出现针对 Agent 典型工作负载（高并发等待 + 突发工具执行）的公开可复现基准测评，同时晒出批量创建吞吐、空载内存占用、挂起恢复时延和隔离防逃逸强度。
5. **KV Cache、Memory、Skill 等共享状态怎么既复用省钱又默认防串租户？** 如今推理引擎开始支持通过显式分域参数把前缀缓存按可信入口绑定到指定租户域。**验收标志**：租户硬分域从“可选项”变成“出厂默认不可关闭选项”，且配套跨租户越权探测测试。
6. **评估怎么从离线题库走向系统级综合基准？** **验收标志**：出现能在相同并发负载、同样权限边界和 SLA 下，同时把**任务质量、单位成本和防绕过安全**放一张表里比高低的公开方法。
7. **自进化的“免审边界”画在哪？** **验收标志**：形成被广泛接受的变更分级规范——哪类低风险 Prompt/Skill 微调只需离线回归过关即可自动灰度上线且随时回滚，哪类改动必须锁死人工签字。

在这七个问题之上，还有一个更底层的方向正在冒头：**干脆围绕 AI 负载重写执行基础机制。** 研究侧已经拿出具体样机：LithOS 针对 ML/AI 负载重做 GPU 细粒度调度与算子核函数拆分；Agent libOS 把授权上限、预算租约和外部调用的“准备 / 派发 / 结算”三段状态直接写进底层运行时原语，从根上杜绝故障恢复时的盲目重放。这些探索的共同思路是把表 30-2 的核心对象直接立为基础原语，而不是在老概念上面反复打补丁套壳。不过它们目前全都还停留在特定实验场景，距离通用操作系统还有很长的路——本书的判断是，这类底层重构大概率会**先在代码修改测试、数据分析、受限工具沙箱这类边界极清的专用执行域里落地验证**，然后再慢慢向外铺开。

## 30.8 本章小结

把全书拉回第 01 章的起点：**Model 是认知大脑，但可靠性绝不能押注在模型自觉上。** 前 29 章顺着这句话，把“模型之外还得配齐什么”拆成了架构设计、构建、运行、治理和调优五个阶段的实操清单。

第 30 章往前推了一步：当同一家企业同时跑起多个 Agent、混用多套框架、服务多个租户时，这些共性能力一定会从“每个应用自己写一遍”坍缩成“共享的系统底座”。这个底座正在两头夹击中成型——上层的平台能力往下沉，下层的系统与内核能力往上迎，双方正汇合在**任务、环境、授权与证据**这九个核心对象、三层职责边界，以及**复用性、强制性、可验证性**三条下沉铁律上。

所以未来一两年真正决定胜负的，不再是谁又发明了几个唬人的架构新词，而是谁能把已经看清的工程边界变成**跑得稳、卡得住、验得出**的硬机制。评判任何一套 Agent 底座或 Agentic OS 方案到底成不成立，不用看宣传册有多厚，拿最后这三个问题一扎就透：

1. **当被管住的 Agent 不配合、甚至被诱导绕路时，你的限制还管不管用？**
2. **任务成功也好、越界出事也罢，你能不能拿出独立于执行方自己的硬证据？**
3. **模型和框架每三个月换一轮血，你的这套架构在持续版本演进下还维不维护得住？**

Agentic OS 最终能不能成为像 Linux 一样稳固的行业基石，就看这三条在多少条真实生产路径上拿到了肯定的答案。
