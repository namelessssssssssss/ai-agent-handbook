# 第 11 章　Multi-Agent 协作与编排

单个 Agent 越做越顺手之后，很多团队会下意识觉得「既然一个这么强，那我拉三五个 Agent 组个团队，岂不是更快更强？」

现实往往正好相反——没有清晰编排就直接把多个 Agent 凑到一起，线上翻车比单兵跑得还要惨烈：

- **「隐形 Token 税」爆表**：为了同步进度，每个子 Agent 把几万字主对话历史全读一遍，干一点活烧掉五倍 Token；
- **文件交接变成「盲人摸象」**：开发者本地电脑上的 Coding Agent 跑完测试回了一句「报告已生成在 `/tmp/report.md`」，云端的业务 Agent 根本摸不到那个本地路径，整个流水线直接卡死；
- **两个 Agent 来回踢皮球到额度烧光**：测试 Agent 说「不通过」打回给编码 Agent，编码改完一版没打版本号，测试拿着旧报告又打回去，双方在没有全局止损条件的情况下互相返工三十轮；
- **权限越传越大变成漏洞**：用户只授权业务 Agent 查一下依赖漏洞，结果业务 Agent 转手调起本地终端助手，顺带把用户本机上所有的个人私钥和账号权限全继承过来了。

多 Agent 编排的核心，不是追求角色热闹，而是回答：**到底什么时候才值得拆队？怎么让不同框架甚至跑在个人电脑上的 Agent 安全干同一件事？交接什么、怎么停、出了事怎么查账？**

## 11.1 先问一句：到底需不需要上 Multi-Agent

如果一个任务目标单一、上下文高度耦合、步骤必须严格一步步串行推进，**老老实实用单 Agent 最稳、最快、最省钱**。

只有当业务同时出现三个需求时，拆成团队才真正划算：需要明显不同的专业工具与能力（比如查业务库 vs 改代码跑单测 vs 安全扫描）、部分子任务天然能并行推进、或者必须把高危操作和普通查询按权限和环境硬隔开。**只有分工、并行和治理带来的收益，明显超过任务拆分、信息传递和状态对齐的协调成本，团队才成立。**

![image](../assets/imgs/chapter-11/image-001.png)

图 11-1　Multi-Agent 协作与编排总体架构

看懂图 11-1 的分层，就能避免把编排层做成另一个臃肿大管家：
- **用户与业务验收层**：管提目标、定约束，以及最后下载成果、确认接受和归档；
- **团队协作与编排层**：管稳定 Team 关系、拆 Task 和依赖计划、路由分派、版本化聚合成果和全局止损条件；
- **Agent 团队成员**：每个成员依然保留自己的独立 Harness 和上下文空间，在各自能力边界里自主推进；
- **运行与连接基础 + 全程治理**：Runtime、Sandbox、Gateway、A2A、MCP 提供连接和恢复底座，身份、委托、权限、预算和审计贯穿全链路。

**最关键的克制**：编排层负责对齐目标、依赖和验收口径，**千万别让所有微小的中间步骤都先汇报给一个主管 Agent 审批再往下走**——否则很快又退化回慢吞吞的单点决策瓶颈，把多 Agent 的并行优势全抵消掉。

## 11.2 异构接入：框架、Coding Agent 与个人电脑助手怎么进同一个群

拿一个真实场景串通全章：**业务 Agent** 线上排查出某服务第三方依赖有高危漏洞，需要**开发者电脑上的 Coding Agent** 改代码升级并跑测试，再由**测试 Agent** 独立验证，**Leader** 统筹汇总，最后交给人拍板收货。

这些人手用的往往不是同一套技术栈——有的自己用框架写代码、有的是买来的产品化 Coding Agent、有的是外部托管 API、有的就跑在员工笔记本上。强迫所有人重写成同一种框架根本不现实，正确的做法是**保留每个 Agent 原生的 Harness 执行循环，只在外面包一层协作适配**：

| 你手里握着什么控制权 | 怎么接进团队 | 适配层重点补齐什么 |
| --- | --- | --- |
| 能改 Agent 应用代码 | 在原有框架里嵌入协作 SDK 或任务接口 | 接任务、报进度、提阻断、交成果（可用确定性代码写死，不一定要让模型调工具） |
| 能装插件或控制进程启动 | 上插件 + 启动适配程序 | 装配协作 Skill/工具、拉起进程、把协作会话映射到内部 Session |
| 只能调远端服务 API | 在外部包一层适配服务 | 记住「团队任务 ID ↔ 远端任务 ID」映射，定期查状态取结果（只支持吐终稿就别硬报实时进度） |

### 11.2.1 接入 Coding Agent 和个人工作区的五个隐蔽陷阱

很多团队接通通信就以为完事了，一上真实仓库立刻踩进五个坑：

1. **挂断输出流 ≠ 取消了后台命令**：适配程序接到「取消任务」指令时，必须把取消传进 Coding Agent 正在跑的任务并**核实后台进程真杀干净了**，别只把 SSE 输出连接一关了事。
2. **内部子代理不自动升格成团队成员**：Coding Agent 自己内部拉起来看文件的子 Agent，依然归它自己的 Harness 管，只有需要跨团队独立派活和算账时才给它建正式成员身份。
3. **设了个 `--cwd` 目录参数 ≠ 安全沙箱**：只传一个工作目录参数挡不住程序去读硬盘上其他文件；需要限制读写和命令，必须靠第 07 章讲的权限控制或沙箱隔离。同样，**团队任务接入员工本地工作区时，绝不能自动继承他个人目录里的全部 Skill 和全部账号权限**，必须由用户显式勾选授权。
4. **本地绝对路径出了这台电脑就是废话**：本地跑完生成的补丁或报表，绝对不能只回一条「保存在 `/Users/dev/out.md`」——必须通过约定的产物通道上传并附带接收方能访问的稳定引用；同时只上传任务明确要的产物，别把人家整块工作目录全量同步出去。
5. **在本地跑 ≠ 数据不出本地**：哪怕进程跑在员工本机，只要它调了云端大模型或外部工具，数据一样出域了，接入前必须核对数据合规口径；还要应对笔记本合盖休眠、断网和本地登录态过期的状态反馈。

接入完怎么验真？别一上来就跑巨无霸需求，先拿一个极小的真实工单做五项冒烟验收：

| 验收项目 | 亲眼看到什么才算过关 |
| --- | --- |
| 1. 任务送达 | 指定成员收到了对的输入，工作目录和运行身份都没跑偏 |
| 2. 连续追问不串台 | 下一条补充指令准确落进同一条会话，没混进别的并行任务里 |
| 3. 状态不撒谎 | 能清楚报出运行中、等确认、被卡住（含缺什么依赖）、已结束，别统一吐一句「出错了」 |
| 4. 成果拿得到 | 远端接收方真能下载并打开补丁和测试报告，且能核对属于本次任务 |
| 5. 控制命令真管用 | 凡是声明支持取消、重试和断点恢复的，逐个发指令实测一遍，不听接口口头承诺 |

## 11.3 团队组织拓扑：选结构看耦合，不看人数

![image](../assets/imgs/chapter-11/image-002.png)

图 11-2　Agent 团队的三种组织拓扑

先理清两个常混用的概念：**Team** 是能连续接活的稳定组织，不会跑完一单就解散；**专业能力**（擅长写代码还是跑测试）和**组织角色**（谁统筹、谁干活、谁复核）也不是绑死的——最能写代码的 Agent 未必该当 Leader，同一个 Agent 在 A 组当执行者、在 B 组完全可以当验收者。团队成员名单、任务可见权、实际干活权、验收拍板权必须分开记，别觉得「拉进群里 = 每件事都得参加 = 有权验收」。人类负责人也不只是卡壳时的临时救火队员，而是需求澄清、关键拍板和最终收货的正牌成员。

图 11-2 对比了三种常见组织方式——它们**不是从低级到高级的升级路径**，只看业务怎么干最顺手：

| 拓扑结构 | 怎么配合 | 最适合什么活 | 最容易翻车在哪 |
| --- | --- | --- | --- |
| 主管—执行（Leader-Workers） | Leader 定目标、拆依赖、汇结果，Workers 在边界内自主干活 | 目标清楚、需要统一收口交付的任务（如标准研发改版） | Leader 管太细成了单点瓶颈，甚至抢在执行者前头把活自己干完或重复验两遍 |
| 对等协作（Peer-to-Peer） | 成员按职责直接碰头协商、相互复核，不事事过主管 | 强探索型任务，几个专家地位平等需要快速碰撞 | **没提前定好裁判规则**：两人吵起来谁拍板、谁最后整合交付没人扛责 |
| 分层编排（Hierarchical） | 根 Leader 对接几个小组 Leader，小组内部自己消化细节 | 盘子大、而且每个专业小组真能独立扛下一块完整交付 | 需求一层层传话变味失真、汇报链路变长、跨层沟通磨洋工 |

记住一条：**组织拓扑管的是「谁对谁的交付负责」，不限制成员之间直接对碰技术细节**——主管结构里编码 Agent 和测试 Agent 照样可以直接对话查报错，只要改任务归属和验收口径时走正经任务状态流转就行。

## 11.4 协作机制：任务拆解、版本返工与团队止损线

![image](../assets/imgs/chapter-11/image-003.png)

图 11-3　依赖修复任务的协作与验收流程

顺着图 11-3 把「升级服务依赖并验收上线」跑一遍，就能看清多 Agent 干活怎样才不乱套：

### 11.4.1 Task、Task Run 与 Session 三分法

- **Task（任务契约）**：记清楚目标、输入、交付物、验收条件和负责人；只有存在**独立交付物、不同负责人或明确依赖**时才拆成子任务，同一个成员连续敲三步命令别闲着没事拆三个子任务。
- **Task Run（一次真实执行）**：因为失败重试、断点恢复或换人重派，同一个 Task 可以跑出好几个 Task Run，互不覆盖。
- **Session（代理会话上下文）**：Agent 自己的对话现场，按需跟 Task Run 关联。

**排计划有一条常识常被忽略**：子任务**创建出来的顺序，不等于能开始执行的顺序**！在依赖修复例子里，Coding Agent 正在写补丁的同时，测试 Agent 完全可以**并行先去搭好测试环境和用例**，等 Coding Agent 正式提交了 **Artifact V1** 再开跑完整验证——既省了干等时间，又绝不会拿半成品代码跑出假测试报告。中途万一需求升级版本变了（比如从 V1 升到 V2），必须标清哪些老分析还能复用、旧补丁对应哪个版本、哪块需要返工，千万别一把抹掉重头来。

### 11.4.2 返工闭环与必须提前设好的「团队止损条件」

Coding Agent 交出补丁 **Artifact V1**，测试 Agent 一跑挂了 2 条用例——怎么闭环？把失败用例、对应的 V1 版本引用和修订要求挂回给实现子任务；Coding Agent 改出 **Artifact V2** 交上来后，**旧 V1 记录作为历史事实保留，但测试只盯着当前有效版本 V2 验**，这样重试、返工、改需求三笔账永远不会混。

更重要的是，**开跑根 Task 之前，必须在团队级别写死「停止条件（止损线）」**，绝不能只在单个 Agent 里写个「最多重试 3 次」就完事：
- 总时间与总费用预算天花板；
- 最大委派深度、最多能派生多少子任务；
- 单项重试次数与**最大返工轮次**；
- 连续几轮没有任何有效新产物或状态推进时的强制刹车。

一旦撞线，编排层立刻暂停派生和自动返工，保住已经做完的成品、当前阻塞点和剩余预算，把根 Task 标成阻塞或失败，交给人决定终止、加钱还是改范围。

### 11.4.3 四种「完成」别混淆，归档前都不算彻底结案

看图 11-3 最右列，多 Agent 协作把「做完了」切成了四个递进状态，少一步都不算完：
1. **执行者交稿**：产生了候选成果（只是原始材料）；
2. **团队内部接受**：Leader 或审核者核对过版本一致（代码补丁 + 修改说明 + 测试报告都对得上 V2）、证据齐备，允许往下游流转；
3. **根 Task「已完成」**：所有成果凑齐、满足交付条件——注意，**这依然不是终点！**
4. **用户下载验收并归档（真正终态）**：业务发起人或指定人工验收者真正拿到手打开验证通过、确认接受并归档。没过验收的话，**直接沿用原 Task 和版本关系继续修**，别再另起炉灶新建任务搞丢前因后果。

## 11.5 共享信息：要「按需编译视图」，不要「全员共用一个大脑」

把所有成员的聊天记录全塞进一个无限膨胀的共享群里，效果必定越来越差——编码 Agent 根本不需要看安全 Agent 之前查过的两百条无关日志，看多了反而注意力分散、花光上下文额度。

正确的共享设计是：**共享统一的事实来源，各自渲染最小充分的局部视图**：

- **交接（Handoff）只传四样干货**：① 当前目标与交付标准；② 已经核实过的事实与进度；③ 还没解决的卡点、依赖和约束；④ 可直接读取的 Task 与 Artifact 稳定引用。**别把冗长的试错检索过程和没验证的猜测原封不动倒给下一个人**。
- **团队共享记忆必须「验明正身」再入库**：探索期间模型猜出来的假设千万别直接写进共享长期记忆，否则下周另一个 Agent 会把错误猜测当铁律执行。只有经过测试结果、权威数据或人工确认的方法与事实，带齐来源和有效期后才能沉淀下来。
- **消息通知只管喊人，事实还得回账本和产物库读**：收到一条「报告写好了」的消息时，下游应该拿消息里的引用去读真正的 Artifact 和 Task State，别光听二道贩子在消息摘要里转述。

最后拿一张表把协作里最容易叫混的六个词彻底钉死：

| 对象 | 回答什么问题 | 活多久 | 典型装什么 |
| --- | --- | --- | --- |
| Context | 这个 Agent **此时此刻**需要看什么 | 当前这一步或当前这一轮 | 裁剪拼装出来的目标、约束、依赖结果、交接摘要 |
| Memory | 团队**过去攒下**什么有效经验 | 跨任务、跨会话 | 经过核验的领域事实、有效方法、决策约定 |
| Task State | 这项活**眼下推到哪**了 | 跟随整个 Task 持续 | 负责人、依赖关系、进度、版本、验收状态 |
| Artifact | 团队**真做出来**了什么东西 | 按业务留存政策长期保留 | 不可变报告、代码补丁、数据集、测试结果 |
| Workspace | 干活时**在哪块目录/资源**上改 | 按任务或项目挂载延续 | 源码目录、分支、快照，以及映射进去的工具凭证 |
| Environment | 这次跑在**什么运行条件**里 | 随具体运行实例和部署变动 | 计算配额、网络出口、隔离沙箱、临时凭证映射 |

## 11.6 团队通信与路由：协议接通 ≠ 协作靠谱

协议分工很清楚：**MCP** 管调工具和资源，**A2A** 管异构 Agent 之间派任务交作业，**内部消息队列/事件总线**管平台状态广播和解耦（协议深层机制详见第 12 章）。

但接入 **A2A** 时有两个容易滑坡的点：第一，**Agent Card 就像一张个人名片**，它写了「我能干代码审计」，不代表你就可以无条件相信它、把敏感库喂给它——必须经过签名验证、来源校验和团队授权策略；第二，**A2A 协议里的 Task、Message、Artifact 是互操作信封**，适配层必须把它们精确映射到你业务系统自己的 Task、Artifact 和验收体系，不能因为名字一样就混用生命周期；A2A 的 Streaming、轮询和 Push Notification 可以按网络条件混用，别以为全都能做到「零连接开销」。

至于团队大了之后不知道「该把活派给谁」，别全靠大模型凭感觉猜，用**混合路由**最稳：**模型先根据语义推荐几个候选人 → 确定性规则卡死团队边界、权限范围、实时负载和成本预算，拍板最终派单并留痕**。

## 11.7 团队治理：入站出站权限分开、用 Span Links 串起长任务 Trace

### 11.7.1 身份六件套：凭证和委托本身不是「身份」

查出越权事故后，最惨的是只看到「某容器调了某接口」，完全查不出背后是谁发起的。身份治理必须把六层对象拆开：

| 对象 | 管什么生命周期 | 核心硬规矩 |
| --- | --- | --- |
| 人员主体 | 随员工入转调离 | 对接公司 SSO，人员离职/停用权限立刻失效 |
| 服务主体 | 随业务应用或定时任务 | 独立于个人账号，支持密钥轮换和最小权限 |
| Agent / 工作负载主体 | 随 Agent 发布和下线 | 每个数字员工有唯一固定身份，不跟临时容器或底层模型混绑 |
| 执行主体 | 随单次运行实例生灭 | 运行时真正干活的实例，必须关联 Agent 版本、Task Run 和环境 |
| 临时凭证 | 按次/按资源短时签发 | 锁死资源、动作和有效时段，**严禁落盘长期密钥**（凭证只是证明，不是身份） |
| 委托授权 | 随 Session 或 Task Run 生效与过期 | 明文记清谁授权给谁、能干啥、有效期到何时、审批依据（委托也不是身份） |

### 11.7.2 权限铁律：入站鉴权与出站权限彻底分离

记住下面这两句能保命的架构红线：

1. **权限只做交集、绝不做并集**：每次真正执行动作前，有效权限 = `人员权限 ∩ 团队边界 ∩ Agent 策略 ∩ 资源策略 ∩ 委托范围`，任何一条显式拒绝一票否决。**Agent 之间互相交接活时权限只能缩不能扩**，高风险写操作与紧急授权必须有短时效、人工审批和事后复核；每次 Task Run 固化当时的策略版本，拒绝时必须吐清楚「缺哪个角色/哪个委托过期/超出哪个边界」，别只丢一句冷冰冰的「无权限」。
2. **入站归入站、出站归出站**：用户能调起 Agent A，**绝不代表 Agent A 就能拿着用户的全量权限去外部系统大杀四方**！入站权限管「谁能叫我干活」，出站权限管「我干活时拿着临时委托凭证能碰哪些外网、库和工具」。每当调用人、任务目标或委托范围变了，出站权限必须重算重审，任何环节校验失败直接拒绝，**绝不允许降级成「平台默认共享超级账号」硬跑**！

### 11.7.3 全链路可观测：用 Span Links 串起长任务，别硬塞一棵 Trace 树

一个多 Agent 长任务今天跑一小时、等审批睡两天、后天唤醒接着分叉并行，**千万别强迫整个生命周期硬塞进同一条调用链 Trace 里**！

工程上正确的做法是：**用根 Task 编号、Task Run 编号、会话编号串起跨恢复业务账本，在具体调用段用 W3C Trace Context 传播上下文；跨休眠恢复或并行汇合无法拼成简单父子关系时，用 OpenTelemetry 的 Span Links 关联因果**（选用 GenAI 语义约定时锁死版本做内部字段映射）。指标只统计低基数聚合趋势（成功率、排队耗时、Token 成本、策略拒绝率），日志做摘要脱敏不落原始密钥与全量敏感 Prompt，评估打分和客观事实分表存储——这样观测系统既能精准揪出「卡在哪个交接环节、谁在死循环返工」，又不会自己变成新的数据泄密源。

## 11.8 本章小结

把多 Agent 带进生产，考验的不是写多复杂的角色 Prompt，而是团队工程秩序：

1. **能单兵绝不硬拆队**：只有专业分工、并行提速和权限隔离的净收益盖过协调成本时，才组 Multi-Agent；接异构成员时保留它自己的 Harness 循环，用适配层补协作和五步冒烟测试。
2. **用 Task + Artifact 锁定事实，用止损线防止失控**：区分 Task、Task Run 与 Session，返工只认新版本 Artifact；开跑前必设团队级预算、深度、返工和无进展止损条件；人没下载验收归档前，任务就不算终结。
3. **视图做减法，权限做交集**：交接只给四项干货不倒垃圾历史；入站不推导出站，跨 Agent 交接权限只减不增；长任务跨段轨迹用 Span Links 串联，让每一分成本和每一次返工都有账可查。
