# 第 10 章　Agent 异步任务与自动化流程

写一个本地问答 Demo，用户发一句、Agent 调一次模型吐回复，一条 HTTP 请求就能从头走到尾。可一旦把 Agent 放进企业真实业务——比如跨系统拉数据出分析周报、自动分诊审批工单、每天凌晨跑安全巡检——同步请求模型立刻就会撞墙：

- **网关超时了，任务其实还在半路**：模型和多步工具还没跑完，网关 60 秒断了连接，调用方以为失败又重发一遍，后台同时跑起两份相同任务；
- **干等外部条件烧空算力**：发出去一个审批单或等待第三方回调，Agent 进程干占着容器和内存傻等几小时甚至好几天；
- **进程退出了不等于事情办成了**：后台脚本退出码返回 0、甚至运维在面板上点了「强制标成功」，结果生成的报告里引用的全是错数，业务方根本不能收货。

所以生产级异步系统要解决的不只是「丢进后台队列跑」，而是把 **谁定义了任务（Task）、谁负责调度和重试（Runtime/调度器）、谁判定事情真成了（Outcome）** 拆得清清楚楚。

## 10.1 先定边界：进程跑完 ≠ 业务成功

### 10.1.1 六个核心对象的权威归属

在异步和跨天长任务里，**Task（业务任务）** 才是最小持续单元，它可以跨越好几次挂起、人工审批和实例重启；**Session（会话）** 只是某一段交互或执行视图——跨 Session 续跑一个 Task 时，必须由 Runtime 显式加载经授权的 Task State，**绝不能默认不同 Session 天然共享上下文**，更不能拿 Session 边界当隔离边界（真正隔离靠租户、运行身份、凭证和沙箱环境）。

先把这六个经常搅在一起的对象分清归属：

| 对象 | 谁拥有权威 | 能活多久 | 里面装什么 |
| --- | --- | --- | --- |
| Task | 业务应用 / 任务模型 | 跨 Session、跨挂起、跨恢复 | 任务编号、业务参数、成功标准、当前状态 |
| 业务 State | 业务应用 | 与整个 Task 同寿 | 业务推进字段、累计结果、外部副作用记录 |
| Session Context | Harness / Runtime | 随某一段交互会话持续 | 对话历史、当前控制循环上下文 |
| Checkpoint | 工作流引擎 / Runtime | 按恢复契约持久化保存 | 节点输入输出、中间计算结果、版本号 |
| Runtime State | Runtime | 单次执行租约期内有效 | 心跳、租约、当前干活的 Worker 标识、步骤 |
| 外部副作用 | 被调用的外部业务系统 | 与外部系统状态同寿 | 已写入的数据库行、已发出的消息、已扣的款 |

### 10.1.2 五层完成语义：为什么「强制成功」不能直接拍板业务结案

线上排障时最容易吵架的一句话是：「系统明明显示 succeeded 了，怎么业务方说没拿到结果？」把下面五层拆开，责任立刻一目了然：

1. **执行状态（Execution Status）**：Runtime 告诉你的物理运行信号（比如跑完了还是崩了），只回答「这次执行跑没跑完」。
2. **节点运维状态（Operational Status）**：Worker 在不在线、租约到没到期、依赖服务降没降级，用来帮调度器避坑。
3. **候选证据（Candidate Evidence）**：跑过程中留下的原始日志、Trace、快照、Artifact 和模型原始响应，还没经过核验。
4. **Evidence（有效证据）**：对照业务成功标准核对过来源和完整性、确实能支撑验收的材料（例如报告里每个关键数字都能追溯到授权数据源）。
5. **业务 Outcome（最终结论）**：只有**业务应用或获授权的 Verifier** 才能拿着成功标准 + Evidence 最终拍板。LLM-as-a-Judge 只是评估打分手段，除非获明文授权，否则没有终局拍板权；运维在控制台点的「强制标记成功（`mark_succeeded`）」也**只能改变调度执行状态并写审计日志（谁、何时、为什么改），绝不能越权直接宣判业务成功**。

### 10.1.3 Checkpoint 管重算，不管外部副作用幂等

很多研发以为「每一步都存了 Checkpoint，崩溃重跑就安全了」，这是个致命误解。

Checkpoint 保存的是输入输出和中间计算，作用是**跳过已经算完的步骤别重算**。但如果某一步先向外部数据库插了一条记录或发出一封邮件，还没来得及写 Checkpoint 进程就崩了，新实例恢复后照样会把这一步再跑一遍——**外部副作用照样重复执行**！

调度器只负责尽量少重复投递，**业务副作用到底能不能安全重跑，必须结合外部系统能力自己兜底**：按场景选用幂等键、去重账本、事务性 Outbox/Inbox、租约围栏、结果查询对账或补偿（不是所有场景把全套全堆上去，看后端支持什么）。Watch、回调、轮询都只是「可能变了的提示信号」，信号丢了老老实实回去查权威状态做对账。

## 10.2 异步任务架构：排队、防背压雪崩与真假状态同步

把耗时操作从 HTTP 请求里剥离出来很简单：客户端提交任务、拿回一个 Task ID，后台队列和调度器接手执行，跑完后靠 Webhook、推送或查询接口交卷（当然，异步化不扩大模型上下文窗口，上下文压缩裁剪依然归 Harness 管）。

![image](../assets/imgs/chapter-10/image-001.png)

图 10-1　任务调度、执行与权威状态的协同

一个能抗住生产流量的异步任务底座（图 10-1），核心由**任务队列 + 调度器 + 任务状态机**咬合运转。提交 Task 时，除了名字、指令、优先级（同级先进先出）、目标 Agent 池、关联 Session、成功标准、超时和重试策略外，定时与离线任务还要带上计划调度时间、数据业务时间和实际开始时间。

### 10.2.1 队列、调度器与真正的「背压」

- **任务队列（缓冲与积压降级）**：上游突然涌进十倍流量或下游 Worker 大面积挂掉时，队列深度是最直观的报警灯。降级手段包括拒绝新任务并吐明确错误、给低优任务限流、告警触发扩容。
- **调度器（选 Worker 与背压）**：选 Worker 可以轮询、按可用槽位、按算力加权，或者配合恢复契约做亲和路由。真正容易搞错的是**背压（Backpressure）**——很多人以为只要维护一张「空闲/繁忙 Worker 表」就叫背压，其实那只适用于单 Worker 同时只能干一件事的玩具场景。生产级背压靠组合拳：**单 Worker 并发配额 + 队列高水位暂停拉取 + 按完成速率自适应调节拉取批量 + 租约超时回收 + 心跳动态报槽位**，核心是让拉活速度永远别超过实际消化速度。

### 10.2.2 任务执行状态机与图 10-2 的细节

| 执行状态 | 当前在干嘛 | 允许流转到哪些状态 |
| --- | --- | --- |
| `waiting` | 任务已初始化，在等前置依赖或调度时间到达 | `queued`、`hold`、`skipped`、`mark_succeeded` |
| `queued` | 依赖已满足，在队列里排队等算力 | `running`、`killed`、`skipped`、`mark_succeeded` |
| `running` | 已经派给 Worker 正在执行 | `succeeded`、`failed`、`killed` |
| `hold` | 人工审批、外部输入或条件挂起中 | `waiting`、`skipped`、`mark_succeeded` |
| `succeeded` | 这次执行顺利跑完 | `queued`（人工触发重跑） |
| `failed` | 执行失败 | `queued`（重跑）、`mark_succeeded` |
| `killed` | 被人手动掐掉 | `queued`（重跑）、`mark_succeeded` |
| `skipped` | 被人为跳过 | `waiting`（取消跳过）、`mark_succeeded` |
| `mark_succeeded` | 运维人工强制标记调度状态成功 | 终态（仅改变调度状态，不代表业务 Outcome） |

![image.png](../assets/imgs/chapter-10/image-002.png)

图 10-2　任务执行状态转换图（图中标注为对应状态标签，如 `Held` 对应 `hold`、`Mark_Success` 对应 `mark_succeeded`）

权威状态一定要落在 Postgres/MySQL 这类持久化数据库里，内存只当读取加速缓存，别把内存或本地文件当成唯一真相。

### 10.2.3 状态同步的三个常见翻车点

调度器把活派给 Worker 后，怎么知道它什么时候跑完？三种信号各有暗坑：

1. **调度器主动轮询**：控制权集中，但太密压垮服务、太疏延迟高。**最大误区**：某一次查状态接口超时失败，就直接判任务挂了——其实 Worker 可能只是在 GC 卡顿或网络抖动！判定失联应该靠**周期性续租**，租约失效后把任务转进 `unknown`（如图 10-1 下方提示），先核对现场再重派。
2. **Worker 主动回调**：实时性最好，但 Worker 瞬间崩溃可能根本发不出最后一条回调，所以必须配超时兜底；回调包必须带**任务编号、事件递增序号/版本号、Worker 标识和租约令牌**，防迟到老回调把新状态覆盖掉。
3. **共享存储 + 变更通知**：看着最稳，其实组件坑最多——**Redis 的 Keyspace Notification 默认是关的，而且断连期间事件直接丢光**，重连必须全量对账；**etcd 的 Watch 如果消费慢了超过历史压缩（compaction）窗口，会直接报 `ErrCompacted` 断开**，必须拿最新 revision 重建监听并重读全量。

所以生产上三招得一块用：**回调跑主路 + 轮询与租约兜底 + 权威数据库对账**。

### 10.2.4 HITL 人工审批与内置/外置调度的取舍

Agent 遇到高风险操作要从 `waiting` 切进 `hold` 等人审批，一等可能就是半天。不少人把「能不能在等待期间释放计算资源」跟「调度器是不是外置」划等号，其实错了：

![image](../assets/imgs/chapter-10/image-003.png)

图 10-3　内置与外置调度的责任边界

如图 10-3 所示，**只要状态和恢复契约持久外置，内置调度一样能释放执行容器；反之如果状态全捏在内存里，不管怎么拆都会把进程占死**。至于用应用内置还是外置专用调度（如 Apache Airflow 3.1.0 原生引入了 HITL 人工节点、阿里云 MSE-XXLJOB 也提供暂停/恢复人工节点），区别在于触发统一性、跨多服务统一运维和大并发弹性：

| 对比维度 | 内置调度（应用进程内） | 外置调度（独立调度系统） |
| --- | --- | --- |
| 队列/状态机位置 | 跟业务应用部署在一起 | 独立服务统一管理触发与分配 |
| 等待期能否释放计算资源 | 看状态是否外置可恢复 | 具备恢复契约时可彻底释放 Worker |
| 等待期还有什么开销 | 进程算力（若未释放）+ 调度逻辑 | 调度系统、状态存储、审批通道和保留环境照样花钱 |
| 接入门槛 | 低，开箱自包含 | 需对接调度 API 并暴露标准恢复回调口 |
| 适用场景 | 小规模、等待较短、不想多运维一套平台 | 大规模、等待时长难预测、需要弹性扩缩和统一运维大盘 |

另外画架构图时最容易糊弄过去的一笔是「审批通过 → 回调唤醒 Agent」——**别忘了明确是谁接回调、怎么防重放！** 审批事件必须带上 Task ID、审批版本号、授权主体和结论，直接发给 **Runtime 或调度器**，由它核验没过期、没重复、且当前任务状态合法后再重新入队，绝不能跳过校验直接唤醒执行。

## 10.3 定时任务与事件触发：走同一条流水线

要让 Agent 从被动工具变成主动数字员工（每天早 9 点出经营日报、每小时扫漏洞、每逢代码库推送自动做审查），触发源无非两类：

- **时间触发**：Cron 周期、指定未来一次执行（ScheduledAt）、固定频率（FixedRate）；
- **事件触发**：Webhook（外部业务方主动推过来）、MQ 消息、内部其他任务状态变更。

![image](../assets/imgs/chapter-10/image-004.png)

图 10-4　时间与事件触发共享任务执行链路

如图 10-4，这两条入口走过「身份与来源校验 + 发生键/事件键去重」之后，就完全汇入同一条 Task 队列流水线，共用并发控制、重试和对账。

配置定时任务时，最容易出事故的四个细节是：
1. **并发与阻塞策略**：把单任务并发限制为 1（串行）后，上一趟还没跑完下一趟又到点了，新触发是排队、跳过还是合并成最新一条，必须显式配好。
2. **时区、夏令时与发生键去重**：写死服务器本地时间早晚在跨区部署时出乱子；每次触发用「调度 ID + 计划发生时间」作去重键。
3. **错过触发（Misfire）怎么补**：调度器挂了半小时恢复后，错过的点怎么处理必须提前定好（见下表）。
4. **外置调度也会重复触发**：把调度交给 XXL-JOB、SchedulerX 或 Airflow 能减少多实例抢跑，但**故障转移（failover）切换瞬间子任务依然可能被执行两次**，所以业务侧幂等永远躲不掉；同时调度系统只管触发和 Runtime State，业务 State 依然归业务应用。

| 错过策略 | 恢复后怎么干 |
| --- | --- |
| `run_latest` | 错过再多趟也只补跑最近的那一次，其余忽略 |
| `run_all` | 把错过的次数在并发和限速上限内挨个补齐 |
| `skip` | 过去的既往不咎，老老实实等下一个正常未来时间点 |
| `prompt` | 系统不乱拍板，直接挂起告警等运维或业务方决定怎么补 |

## 10.4 Agent 工作流（DAG）：循环别硬塞、OR Join 别忘取消

当任务拆成多步固定协同，业界通常在三种编排里做组合：单 Task 内自主 ReAct 循环、预定义有向无环图（DAG）工作流、Planner 动态派活给多个专业 Agent。注意它们完全可以套娃：DAG 的一个节点内部可以是自主决策的 Agent，Planner 的派活范围也可以锁死在预定义子图里。**预定义 DAG 能把主干路径固定下来方便测试，但消不掉节点内部模型犯傻、工具超时的成本**。

### 10.4.1 严守 DAG 无环原则：带环流程请用状态机

本章讨论的工作流限定为 **DAG（有向无环图）**：节点按拓扑顺序推进。遇到「逐条处理列表」或「有限次迭代」时，用运行时有界展开的 `ForEach` 或设置最大迭代上限的 `Loop` 子工作流，保证父图本身依然无环。**如果业务天生需要带环打回重来**（比如审批驳回退回起草、改完再审直到达标），请老老实实用更上位的**状态机**建模，千万别往 DAG 里硬塞回边！

节点按职责分成**干活的业务节点**（调 Agent、调外部 API/DB、跑 Python/JS 脚本、RAG 检索、人工审批、发 IM/邮件通知）和**控流向的逻辑节点**（条件分支、并行 Fork、汇聚 Join、有界循环、等待 Timer、错误处理 Fallback、子工作流）。记住：就算不显式画控制节点，多条边连向同一个业务节点也能表达并行与汇聚。

### 10.4.2 最容易写出 Bug 的地方：三种依赖边与 OR Join 取消

同一张图里，「等所有前置都完成」和「谁先到就先走」如果不写死规矩，调度器必定打架：

| 依赖边类型 | 什么时候算就绪可以往下走 | 没被选中或没跑完的分支怎么办 |
| --- | --- | --- |
| 普通依赖边 | 上游节点是 `succeeded` 或 `skipped` | 上游 `failed` 按降级/重试/终止策略处理 |
| AND Join | 所有上游入边都到了终态，且满足策略（如全成功，或至少 N 个成功） | 只要不满足要求，按策略决定终止还是降级 |
| OR Join | 任意一条上游分支率先满足条件，立刻往下推进 | **引擎必须显式取消其余还在跑的分支！** 迟到结果只记进审计日志，绝不许再改下游状态 |

**OR Join 不取消其余分支是典型生产灾难**：比如两条路并行去调大模型或者起审批，A 路 2 秒回来已经把下游发走了，B 路没被取消在后台又跑了 3 分钟顺手把外部状态改了，下游结果直接精神分裂。

### 10.4.3 运维视图与「全量采集上下文」的安全陷阱

生产级工作流面板要在 DAG 拓扑上直接亮出每个节点的实时状态（`waiting` 到 `mark_succeeded`）、耗时、重试次数，并支持重跑、跳过、挂起、终止等人工干预。

**特别提醒一个高危安全陷阱**：很多团队顺手做了个「点击任意节点查看完整输入输出与 LLM 原始 Prompt」的功能，而且默认全量落库对所有研发运维开放。要知道，无人值守的后台工作流上下文里塞满了客户隐私、内部 Token 和商业机密，这么干等于在公司内部建了一个无授权明文泄密库！可观测采集必须**默认最小必要原则、敏感字段脱敏散列、严禁凭证入库、按 RBAC 分级授权并设留存期限**，审计日志只追加防篡改。

## 10.5 横切治理：没人盯着时，怎样防泄密、防超权、防烧爆账单

1. **三层评价别串台**：Observability 只提供事实原材料（Trace/日志/Artifact），Evaluation 负责用规则或 LLM-as-a-Judge 打分归因，**Outcome 只由业务应用或获授权 Verifier 拍板**。
2. **无人值守任务的四把安全锁**：用受控的服务身份和自动轮转凭证运行、严守多租户状态和产物隔离、出口网络收口进受审计代理，以及一条死规矩——**人工审批 `hold` 超时绝对不能视为默认批准**（只能保持等待、拒绝或升级告警）。
3. **给死循环套上预算刹车**：把 Model Token、外部 API、沙箱算力、存储、跨区网络、失败补偿和人工审批全算进总账。无人值守的定时 Agent 一旦在某个报错里陷入死循环，几小时就能刷出惊人的账单，所以单次 Token 上限、总时长硬顶、外部写操作次数上限和日/月累计预算熔断必须上线前配齐。

---

## 10.6 本章小结

把 Agent 做成可靠的后台生产力，不靠往流程里硬堆更多框架，靠分清五条边界：

1. **Task 与 Session 脱钩**：Task 带着业务 State 跨挂起、跨恢复持久活着，Session 只是其中一段执行窗口。
2. **完成语义分五层**：执行跑完不代表证据合法，证据合法不代表业务达标，运维手点强制成功更不能越权替业务验收。
3. **恢复和幂等按系统能力组合**：Checkpoint 只保计算不重算，保不了外部写入不重复；回调、Watch、轮询只是信号，信号断了必须回权威数据库对账。
4. **编排和触发按需拼装**：时间和事件触发汇入同一条队列；DAG 保持无环（带环回退走状态机），OR Join 必须显式掐掉没选中的分支。
5. **无人值守先锁死风险和账单**：审计采集做最小必要脱敏，审批超时绝不自动放行，预算熔断防住半夜死循环烧钱。
