# 第 12 章　Agent 分布式通信

前面几章把任务、信息、行动、沙箱、状态存储和网关都拆明白了，但它们能配合起来有个隐含前提：**参与者之间得先能可靠地说上话、接得住返回**。当 Agent 从单机单进程走到分布式多节点，传统后端开发习惯的四条通信默认假设会全部失效：

1. **调用耗时没法一刀切**：查一下日历只需要 50 毫秒，可让 Agent 改完代码跑完 CI 再等人点个确认，可能要等半天——你不可能把一个 HTTP 请求的超时硬拉长到 12 小时；
2. **连接和会话早就不是一回事**：前端手机切个 Wi-Fi 或合上笔记本盖子，TCP 连接瞬间就断了，但后台的 Agent 任务还在跑，过一会儿打开网页还得接上刚才的进度看；
3. **干等期间也在烧钱**：同步阻塞等着工具或人工响应，如果工作进程必须常驻内存干等，上万个并发任务光待机就把集群拖垮；
4. **物理地址随时会换**：容器缩容、故障漂移、沙箱休眠换机器唤醒之后，IP 全变了——按老地址调回去根本找不到人。

所以设计 Agent 分布式通信，重点不是一上来争论「该选 Kafka 还是 RocketMQ 还是 gRPC」，而是先沿着「**连接断了以后，状态到底寄存在哪、怎么接回来**」这条主线，看清每种通信语义的真实账单。

---

## 12.1 一条核心主线：让必要状态独立于连接存在

先看清楚状态可以寄存在哪三个地方，以及断线或重启后各自会掉什么东西：

| 状态寄存位置 | 常见存放什么 | 一旦断连或进程挂掉会怎样 | 怎么才能恢复回来 |
| --- | --- | --- | --- |
| 连接与进程内存 | 当前正在吐的响应流、临时局部变量 | 断网或容器一重启，没落盘的东西直接蒸发 | 重查后台持久化任务，或重跑幂等安全的调用 |
| 外部状态存储 | 业务任务进度、Checkpoint、Artifact 引用 | 只要存储没挂且原子提交了，进度纹丝不动 | 凭任务编号捞出最新可信状态，接着往下干 |
| 持久消息通道 | 有序交互事件流、消息序号、消费位点 | 只要还在消息保留期内、消费位点没丢，一条不漏 | 从上次确认的位置补读错过的事件，应用做好幂等去重 |

**特别提醒**：引入了消息队列，不等于自动拥有了「可恢复业务状态」。消息队列只负责把通知和事件安全递过去，除非你严格实现了全套事件溯源契约，否则业务状态照样得老老实实存在任务表或存储里；重放消息也绝对不能自动把挂掉的进程拉起来，更撤不回已经发出去的外部操作（比如 RocketMQ-A2A 的 FSE 2026 研究论文曾用会话级可重播事件流讨论大规模通信容错，读这类压测结论时也要看清消息体大小、并发和故障注入前提，别直接套成协议普适上限）。

## 12.2 通信选型地图：四个通信面 × 四档交互语义

为了不把客户端推流、工具调用、多 Agent 派活和底层组件消息混成一团麻，我们按「**谁跟谁说话**（四个通信面）」和「**双方在时间/空间上解耦到什么程度**（四档交互语义）」画出一张选型地图。

### 12.2.1 按通信双方划分四个通信面

| 通信面 | 谁跟谁通信 | 对应主流协议 | 典型方式 | 工程上最拧巴的核心矛盾 |
| --- | --- | --- | --- | --- |
| **人机面** | 用户/前端 ↔ Agent | AG-UI（等前端事件流） | Token 增量流、前端进度同步、待办收件箱、人工审批 | 用户最需要实时看见每一步且随时能打断，但偏偏手机/浏览器的前端连接最不可靠 |
| **能力面** | Agent ↔ 工具或数据源 | MCP（垂直方向） | 工具发现与调用 | 同一个协议下面，毫秒级查天气和耗时几分钟跑分析的任务混在一起，超时策略极难一刀切 |
| **协作面** | Agent ↔ Agent | A2A（水平方向） | 跨 Agent 任务委派与交卷 | 任务天生跑得长，且 Agent 数量一多，点对点两两集成和信任配置呈平方级爆炸 |
| **内构面** | 服务端内部组件之间 | 无统一行业标准 | 消息队列、事件流、内部 RPC | 百万级同时在线会话如果建独立通道，控制面元数据会先于业务把队列压垮，且多租户隔离难 |

### 12.2.2 按解耦程度划分四档交互语义（不是成熟度升级阶梯）

别把这四档理解成「必须从 S1 一路升级到 S4 才高级」——**成本和风险允许的情况下，能用越低一档解决就别硬上高一档**：

| 档位 | 怎么交互 | 时间耦合 / 空间耦合 | 状态放哪 | 解决了什么 | 解决不了什么 |
| --- | --- | --- | --- | --- | --- |
| **S1 请求—响应** | 一问一答同步拿结果 | 强耦合（等待期内连着、且认准固定端点） | 内存临时态（可关联持久记录） | 短调用最简单、排查直观 | 扛不住长任务，断连没法补结果 |
| **S2 请求域流式** | 一条请求里分批吐 SSE/流事件 | 流存在期间绑死当前连接和端点 | 当前流内存 | 过程实时可见、用户体验顺滑 | **流本身不自带断点续传和离线恢复** |
| **S3 任务句柄** | 先交任务拿回 ID，稍后查结果或等推送 | **执行和首次请求彻底解耦**，仍需可访问查询入口 | 持久任务表与产物引用 | 长任务、挂起等审批、离线回来取结果 | 光有句柄不一定能按条补读全套历史事件 |
| **S4 持久通道** | 读写带序号的命名通道，记消费位置 | 生产消费时空全解耦，通过逻辑通道名寻址 | 消息日志 + 消费位点 | 削峰填谷、事件补读、多端广播、通道级流控 | 依然替代不了业务状态机、幂等和运维清理 |

### 12.2.3 最常见的混淆：SSE 流式输出 ≠ 任务异步化

很多团队看到页面上在实时打字吐流，就以为「我们已经是异步长任务架构了」——**完全不是一回事**！SSE 只是数据怎么一点点吐过 TCP 连接的传输格式。真要验成色，就问两个独立的问题：**第一，连接断了以后，手里有没有一个脱离连接的任务句柄去查结果？第二，重连上来时，服务端支不支持从刚才断掉的序号把中间漏的事件补齐？**

典型反例就在 **MCP 2026-07-28 规范**：新版直接移除了传输层的 SSE 断线续传机制，流断了再重发必须靠应用层自己做业务幂等；而 **A2A** 允许流式订阅关联到后台持久化的 Task，流断了照样能拿任务 ID 去重新订阅或查询结果。

### 12.2.4 落到实操：四×四组合分布与六要素检查表

| 通信面 | S1 请求—响应 | S2 请求域流式 | S3 任务句柄 | S4 持久通道 |
| --- | --- | --- | --- | --- |
| **人机面** | 传统表单式一问一答 | 实时打字流、前端事件流 | 待办收件箱、后台任务列表 | 手机/电脑多端同步看同一个长会话 |
| **能力面** | 常规短耗时工具调用 | 秒级工具请求内进度流 | MCP 可选 Tasks 扩展 | 需额外加持久通道契约 |
| **协作面** | 轻量交互直接回 Message | A2A 任务流式进度推送 | A2A 持久化 Task + 查询/回调 | 基于消息中间件的 Agent 网格 |
| **内构面** | 内部微调用 RPC | 内部组件间流式转发 | 权威任务表 + Worker 认领 | 会话级轻量通道、事件总线 |

无论最终挑中哪一格，签一份生产级通信契约之前必须把这 **六件事** 白纸黑字写清楚：
1. **标识分离**：会话 ID、任务 ID、轮次 ID、消息 ID 各自独立、显式关联——千万别拿群聊线程 ID 硬当任务 ID，否则一个任务想跨渠道或者开后台子分支就全卡死；
2. **保序范围**：只要局部保序（比如同一个会话内、同一任务内按分区键保序）就行，别妄想跨全平台全局有序；
3. **投递保证与去重**：明示至少一次/至多一次，并配好消费方幂等去重键；
4. **续传光标**：断连重连后拿哪个序号或位置补读（和任务查询接口分开定义）；
5. **通道生命周期**：临时会话通道什么时候建、没人聊多久后自动回收（回收前确认没活跃任务和未确认消息）；
6. **全链路背压**：过载时客户端退避、网关限流、消息队列暂停投递怎么一层层传递减速，别全靠硬扛 OOM。

## 12.3 同步、流式与异步怎么选：先算收益，别盲目全异步

能用 **S1 同步请求—响应** 稳稳干完的短活（比如几十毫秒查配置、几秒内结束且超时有幂等查询兜底的工具），**千万别为了「看起来高级」硬改成异步消息队列**。同步通信有四条真金白银的工程优势：控制路径直白、无异步队列/死信队列（DLQ）/重投风暴的运维地狱、短调用成本结构最简单，以及——**注意分清范围**——在**单机进程内不跨进程边界**的调用段里，调用栈天然就是最完整的排障现场（一旦跨了网络进程，同步 RPC 照样需要 W3C Trace 串链路，这点和异步一样）。

选型时就卡三把尺子：**① 耗时能不能稳稳卡在超时窗口内？② 有没有突发流量需要队列削峰解耦？③ 超时结果不明时，有没有幂等键和查询接口把结果核对回来？** 只要三项都答「能」，同步或加个 S2 流式就够用；真出现耗时不可控、连接保不住、需要跨天挂起或离线补读时，再按需升到 S3 任务句柄或 S4 持久通道。

而真决定上异步和持久通道（S4 须满足**按业务命名通道、`(通道, 序号)` 续传光标、保留期内可补读、未确认重投 + 消费端幂等**四条最小语义）时，下面这笔**架构代价清单**必须在立项前心里有数：

| 异步引入的新代价 | 线上真实长啥样 | 必须配套补齐的工程动作 |
| --- | --- | --- |
| 多跳累计延迟 | 进队列、落盘持久化、出队列排队，每多一跳都在加耗时 | 端到端链路卡实测延迟，实时交互尤其小心 |
| 强制要求幂等 | 网络一抖、消费者一重启，同一条消息再投一遍是常态 | 每个写步骤必带幂等键，恢复前先查外部系统现状 |
| 历史留存烧钱 | 几十万个长会话全保留完整事件流好几个月，存储账单暴涨 | 按容灾恢复和审计底线定好 TTL 过期清理 |
| 无超时边引爆故障 | 上游不设截止时间拼命重试，下游失败被指数级放大 | 每条调用边和等待节点设死绝对超时、重试上限与熔断 |
| 调用栈彻底断片 | 出 Bug 时再也没法看一个完整堆栈定位问题 | 全链路贯穿 Trace Context 与任务/会话关联标识 |

## 12.4 能力面（MCP）与协作面（A2A）：为什么一个在做轻，一个在做重

把行业里最常一起提到的 **MCP** 和 **A2A** 拉到同一张表上对比，立刻就能看透为什么两个协议演进方向表面看似相反：

### 12.4.1 MCP 的四代演化与「协议无状态 ≠ 应用无状态」

| 协议版本 | 传输形态 | 状态放哪 | 带来的工程变化 |
| --- | --- | --- | --- |
| `2024-11-05` | stdio + HTTP/SSE 双端点 | 服务端绑死会话级长连接 | 负载均衡和长连接运维极重 |
| `2025-03-26` | Streamable HTTP 单端点 | 会话标识头 + 可选事件重放 | 扩缩容仍需粘性会话或共享会话存储 |
| `2025-11-25` | 保留会话与握手 | 同上 + 首次引入实验性 Tasks | 开始尝试为长耗时工具提供句柄 |
| `2026-07-28` | **无状态核心（Stateless Core）** | 每条请求自带元数据 + 应用层显式任务句柄 | 删掉协议会话与握手，重放和长任务责任下沉应用层或官方可选 Tasks 扩展 |

2026-07-28 版大刀阔斧砍掉了协议级会话标识和初始化握手（initialize），改为每条请求携带版本和能力元数据、靠按需发现接口（`server/discover`）获取能力、变更通知走统一订阅流（`subscriptions/listen`）、反向输入靠多轮往返请求（同时 Roots、Sampling、Logging 进入弃用流程）。

**最容易被理解歪的一句话**：「MCP 已经无状态了，工具后端随便用无状态轮询就行！」——**大错特错！** 协议层甩掉了会话包袱，只意味着 HTTP 连接不再绑定协议状态，**业务执行如果跑几分钟，任务状态和结果照样得由应用层自己存进数据库或 Tasks 扩展后端里**，断线重交照样得自己做幂等去重。

### 12.4.2 A2A：把「去拉取」做成规范，和 MCP 天然互补

A2A 天生为了跨 Agent 长任务与人在回路交互而生，所以自带完整的 Task 状态机（已提交、执行中、需要输入、需要授权、完成、失败、取消、拒绝）。注意它两种异步机制的精确分工：
- **流式接口（S2）**：只在当前 HTTP 响应流里实时吐过程更新，流断即止，别指望它保证终局送达；
- **推送通知（S3 增强）**：服务端状态变了主动发个回调给你——规范特别讲究地指出，**推送只是个「闹钟触发器」，客户端收到提醒后应该拿 Task ID 再发一次任务查询去拉取完整权威结果**，这样就算推送通知半路丢了一个，或者载荷不全，查询接口依然能兜住底。

| 对比维度 | MCP（能力面） | A2A（协作面） |
| --- | --- | --- |
| 通信方向 | 垂直：Agent 调工具与数据源 | 水平：自治 Agent 之间派活协作 |
| 核心交互单元 | 一次工具/资源调用 | 有状态、可挂起恢复的持续任务（Task） |
| 能力怎么发现 | 按需调 `server/discover`（2026-07-28 起） | 预发布可带签名的 `Agent Card` 名片 |
| 状态归属 | 协议核心无状态，状态上推给应用层或可选 Tasks 扩展 | 协议内建完整任务生命周期状态机 |
| 演进方向 | 不断剥离传输会话，变轻变好负载均衡 | 不断强化长任务追踪、通知和产物交接 |

两者压根不是竞争关系，实际生产中经常**并排用**：编排 Agent 通过 **A2A** 把子任务派给专业 Agent，专业 Agent 自己通过 **MCP** 去调工具查数据。

## 12.5 内构面实战：通道键决定治理粒度、「手脑分离」与海量会话陷阱

真正决定高并发线上平台稳不稳、贵不贵的，往往是没有公开标准可抄、全靠自己设计的**内构面（服务端内部组件通信）**。

### 12.5.1 通道键选什么，限流、隔离和排障粒度就长什么样

来看阿里系生产实践里的三个真实架构图，它们把同一个规律用得炉火纯青：**把并发治理单元直接选成消息通道键（Channel Key），就能把复杂的应用层路由表和限流逻辑全部下沉给消息引擎**。

**案例一：高并发智能语音交互（按「会话标识」建通道）**

![image](../assets/imgs/chapter-12/image-001.png)

如图 12-1，客户端与网关、处理系统与 ASR/LLM/TTS 之间全是大并发长连接。以前最大痛点是「分布式会话粘滞路由表延迟导致音频帧推错节点」和「本地连接表把节点变成有状态孤岛」。解法是上下行彻底拆开：**上行请求**按会话 ID 哈希进分区顺序 Topic，保证同一段语音严丝合缝有序消费；**下行响应**直接以会话标识作为轻量通道名，每个连接网关节点只动态订阅连在自己身上的会话，断连取消订阅、重连续订。结果连接层和业务处理层双双变成彻底无状态的纯计算池，排障也从「大海捞针」变成直接看「哪个通道消息堆积最多」。

**案例二：百炼平台网关限流（按「用户 × 模型」建通道）**

![image](../assets/imgs/chapter-12/image-002.png)

如图 12-2，几十万组「租户 × 模型」同时打向扩容周期很长的 GPU 推理集群。如果在网关 JVM 内存里硬做漏桶缓冲，一波脉冲直接把网关内存撑爆（OOM）。百炼的解法是**把漏桶阵搬出网关进程**：网关只用固定窗口卡死硬上限、防止超额，然后把请求按「用户 + 模型」投进对应的轻量队列；消费端一组无状态 Pod 用通配符订阅父主题，按均匀节奏拉取，一旦某租户某模型触发限流，消费回调直接返回一个挂起指令（`Suspend`）让这条队列单独歇几十毫秒再自动恢复——既保护了 GPU，又把网关释放得轻轻松松。

**案例三：百炼资产中心（按「用户」建通道，且消息只带索引不带大文件）**

![image](../assets/imgs/chapter-12/image-003.png)

如图 12-3，用户批量生成大量图片视频时，**消息体里绝对不传几十 MB 的文件本体，只传对象存储临时地址和元数据**；通道按「用户 ID」动态创建、按存活时间（TTL）自动回收，再过白名单校验和安全检测后持久化进长期资产库。某个土豪用户瞬间刷出几千张图触发限流挂起，只停他自己那一条队列，完全不阻塞其他几十万正常用户。

### 12.5.2 手脑分离（Decoupling Brain from Hands）的两条代表路线

把决策循环（脑）和沙箱工具执行（手）拆到不同进程，各自独立扩缩容，已成为主流长任务架构共识，但落地深度有别：

- **Anthropic Managed Agents（抽象层范式）**：他们直白地指出这套设计源于「**Harness 老化**」——以前为老模型「上下文焦虑」硬编码进 Harness 的上下文重置逻辑，在新一代强模型出来后反而成了拖油瓶。因此他们像操作系统抽象「进程与文件」一样，把系统虚拟化成三个独立部件：**Session**（只追加的客观事件日志，永远留全量事实，不做有损裁剪）、**无状态 Harness**（随时可替换，醒来拉事件日志续跑并按需裁剪成窗口视图）、**降级为普通工具的沙箱**（手挂了就当工具报错重申请一只，别把大脑和会话一起拖死）。
- **Qoder Cloud Agent（QCA，通道层工程参考架构）**：把「手脑分离」落到了实打实的 RocketMQ 消息总线上（详见极客时间公开课 [Qoder Cloud Agent的工程实践](https://time.geekbang.org/course/detail/101180401-1004201?utm_campaign=geektime_search&utm_content=geektime_search&utm_medium=geektime_search&utm_source=geektime_search&utm_term=geektime_search)）：

![image](../assets/imgs/chapter-12/image-004.png)

| 层级 | 角色定位 | 干什么活 |
| --- | --- | --- |
| 脑 — Agent Runtime（QCA 控制面） | 决策与推进 | 管鉴权接入、Task 编排、状态推进、多 Agent 与中途插话 |
| 路 — RocketMQ 消息总线 | 异步交接主干 | 跑三类流：① 任务指令（QCA → Worker 异步削峰）；② 执行事件（Worker → QCA 保序/重试/死信）；③ 异步工作项（按环境路由弹性消费） |
| 手 — 弹性 Sandbox Worker | 按需算力工位 | 从消费组认领活，跑模型/MCP/沙箱计算，检查点落盘后立刻释放 |
| 底 — 状态与对象存储 | 持久化事实 | 接单记录、Checkpoint、产物与上下文持久化，支撑任意节点接力续跑 |

这套架构最精妙的一句话总结是：**「会话常驻、计算流动、状态可续」**——不要再把工作进程「当成有名字、有状态、死不得的宠物」供在内存里，Worker 只是一棒接一棒跑完就换的接力选手。

| --- | --- | --- | --- | --- |
| 智能语音交互 | 会话标识 | 请求侧会话内严格保序 | 单个会话 | 消除分布式粘滞路由表，响应精准回推 |
| 百炼网关限流 & 资产中心 | 用户 × 模型，或用户 | 不强求全局顺序 | 用户级 / 租户模型级 | 进程外漏桶抗脉冲，防单用户拖垮全局 |
| Qoder Cloud Agent | 会话标识与环境标识 | 任务内有序 + 会话级保序 | 会话与执行环境 | 脑路手底解耦，Worker 弹性扩缩无状态流动 |

### 12.5.3 规模化暗礁：万级并发会话直接用传统 MQ 会瞬间炸掉

如果看上表觉得「一会话建一个队列」挺美，真等同时在线会话冲上几万、几十万，直接拿普通消息队列的 Topic 套上去，下面三种直觉方案会瞬间把集群拖死：

| 直觉方案 | 十万级并发会话一到，先炸在哪 |
| --- | --- |
| 每个会话建一个标准 MQ Topic | 大量标准 Topic 的元数据、路由表同步和创建销毁开销会把 Broker 控制面直接压垮 |
| 发广播消息让节点自己过滤 | 全量消息在所有节点之间无效满天飞，单节点网卡和 CPU 过滤先碰天花板，水平扩容失效 |
| 每个会话起一个独立消费组 | 消费组数量大爆炸，动态协调开销等同于在队列外面又硬搓了一套路由器 |

这就是为什么刚才三个阿里系生产案例全都选用了 **Apache RocketMQ 的 LiteTopic（轻量主题）** 机制（或同类逻辑通道复用技术）：它不在 Broker 里为每个会话建重型物理 Topic，而是让成千上万条逻辑通道挂在极少数预建父主题下，服务端内存里只存轻量字符串键和双向索引，做到**首次发送免声明自动建通道、按活跃就绪集合公平调度（调度复杂度只看活跃通道数，不跟总订阅数硬算）、单通道挂起限流不拖累别人、通配符统一订阅+精确订阅混用、空闲超时自动回收**。当然，验收时依然以你实测的持久性、保序、隔离和恢复成本为准，不唯产品名字论英雄。

## 12.6 人机面（AG-UI）与全书默认选型表

人机面是**全书最拧巴的一层**：产品要求流式打字越快越好、用户随时点「停」或插话纠偏得立刻响应，偏偏手机 4G 切 Wi-Fi、网页切后台是最爱断线的。

解法只有一条：**把前端连接彻底降级成「当前的一扇观察窗」**。任务和状态独立活在服务端，客户端断了只是暂时没人在窗口前盯着看，后台照跑不误；重连后拿着续传位置补读或者直接拉最新状态快照。Claude Code 的 Remote Control 就是这个路子——允许手机、平板、浏览器同时接入终端里正在跑的同一场会话，它文档说得很直白：客户端只是会话的展示器，绝不是代码跑的地方（不过它走的是 Anthropic 自有协议，不是 AG-UI）。

人机交互里还要把两种人在回路拆开：**边跑边插话引导**只在活跃期有用，走 **S2 请求域流式**就够；而**阻塞式人工审批**动辄等几个小时，必须落进 **S3/S4 持久化待办收件箱**（按「待输入 / 出错 / 已完成」组织）。此外，如果采用仍在快速演进中的 AG-UI 协议，记得锁死 SDK 版本，并且别把「支持状态快照」误当成「断线后保证一条不漏重播全部历史事件」。

### 四大通信面的默认起跑线与升级触发条件

不要过度设计，记住这张最低充分起步表：

| 通信面 | 默认起步档位 | 什么时候才值得往高一档升级 |
| --- | --- | --- |
| **人机面** | S2 请求域流式 | 出现长时间阻塞人工审批，或需要手机/电脑多端离线接力看进度时 → 升 S3 或 S4 |
| **能力面** | S1 请求—响应 | 单个工具跑得比网关超时还久，或要跨实例断点恢复时 → 升 S3（如 MCP Tasks 扩展） |
| **协作面** | 持续协作起手 S3（简单问答可 S1） | 需要大量事件补读、扇出广播和独立消费限流治理时 → 组合 S4 |
| **内构面** | 按职责用 S1 RPC 或 S3 任务表 | 需要削峰填谷、会话级保序手脑分离、多租户通道级流控时 → 组合 S4（如轻量通道） |

## 12.7 本章小结

分布式通信设计不需要把全套消息中间件全叠一遍，只需死守四条工程判断：

1. **让状态离开连接独立活着**：连接只是当前一根网线，断线后能不能续上，全看外部状态存储和持久通道里留没留着任务标识、续传光标和幂等记录。
2. **协议无状态不等于业务无状态，流式不等于异步**：MCP 2026-07-28 变轻了，只是把长任务状态的担子推回给了应用层；判断是不是真异步，看断网后还能不能拿着句柄找回结果。
3. **选对通道键，内构治理就赢了一半**：把「会话」或「用户 × 模型」做成轻量逻辑通道键，就能天然实现手脑分离、单租户漏桶流控和百万级无状态弹性扩缩。
4. **每个通信面从最低够用那一档起步**：短活直接同步，长活给句柄，真有脉冲削峰和事件补读刚需再上持久通道，别让过度异步的复杂度拖垮团队维护成本。
