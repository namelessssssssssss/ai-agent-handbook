# 第 07 章　Agent 运行时与沙箱

一个只会嘴上聊天的问答机器人，只需要调用大模型就够了；但一个真正干活的 Agent，必须能写代码、跑测试、操作浏览器、改文件，甚至在遇到报错后自己修完再重跑一遍。

很多团队把这种 Agent 往生产环境一丢，马上就会踩进四个典型的线上坑：

1. **算力一闲就回收，文件全丢**：Agent 刚装好依赖、改了一半代码，停下来等大模型返回或者等人工确认；平台看容器 CPU 几乎为 0，顺手就把实例销毁了，用户下一句追问过来，工作区干干净净，一切从零开始。
2. **休眠醒来接口返回 200，任务却死在半路**：把环境暂停再恢复，磁盘文件虽然还在，但长连接早就断了、临时凭证过期了、本地预览服务端口也挂了，不检查就继续跑，下一步工具调用立刻报错。
3. **节点失联拉起新副本，新旧双写引发脑裂**：旧容器只是网络抖动或 GC 卡顿，没真死透；Runtime 以为它挂了，拉起新实例接管同一个工作区，结果两个进程同时往同一份代码或外部系统里写数据。
4. **评测回滚了沙箱快照，外部数据库却没回滚**：跑强化学习或批量评测时，用快照分叉出几十个分支同时试错，回滚后容器是干净的，但刚才分支发出去的测试请求、改过的外部数据库却留在了线上。

这些问题说明：Agent 需要的不只是一个能执行代码的隔离容器（Sandbox），还需要一套懂长任务生命周期的调度与恢复宿主（Runtime）。本章就围绕这两者的分工，拆解 **真实翻车点 → 核心机制与图表 → 工程落地取舍**。

## 7.1 先分清边界：Harness、Runtime、Sandbox 各管什么

在真正动手搭环境之前，先把三个经常被混叫的名词对齐，免得后面职责打架：

- **Model（认知大脑）**：只负责理解意图、推理和决定下一步干什么，本身概率输出、没有持久状态。
- **Harness（外层任务控制脚手架）**：包在模型外面的循环控制层，负责拼装上下文、维护任务进度、管理工具和权限拦截、做交付前验收。
- **Runtime（长任务调度与故障恢复宿主）**：管任务和环境的生命周期——什么时候创建、挂起、休眠、唤醒、切副本、防脑裂、超时回收。
- **Sandbox（隔离执行空间）**：真正让代码、终端、浏览器和桌面跑起来的隔离工作区，决定 Agent 能碰哪些文件、用哪些依赖、连哪些网络。

如果参数固定、动作确定（比如按订单号查物流），直接调业务 API 就好，根本没必要开 Sandbox。**只有当操作路径需要在执行中边试边改**——比如处理一批表头乱七八糟的报表、写脚本清洗数据、改完代码跑测试再修 Bug——才需要把可编程的 Sandbox 接进循环。

## 7.2 工具执行：从单点解释器到共享工作区

### 7.2.1 代码沙箱：让 Agent 边试边改，而不是硬凑 API

做经营数据分析时，用户丢进来五六个格式各异的 CSV 和 Excel。如果全靠后端提前写死解析接口，稍微换个列名就瘫痪；放进代码沙箱后，Agent 先用脚本探查前十行列名和脏数据，装上解析库写转换脚本，跑出异常再对照报错自己改映射逻辑，最后交付输入版本、处理脚本和结果图表。

高明团队的做法往往是「**固定高频 + 沙箱探索**」组合：把稳定、高频的动作沉淀成固定 API 工具；把长尾、临机应变的数据清洗和验证留给沙箱，最后用输出文件和数据范围校验来兜底验收。

### 7.2.2 浏览器、桌面与 AIO 共享工作区

很多任务单靠命令行根本完不成：比如去有登录态的后台下载导出文件、把本地改好的前端页面拉起来点一遍看排版、或者操作没有开放 API 的老旧桌面软件。这就需要浏览器沙箱和桌面沙箱，把页面 DOM、截图、下载文件和系统日志都变成反馈信号。

但如果浏览器在一个容器、代码解释器在另一个容器，很快就会出现「**文件传来传去**」的折磨：浏览器下载完文件，先传回对象存储，再下载到代码沙箱算完，再上传给浏览器预览——中间光路径转换和版本对齐就能写出一堆 Bug。

![image](../../assets/imgs/chapter-07/image-003.png)

图 7-3　共享工作区支撑跨工具任务

**All-in-One（AIO）共享工作区**（如图 7-3）把浏览器、终端、代码解释器挂到同一个任务工作目录上：浏览器下载即落盘，代码原地读取计算，生成的页面就地打开预览。当然，共享也有代价——AIO 镜像通常更重、启动更慢；而且**共享范围必须锁死在「同一任务内」**，不同租户、不同项目绝对不能混用工作区；如果有并行子任务要改同一文件，必须提前定好分支或合并规则，不能互相覆盖。

### 7.2.3 承载带本地依赖的 MCP Server 与 Skill

MCP 定义了工具怎么被发现和调用，Skill 沉淀了任务步骤和脚本，但它们真跑起来时，背后照样可能依赖特定 Python 环境、命令行工具甚至无头浏览器。以前只能跑在某台开发机上的本地工具，放进沙箱后，通过前面一层协议适配网关把远程请求转成进程标准输入输出（stdio），就能按需拉起、空闲休眠、按任务隔离，彻底摆脱「在我电脑上是好的」环境诅咒。

| 环境类型 | 典型场景 | 核心产出 | 沙箱带来的直接收益 |
| --- | --- | --- | --- |
| Code（代码） | 数据清洗、写脚本、编译跑单测 | 代码补丁、报表、测试结果 | 按任务隔离依赖库，报错即改形成闭环 |
| Browser（浏览器） | 网页操作、下载文件、前端实景预览 | 截图、下载文件、DOM 状态 | 拿到真实页面交互反馈，而不只靠猜 HTML |
| Computer（桌面） | 操作无 API 的桌面软件或复杂 GUI | 软件导出件、操作录屏与状态 | 打通传统无接口客户端软件的自动化断点 |
| AIO（综合工作区） | 跨浏览器下载、计算加工与预览交付 | 端到端完整交付物 | 多种工具直读同一份工作目录，消灭文件搬运 |
| MCP / Skill 环境 | 运行带重型本地依赖的工具或脚本 | 结构化工具结果、中间制品 | 把单机工具变成可弹性扩缩、按租户隔离的服务 |

## 7.3 长时任务：怎么扛住等待、休眠与节点故障

把 Agent 放到真实项目里跑几个小时甚至几天，才是 Runtime 真正见真章的地方。下面四类坑，几乎每家做长任务平台都会挨个踩一遍。

### 7.3.1 翻车现场一：CPU 一闲就驱逐，项目成果原地蒸发

假设一个 Coding Agent 已经拉下代码、装好上百兆依赖、改通了三个模块，然后停下来等模型生成下一段方案，或者等用户晚上回家再确认。**如果沿用普通无服务器容器的默认策略——看见 CPU 利用率低就自动缩容回收——只要实例内盘没外置，用户下一句话发过来，沙箱已经换了台新机器，之前所有修改和依赖全没了。**

要把弹性缩容和项目连续性同时保住，靠两条独立但配合的映射：

1. **会话亲和（请求 → 环境）**：用户请求带着稳定的会话标识进来，网关或路由层查表找到对应的活跃环境，或者触发恢复流程——调用方永远不能把某个容器的临时 IP 当作长期入口。
2. **动态工作区挂载（环境 → 数据）**：平台先核验「租户 + 用户 + 项目」的合法归属，再把持久化存储目录挂进沙箱。**千万别只靠拼接用户名拼路径名来做目录隔离**，必须有服务端权威鉴权；如果挂载失败或目录校验不匹配，宁可直接报恢复失败阻断执行，也绝不能给 Agent 挂一个空目录继续跑，否则 Agent 会以为仓库没拉下来而把数据全重覆盖一遍！

同时记住**工作区文件与任务事实分离**：代码、下载件放在工作区；「任务跑到哪一步、哪些外部写入已经生效、下一步该干嘛」必须落在外部状态存储里。至于运行中临时装的包：高频固定依赖提前打进版本化模板，临时依赖装到持久化覆盖目录，系统级目录改动要么保留可重建脚本，要么纳入环境快照——工作区挂载只恢复它管的那块目录，管不了系统全局目录。

### 7.3.2 翻车现场二：休眠醒来接口 200，TCP、凭证和端口全断了

长任务大部分时间其实在「等」：等大模型吐字、等审批、等 CI 构建、等用户第二天上班。一直开着高配容器太烧钱，每次等待都删干净重建又太慢，于是就有了休眠与唤醒机制。

![image](../../assets/imgs/chapter-07/image-004.png)

图 7-4　长会话的等待、休眠与续行

图 7-4 揭示了一个极容易做反的设计原则：**唤醒入口必须放在休眠沙箱外面**。沙箱一旦睡着了，里面的进程就停了，不可能自己监听定时器或用户消息；必须由外部网关、消息队列或定时器接住事件，先恢复环境再把任务递进去。而且休眠前不能只看「半分钟没新请求」就强行挂起，得确认里面没有正在跑的后台构建，并且把关键进度在平时就随手落盘，别全指望收到终止信号那一瞬间才抢救写入。

更重要的是，不同休眠深度的代价和坑点完全不同（比如 E2B 区分 pause 与 kill，阿里云按保留资源计费区分浅/深休眠）：

| 状态策略 | 保留了什么 / 释放了什么 | 适用场景 | 最容易忽略的代价 |
| --- | --- | --- | --- |
| 持续运行 | 进程、内存、磁盘、连接全在线 | 连续高频交互、后台预览服务常驻 | 等人期间 CPU/内存照样全额计费 |
| 浅层暂停 | 冻结计算、保留内存和文件 | 几十秒到几分钟的短等待，追求秒级醒 | 内存仍然占位计费；长连接超时照样断 |
| 深度休眠 | 内存/状态持久化落盘，释放计算资源 | 等人几小时甚至跨天，想保留运行现场 | 恢复耗时变长；外部 TCP、临时凭证、端口全失效 |
| 仅留文件重建 | 只保留持久化工作区和任务账本 | 进程重启很便宜，核心资产都在代码/文件里 | 服务进程和内存上下文得从头拉起 |

**最关键的恢复铁律**：E2B 与阿里云休眠文档都明确提醒过，暂停或休眠恢复后，磁盘文件虽然回来了，但**外部 TCP 连接可能已被对端掐断、STS/OAuth 临时凭证可能已过期、沙箱里原来监听的本地预览端口也可能挂了**。所以「恢复接口返回成功」只是第一步，Runtime 必须接着做一遍存活校验（文件在不在、进程活没活、端口通不通、凭证有效吗），确认任务真能往下跑，才算恢复完成。

### 7.3.3 翻车现场三：心跳失联引发「双写脑裂」

线上一定会出现这种情况：旧容器因为网络抖动、宿主机卡顿或 JVM/运行时 GC 暂停，连续漏掉几次心跳。控制面以为它死了，立刻拉起新副本挂载同一个工作区继续跑。五秒后旧容器缓过气来，接着往同一个文件或外部接口写数据——**这就是典型的分布式脑裂**。

解决脑裂不能只靠「在数据库里把 owner 改写成新实例 ID」，因为旧进程根本不会去查你这张表！真正的解法有两道锁：

1. **执行代次 + 围栏令牌（Fencing Token）**：每次接管都把任务代次加 1，新实例带着更高代次的令牌去写存储、写文件或调网关；受保护的底层存储和写入入口必须校验这个代次，**硬生生拒掉拿着旧令牌的写入请求**，从物理上把旧实例关进门外。
2. **外部副作用先查再试**：如果旧实例失联前已经向外部系统提交了一个构建请求、发了一封邮件或发起了一笔变更，新实例接管后绝不能无脑重跑，而应该先凭原请求 ID 去外部系统查结果。实在查不清结果且无法安全重放的写操作，就挂起等人工核对，别让系统盲目重发酿成二次事故。

## 7.4 训练与评测：快照分叉的威力与外部状态陷阱

除了线上服务，还有一大类刚需是给模型强化学习（RL）和 Agent 离线评测批量拉环境。每一轮从拉仓库、装依赖、跑交互到出测试结果，就是一条完整轨迹（rollout）。如果一万条并发任务全从零拉代码、装包，模型卡空转等环境都能把集群拖垮，环境故障还会被误算成「模型能力下降」。

![image](../../assets/imgs/chapter-07/image-005.png)

图 7-5　快照与分叉支撑并行探索

把 **Template（模板）、Snapshot（快照）、Fork（分叉）、Reset（重置）** 四个机制拆开用，就能把公共准备和并行试错解耦：

- **Template**：定义干净的起点（操作系统、语言版本、基础工具链）；
- **Snapshot**：把「已经拉完大仓库、装完依赖、跑通基线测试」的这一刻存成快照；
- **Fork**：从同一个快照瞬间分叉出几十个互不干扰的可写分支，让不同模型或不同 Prompt 并行去改代码、跑测试（区别于长任务里一对一的暂停恢复）；
- **Reset**：一轮跑完立刻把环境打回干净初态，绝不让上一题的残留文件污染下一题。

但快照分叉在评测与 RL 里有**两个必须提前堵死的坑**：

1. **沙箱快照回滚不了外部世界**：沙箱快照只管容器里的磁盘和内存。如果 Agent 在测试过程中调了外部测试库、发了条群消息、或者改了某个共享 API 的状态，哪怕本地把沙箱 Reset 得一尘不染，外部世界已经脏了。评测环境必须配合**独立测试数据库副本、独立测试租户或显式外部重置钩子**，且分支写入只能进各自隔离的可写层。此外，沙箱快照存的是环境运行态，别和模型训练存权重/优化器的 Checkpoint 混为一谈。
2. **严防 Agent 自己改掉考卷**：做代码修复类评测时，如果测试脚本和评分标准就明晃晃放在 Agent 有权修改的目录里，聪明的模型有时会直接修改断言或者删掉失败用例来骗取满分！评分规则和核心验证材料必须放到沙箱外或受只读保护，同时分阶段埋点记清楚到底是「环境超时没拉起来」还是「Agent 真没解出来」。

## 7.5 成本、延迟与容量：别被「空容器启动 100ms」骗了

很多沙箱方案喜欢宣传「冷启动只需百毫秒」，但工程上唯一真实的口径是**业务首次可用时延**：从用户任务发起算起，一直到请求排队、资源调度、镜像拉取、工作区挂载、用户凭证注入、进程与依赖全部就绪、能接第一条命令为止。空容器启动快，不代表挂完 2GB 代码仓和恢复会话之后还快。

同样，算成本也不能只看单小时容器单价，而要算「**单位成功任务成本**」：把测量窗口里计算、存储、快照、出口流量以及**预热池空转、失败重试、无效探索烧掉的钱全加起来，除以真正验收通过的任务数**。有时候深度休眠省了 30% 待机费，结果每次恢复拉镜像、重连服务多花 20 秒，反而把用户体验和总体完成率拖垮，那就得不偿失。

| 真实执行闭环 | 代码/浏览器/桌面沙箱与标准反馈 | 从空谈计划变成可验收的交付产物 | 任务完成率、有效反馈率、产物验收通过率 |
| 压缩重复准备 | 版本化模板、镜像缓存、AIO 共享工作区 | 缩短冷启动和跨工具倒腾文件的时间 | 端到端首次可用时延、重复准备占比 |
| 长任务断点续跑 | 会话映射、独立持久化工作区、恢复后巡检 | 重启或跨天再聊时接着已有进度往下干 | 恢复成功率、工作区与状态一致率 |
| 压低等待期开销 | 浅/深分层休眠、按需唤醒、过期快照清理 | 消除等人、等模型期间的算力空烧 | 活跃计算占比、单位成功任务总成本 |
| 支撑高并发探索 | 强隔离分支、写时复制分叉、预热池与限流 | 批量产出干净、可比对的评测与训练轨迹 | 有效轨迹吞吐、重置耗时、跨分支污染率 |

表 7-4　Sandbox 能力、实现机制与验证方式

**弹性容量和预热池也要防「瓶颈转移」**：预热池确实能抗住突发工具请求，但它只能提前把「与用户无关的通用底座」启动好；用户身份鉴权、私有工作区挂载、权限校验还得在分配那一刻现做。而且并发拉高之后，瓶颈经常瞬间从计算节点转移到共享存储 IOPS、出口带宽或控制面 API 限流上。因此平台必须给单实例并发、资源池上限设硬顶，容量打满就明确排队或拒绝；缩容时先摘新流量，等在途任务做到可恢复边界再下线——再次强调，**千万别单凭 CPU 低就乱杀实例**。

## 7.6 生产接入：隔离底座、三平面架构与选型路径

把沙箱真正接进公司生产平台时，架构可以按三平面清晰拆开，如图 7-6 所示：

![image](../../assets/imgs/chapter-07/image-006.png)

图 7-6　Sandbox 在三平面架构中的位置

- **控制面**：管身份认证、模板准入、租户配额、安全策略与生命周期规则；
- **执行面**：Harness 编排层推进任务循环，Agent Runtime 负责调起、等待、休眠、围栏接管与回收，Sandbox 承载实际命令与工具执行；
- **数据与资源面**：管镜像仓库、持久化工作区、快照、任务账本和最终交付的制品。

观测指标（事件、日志、轨迹、费用）贯穿三个平面，把用户一次任务到底用了哪个版本的模板、占了多久资源、调了什么外部系统全串起来。

### 隔离技术怎么选，才不会被营销词忽悠

- **普通容器**：镜像生态最好、启动最快，但默认共享宿主机内核；适合内部可信代码，跑不可信第三方代码风险高。
- **用户态内核（如 gVisor）**：在容器和宿主机内核之间加一层拦截翻译，大幅缩小内核攻击面；但系统调用有开销，部分冷门软件或特殊系统调用需要实测兼容性。
- **轻量虚拟机（如 Firecracker MicroVM）**：硬件级虚拟化，每个沙箱独立内核，隔离强度最高；需要配套虚拟网络、存储和镜像管理体系，运维复杂度更高。

提醒一句：**对外提供漂亮的 SDK 或者跑在 Kubernetes 上，本身完全不代表隔离有多强**；浏览器自带的进程沙箱也只能保浏览器自己，保不住同一容器里的其他目录和出口网络。所有多租户池必须做到：公共能力只读共享、任务私有目录严格隔离、短期凭证按任务按需注入、预热实例分配前零数据、回收重置前彻底洗净进程/挂载和网络规则，出口流量走受控代理。

### 两条接入路线的取舍

![image](../../assets/imgs/chapter-07/image-007.png)

如上图（图 7-7）所示，SDK/API 接入和 Kubernetes CRD 接入不是谁替代谁，背后完全可以复用同一套 Sandbox 能力底座（Agents、阿里云容器服务等都同时提供了这两种口子）：

## 7.7 落地与验收：拿五把硬尺子测过再上线

业界已经把沙箱用出了几种很成熟的模式：比如把带重型本地依赖的 MCP 工具包装成按需弹性的远程服务；像 Z.ai 那样围绕「写代码 → 起预览 → 改代码」搭全栈应用沙箱；像 MiniMax 那样靠分层休眠扛住海量长会话资源开销；或者像 Qwen 与百炼那样把批量快照分叉直接接进训练评测流水线。

但不管借鉴哪种模式，**落地顺序都是：先跑通单条完整任务链 → 再上状态复用与休眠 → 最后放大并发**。上线前切忌拿「空容器启动耗时」当业务 P95 指标，也切忌只测「新建任务成功」不测「故障恢复」。必须对照下面这张五场景验收清单，拿同一个真实项目逐项演练打勾：

| 必测故障 / 恢复场景 | 验收过关的硬标准 |
| --- | --- |
| 1. 执行中实例突然被杀 | 新实例能重新挂回持久化工作区、补齐依赖，从上次提交点继续往下跑，不从零重来 |
| 2. 工作区挂载失败或归属不符 | **必须硬阻断后续执行**，绝不拿着空目录或别人的目录继续跑、覆盖写 |
| 3. 旧实例失联后又「诈尸」回来 | 围栏令牌直接拒掉旧实例的写入；对已发出的外部写操作先查状态再决定补偿或人工介入 |
| 4. 等待期间任务被取消或打满配额 | 立刻停掉新动作，安全保存已完成部分和记录，干净回收计算与临时资源 |
| 5. 新版本模板上线后恢复老任务 | 老快照和老任务仍能用兼容环境恢复，权限、依赖版本和挂载路径不出岔子 |

表 7-6　长时任务的恢复与生命周期验证

尤其是第 5 条最容易翻车：很多团队发版升级镜像模板时只测了「新任务创建一切正常」，结果线上大批昨天休眠的老任务一唤醒全挂——因为旧快照里还是老版本依赖和快过期的挂载协议。任何涉及状态格式或目录结构升级的发布，都必须同时验证**新建链路**和**存量恢复链路**，确认老引用全迁移完了再下线旧配置。

## 7.8 本章小结

把 Agent 从聊天框里放出来干真活，执行环境这一关躲不过去：

- **Sandbox** 提供隔离、可编程的工作空间（代码、浏览器、桌面、AIO、MCP/Skill 依赖），把模型猜测变成可检验的运行反馈；
- **Runtime** 负责让环境跨过等待、休眠、驱逐和故障继续活下来——用独立工作区与状态外置扛住容器回收，用外部唤醒与恢复后巡检扛住断网断凭证，用执行代次与围栏令牌防住双写脑裂，用快照分叉配合外部数据隔离跑通并发评测；
- **落地评价标准只有一条**：别只看空容器冷启动有多少毫秒，要算从任务发起、故障恢复到产物验收通过的**全链路完成率、真实首响时延和单位成功任务总成本**。
