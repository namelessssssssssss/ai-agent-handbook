# AI 网关与统一流量治理综述

当团队只有一两个应用直接调大模型时，代码里写死个 SDK、配个 API Key 就能跑。可一旦模型多起来、团队多起来、MCP 工具和 Agent 各自上线，你会发现每个人都在重复干同一堆脏活——**并且全线失控**：

- **Key 满天飞**：每个项目配置里都塞着长期密钥，出了问题不知道是谁在调、哪条业务线在烧钱；
- **账单莫名其妙超支**：限流器写着「余额 100 才放行」，结果两笔并发 80 的请求同时通过检查，直接花掉 160；
- **重试把故障乘倍放大**：客户端 SDK 重试 3 次、网关又重试 3 次，一次失败往上游打出去 9 倍流量和 9 份账单；
- **HTTP 200 照样翻车**：SSE 流式响应刚开始就返回了 `200 OK`，中途流里吐出报错或者干脆断流，监控面板还一片绿；
- **工具接入等于裸奔**：MCP 清单里列了 50 个工具，模型随便挑着调；或者高风险退款操作在审批超时后，被系统自作聪明「自动降级成只读」或者糊里糊涂放过去。

**AI Gateway（AI 网关）** 就是为了把模型、工具和 Agent 的流量入口收口到同一道策略关卡上——管准入、管路由、管预算、管审计。但同样先把红线划清楚：**网关只管流量进出与调用记录，不管业务成功标准、Task 状态或断点恢复**，别指望往网关里塞几个插件就能替代业务系统本身。

本章主要以 **Higress**（基于 Envoy 数据面 + Wasm 插件 + Istio 控制面）为参考实现，对照模型代理、托管聚合服务等路线，并按 **MCP 2026-07-28** 规范与 Higress 基线提交（`f053bb08360d432a1226d4b61eb69871c74b9021`）核验关键能力。文中设计字段仅作架构说明，不直接充当可部署配置 Schema。

## 9.1 为什么传统 API 网关直接接 AI 会水土不服

### 9.1.1 AI 流量带来的四个新约束

API 网关和服务网格（mTLS、限流、认证）那套底座并没过时，但 AI 流量把四件原本简单的事全变复杂了：

| 流量特征 | 线上常见翻车点 | 网关必须补上的能力 |
| --- | --- | --- |
| 长流式输出（SSE） | HTTP 刚握手就回 `200`，流吐到一半才报限流/内容异常；首字节往往只是心跳包，不是首个有效字 | 把连接、首字节、首有效 Token（TTFT）、流空闲、总超时拆开记；能抓流内错误 |
| 大请求体与长上下文 | 动辄几 MB 的对话历史全量缓存在内存里，高并发一来数据面直接 OOM | 按路由控制内容缓冲上限、增量流式解析、报文大小限制 |
| 按 Token 与复合资源计费 | 进门前不知道这次生成到底吐多少 Token；并发请求同时过检查把余额打穿 | 区分速率限流、时间窗配额和严格原子预算，结算与对账分离 |
| 多轮交互与长程任务 | 把 KV Cache 缓存亲和当成了状态恢复，实例一重启任务直接失踪 | 传透可信任务/会话标识、分层观测，但把状态权威留给执行系统 |

特别提醒两个常被混为一谈的概念：第一，**SSE 不是天然的业务消息边界**——底层 TCP 一次读到的字节切片可能只有半个事件，也可能粘着好几个事件，首个包甚至只是心跳，所以计算 TTFT（首 Token 时延）不能偷懒拿 HTTP 首字节代替；第二，**KV Cache 前缀亲和只是性能优化**，命中率掉下来最多是首字变慢一点，绝对不能因为缓存没命中就把用户的业务 Task 给搞丢了。

### 9.1.2 三种可组合的治理语义（不是升级阶梯）

![image](../../assets/imgs/chapter-09/image-001.svg)

图 9-1　三种可组合的治理语义

按直接管辖的对象，AI Gateway 可以拆成 **LLM Gateway、MCP Gateway、Agent Gateway** 三种治理语义（图 9-1）。记住，这是按职责拆的**并列积木**，不是「先建 A、再升级到 B」的成熟度阶梯，企业可以按需要塞进同一个数据面，也可以独立部署，关键是**主体映射一致、调用记录能串起来、不要同一笔请求穿两个组件被算两次钱**：

| 治理语义 | 管谁 | 解决什么核心问题 | 绝对不越界的红线 |
| --- | --- | --- | --- |
| LLM Gateway | 模型调用与每一次实际重试 | 选模型/选端点、流控容灾、按 Token 计费与预算 | 不判断模型回答是否满足业务验收标准 |
| MCP Gateway | MCP 协议请求与工具调用 | 协议代理、资源目录对接、工具与参数级鉴权 | 不把「工具能被查到」当成「已授权或健康可用」 |
| Agent Gateway | Agent 入口与任务关联流量 | 身份映射、租户配额、路由亲和、并发与 Task 归因 | 不拥有业务 Task、State、Checkpoint 或恢复权威 |

用一个真实链路串起来看就明白了——比如「**客服 Agent 查订单并申请退款**」：
任务从 **Agent 入口** 进来，网关核验委托身份后按能力标签路由到拥有订单和退款工具的 Runtime → 模型推理经 **LLM Gateway** 完成路由和失败切换 → 查订单是只读操作，**MCP Gateway** 鉴权通过直接放行 → 到「申请退款」这种动钱的高风险工具时，网关挂起等待业务审批（不傻傻占着 HTTP 长连接） → 审批通过后，**重新核验身份、委托范围、参数摘要和预算预留**再真正放行调用 → 最终结果和用量回写任务账本。

### 9.1.3 网关在基础设施里的位置与生态口径

把周边组件职责对齐，才不会把网关做成臃肿的大泥球：

| 组件 | 核心职责 | 与 AI Gateway 的边界 |
| --- | --- | --- |
| API Gateway / Service Mesh | 入口路由、通用限流、mTLS 与服务身份 | 承载 AI 协议插件、提供底层服务间通信安全 |
| Registry（资产目录） | 管理端点、版本、声明能力的目录 | 网关控制面去查它，但目录本身不等于授权 |
| Harness / Orchestrator | 跑控制循环、拼上下文、派任务 | 通过网关调模型和工具，并透传任务关联 ID |
| Agent Runtime | 管任务生命周期、Checkpoint 与故障恢复 | 接路由过来的流量，按恢复契约续跑 |
| 业务应用 & 获授权 Verifier | 定义 Task 成功标准并最终判定 Outcome | 持有业务真相；网关只交回调用日志和用量事实 |

选型比较时一定要**盯紧具体版本和数据路径**：比如原 Envoy AI Gateway 项目已更名为 Agent Router，v1.0.0 于 2026 年 6 月 23 日正式 GA（产品标了 v1.0 也不代表所有控制面 API 都进了 v1）；Kong、APISIX、LiteLLM、Portkey、OpenRouter 各有定位。企业常见落法是**先统一收口凭证与模型入口 → 再补齐项目级用量归因和工具鉴权 → 最后才上路由实验**，每步都要拿「Key 是否不再散落客户端」「拒放是否有审计依据」来验收，而不是比谁装的插件多。如果怕 AI 长连接拖垮原有核心业务，可以**共享控制面身份策略，物理隔离两套数据面**。并且千万注意：网关多副本只能防单机宕机，一旦依赖了共享 Redis 或内容安全服务，每一条外部依赖故障分支都必须提前测透。

## 9.2 LLM Gateway：路由、防重试雪崩与严格预算

LLM Gateway 要在每次模型调用上同时端平三碗水：**选对模型/端点、别把重试放大成雪崩、把预算算准不透支**。

![image](../../assets/imgs/chapter-09/image-002.svg)

图 9-2　模型调用准入与预算结算

### 9.2.1 统一接口与路由：模型选择和端点选择分开

用 OpenAI 风格或 Anthropic 风格统一接入契约能省掉大量适配代码，但**各家在工具调用、多模态图片、推理思维链、缓存用量和停止原因上并不完全无损互通**。靠谱的网关应该明示支持的能力子集、对不支持的参数明确报错（别静默丢弃），同时在账本里记清适配器版本、真实厂商模型和请求别名，免得后面账目对不上。

路由决策也别混为一谈，得拆成**选模型**（静态灰度权重、成本感知路由、基于评估的语义路由）和**选推理端点**（同一模型背后多个 GPU 实例按队列、在途请求或 KV 前缀缓存挑选）：

- 看 **Gateway API Inference Extension** 生态时要分清版本：`InferencePool` 已有稳定 v1 API，但队列/KV Cache 感知由具体端点选择器（EPP）提供；到 v1.6.0 后完整 EPP 实现迁往了 `llm-d`。**API 稳定不等于所有调度算法都成熟开箱即用**。
- Higress 的 `ai-load-balancer` 会记录全局在途请求与前缀关联来优化选址，但**网关记录的「前缀可能命中缓存」只是提示信号**——真遇到后端缓存驱逐或实例重启时，必须允许平滑失配重选。

### 9.2.2 翻车重灾区一：多层重试叠加引发 9 倍雪崩

很多线上故障不是模型挂了，而是**重试机制把一次抖动放大成自我 DDOS**：客户端 SDK 配了失败重试 3 次，网关转发又配了重试 3 次，一次逻辑请求瞬间打出去 9 次上游调用（如果供应商内部还重投，倍数更高），延迟、并发、费用直接按乘积爆炸。

另外还要守住四条可靠性红线：
1. **先分错误类型再决定能不能重**：限流（429）看重置窗口换备用端点；鉴权错（401/403）直接停下来修凭证；**上下文超长（Context Overflow）绝不能由网关擅自截断历史去重发**，否则等于篡改任务输入，必须交回 Harness 决定压缩、换长窗模型还是报错。
2. **流吐出一半不能透明重放**：一旦响应流已经吐给客户端，中途断掉网关没法替客户端「时空倒流」。而且「还没收到 HTTP 响应体」绝不等于「上游没执行、没扣费」。
3. **跨层传递绝对截止时间与剩余重试额度**：别让客户端和网关各自按「相对超时 30 秒」各算各的，而要把<strong>绝对截止时间戳、剩余尝试额度、逻辑调用标识（call ID）和单次尝试标识（attempt ID）</strong>沿链路传下去，网关扣减额度用完了就直接报额度耗尽，同时确保切换备选模型前校验工具调用、结构化输出和数据合规地域是否兼容。
4. **分清五种超时和账单结算**：建连超时、首字节超时、TTFT、流空闲超时（警惕只发心跳不吐字绕过空闲超时！）、总截止时间各有分工。对需要主动要求返回用量的接口（如注入 `stream_options.include_usage`），如果流中断没拿到 usage，**绝不能记成 0 消耗**，必须标为估算或待对账状态。

### 9.2.3 翻车重灾区二：预检余额的并发竞态

看图 9-2 对比的两条路径：**「检查当前余额、调用完再扣减」根本保不住硬预算上限**。假如账户只剩 100 块，两个最坏可能花 80 块的并发请求同时进网关：两人都读到「100 ≥ 80，通过！」，跑完各自扣减后账单直接变成 160，预算击穿。

要真正锁死硬预算，准入时必须靠同一原子操作或事务完成这条不变量校验：

> **可用额度 = 已授权额度 − 已结算消耗 − 在途预留**；只有 **本次最大可能消耗 ≤ 可用额度** 才放行，并立即把这笔最大消耗锁进「在途预留」；调用结束拿到真实用量后幂等结算、退回多余预留；每一次重试都单独占一笔预留；如果流中断没拿到真实用量，**不能因超时直接退款，而要保留预留等对账**。

落实到参考基线上的具体产品边界：Higress 的 `ai-token-ratelimit`（时间窗计数）和 `ai-quota`（准入查余额、响应后扣减）在应对并发或严格资金硬顶时，都**不能单靠默认路径宣称严格并发预算**，且在 Redis 读失败/写失败上的分支表现并不完全统一（具体故障分支与设计字段见 9.8.2），上线前必须按所选版本把读错、写错、超时和对账分支逐项压测。

### 9.2.4 语义缓存与代理选型提醒

语义缓存确实能挡掉重复提问，但向量计算与检索也有成本，且**缓存键必须拼进租户、权限范围、模型版本、系统提示和知识库版本**——否则 A 部门的机密摘要可能被语义相似的 B 部门用户命中，造成严重越权！带有外部副作用的工具调用结果绝不能直接重放缓存。代理路线上，LiteLLM 胜在生态易集成，Portkey 偏托管控制，OpenRouter 做多模型聚合，Higress 长于贴合云原生入口治理——别按「托管还是自建」贴标签，拿目标协议字段、数据出域合规和故障表现去验真。

## 9.3 MCP Gateway：看得见工具，不代表能调、安全或可用

MCP（Model Context Protocol）用 JSON-RPC 把工具、资源和提示统一接进模型，但它只解决「怎么连」，没解决「谁能用、凭证放哪、调坏了怎么办」。

![image](../../assets/imgs/chapter-09/image-003.svg)

图 9-3　MCP 发现、授权与执行的分离

如图 9-3 所示，MCP Gateway 必须把<strong>目录发现（Registry）— 入口鉴权（Gateway）— 实际执行（MCP Server / 后端）</strong>拆得干干净净：

1. **看懂 MCP 版本演进带来的网关变化**：早期版本靠握手维护协议会话；2025-03-26 推出 Streamable HTTP，2025-11-25 试水 Tasks，到 **2026-07-28 基线**变为**无协议会话的逐请求元数据 + 按需发现（`server/discover`）**，并把 Tasks 挪成官方可选扩展（演进脉络详见第 12 章）。
2. **协议声明不等于身份证明**：Modern 协议里的逐请求元数据和 HTTP 镜像头只是告诉网关「这是什么方法、调哪个名字、客户端是什么版本」，**绝不能拿客户端自报的描述或名称当权限依据**；并且网关在最终转发前必须校验 HTTP 头部和 JSON 正文里的工具名完全一致，防住「头里报只读工具绕过鉴权、正文里塞高危工具执行」的走私攻击！
3. **只声明支持的桥接方向**：Higress 参考提交的 `mcp-server` 支持 **Modern 下游调用 Legacy 上游** 的单向桥接（把握手隔离在单次交换内，避免网关长持会话），但反向路径并未声明支持；`mcp-router` 按前缀路由工具，`McpBridge` 则是服务发现资源，各自职责别混叫。
4. **安全防线必须在 `tools/call` 再查一遍**：过滤 `tools/list` 清单只是帮模型少选错，真调用 `tools/call` 时必须拿「调用者权限 ∩ 工作负载权限 ∩ 任务委托 ∩ 资源端限制」重新鉴权。并且**只有当长期密钥不发给 Agent、出站网络锁死在网关、直连路径全封堵时，网关才算真正不可绕过**。
5. **REST 转 MCP 与参数安全**：把老 REST API 包装成 MCP 工具时，严防参数拼接变成 **SSRF（服务端请求伪造）** 漏洞（死锁目标主机与路径白名单）；数据库工具绝对别靠检查 SQL 字符串是不是 `SELECT` 开头来防注入，必须配合数据库只读账号和授权视图限制；管理员用自然语言写的策略（如「生产禁写」）必须先转成结构化规则、做冲突预览和回归验证再发布，别让模型在运行时临场解释权限。同时别忘了：**工具吐出来的返回值照样可能藏着提示注入**，网关内容检测只是纵深防御的一层，后端最小权限才是最终保命线。

## 9.4 Agent Gateway：入口路由、任务账本与 HiRoute 本地路由

把视角从单次模型/工具调用拉高到整个 Agent Task：一项任务可能跑好几个 Session、等审批挂起一天再恢复，中间还可能派出去子 Agent 干活。**Agent Gateway 负责把可信身份和任务标识带进每一跳流量，但记住：它不接管业务 Task 的状态定义、Checkpoint 或成功判定**（图 9-4）。

![image](../../assets/imgs/chapter-09/image-004.svg)

图 9-4　Task 账本与执行责任边界

### 9.4.1 协议口径与归因链路

- **协议别混为一谈**：**ACP**（面向 IDE/编辑器与本地编码 Agent 交互，截至核验日 v2 仍为 Draft）和 **A2A**（面向 Agent 间异步协作，v1.0.0 已正式发布）服务不同边界，成熟度也不同。
- **从 Session 账本升级到 Task 分层账本**：只按 Session 算钱，根本算不清一个跨会话恢复的长任务总共烧了多少。标准下钻账本链路为：
  **任务（Task）→ 会话（Session）→ 轮次（Turn）→ 模型/工具调用（Call）→ 实际尝试（Attempt）**。
  注意三件事：第一，入口收到客户端传来的任务 ID 头时必须校验租户归属，防别人伪造头把账算到你头上；第二，多 Agent 协作通过父子任务关联，别强行捏造归属；第三，**Trace 会有采样和断层，网关日志也只管进出流量（漏掉了沙箱时长等费用）——两者都只是账本数据源，不能直接冒充权威财务/Task 账本**。
- **区分「模型意图」和「实际工具执行」**：模型吐出一个 `tool_calls` JSON 只是表达「想调工具」，不代表工具真跑了、花了钱，日志事件必须严格分开。

### 9.4.2 租户隔离与并发槽位

认证身份（人/服务/Agent/Task）和财务归属（组织/团队/项目）是两条正交轴，一个 Agent 完全可以同时服务多个项目。限流并发也要跟执行侧对齐：**HTTP 请求 200 返回了，后台异步任务可能还在跑着占资源**，只有 Runtime 和调度账本才知道槽位放没放出来。

### 9.4.3 当入口来到开发者本机：HiRoute 的「模型路由 + 任务路由」

当场景从云端网关转到开发者电脑上的 Coding Agent，业界开始把「想」和「做」拆开：大模型负责读需求、定方案和验收，把有界的机械实现交给便宜模型，成本能差出一个数量级。开源项目 **HiRoute** 把这件事做成了可落地的本地路由机制（更详细的实验数据与实战请看本章第 2、3 篇）：

| 维度 | HiRoute 在本机网关层怎么管 |
| --- | --- |
| 多工作 Harness 调度 | 不局限在同一个壳里换模型，而是按任务直接调起 Codex、DeepSeek Harness 等不同工作 Agent，保留各自工具链与登录 |
| 计划（Plan）即契约 | 每份路由计划有稳定名字和用途说明，独立声明候选模型和思考档位；主 Agent 按用途显式提交任务，不靠黑盒自动猜测 |
| 任务生命周期治理 | 每个委派任务有独立身份，支持提交、等待、取结果、继续、取消与幂等去重，且锁定受理时的计划版本执行，不怕中途改配置跑偏 |

## 9.5 统一治理：身份不伪造、审批真挂起、超时不乱降级

如果模型、工具和 Agent 各自记各自的账号和权限，系统就会出现「模型入口被限了、换个 MCP 通道照样跑」的漏洞。转发路径上的统一治理，核心就盯着下面这张图里的闭环（图 9-5）：

![image](../../assets/imgs/chapter-09/image-005.svg)

图 9-5　有拒绝与异步审批的治理流程

对照图 9-5，工程上必须死卡四条底线：

1. **抹掉客户端伪造头**：像 Higress 里用 consumer 统一做策略主体抽象时，入口认证完第一件事就是**清空或覆写客户端自带的内部身份头**（例如 `x-mse-consumer`），绝不盲信外部传来的身份声明；跨代理传递要有清晰信任边界；默认不把下游凭证直接透传给上游工具，委托范围必须与调用者原有权限取交集。
2. **异步审批决不占死 HTTP 连接，批准后必须「重新准入」**：需要审批的高风险动作，网关直接拒绝执行转给业务审批服务持久化状态、放掉连接。等人在几小时后点「批准」回来，**绝对不能直接开闸放行**——因为这几小时里，调用者可能离职了、参数可能被篡改了、项目预算可能已经花光了！必须拿着绑定工具版本、参数摘要与时效的审批单，**重新走一遍身份、权限、参数摘要和预算预留校验**，全过才执行（全图只有一个真正执行节点）。
3. **审批超时/拒绝绝不自动降级为「只读执行」**：所有拒绝和超时全部终止执行并写审计，**不能因为超时没批就自作主张改成只读调用**，那会改变原本请求语义甚至泄露敏感数据。遇到外部写操作超时结果未知，老老实实交给业务查询或补偿，别盲目重发。
4. **Higress 管道顺序核验 & 财务对账**：组合多个 Wasm 插件时，别死背优先级数字当跨版本承诺，每次升级都得实测：鉴权与预算必须发生在转发前、用量必须在生命周期结束准确结算、内容日志绝对不能在脱敏前提前落盘。同时承认财务报表与准入实时账之间会有价格版本、缓存折扣和账期时延，留好对账规矩。DLP 检测失败时到底放行、拦截还是转人工，也要按风险预先定死，别故障现场拍脑袋。

## 9.6 控制面联动：Evaluation 绝对不能直接改生产配置

做了这么细的观测和评估，很自然的冲动是搞一套「自动闭环」：Evaluation 一发现某模型变慢或太贵，自动切路由、调配额。**但生产环境最怕这种无门禁的自动驾驶**。

![image](../../assets/imgs/chapter-09/image-006.svg)

图 9-6　评估经验证与授权进入生产

看图 9-6 里那条清晰的**红绿方向与权限墙**：

- **评估只能提提案，不能直写控制面**：正确的路径是 **观测发现问题 → Evaluation 产出候选建议 → 跑回归与安全验证 → 治理授权/发布门禁 → 控制面灰度下发（如 Higress 通过 Istio/xDS 的 LDS/RDS/CDS/EDS 和 CRD + OCI 制品热更新）**。哪怕是预授权的低风险自动调参，也必须锁死调节幅度、资源白名单、验证测试和自动回滚机制——千万别以为改个「缓存命中阈值」属于低风险，改歪了照样会导致跨租户串数据！
- **别把高基数 ID 塞进监控指标标签**：把模型、路由、错误码放进 Prometheus 指标标签聚合完全没问题；如果把每次请求的任务编号或会话编号塞进监控指标标签，高并发下直接把监控时序库打爆。这类高基数标识应该留在日志、事件流和 Trace 里，且采用 OpenTelemetry `gen_ai.*` 语义约定时要锁死版本（目前仍在 Development 阶段）。
- **区分「策略内在线微调」和「修改治理策略」**：比如 Higress `ai-load-balancer` 里的 AdaptiveScore，用 EWMA（指数加权移动平均）首包/总时延、在途请求和冷却信号实时挑更快的后端端点（Redis 挂了就退回本地评分）。这属于**已授权候选池内的在线自适应**，它绝对无权自己扩充新模型、突破数据地域红线或调高预算额度。
- **回滚不只是改回 YAML**：回滚入口策略很快，但之前已经跑出去的工具副作用、没结算的预算预留和还在跑的在途长任务，必须有对应的处理和跨集群版本确认机制。

## 9.7 本章小结

AI Gateway 的核心价值，是在模型、工具（MCP）和 Agent 三条流量入口上，用一致的身份、预算、审计与安全边界把混沌收住。落地的四个最实用判断：

1. **三层语义按需组合，别抢业务系统的饭碗**：网关负责准入、转发、预算护栏与调用记账，业务成功标准、Task State 和断点恢复权威永远归业务系统与 Runtime。
2. **真假护栏一眼分辨**：靠 HTTP 状态判流式成功、靠客户端网关各重试 3 次、靠「请求前查余额 + 结束后扣款」管并发预算，全都会在真实并发下穿孔；真正管用的是分阶段流式超时、跨层传递绝对截止时间与尝试预算、以及「最大消耗原子预留 + 幂等结算」。
3. **安全和审批守住最后一道物理门**：发现工具 ≠ 授权调用，批准审批 ≠ 直接放行（必须重新核验）；只有密钥收敛、出站网络锁死在网关，且绝不在超时后擅自降级执行，入口才真的不可绕过。
4. **控制面变更必须过门禁**：在线端点自适应可以在白名单内跑得飞快，但任何改写模型映射、权限、缓存边界和预算的优化，都必须经过验证、授权和可追踪灰度才能上生产。

## 9.8 本章实现说明

本节收录版本敏感的协议字段与参考实现细节，供工程对接时核验，部署前请以实际采用版本的制品为准（协议按 **MCP 2026-07-28**；插件行为核验基线为 Higress 提交 `f053bb08360d432a1226d4b61eb69871c74b9021`）。

### 9.8.1 MCP 逐请求元数据

Modern RPC 请求必须在 `params._meta` 中携带协议版本和客户端能力（能力对象可为空），客户端信息为推荐字段而非认证凭据。HTTP 传输同时要求头部镜像：

| 字段 | 要求与含义 |
| --- | --- |
| `io.modelcontextprotocol/protocolVersion` | 请求元数据必需字段，声明协议版本 |
| `io.modelcontextprotocol/clientCapabilities` | 请求元数据必需字段，允许为空对象 |
| `io.modelcontextprotocol/clientInfo` | 推荐提供客户端名称与版本（非认证凭据） |
| `MCP-Protocol-Version` | HTTP 请求头，须与正文协议版本一致 |
| `Mcp-Method` | HTTP 请求头，须与 JSON-RPC 方法一致 |
| `Mcp-Name` | 对 `tools/call`、`resources/read`、`prompts/get` 等具名请求必需，镜像对应工具名、资源 URI 或提示名 |

一次 Modern 工具调用请求头与报文示例（生产环境还需补齐独立认证与传输安全策略）：

```http
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: get_weather
Content-Type: application/json
Accept: application/json, text/event-stream
```
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {
        "name": "example-client",
        "version": "1.0.0"
      }
    },
    "name": "get_weather",
    "arguments": {"location": "Hangzhou"}
  }
}
```

网关须按对应方法校验镜像关系：既不能对无名称方法强制要求 `Mcp-Name`，也不能把所有名称都硬读成 `params.name`；请求头只用于轻量路由分类，最终执行前必须校验与正文完全一致。协议弃用窗口（通常核心规范功能从 Deprecated 到移除不少于 12 个月）不代表所有端点都必须无条件接受所有旧版本，具体支持版本集合及安全例外以服务声明为准。

### 9.8.2 Higress 预算插件的故障分支与严格预算设计要点

在参考提交中，`ai-token-ratelimit` 在相关读取错误路径上会允许请求继续；`ai-quota` 在异步读回错误、余额缺失或非正值时拒绝请求，但部分同步调用错误与扣减失败路径并未形成「任意 Redis 故障均可靠拒绝」的统一保证。因此不能简单贴一个「fail-open」或「fail-closed」标签了事，部署前必须对读失败、写失败、超时及恢复后对账逐条测试。

若要在业务侧或预算服务中补齐严格预算控制，策略模型至少需表达以下设计要素（注意：这是设计示意图，并非 Higress 原生插件字段，不能直接提交给 Higress 控制面）：

```yaml
budget_design:
  accounting_scope: organization / team / project
  subject_mapping: authenticated_subject
  admission_mode: reserve_worst_case_cost
  reservation_key: call_id / attempt_id
  settlement: idempotent_actual_usage
  unknown_usage: retain_reservation_and_reconcile
  retry: reserve_each_attempt
```
