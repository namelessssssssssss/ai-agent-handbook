# 智能路由：如何利用便宜模型提升智价比

最近几乎每隔几周就有新模型发布：价格只有旗舰模型的零头，可公开评测榜上的分数却已经咬得很紧。每次看到都忍不住心动，紧接着又会犯嘀咕：手头上真刀真枪在跑的 Agent 任务，真的敢放心交给它吗？

这段时间我在做一个开源项目 [HiRoute](https://github.com/higress-group/HiRoute)——一个跑在开发者本机的 Agent 智能路由器。这篇文章想聊聊做它的过程中，我对这个问题的几点一线观察：**Agent 的「智价比」到底怎么提，以及怎么在自己的日常工作里，用证据判断一个便宜模型靠不靠谱。** 文中的数据来自公开研究、我们自己的对照实验和真实研发会话，最后也会介绍这套思路在 HiRoute 里怎么落成产品机制。

## 智价比：便宜的模型越来越多，难的是怎么用好

先看一组硬数据。Epoch AI 是一家成立于 2022 年的独立非营利研究机构，专门用数据追踪 AI 的长期趋势，斯坦福《AI 指数报告》和 Our World in Data 都在引用它的数据。

它在《The plunging price of thought》报告里算过一笔账：2023 年以来，大模型达到同一能力水平的成本**平均每季度下降约 47%**，相当于每年跌到原来的十三分之一左右。按报告横向对比，这个降速是 DNA 测序的 4 倍、通用算力的 6 倍、锂电池的 18 倍。

![智能路由配图](../../assets/imgs/chapter-09/image-007.png)

*图 1：达到同一能力水平的成本每季度下降约 47%；在 GPQA Diamond 上答对 75%，每题成本不到 18 个月降了 725 倍*

报告里举了个很震撼的例子：在 GPQA Diamond 这套博士级物理、化学、生物选择题上答对 75%，2025 年 1 月每道题平均要花 0.3 美元左右；不到 18 个月后只要 0.0004 美元，降了 725 倍。它还发现一个规律：一项能力刚摸到最前沿门槛时降价最猛，平均每年降约 75 倍；成熟两年后降速才会放缓到每年约 4.7 倍。

大方向非常明确：今天只有昂贵旗舰模型才稳得住的活，过不了多久就会落进便宜得多的模型射程里。真正卡住团队的，早就不是「有没有便宜模型」，而是「**怎么在不把事情干砸的前提下用好它们**」。

这里要特别盯紧一个 Agent 场景下的口径：Epoch AI 算的不是 Token 单价，而是**答对一题的总成本**——因为便宜模型往往需要多绕几轮、多吐很多 Token 才能撞出正确答案。评估 Agent 更是如此：一轮任务动辄调几十次模型，便宜模型哪怕只在最关键的那一步拍歪了方向，后面的返工、排查甚至选错架构方案，烧掉的钱和时间早就把省下的那点单价亏出十倍去。

所以我更愿意用「**智价比**」这把尺子：**在同样的验收标准下，把一件事彻底办成总共花了多少钱。** 按这把尺子看，问题就不再是「全量换成哪个便宜模型」，而是「手头这件工作里，哪几步可以放心交给便宜模型」。

## 场景与难度：复杂场景里也藏着大量简单的活

现在最常见的做法是按场景粗暴分工：写代码配主力强模型，整理资料配便宜模型，再按场景调一下思考档位。大方向没错——不同场景对「什么是难题」的定义本来就不一样：写代码难在定位未知根因和做架构取舍；做调研难在从一堆杂乱资料里提炼出靠得住的结论。

但我们在真实研发会话里反复看到一个事实：**任务的难度是一步一步跳变的，绝不是一整个场景对应同一个固定值。** 复杂任务里塞满了枯燥机械的简单活，简单任务里也随时会冒出要命的暗礁。

HiRoute 仓库里记录过我们做的一次对照实验：做一次消息系统技术选型，前半段是调研 6 种候选技术、核验官方发布说明和文档，后半段是一份关键方案的决策文档。结果一目了然：

- **把资料搜集和整理交给便宜模型、关键方案拍板交给主力模型**：关键决策质量和全程用主力模型持平，**整单任务总成本直接降到后者的十二分之一左右**；
- **全程用便宜模型**：前期整理资料一点不差，但最关键的三次架构判断里直接出了两次严重错误。

你看，同样挂着「技术选型」四个字，80% 的耗时其实花在资料搬运和核对上，真正需要顶尖智力顶上去的只有那两三步拍板。如果整个场景全绑死强模型，钱全白白烧在整理文档上；反过来全切给便宜模型，又会在最致命的地方翻车。

因此，合理的分层方式是：**场景配置决定「备选池里放谁、最后按什么标准验收」，而这一步到底派谁上，必须到每一轮行动时现判。**

> 顺带提一个极关键的工程细节：**一轮之内别乱切模型**。Agent 在同一轮任务里会连续发出二三十次模型调用，前面一直靠上下文缓存省钱省时。如果一轮中间来回换模型，缓存直接失效重算。我们的做法是只在收到新用户消息、或者上下文压缩重建的边界重新做路由选择，一轮之内锁死同一个模型。实测一段连续发了 21 次请求的会话里，全留在一个模型上缓存命中率接近九成；就算下一轮真的换了模型，也只有切换后第一笔请求会撞一次缓存未命中。

## 模型能力：通用榜单只能做海选初筛

刚才那个实验还戳破了另一个执念：选模型不能只盯着公开排行榜看。

榜单适合拿来做海选——先圈出哪几个新模型值得拉进备选池。但排行榜分数回答不了最核心的问题：**「它在我的业务代码库和私有规范里，到底行不行？」**

Scale AI 发布的 SWE-Bench Pro 就是个血淋淋的旁证。为了防模型在预训练时「背过开源代码原题」，它的公开题专门挑强 copyleft 协议仓库，另外专门从创业公司拉了 18 个从未公开的私有代码库出题。测试结果一出来很有意思：在传统 SWE-bench Verified 上能解掉七成以上问题的头部模型，到了 SWE-Bench Pro 公开题上直接跌到 23% 左右；换到那 18 个没见过世面的创业公司私有库上，最高分继续掉到 17.8%。

当然这里面有题目本身变难的因素，但**公开题和私有库是用同一套方法出的题**，后半截从 23% 掉到 17.8% 的落差已经够说明问题：一碰到真实世界没见过的私域代码和隐性约束，模型表现就是会打折——而你每天在改的那摊业务代码，对模型来说就是这样的盲区。

新模型每隔几周就发一版，研发团队不可能每来一个就停工攒一套黄金测试集。我的思路是**在日常工作流里「边用边评」**：初期只把容错高、边界清楚的简单步骤交给新模型，每步跑完看结果，一旦翻车立刻由主力模型接盘，等实打实攒够了通过率证据，再一步步往外放手。

判断「刚才这一步干得行不行」，其实最直接的裁判就在用户的下一句回复里。用户明确打回、指出哪错了，就是实打实的扣分证据；用户顺着往下提下一个需求，或者沉默没反对，就说明这一步大概率过关了。

拿 HiRoute 自己的一段真实会话来看（配置了一个经济模型组和一个主力模型组，用户连续提了五个需求）：

![智能路由配图](../../assets/imgs/chapter-09/image-008.png)

*图 2：基于 HiRoute 真实会话观测的路由时间线（已隐去模型名称；「常规」即经济模型组）*

1. **补测试与讨论设计取舍**：这两步不够简单，直接交给主力模型稳稳拿下；
2. **给运维同事写使用说明**：边界清楚、足够简单，路由给经济模型去写；
3. **用户反馈翻车**：「读起来像功能介绍」，上一轮胜任度评分只有 0.32，而且下一轮改写直接依赖这步的问题，HiRoute 触发保护立刻切回主力模型接管重写；
4. **验证过关、回归常规**：重写版本评分拉回到 0.83，问题解决了，下一步导出数据又放心切回经济模型。

单步评分难免偶尔看走眼（毕竟打分的决策模型也会有波动），所以调大或调小「放手比例」绝不能凭一两次体感，必须看统计窗口。我们目前用的升降级门禁规则如下：

- **建议多放手**：自上次调整后至少攒够 30 个已评分步骤（且来自至少 3 个不同会话），已评分步骤占比超过六成，且其中 **85% 以上达到胜任线**；
- **建议收回权限**：至少 30 个已评分步骤里，达标率跌破 **70%**。

![智能路由配图](../../assets/imgs/chapter-09/image-009.png)

*图 3：HiRoute 的模型表现报告——每条规则的实测值与门槛并排列出，并支持按历史记录回放调整效果*

这里故意把「**放手**」的门槛设得比「**收回**」高得多：偶尔蒙对几次不代表稳了，但只要苗头不对、连续出岔子，就必须麻利地把权限收回来。而且每次动阈值前，先拿自己最近的历史会话完整回放一遍，看清楚「调完之后过去哪几步会换模型」，心中有数再点生效。

## 三个问题：让模型只负责看现象，让程序按阈值做决定

前面说的判断每一轮都要跑一次。最直觉的懒办法，是把上下文、历史表现和路由规则打包全塞给一个决策模型，直接问它：「这一步该选主力还是经济？」

我们真这么干过，结果极不稳定——让一个轻量模型同时权衡任务难度、历史得分、上轮坑填没填上、策略怎么规定的，任何一项稍微想歪一点，选出来的组就错了。

后来我们彻底改了思路：**把「做选择」拆成三个相互独立的原子问题，一次请求里让模型各自作答，最后选谁交给确定性程序算阈值**：

![智能路由配图](../../assets/imgs/chapter-09/image-010.png)

*图 4：把复合路由决策拆成三个独立问题*

1. **上一步做得怎么样？** 只给客观胜任度评分（0 到 1）；
2. **接下来这一步有多难？** 只给简单概率判断；
3. **上一步留下的坑会不会拖累这一步？** 只判断已知未解决的错误是否仍然适用，不去瞎猜下一步能不能成功。

这么一拆，**调整对经济模型的「信任度」时，改的只是程序里的判定阈值，不用去来回魔改决策 Prompt**。

在 HiRoute 仓库里我们公开了对应的量化验证论文、中英文数据集、原始模型响应和离线回放工具。对照实验里，让两个不同决策模型读完全相同的上下文和路由策略，一组直接选模型组，另一组回答这三个问题由程序组合判定，在「工程」和「数学状态依赖」两个场景下对比准确率：

![智能路由配图](../../assets/imgs/chapter-09/image-011.png)

*图 5：拆成三个问题后，两类决策模型在工程和数学两个场景的选组准确率都明显提高*

- **工程场景**：决策模型 A 从 **67.31%** 飙升到 **96.15%**，决策模型 B 从 **50.00%** 提升到 **91.35%**；
- **数学依赖状态场景**：决策模型 A 从 **54.86%** 拉满到 **100%**，决策模型 B 从 **65.97%** 提升到 **88.89%**。

这组实验里还有一个特别扎眼的细节：**直接让两个模型选组时，它们俩犯错的方向竟然截然相反**！

在数学场景里，A 属于「盲目乐观派」——24 条该切主力保护的记录里只对了 6 条，该护的时候没护住；B 属于「过度谨慎派」——16 条本来可以放回经济模型的记录只对了 2 条，全死死锁在主力模型上。**而把问题拆成三问以后，两边跑偏的毛病同时被压平了**：A 的 24 条保护和 16 条解除全对（100%）；B 的解除从 2 条跃升到 14 条，保护也稳稳守在 22/24。

这印证了我们的核心判断：**拆三问不是因为某个模型突然变聪明了，而是把人都会想拧巴的复合权衡拆开，消除模型自带的性格偏差**。成本和延时也完全兜得住：按其中一款决策模型计价，**每跑一千次「三问决策」只需约 0.085 美元，单次中位耗时半秒到一秒**，每一轮用户交互触发一次完全无感。

*图 6：多份路由计划、System One 三个问题、模型表现报告与新模型试用*

- **低风险试新模型**：首页「新模型」选好想试的候选和手里用顺手的主力模型即可试跑；切换设置后，Agent 端配置的模型名保持不变，零侵入。

## 延伸：从「选模型」进一步走向 Super Agent 式「选执行者」

如果再往前迈一步：写代码习惯用 Codex CLI / Qoder CLI，查资料喜欢用轻量快速的 Pi，难道每次都要自己切窗口、手动搬运上下文吗？HiRoute 把这套思路做成了**任务路由（Task Routing）**：每份路由计划不但能绑定经济/主力模型，还能直接绑定对应的执行 Agent（Worker Harness）。

DeepSeek 公开的 Super Agent 研究原型把系统拆成常驻的 **Router**（保持对话、拆活分派）和独立执行的 **Worker**（在隔离上下文里埋头干活）。用 **Hermes + HiRoute** 在本机就能直接搭出完全同构的协作流：

- **主对话只管分派**：Hermes、OpenCode 或者任何能调命令行（如 OpenClaw）的个人 Agent，都可以直接按用途挑一份 HiRoute 计划，把任务和验收条件扔出去；
- **后台静默给 Worker 跑**：`hiroute worker exec --no-wait` 接单立刻返回，主会话不用傻等、还能同时派好几条支线并行查；
- **跑完自动叫醒交卷**：以 Hermes 为例，后台进程配合 `notify_on_complete` 等到 Worker 彻底交卷再唤醒主会话，把结果摘要干干净净带回对话里。

```sh
# 把资料搜集交给绑定 Pi 的计划，提交后立即返回
hiroute worker exec --plan <PLAN_ID> --cwd /work/mq-research --no-wait \
  -- "搜集三种消息队列的官方文档和发布说明，整理成对比表"

# 随时查看进度；任务结束后取回结果
hiroute worker status --run <RUN_ID>
hiroute worker result --run <RUN_ID>
```

这样一来，**场景层解决「找哪个专业 Agent 干」、轮次层解决「这一轮派主力还是经济模型」**，两层路由顺畅咬合，都在同一份计划里版本化管起来（更多实战用法见社区文章：[https://hiroute.ai/news/hermes-super-agent/](https://hiroute.ai/news/hermes-super-agent/)）。

## 写在最后

便宜又好用的模型只会一波接一波地往外冒，这件事基本没有悬念；真正没有标准答案的，是它们在**你自己的那摊代码和业务规矩里**到底稳不稳。榜单给不了你这个答案，唯一靠谱的办法就是在自己日常任务里带好验收尺子、一边跑一边攒证据。
