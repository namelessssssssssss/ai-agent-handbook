# 第 08 章　Agent 状态存储与语义资产

第 07 章解决了执行环境能不能活下来、断了怎么接回来的问题；这一章进一步回答：**让任务接得回来、成果交得出去、经验越用越准的那些数据，到底该怎么存？**

很多团队一上来就把所有东西一股脑塞进「MySQL 一张大表 + 一个向量库 + 容器本地磁盘」，结果上线不到两周就会遇到四类典型翻车：

1. **容器重启重跑，把审批单连发了三次**：任务进度和工具调用记录散在内存或普通日志里，实例重启后系统搞不清「发审批」到底执行过没有，干脆重跑一遍，直接造成重复操作。
2. **文件覆盖找不到历史版本**：数据分析脚本、中间报表和最终代码全扔在容器 `/tmp` 目录，多轮修改或子 Agent 并行一写就互相覆盖，想回滚到前一版根本找不到。
3. **过期记忆和跨区文档把决策带偏**：寒暄调试全塞进记忆库，三个月前的旧偏好盖过了最新指令；知识库切片把标题上下文切丢了，把「海外退货政策」直接套到了国内订单上。
4. **删了源文档，向量库和缓存还在吐答案**：权限改了或文件删了，下游派生索引没跟着失效，甚至检索时先跨租户捞出结果再过滤，埋下严重的数据越权隐患。

根本原因在于：Agent 产生和消费的数据不是铁板一块，**运行时事实、工作区产物、长期记忆、外部知识、业务本体**这几类东西，对一致性、版本和权限的要求完全不同，硬塞进同一套存储语义里必然互相打架。

本章就按 **总览分层 → 运行时与工作区底座 → 记忆、知识与本体语义层 → 多租户与工程选型** 的顺序，结合 **Lakebase** 的参考架构，把每一类存储的坑点、机制和取舍讲透。

## 8.1 先画分层地图：五类状态，各用各的规矩

### 8.1.1 为什么传统应用的数据分法不够用了

传统业务系统的数据分工很固定：订单和账户进关系库，附件进对象存储，离线分析走数仓。数据是谁写的、归谁读、生命周期多长，上线前就定死了。

Agent 不一样。拿「分析客户流失原因并出挽留方案」来说：Agent 要拆步骤、查客户档案和历史工单、写脚本跑数出图、根据结果改方案、挂起等人工拍板，最后再沉淀经验。**每推进一步既在消费历史状态，又在生成新的状态**，而且这些状态的读者和消费方换成了随时可能扩缩容、跨节点迁移甚至多个并行的 Agent。

状态外置之后，存储层不再只是被动存盘，而要接住三件事：**任务中断后从哪接（运行时状态）、做出来的东西怎么留和改（工作区与产物）、以前学到的和公司的规则怎么安全复用（记忆、知识与本体）**。

### 8.1.2 不同状态对象，一致性要求天差地别

直接把五大类数据对象的核心差异拉通对比，就能看清为什么不能一锅炖：

| 数据对象 | 典型内容 | 核心痛点与正确性红线 | 匹配的底层能力 |
| --- | --- | --- | --- |
| 运行时状态 | Event Log、Checkpoint、进度、租约、状态指针 | 绝不能丢顺序、绝不能双写覆盖，否则重启就会重复下单或任务卡死 | 事务型/强一致状态存储 |
| 工作区与产物 | 代码、文件、表格、快照、分支、Artifact | 要能低成本分叉回滚，正式成果一旦交付必须有稳定引用且不可原地篡改 | 共享文件存储 + COW 快照 + 对象存储 |
| 长期记忆 | 经过筛选的偏好、行为经验、业务事实、多模态记录 | 寒暄别乱记、冲突要消解、用户要求删必须全链路删干净（含索引缓存） | 结构化存储 + 向量/BM25/图混合索引 |
| RAG 与知识库 | 企业文档切片、表格图文解析、向量与图谱索引 | 切片别丢上下文、权限必须在检索前过滤、每条答案必须能溯源到版本段落 | 文档解析管线 + 湖库冷热分层 + 混合检索 |
| 业务语义与治理 | 本体（对象/关系/动作/规则）、租户边界、血缘、审计 | 语义定义和执行/授权分离；不能把大模型猜出来的推断直接写成公司规则 | 图存储 + 统一元数据目录与策略引擎 |

## 8.2 运行时状态存储：让任务跨故障接续，且不重复动作

### 8.2.1 只存对话历史救不了长任务

一个真正干活的 Agent 动辄跑几十分钟甚至跨天，中间要经历规划、调工具、等回调、等审批。如果实例重启后只保存了聊天记录文本，新实例根本不知道「第 3 步调接口到底发出去了没有、工作区切到哪个快照了、现在谁有写入权」。

运行时状态存储真正要兜住的，是**可恢复的任务事实**：当前处于哪个阶段、哪些步骤已经提交、已调用的外部动作和结果是什么、挂起在等什么条件，以及对应的工作区和产物指针。

### 8.2.2 Event Log：防乱序、防漏记，但别搞全局串行锁死并发

**Event Log（只追加事件日志）** 是还原任务真相的流水账：规划生成、抢到租约、发起工具调用、收到返回、等待确认、提交结果，每跨过一个有业务意义的节点就追加一条不可改写的事件。

线上最容易踩的三个坑和解法：

- **坑一：动作做了，事件没记上（或者记反了）**。比如审批请求已经发出去了，结果写 Event Log 前进程崩了，恢复时重跑就会再发一次审批。解法是**业务状态变更与事件写入必须在同一个本地事务里提交，或走可靠的 Outbox 模式并用事件标识去重**。千万别拿调试用的诊断日志或大模型原始文本输出凑合当 Event Log。
- **坑二：一提「强一致」就把整个平台锁成单队列**。顺序强一致的边界应该是**单个任务、会话或业务对象**，彼此独立的任务完全应该并发写各自的分片日志，不能互相卡脖子。
- **坑三：日志无限膨胀把盘撑爆**。近期活跃任务保留细粒度事件，跑完的稳定任务定期合并成可验证的快照，再按合规要求设保留期归档。

### 8.2.3 Checkpoint：增量落盘，卡在关键边界

Task 跑了几百步之后，每次崩溃都从第 1 条 Event Log 重新回放显然太慢。**Checkpoint** 就是定期把「此时此刻的可信运行态」拍成快照——注意，它不只是拷贝模型对话上下文，必须同时打包：**当前阶段、已完成/未完成步骤、工具调用结果引用、关联的工作区快照版本、子任务状态、等待条件和状态版本号**。

没必要每次局部变动都拷一遍全量快照（查询类几秒钟的小任务甚至不值得打 Checkpoint）。工程上通常两手配合：

1. **卡在关键边界打点**：外部写操作发起前后、耗时计算刚完成、人工审批前后、工作区发生大改后、准备交接给其他 Agent 前。
2. **全量基线 + 增量 Delta**：每次只把变更字段、新增子任务状态或新工作区指针按版本号写成增量，恢复时用「最近一次完整 Checkpoint + 增量 + 后续少量 Event Log」组合还原，在成本、速度和恢复精度（RPO/RTO）间拿捏平衡。

### 8.2.4 Durable Execution：租约、围栏与「不承诺天然恰好一次」

把执行实例当成随时可杀可换的计算工位，让任务事实靠外部存储活着，这就是 **Durable Execution（持久化执行）**。但实际接管时必须死守两个底线：

- **先抢接力棒（租约 + 围栏），再写状态**：旧实例失联不代表它真死了，万一它卡完 GC 醒过来继续写，就会出现双写脑裂。恢复时新实例先拿带更高版本号的执行租约（类似接力棒），写存储时必须带上**围栏标识（Fencing Token）**，让存储端直接拒绝旧实例的迟到写入。
- **把 Checkpoint 和状态指针串起来**：状态指针就像任务总目录，把任务、事件序号、最新 Checkpoint、工作区快照和产物引用绑到一起，新实例一读指针就知道从哪接。
- **认清现实：Durable Execution 不等于外部操作自动「恰好一次」**。一旦涉及发消息、扣款、提交审批、写外部库，必须把「调用意图 + 幂等键 + 外部返回结果」一并记进状态，不能只含糊记一句「正在执行」；恢复时先拿着幂等键去对端查结果，再决定继续、跳过还是走补偿。

高并发脉冲来袭时（比如整点定时批量任务或超时后集中恢复），计算实例和存储层分开扩容，近期任务放低延迟热存储，已完结的按需下沉冷归档，系统才不会被历史任务拖垮。

## 8.3 工作区与沙箱快照：把临时目录升级为任务资产空间

运行时状态记录「走到哪一步」，工作区与产物记录「做出了什么东西」。只要任务还会产代码、报表、图表和附件，工作区就不能是容器里随用随删的 `/tmp` 临时目录——容器一回收、切换分支或多人接手，本地文件就全失联了。

![image](../../assets/imgs/chapter-08/image-002.png)

图 8-2　Agent Workspace 总体架构

图 8-2 展示了 Lakebase 参考架构里工作区的组合逻辑：**计算实例只是工作区的一个临时挂载点，工作区本身有独立的身份、版本历史、权限和生命周期**。

### 8.3.1 多形态存储拼成统一入口

代码配置需要高频小文件读写和完整目录树，适合共享文件存储；大模型产物、数据集和音视频体积大且稳定，适合对象存储；高频热点文件贴着算力节点放一层近端加速缓存。但对 Agent 来说，它不需要管文件到底在哪个后端，统一通过「当前工作区 / 某次快照 / 某个分支 / 某份产物」的逻辑视图访问就行。

### 8.3.2 三层结构 + Copy-on-Write（COW）：零复制成本随便试错

怎么做到秒级启动、多分支并行试错还不互相污染？靠**三层挂载 + 写时复制**：

1. **基础层（只读共享）**：操作系统、语言依赖、公共模板，由平台统一维护，Agent 改不动，所有任务秒级复用；
2. **共享层（只读/受控共享）**：同团队或跨任务复用的项目数据与公共依赖；
3. **可写层（任务私有）**：当前任务独占的增量修改，跑坏了直接扔，绝不影响其他租户和基础镜像。

当 Agent 想同时试三种改造方案时，**Copy-on-Write（COW）快照**不需要把整份工作区拷贝三遍，未改的数据块继续共享，只有改写的新内容才分配新块。而且**每次打运行时 Checkpoint 时，必须把当时的工作区快照版本号一并记进去**——不然任务进度回滚到第 3 步，磁盘文件却还是第 6 步改残的样子，状态和环境直接脱节。当然还是要提醒一句：**工作区回滚撤销不了已经发出去的外部邮件或数据库修改**。

### 8.3.3 并发围栏与不可变 Artifact Store

同样要注意工作区的并发覆盖问题：**光在任务状态表里改了租约归属，挡不住手里还攥着旧文件句柄的僵尸进程继续改盘**！写入层必须单独做围栏校验——要么在写入接口验代次、要么强制独占挂载并撤销旧端授权、要么让每个实例写自己的私有分支，只允许当前租约持有者合并发布。

多 Agent 协作时也别让两个 Agent 对着同一个目录直接互相写，更稳妥的做法是：A 在自己分支跑完后，把正式成果推进 **Artifact Store（不可变产物库）**，B 通过稳定版本号去读。

**Artifact Store 与临时目录的本质区别是「不可原地篡改 + 完整血缘」**：一份报告、一个补丁一旦定版发布成 Artifact，以后再改必须生成 V2、V3 新版本，并自动带上生成任务、来源输入、版本号、审批状态和保留期限。这样下游永远不会读错版本，中间垃圾文件也能在任务结束时按策略自动清理，互不耽误。规模化之后配合冷热分层和独立元数据索引，即使存了百万级工作区和产物，检索审计照样跑得动。

## 8.4 长期记忆：别把所有聊天流水账都当成记忆

会话一关，用户下次来一句「按上次那个口径出」，Agent 如果全忘了就很蠢；但如果把每次废话、临时调试指令、过时要求全原封不动塞进向量库，用不了两个月召回率就会被垃圾信息彻底淹没。

![c991893210c74d4ba4ce6995b47d02e1.png](../../assets/imgs/chapter-08/image-003.png)

图 8-3　长期记忆的分层组织与混合召回

### 8.4.1 用两个正交维度管记忆，别混为一谈

图 8-3 给出的记忆组织法非常清晰，把「**从哪来**」和「**稳不稳**」拆成两个独立维度：

- **来源维度**：① 用户显式表达（偏好、纠错、明确要求）；② Agent 行为归纳（走通的排查路径、工具搭配规律）；③ 外部业务事实（订单结果、审批结论等由业务系统同步过来的事实）。
- **稳定性维度**：① **人设与身份层（Persona）**——注意，这不是 Agent 自己从聊天里悟出来的经验，而是开发/治理方显式配置并受版本控制的规则基底；② **画像层**——按周或按月变的长期偏好与角色习惯；③ **事件偏好层**——特定任务当下才生效的易变细节。

高频用的记忆进向量索引 + 热缓存，低频老记录下沉低成本持久存储。

### 8.4.2 写前先筛、多路召回、真删干净

1. **写入管线：宁缺毋滥**。先从对话和行为日志里抽取对未来有预测价值的信号（过滤寒暄、一次性查询），再做语义去重与合并（多次独立印证才提高可信度）；遇到新旧冲突，结合时效和来源权威度决定是覆盖还是挂起待确认——比如用户提过两次「少放辣」，只能记成候选饮食偏好，不能武断推成所有餐食规则。
2. **混合召回 + 慎用时间衰减**：光靠向量相似度抓不住专有名词，因此通常用**语义向量 + BM25 关键词 + 实体关系**三路一起捞，经 Rerank 精排再按时间衰减和类别过滤。但有两个常见误区：**第一，长期有效的高优约束不能因为好久没被调用就被时间衰减挤没了；第二，被调用次数多不代表它是对的**，还得看来源核验。
3. **遗忘、彻底删除与多模态**：后台趁空闲做增量合并和摘要压缩（压缩后必须保留原始引用）。**最关键的合规红线：用户要求删除某条记忆时，必须同步把原始记录、摘要、向量索引和缓存全删干净，并且防止后面重建索引时又把备份复活出来！** 对截图、语音备忘、操作视频等多模态记忆，同样提取语义特征建统一索引，返回时保留原资源引用方便核对。
4. **怎么验收记忆服务**：光说「日活多少、延迟多少毫秒」是自欺欺人。规模化验收必须同时摊开：活跃用户数、记忆条目总量、查询并发、召回准确率、P95/P99 时延，以及**用户纠错、撤回权限、索引滞后、节点重启恢复后，回答有没有立刻跟着改对**。

## 8.5 RAG 与知识库：找得到片段，更要防断章取义

记忆是 Agent 自己「经历」攒出来的，知识库则是从企业文档、手册、合同、Wiki 外部「引入」的权威资料，由知识管理员维护。**两边有一个共同铁律：不是存进去了就自动变成真理**，都必须保留来源、版本，并在检索后核对适用条件。

![image](../../assets/imgs/chapter-08/image-004.png)

图 8-4　RAG 与 GraphRAG 的双轨知识检索架构

对照图 8-4，生产级知识引擎比「直接切 500 字扔向量库」多了四道关键卡口：

1. **深度文档解析与智能切片**：合同、研报、带表头的复杂表格如果傻瓜式硬切，很容易把「海外业务专用」的大标题切在上一块、把具体退货规则切在下一块，Agent 搜到后直接把海外规则套用到国内订单！解析必须保住标题层级、表格结构和图文对应关系，切片时把父级标题上下文一并带上。
2. **变更检测与带水位的增量更新**：企业文档天天在改，全量重建太慢太贵。平台应做变更检测只重算改动部分，记录源版本、解析版本和索引水位——**必须等新索引构建并校验达标后再切换查询入口**，不能搜出一半新一半旧的残次品。
3. **混合检索 + GraphRAG + DataProbe 三剑客**：
   - 常规问题走**向量 + 全文关键词 + 元数据过滤（时间/部门/密级）**；
   - 遇到股权穿透、供应链上下游、跨法规条款审查这种答案散落在十份文件关联关系里的问题，按经过验证的路由规则走 **GraphRAG** 图谱遍历；
   - 遇到查精确数字或实时业务明细（非结构化文档里没有），通过 **DataProbe** 把自然语言转成受控查询去查关系库——**硬约束：DataProbe 只能用只读账号，且表和字段范围死死锁在授权 Schema 内**。
   - 多路结果汇入统一 Rerank 排序，输出时必须带上可点击核查的**文档、段落与版本溯源**。
4. **检索前权限过滤与湖库冷热分层**：权限过滤必须在召回之前就嵌入索引空间和过滤条件，不能等召回出来再剔除，防模型或中间链条泄漏越权信息。百万级文档不可能全塞进昂贵内存，热点进内存/SSD，冷知识下沉低成本对象/数据湖存储，按访问透明回温（湖库一体）。

## 8.6 本体（Ontology）：别盲目上马，用对地方才值钱

RAG 能帮你搜出一段「客户订单已逾期」，但它天然回答不了：「这个客户还买过哪几款高风险产品、受哪条风控规则管、当前谁有权限拍板放行」。如果公司大量需求卡在跨对象关系、业务规则和严格多跳推理上，就轮到**本体**（Ontology）出场了。

![image](../../assets/imgs/chapter-08/image-005.png)

图 8-5　本体的三层语义建模与可解释推理

### 8.6.1 四要素、三层次与「语义/执行/授权」解耦

看图 8-5，Lakebase 的本体建模把业务世界拆成四个要素——**对象（是什么）、关系（有什么关联）、动作（能做什么）、规则（遵循什么红线）**，按自上而下三层组织：

- **语义层**：管对象、属性和关联关系；
- **数据流转层**：管动作触发条件与实时数据同步；
- **智能决策层**：管业务专家沉淀的规则、策略与 Agent 绑定关系。

**最关键的架构防线是三权分立**：本体只管「语义定义」；动作真要跑起来，生命周期交给 **Runtime** 执行；谁能调、能改什么，由**治理方**做授权决定。绝对不能把运行代码或硬编码权限揉进本体模型里。同时，**实例数据更新（订单状态变了）和 Schema/规则变更（风控口径改了）走两条完全不同的流水线**，前者看同步水位校验防漂移，后者必须走版本管理与影响面评估。

### 8.6.2 确定性规则 + LLM 协同，记住「绝不让模型直写规则」

图谱规则遍历解决「确定性骨架」，LLM 负责在结构化上下文里处理边缘例外。**但上了本体不代表结果就天然正确**：确定性规则取决于规则本身和输入数据干不干净，LLM 的推断同样必须校验，并把「走了哪条关系、命中哪条规则、参考了哪份上下文」作为可审查的推理路径一起吐出来。在金融（客户—持仓—风险等级）和制造（零部件—供应商—产线—成品）这类严肃行业里，这条可解释链路比回答本身更重要。

在整套语义层里，**本体是骨架、知识是依据、记忆是经历**：本体给文档切片定坐标，知识让一条「上次交付晚了」的记忆对应到具体订单与合同规则，海量记忆和工单反过来又能提示维护者「这里冒出了新概念，本体是不是漏建模了」。**但这是一条受控反馈环——交互中挖出的新规律只能作为候选建议提交审阅，绝不能让大模型直接把自己的猜测改写成企业本体规则！**

**最后说一句大实话**：本体建模和维护成本非常高。如果业务现在只需要搜几十份操作手册、回答常规 FAQ，用好基础 RAG 就够了，千万别为了架构图好看强行上本体；只有当核心实体身份、复杂关系约束和多跳规则推理成为每天都要用的刚需时，再把这笔成本投入进去。

## 8.7 平台化治理与工程选型：收口到统一契约

当几十个 Agent 同时在线服务多个部门和客户，存储层要回答的就不只是「能不能存下来」，而是隔离、一致性、血缘、成本、选型与容灾六个硬问题。

### 8.7.1 多租户隔离：必须做「检索前过滤」

隔离必须贯通 **组织 → 工作空间 → Agent → 用户 → Task → 运行实例** 这 6 级边界，按敏感度组合物理隔离（强监管核心客户独享存储池）、逻辑隔离（独立库/Schema/命名空间）和行级隔离（共享库按租户与标签控制）。

**极易踩穿的一条红线**：做向量和图谱检索时，**必须把租户和权限条件塞进检索之前（Pre-filtering）**！先全局召回 Top-50 再在应用层按权限过滤掉 45 条，不仅直接把无权数据暴露进了候选和重排上下文，还极易出现「有权限的 5 条根本没进 Top-50，导致返回空结果」的诡异 Bug。

### 8.7.2 一致性设计：权威事实 vs 派生视图

Agent 跑一次会同时改 Event Log、Checkpoint、文件、记忆、向量索引和图谱。**千万别幻想用分布式事务把所有组件强绑成原子操作**，不仅性能崩盘，而且根本不现实。工程上正确的切法只有一刀：

- **权威事实（Event Log、租约、元数据、外部确认记录）**：走事务提交或可靠持久化，保证强一致和顺序；
- **派生视图（向量索引、全文索引、图谱投影、读副本、缓存）**：通过异步或增量流水线同步，允许短暂延迟，**但必须明明白白标出源版本号和索引水位**。

这么拆还有一个巨大好处：当用户投诉「Agent 怎么又答错了昨天的老政策」时，研发看一眼版本号和水位就能立刻定位——到底是源文件没改、模型推理犯蠢，还是索引延迟还没追上，不再把所有锅全扣给「模型幻觉」。

### 8.7.3 统一元数据、血缘与成本分层

统一元数据目录记录每个对象的身份、来源、密级、版本和策略。加上**血缘追踪**后，一旦源文档被修订或撤回权限，平台就能顺藤摸瓜让对应的切片、向量和记忆摘要失效——当然，**涉及合规留存的不可变审计日志和法律保留数据，必须有显式豁免规则，不能被级联误删**。

成本治理则按**数据业务价值**（而不是按技术组件）做冷热分层与显式保留期：运行时热状态快速清理，Checkpoint 留到恢复窗口结束，正式产物和文档版本按审计周期归档，靠内容去重和增量压缩防衍生副本爆炸，并把存储与重建索引的账单精细归因到每个租户和任务类型上。

### 8.7.4 选型取舍：自己拼组件 vs 上一体化 Agent 数据库

| 选型路线 | 你能拿到什么 | 你要自己扛什么代价 | 适合什么团队 |
| --- | --- | --- | --- |
| 自己组合既有组件（Postgres + S3 + 向量库 + 图库） | 复用公司现有基础设施，单组件独立扩缩容灵活 | 应用或平台要自己维护跨组件的身份映射、版本水位对齐、权限联动与同步删改 | 单轮交互为主、低敏感度轻量应用，或已有强平台团队自建底座 |
| 一体化 Agent 数据库（如 Lakebase 参考路线） | 统一对象模型、服务接口与治理控制面，状态/工作区/记忆/知识/本体自带一致契约 | 对选定产品的能力边界、迁移路径与故障域有强依赖 | 多 Agent 协作、长周期任务、高合规强治理要求的生产团队 |

无论选哪条路，**别看 PPT 里的功能打勾，拿这五项直接上真负载测**：① 关键状态能不能原子提交；② 产物引用稳不稳定；③ 权限撤回和删除多快能在检索层彻底生效；④ 各层能不能独立备份恢复；⑤ 未来不想用时数据能不能完整导出迁移。

### 8.7.5 容灾演练：数据库活着，不代表 Agent 能续跑

Agent 容灾最致命的误区，是以为「RDS 主从切换成功 = 服务高可用」。真出机房故障时，如果只恢复了数据库，却搞丢了正在跑的租约状态、不知道某笔外部 API 调用到底发没发出去、或者工作区挂载版本对不上，恢复起来只会瞬间产生重复操作和脏结论。

高可用必须和第 07 章的 Runtime 演练联动：**先保权威事实（Event Log/Checkpoint/租约/幂等键）和产物引用不丢，再按数据源重建向量和图谱索引**；定期真实拉闸测试主区切换、索引损坏重建、误删恢复，确认切换后新实例真能接着刚才那一步正确往下跑，容灾才算过关。

## 8.8 本章小结

Agent 时代的存储，本质是在回答「当数据的第一读者从人变成到处跑、随时挂的 Agent 时，存储层该怎么设计」。记住三条落地铁律：

1. **按对象特性分层承载，别一锅炖**：运行时状态靠 Event Log + 增量 Checkpoint + 围栏保正确续跑；工作区靠 COW 分层 + 不可变 Artifact Store 管成果交付；记忆靠筛选与彻底删除保干净；知识靠深度切片、溯源和检索前权限过滤保可信；本体只在真有多跳规则刚需时引入。
2. **用统一契约管住多组件，分清权威事实与派生视图**：不强求跨引擎分布式事务，但身份、版本水位、血缘、多租户隔离和生命周期策略必须在控制面完全拉通。
3. **验证不看单组件可用性，看完整恢复闭环**：真正的高可用，是实例被杀、缓存失效、机房切换之后，系统依然能找回正确的状态指针、工作区快照与幂等记录，不重做、不错做地把任务交出去。
