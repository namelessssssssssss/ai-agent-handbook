# 构建篇导读

上一篇画出了 Agent 系统的架构蓝图和责任边界，本篇进入动手落地阶段：**先决定 Harness 由谁来实现、各自担什么责，再把模型“一问一答”的离散推理，组织成能持续推进、断线可恢复、结果可验收的任务流程。**

你会在本篇频繁看到 Coding Agent（编码智能体）的身影。原因很现实：代码仓库、终端命令和自动化测试天生构成了一个极佳的工程试验场——模型改了哪几行、单测过没过、编译报什么错，系统能立刻给出客观反馈。但这并不意味着企业里的所有业务都得照搬 Coding Agent 的流程。审批、交易、客服和运维各有各的业务状态、权限红线和成功标准，企业真正要复用的，是 Coding Agent 背后沉淀出来的这套通用 Harness 机制。

同时先划一条清晰的边界：构建篇负责把“任务怎么流转、每步看什么信息、动作如何受控”这些工程契约写清楚并接通能力；至于进程怎么长期托管、状态落到哪种存储、隔离环境如何弹性扩缩容，那是下一篇《运行篇》要解决的物理承载问题。

| 对应章节 | 本章主线 | 要解决的工程问题 | 核心机制与关键词 |
| --- | --- | --- | --- |
| 第 03 章 | 选路与定责：Harness 的构建范式 | 到底自己从头写、接现成组件，还是交出去托管？多团队做出来的 Agent 怎么管？ | 四类构建入口（高代码框架自建 / 嵌入产品化 CLI·SDK 与工作区助手 / 云端托管执行 / 云平台低门槛拼装）与 Agent Platform 统一纳管 |
| 第 04 章 | 任务契约：推进、协作与收尾 | 模型一轮答不完、中途断连或干脆死循环怎么办？怎么证明它真干完了？ | Agent Loop 五步循环、显式任务状态机、Plan Mode 阶段门禁、Subagent 委派契约、断点续跑与基于证据的 Verifier |
| 第 05 章 | 信息契约：Context、状态与资产 | 上下文窗口就这么大，事实、历史日志、文档知识和历史经验全往里塞怎么办？ | Context 动态编译与 Manifest、Commit/Compact/Rebuild/Validate 压缩闭环、State 与 Workspace 分层、Memory/Knowledge/Skill 治理 |
| 第 06 章 | 行动契约：受控执行与进化闭环 | 怎么防止模型把高危操作直接打到线上？过程怎么推给用户，翻车了又怎么改下一版？ | 统一 Action Plane、Function Calling/MCP/A2A 分层、Sandbox 隔离、Policy 与 HITL 审批、流式交互及 Trace-to-Patch 评估闭环 |

阅读本篇时，建议抓住两条线索：

第一条线索是**四条路怎么选、谁来兜底**。第 03 章拆解的四类构建入口不是“低级到高级”的成熟度阶梯，也不互斥——同一个公司完全可以用高代码框架打磨核心业务 Agent，用产品化 SDK 给现有工作台快速加上编码/分析能力，同时把批量异步任务交给云端托管，或用云平台预置组件快速拼装日常助手；最后再通过统一的 Agent Platform 把身份、权限、目录和观测收拢到一起。

第二条线索是**任务、信息、行动三类契约如何咬合**。任务契约管“下一步干什么、什么时候算完”，信息契约管“模型这一步眼前看得到什么、哪些事实必须落盘”，行动契约管“模型举手申请的动作怎么鉴权、进哪个沙箱跑、结果怎么算账”。为了把这三块讲透，**第 04 至第 06 章共用了同一个贯穿案例——「生产服务漏洞修复与变更发布 Agent」**：顺着它收到支付服务高危漏洞告警、查影响、出计划、派子代理改代码、等发布审批，直到事后复盘修补误审批漏洞的全过程，就能直观看到各个组件在真实工程里是怎么扣在一起的。
