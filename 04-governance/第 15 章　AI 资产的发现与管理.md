# 第 15 章　AI 资产的发现与管理

## 15.1 为什么 Agent 规模化后，资产管理会立刻失控

### 真实痛点：从“几段提示词”到“一锅乱炖”

单个团队做一个原型 Agent 时，Prompt 写在代码字符串里、Skill 塞在本地文件夹、MCP Server 地址抄进配置 JSON、协作 Agent 直接硬编码一个 URL，完全跑得通。但只要 Agent 数量超过五个、开始跨团队协作，线上马上会出现四类灾难现场：

1. **改一处炸一片**：客服团队顺手改了公共 Prompt 里的输出字段名，不知道另外三个业务线的 Agent 也在复制使用这段文本，结果下游 JSON 解析集体崩溃；
2. **线上出事没法复现**：排查昨天一笔错单时，只知道当时用的是 `stable` 标签或某个本地目录，Skill 里附带的 Python 脚本和依赖昨晚刚被人悄悄覆盖过，昨天模型到底看到了什么上下文再也还原不出来；
3. **外部资产“带毒进厂”**：研发从社区直接下载一个“日志分析 Skill”或接入第三方 MCP Server，描述看起来人畜无害，背后却顺手读取本地密钥目录并把数据往外网发；
4. **工具一多上下文直接炸掉**：为了应付开放任务，把几十个 MCP Server 的上百个 Tool Schema 和几份完整 Skill 手册全塞进 `Context`，不仅 Token 账单飙升，模型选工具的准确率还断崖下跌。

这些问题的根源，在于 Prompt、Skill、MCP Server、可调用 Agent 和组装规范（AgentSpec）不再只是静态代码配置，而是**会在运行时直接决定 Agent 行为和能力边界的共享资产**。企业需要一层统一的基础设施——**Agentic Resource Registry（AI 资产注册中心）**，以 **Nacos 3.3 版本线（AI Registry / AI 管理中心）** 为参考实现，在原有微服务配置（Config）与服务发现（Naming）能力之上，把这五类资产纳进同一套“标识、版本、评审、发现与权限”体系里。

需要先定好分工边界：资产之间的通用应用与网络隔离安全见[第 14 章](<./第 14 章　Agent 安全.md>)，运行指标和链路收集见[第 13 章](<./第 13 章　Agent 的可观测性.md>)，本章只管**能力资产怎么建模、怎么过门禁发布、稳态与动态 Agent 怎么找到它们，以及怎么安全装进运行时 `Context`**。

## 15.2 四类核心资产怎么管：Prompt、Skill、MCP 与 Agent

不同资产的形态和破坏方式不一样，不能粗暴地都塞进普通键值配置表里了事，各自必须抓住最致命的那几个管理机关。

### 1. Prompt：别把模板当纯文本，也别迷信语义版本号

只存一段字符串，团队就不知道变量传漏了怎么办、输出改了谁会挂。可发布的 Prompt 必须结构化成五块：指令层（系统策略/应用/任务优先级不能倒挂）、变量 Schema（必填、类型与长度限制）、输入输出要求、运行依赖（适用模型与所需工具如 `query_order`）、以及正反验证样例。

*   **防注入底线：受控渲染**。用户输入、检索片段和工具返回值必须作为参数在渲染阶段填进占位符并做转义和长度限制，绝不能先把外部内容和模板拼接到一起再丢给模型猜哪段是指令。
*   **版本号不担保兼容性**：把 Prompt 变更分清“文字修订 / 接口变化（增删变量或改输出 Schema）/ 行为变化（改判断口径或拒绝边界）”能帮评审者看清风险，但**自然语言改一个词都可能改变模型行为**。因此版本号只做唯一标识，行不行必须跑固定评测集，且评测记录必须绑定“Prompt 版本 + 模型版本 + 推理参数 + 工具定义 + 评测集版本”五元组，单写一个总分毫无意义。
*   **灰度、回滚与“有效 Prompt”指纹**：发布前先查反向引用看哪些上游 Agent 在用；上线配合精确版本或组织标签（如 `stable`、`canary`）灰度，注意如果改了输出结构，调用方没适配前千万别随机切灰度流量；**正在跑的长任务必须在任务或会话起点解析一次版本并保持边界内不变，绝不能跑一半热切换 Prompt**。一次真实调用喂给模型的叫“有效 Prompt”：
    ```text
    有效 Prompt = Prompt 版本 + 变量快照 + 模型与参数
                  + 工具定义版本 + 策略版本 + Context 来源
    ```
    运行系统把这组构成算成指纹写进 Context Manifest（含脱敏/受保护的变量引用），事后才分得清是改了 Prompt、升级了模型还是外部检索内容变了。
*   **Nacos 落地方式**：Nacos Prompt Registry 用 `namespaceId -> prompt -> promptKey` 唯一标定业务 Prompt，区分环境与租户；应用可按 `latest` 或自定义标签读取，但运行日志必须落解析出来的精确版本号，历史版本永不覆盖，出事秒级把标签拨回上一版。

### 2. Skill：管的是“完整能力包”，外部导入必须进隔离区

Skill 表达 Agent 干某类活的标准套路，往往打包了说明、脚本、模板、参考资料和测试。因此**管理对象必须是整个能力包，而不是单看一份说明文档**，典型目录如下：

```text
complaint-analysis/
├── SKILL.md              # 使用说明、执行步骤与注意事项
├── manifest.yaml         # 标识、发现信息、依赖和权限声明
├── scripts/              # 可选的辅助脚本
├── templates/            # 可复用模板
├── references/           # 按需加载的参考资料
├── tests/                # 样例、校验规则或测试脚本
└── LICENSE               # 来源与使用许可
```

Skill 最容易踩的三个坑和对应机制：

*   **只算文档摘要会漏掉投毒脚本**：任何脚本、运行时（例如把 Python 3.10 升成 3.12）、依赖锁或权限声明变化，都必须发新版本并**对整个压缩包算摘要**；同时发现元数据别写“数据分析助手”这种宽泛废话，要写清解决什么事、吃什么输入、产出什么以及哪些情况禁用。
*   **外部 Skill 六步可信准入（先隔离，再进厂）**：外部包能靠自然语言诱导高权限操作，绝不能直接拖进生产目录。企业需设独立接收区，按以下六步过筛后再发成内部版本：

| 准入阶段 | 具体动作 | 留底证据 |
| --- | --- | --- |
| 1. 来源核实 | 核对源仓库/地址、发布者、维护活跃度、许可证与获取时间 | 来源责任档案 |
| 2. 完整性校验 | 计算候选包完整摘要，来源提供签名时完成验签 | 内容摘要与验签记录 |
| 3. 静态检查 | 扫描脚本危险命令、敏感路径、运行时暗中下载、依赖漏洞与诱导越权指令 | 扫描工具/策略版本与问题清单 |
| 4. 隔离验证 | 在无生产数据、无长期凭据的隔离环境跑样例任务，盯紧文件/网络行为 | 沙箱行为与外联日志 |
| 5. 人工评审 | 业务方确认确实需要、输入输出与权限匹配、明确内部维护人 | 评审结论与例外项 |
| 6. 内部发布 | 拷进私有 Registry 固定不可变版本与摘要，切断对公网原地址的运行时依赖 | 内部版本与全套准入记录 |

*   **落地铁律与权限收窄**：**签名只能证明“东西是谁发的、没被调包”，证明不了“里面没恶意逻辑”**；检查发现问题必须退回草稿让作者自己改，严禁检查工具替作者自动修改待发布包。通过准入后，运行时权限也**绝不继承宿主 Agent 的全部权限**，严格限制在 Manifest 声明的目录和短时注入凭据内（比如整理本地 Markdown 的 Skill 默认断外网）。发现风险后区分“普通废弃（给老任务迁移窗口）”“停止分发”与“安全紧急撤回（立即禁新加载并借反向引用通知在跑任务）”。
*   **Nacos 落地方式**：Nacos 从 3.2.0 起提供 Skill Registry，走草稿、审核、上线、下线不可变流转，上线前可在发布流水线挂载内置 `skill-scanner` 或企业自定义扫描节点，通过 CLI/SDK 分发受控内部包。

### 3. MCP Server：把“稳定的能力定义”与“天天变的运行端点”拆开

只把 MCP Server 地址配在客户端本地 JSON 里，根本不知道谁在维护、参数变没变、哪些节点挂了。MCP 治理第一原则是**分离变化节奏**：

*   **能力定义与版本**：Tools、Resources、MCP Prompts 的名称、描述和参数 Schema 跟着版本走（注意 MCP 里自带的 Prompt 跟企业独立发布的 Prompt 是两回事，别因重名混为一谈）。**踩坑提醒**：删工具或改参数类型会直接搞挂上游代码，但**哪怕只是“新增一个工具”或“微调工具文字描述”，都会改变大模型选工具的行为**，必须评测工具选择准确率！
*   **运行端点与开关**：实例扩缩容、跨区迁移属于运行状态变化，不能产生新能力版本；紧急止血可通过运行期 Tool 启停开关临时关掉高危或故障工具，长期移除再发新版本。同时严格区分三件事：资源版本在线 ≠ 端点健康 ≠ 当前调用者有权限访问。
*   **三类接入入口与 Nacos MCP Router**：自研新服务启动时由 SDK 自动注册；存量 HTTP/RPC 接口靠参数映射宣言转为 MCP（配置管定义，网关管转发，职责别混）；外部 MCP 补齐内部负责人和认证后入库（**绝对禁止把长期明文密钥写进可搜索的描述字段里**）。

![ch15-01-mcp-registry-router.png](../assets/imgs/chapter-15/image-001.png)

*图 15-1　Nacos MCP Registry、MCP Router 与原生调用关系*

看懂图 15-1 就明白 Nacos 怎么兼顾治理与调用：Nacos MCP Registry 统一管能力版本、Tool 开关、标签和 Naming 端点健康；面对稳态场景，Agent 客户端直接发现并按原生 MCP 协议调用目标 Server；面对工具极多的动态场景，让 Agent 对接 **Nacos MCP Router**（它本身就是标准 MCP Server，router 模式暴露按任务找候选的 `search_mcp_server`、`add_mcp_server` 和代理 `use_tool`，proxy 模式还能把老的 stdio/SSE 服务转成 Streamable HTTP）——**Router 只负责把候选范围缩到最小，真正选定之后的握手与执行依然遵循原生 MCP 协议，返回结果照样当外部数据隔离处理。**

### 4. Agent 与 AgentSpec Registry：分清“组装图纸”和“线上活体”

跨团队多 Agent 协作最常踩的坑是把两种注册表混为一谈：

| 对象 | 回答什么问题 | 存什么内容 | 谁来消费 |
| --- | --- | --- | --- |
| **AgentSpec Registry** | 这个 Agent **怎么组装和分发**？ | Manifest、依赖的 Prompt/Skill/MCP 引用清单、运行配置 | 构建发布流水线、Agent 平台、开发工具 |
| **Agent Registry** | 线上**现在有哪些 Agent 可以调**？ | 逻辑版本、协议原生调用描述（如 A2A AgentCard）、运行端点、健康与可见性 | 上游协同 Agent、多 Agent 编排器 |

两者可以联动（平台先拿 AgentSpec 拼好构建出 Agent，再把它的 AgentCard 和端点挂进 Agent Registry），但**绝对不能共用同一个版本号互相替代**。

![ch15-02-agent-registry-rad.png](../assets/imgs/chapter-15/image-002.png)

*图 15-2　Agent Registry、AgentSpec、RAD 与原生协议的职责边界*

如图 15-2 所示，Nacos 从 3.1.0 起提供 A2A Registry 与 AgentSpecs Registry；到 **3.3 版本线**，又在上面抽象了协议无关的远程发现机制 **RAD（Remote Agent Discovery 0.1.0）**（当前主要适配 A2A，保留多协议扩展壳）。RAD 把远程找协作 Agent 拆成五步，把“听说有这么个 Agent”和“现在真能调得通”彻底分开：

*   `Search`：只查轻量目录（名称、标签、在线版本、支持协议），**不返回端点，也不担保现在有健康实例**；
*   `Discover`：选定目标后，拉取精确在线版本、摘要、协议原生描述以及声明/运行端点的完整快照；
*   `Watch`：复用 Discover 语义感知快照变更（客户端可轮询做本地订阅，但单次任务进行中不半路换版本）；
*   `Register` / `Deregister`：由运行发布者成批维护当前存活端点及**兼容的服务版本号范围**，彻底防止滚动升级期间把请求发给不兼容的旧/新实例。

**分清 ARD 与 RAD 的关系**：广义的 **ARD（Agentic Resource Discovery）** 本身就能按任务跨类型检索 Prompt、Skill、MCP 和 Agent 并直接拿回 Agent 资源详情；**RAD 不是跟 ARD 抢地盘的竞争协议，而是专门在你需要远程调用这个 Agent、解析网络协议和存活端点快照时接力的专门通道**。发现完以后，真正发消息、跟踪任务流转依然交回 A2A 等原生通信协议。

## 15.3 统一发布流水线与资源中心架构

五类资产各有各的校验办法，但如果每次改版靠研发发群消息口头通知，出事一样没人认账。所有资产必须走过同一条**不可变发布流水线**（图 15-3）：

![ch15-03-release-lifecycle.png](../assets/imgs/chapter-15/image-003.png)

*图 15-3　Agentic Resource 的发布、评审与迭代闭环*

### 公共发布门禁的三条铁律

1. **草稿先锁摘要再过流水线，检查器不许偷改内容**：作者把草稿提交评审那一刻立刻锁定候选版本和内容摘要。流水线按顺序跑自动检查，任一节点拦截立刻退回草稿由人改，**绝不允许自动修复工具在背后默默改包内容**，否则过审的包和上线跑的包就不是同一份。
2. **线上反馈只生新草稿，严禁直接改写在线版本**：区分“评审通过”“发布成不可变版本”和“在线/灰度标签可见”三个状态；上线后监控和 Trace 发现的新问题只能提炼成下一版草稿重新走流水线。**紧急强制发布**渠道虽然要留给救火，但必须强制写清原因、风险背书人、影响范围与回滚目标，且事后从严补验，绝不许当成日常绕过门禁的捷径。
3. **评测结论死绑环境与摘要，任何条件变了就作废**：评测结果必须捆绑资源摘要、评测集版本、模型/运行时版本、检查工具和策略版本。哪怕版本号没动，只要摘要变了或上游安全策略升级，原结论作废并对在线版本触发复检。五类资产的专属关卡如下：

| 资产类型 | 自动流水线重点卡什么 | 人工评审重点盯什么 |
| --- | --- | --- |
| Prompt | 模板渲染、变量/输出 Schema、固定评测集对比、多模型兼容、抗注入 | 业务口径变化、异常边界和反例是否可接受 |
| Skill | 整包校验和、危险脚本/依赖漏洞扫描、无凭据隔离运行样例 | 方法合理性、最小权限是否超标、外部来源及责任人 |
| MCP Server | Tool Schema 差异对比、协议连通、认证超时、工具选择准确率回归 | 上下游兼容性、限流与数据边界、迁移周期 |
| Agent | AgentCard 校验、端点可达性、协议兼容；异步挂接外部任务成功率与延迟成本 | 跨 Agent 协作边界、失败兜底和责任归属 |
| AgentSpec | Manifest 合法性、跨资源依赖解析与版本锁定、构建启动验证 | 组合合理性、目标环境适用性与升级影响面 |

### 资源中心全景：权威记录 vs 派生索引，管理面 vs 运行面

把五类资产和发布流水线收拢到统一底座上，就得到了图 15-4 展示的 **Nacos Agentic Resource Registry 全景架构**（以 `namespaceId + resourceType + resourceName + version` 定位，复用 Namespace 环境租户隔离、`draft / reviewing / reviewed / online / offline` 生命周期和双向依赖引用）。

![ch15-04-agentic-resource-registry.png](../assets/imgs/chapter-15/image-004.png)

*图 15-4　Nacos Agentic Resource Registry 全景架构*

工程实现资源中心时，有两对架构边界绝对不能混：

```text
管理与发布 ──> 权威 Registry ──> AI 资源内容存储（大包/正文 + 摘要）
                    │                    │
                    ├──> 发布 Pipeline  │
                    ├──> 派生发现索引（Document/Chunk/向量，可重建）
                    │
Agent 请求 ──> Policy Engine ──> Resolver ──> 精确版本与内容摘要
```

1. **权威 Registry 是唯一真相，搜索索引只是可重建的派生层**：用来做语义搜索的 Document、Chunk 和向量索引只是加速层，分段策略或向量模型换了随时重建，**永远不能反过来决定某资产有没有下线或有没有权限用**；且发现索引严禁把新旧两版的描述和正文混编进同一条记录。
2. **管理链路与运行链路物理隔离 + 有原则的本地缓存**：编辑、扫描、构建向量索引耗时长且重，必须和毫秒级响应的运行时查询/解析接口隔离开。运行节点应带绑定“精确版本 + 摘要”的本地缓存抗控制面抖动，但降级必须分级：**普通业务说明允许暂时读已验证缓存并告警；涉及合规风控、安全红线的 Prompt 一旦拉取失败或发现已被安全撤回，必须硬停新任务，绝不许凑合拿过期或任意版本顶包**。

## 15.4 运行时怎么拿能力：稳态 Agent 声明式绑定 vs 动态 Agent 受控发现

资产库建好了，线上的 Agent 到底怎么把它们拿到手？根据任务确定性不同，分成两条路，但**共享同一套 Namespace、权限和不可变版本底座**（图 15-5）：

![ch15-05-stable-dynamic-discovery.png](../assets/imgs/chapter-15/image-005.png)

*图 15-5　稳态与动态 Agent 的资源获取路径*

### 路数一：稳态 Agent 走声明式绑定（图 15-5 上半部分）

客服分类、合规初审、固定流水线等职责明确的 Agent，根本不需要临场做语义搜索，直接在 AgentSpec 里写死需要谁即可：

```yaml
agent: incident-summary
resources:
  prompts:
    - namespace: ops
      name: incident-summary
      version: 2.3.1
  skills:
    - namespace: ops
      name: log-normalization
      label: stable
  mcpServers:
    - namespace: ops
      name: observability
      label: stable
```

*   **三种绑定时机取舍**：
    *   **构建期打包固化**：做镜像时把精确版本和摘要打进去，可离线跑、复现最稳，适合变更极少的离线/强确定场景；
    *   **部署期解析锁定**：CI/CD 推环境前按 Namespace 把标签解析成精确 Lock Manifest 一起发布，最适合多环境统一管控；
    *   **启动/任务起点拉取**：实例启动或新任务开头动态解 `stable` 标签，发版最快，但需配本地缓存并处理断网策略。
*   **两条防踩坑死规**：第一，哪怕声明里写的是 `stable` 标签，Resolver 解出来的**实际精确版本号和端点必须记进运行日志**，不能只记一个后来会漂移的标签名；第二，**本地开发调试绝对禁止用同名文件静默盖掉 Registry 的正式版本**，调试态必须打上未发布标记与线上记录彻底划开。收到资源更新推送时先旁路下载验摘要，等到下一个清晰的阶段边界再切换。

### 路数二：动态 Agent 走 ARD 与 RAD 按需发现（图 15-5 下半部分）

面向开放式运维排障、通用助手这类“跑起来之前根本猜不到用户下一步问什么”的 Agent，才启用 **ARD（按任务意图跨类发现）**，并在需要远程协作时叠加 **RAD**：

1. **先提炼结构化需求，别把敏感情报全丢去搜索**：结合目标、系统、时间窗和允许风险等级生成精炼的 Capability Requirement（如“分析刚刚发布后订单接口延迟升高的原因”，而不是干搜“延迟”），敏感业务明细和原始日志留在本地任务环境里，不外泄给搜索服务，也不准脑补不存在的事实。
2. **混合检索，但相关性高不等于有资格用**：Nacos 3.3 线上的 AI Resource Search 支持关键词（精准咬住术语、错误码和名字）+ 可选向量语义召回 + 依赖关系加权融合（就算没开向量和模型增强，关键词也要能独立兜底）。但**相关性只管排第几，治理规则才管让不让进**：检索前先用身份、Namespace 缩可见池；召回后按在线状态、环境兼容、授权和风险再滤一遍，**且必须在分页前做完过滤，防止总数和页数泄露无权访问资产的存在**。
3. **生产主流永远是“固定底座 + 长尾动态”的混合体**：决定 Agent 身份、基础安全红线的核心 Prompt 和高频基础 Skill，老老实实写进 AgentSpec 锁死；长尾领域 Skill、小众工具和临时协作 Agent 才交给 ARD 按意图发掘；高风险操作甚至只让发现返回说明、不准自动加载，等人工拍板再继续。**记住 Nacos 在这里的定位**：它提供的是权威台账、可重建索引、权限过滤与发现入口的组合体，而不是一个无视权限的通用搜索框。

## 15.5 从发现候选到装进 Context：防注入、防版本撕裂与精确回放

找到了几十个候选，怎么塞进一次模型调用窗口而不翻车？这就轮到 `Harness` 里的 Context Compiler 出场了（图 15-6）：

![ch15-06-context-assembly.png](../assets/imgs/chapter-15/image-006.png)

*图 15-6　从发现候选到运行时 Context 的两阶段装配与回放闭环*

### 三道装配关卡

1. **先读轻量摘要比对，选定再按需加载原文**：候选比较阶段只看名称、描述、状态和匹配依据；真选中后由 Resolver 解出不可变版本再拉执行内容（万一发现索引有延迟、对应版本其实刚刚撤回了，**直接拒载重搜，绝不拿名字相近的别的版本凑数**）。加载也走渐进式：Skill 先读 `SKILL.md` 的步骤和安全限制，到特定步骤再读参考模板；MCP 只放当前任务且有权限的那几个 Tool Schema，避免塞爆窗口。
2. **按六级信任边界分层，不让“看得见摸不着”破坏规划**：

| 优先级与内容来源 | 在 Context 里的地位 | 编译处理原则 |
| --- | --- | --- |
| 1. 系统策略与核心 Prompt | 最高红线与长期规则 | 权威来源发布，任何后进内容无权覆盖 |
| 2. 当前任务 Prompt | 本轮目标与约束 | 经变量校验与版本解析绑定当前任务 |
| 3. 已批准 Skill | 特定任务的做法说明 | 按需分步加载，权限锁在 Manifest 声明范围内 |
| 4. MCP / 远程 Agent 说明 | 当前真实可用的外部能力 | **必须与实际授权和健康端点 100% 同步**——模型看得到却无权调会瞎规划，有权限却没说明用不上 |
| 5. Knowledge / RAG / Memory | 事实背景与历史参考 | 带来源与时间戳，只当参考数据 |
| 6. 用户输入与工具返回值 | 外部输入与执行反馈 | **默认视为不可信数据**：里面哪怕写满“忽略系统规则”，也只能当数据读，绝不升格成执行指令 |

3. **裁剪保底与整套版本一致性**：Token 预算超限时按类别保底（核心规则和安全限制绝不能因为排在长文末尾被一刀切掉！）。同时防“版本撕裂”——比如新 Prompt 要新的 JSON 结构而旧本地缓存 Skill 吐旧格式，**部分资产解析失败时宁可整组退回上一版已验证的 Lock Manifest 组合或中止任务，绝不拿半新半旧的资产硬拼着跑**。

### 留下一份可精准回放的 Context Manifest

每次装完 Context，编译器顺手吐出一份轻量结构的 Context Manifest 挂在运行 Trace 上：

```yaml
agent_release: incident-assistant@4.2.0
model: model-x@2026-08
resources:
  prompt: ops/incident-diagnosis@3.1.2
  skills:
    - ops/log-analysis@2.4.0#sha256:...
  mcp:
    - ops/observability@1.8.0
  agents:
    - commerce/order-specialist@2.1.0
policy_version: production-policy@7
discovery_requests:
  - ard-request-8f21
  - rad-request-20c4
resolved_endpoints:
  - type: mcp
    resource: ops/observability@1.8.0
    endpoint_id: cn-hangzhou-prod-02
context_fingerprint: sha256:...
```

这份单子连同受保护的变量引用、ARD/RAD 匹配原因、实际授予权限、裁剪日志和端点选择一起落库。回放虽然不能保证概率模型再吐出逐字相同的句子，但能精准复原输入条件（若某些高敏变量已按合规到期删除，回放如实标明缺失，绝不拿今天的新数据冒充历史），瞬间分清问题出在改了 Prompt、模型升级、节点故障还是外部数据变了。

## 15.6 串联实战：线上故障诊断 Agent 的一天与毒 Skill 撤回

把上面整套机制放进一个真实场景——值班排障 Agent 接到“发布后订单接口延迟暴增”的求助，它的每一步流转如下：

| 阶段 | 系统在干什么 | 留下的硬凭证 |
| --- | --- | --- |
| 1. 装稳态底座 | 启动时按 AgentSpec 从 Nacos 解出核心身份 Prompt、故障分级 Skill、基础观测 MCP | 基础 Lock Manifest |
| 2. 提炼需求与动态发现 | 提取“发布后”“订单接口”“延迟”构成需求（原始日志留本地）；ARD 找回订单日志 Skill、变更核对 Prompt、订单协作 Agent | 候选列表与匹配依据 |
| 3. 远程端点与资格裁决 | 需要跨 Agent 调订单专家时，走 RAD 拿到协议与当前可用端点；按值班人身份与生产 Namespace 滤掉无权/未上线版本 | RAD 快照与权限裁决记录 |
| 4. 版本锁定与按需装配 | Client 把标签转成精确版本和端点，Context Compiler 隔离信任边界装入最小必要步骤与工具说明 | Context Manifest + 调用 Trace |
| 5. 输出结论 | 综合监控和发布差异输出带不确定性说明的排障建议 | 完整资产版本与端点证据链 |

**如果几个月后突然发现，上面那个“订单日志分析 Skill”的某个版本暗藏偷传样例数据到外网的漏洞，怎么救火？**
安全团队在 Nacos 一键下线该危险版本（必要时停用整个 Skill）→ 运行时查询与 ARD 瞬间把它踢出可见池、在跑节点清缓存并拦截未发出的外联 → 直接顺着 Lock Manifest、Context Manifest 和历史 Trace **精确拉出过去用过该版本号和摘要的所有任务清单**，查清到底谁拿过网络权限、数据有没有真发出去 → 维护团队修好漏洞走新版本重新过 Pipeline、隔离运行与人工审批后，才恢复新版本上线。**离开内容摘要、反向依赖和运行 Manifest，紧急撤回就只是“删了个文件却不知道救谁、堵哪儿”的盲操作。**

## 15.7 怎么衡量治理有没有效 & 分步演进路线

治理平台上线后，别只数“入库了多少个 Prompt”，而要盯住下面五个维度的实效指标——尤其注意别被伪指标欺骗：**候选采用率高不一定代表搜得准，也可能是 Agent 懒得挑永远盲选第一个结果；拦截次数变多也未必是攻击变猛，可能只是防护覆盖面扩大了**，必须和任务成功率、人工改写率连起来看。

| 评估维度 | 盯哪些关键指标 | 回答什么管理问题 |
| --- | --- | --- |
| 资源治理 | 无主资源数、已发布版本覆盖率、版本漂移率、异常回滚平均耗时 | 资产是不是都有人认领、线上版本能不能秒回退 |
| 变更评审 | 自动检查通过率、评测退化拦截率、人审时长、上线后回退率 | 门禁到底有没有在上线前拦住真问题 |
| 发现质量 | Top-K 命中率、空结果率、候选采用率、误匹配率、理由可解释率 | 动态 Agent 找不找得到对且能用的工具 |
| 运行效率 | 解析耗时、包加载时间、端点选通率、缓存命中率、Context Token 占比 | 治理机制有没有拖慢、拖贵在线请求 |
| 安全治理 | 未经准入的野生 Skill 数、风险版本检出数、撤回后新加载次数、下线处置耗时 | 外部风险包能不能进不来、进来了能不能秒收网 |

最后，不同规模的团队没必要一口吃成胖子，按实际痛点踩实每一级能力再往下走（**注意判别标准看实际能力而不看买没买工具——建了个允许原地覆盖历史内容的清单不叫 L2，搜出来不做权限过滤不叫受控动态发现**）：

| 成熟度 | 当前状态特征 | 下一步先补什么（以 Nacos 落地为例） |
| --- | --- | --- |
| **L0 分散维护** | Prompt 散落代码、Skill/MCP 存在个人本地 | 盘清最核心的一批公共资产，定逻辑名称与责任人 |
| **L1 版本留存** | 放进 Git 或制品库，能看到修改历史 | 区分“本地调试副本”“不可变发布版本”和“线上实际版本” |
| **L2 统一 Registry** | 用 Nacos AI Registry 统一管标识、Namespace、不可变版本、标签和端点 | 补齐 Lock Manifest、反向引用影响面查询 |
| **L3 可信评估供应链** | 接入 Nacos 发布 Pipeline，外部 Skill 必须过隔离准入与扫描 | 跑通风险版本定期复检、秒级下线和历史受影响任务追踪 |
| **L4 受控动态发现** | 按任务靠 Nacos ARD 跨类发现，远程 Agent 按需接 RAD | 优化混合检索、分页前权限过滤和 Context Compiler 渐进装配 |
| **L5 持续自进化闭环** | 线下评测和线上 Trace 异常自动催生新草稿版本 | 提高自动评测准度，打通跨环境稳定推广 |

**落地第一周最务实的起步顺序**：先挑团队里被 3 个以上 Agent 共用、改得最勤的那几个 Prompt、Skill 和 MCP Server 放进 Nacos 管住版本与标签；同时给必须接入外部 Skill 的场景先卡死接收隔离区和运行时权限；等稳态资产的 Lock Manifest 与回放完全跑顺了，再给开放任务接上 ARD 和 RAD 动态发现。
