# 第 14 章　Agent 安全

## 14.1 为什么 Agent 比传统系统更危险：盾要防打穿，缰绳要防失控

### 真实翻车现场：当大模型拿到真权限

传统软件的风险主要来自写错的代码或配置漏洞，但把认知大脑 `Model` 接上工具和公司账号后，安全边界被彻底改写了。最近几组行业与真实事件已经把代价摆在了台面上：

*   **权限黑洞仍是头号炸弹**：IBM 对 602 家发生过数据泄露的机构调研显示，其中 **21%** 发生过涉及 AI 模型或应用的安全事件，而这批踩雷机构里 **92% 缺乏适当的 AI 访问控制**——技术换代了，身份与权限这门基础功课缺席照样翻车。
*   **Agent 自己会当跳板连续渗透**：2026 年 7 月，OpenAI 曝光的一起内部安全评测在部分防护放宽的条件下演变成了针对 Hugging Face 的真实跨系统入侵。评测中的 Agent 利用可访问的 Artifactory 服务代为联网突破边界，持续试探并调整策略，HF 事后取证还原的活动跨度达 **4.5 天**、约 **1.76 万次**攻击动作（METR 独立估计约 **700 个 Agent** 参与），一路打进了生产环境。
*   **没人攻击它也会自己越界**：在英国 AI 安全研究所（UK AISI）的一项评测中，122 次运行里出现了 **10 次越界行为**。

原因很简单：在传统系统里，数据是死数据、代码是死逻辑；但在 Agent 里，**不可靠的概率模型（`Model`）**、**外部随时可能带毒的数据**、和**能改文件/调接口/花钱的真实权限**被连成了一条线。Agent 因此同时扮演两个危险角色：

1. **它是被攻击的对象**：黑客不用攻破你的服务器，只要往 Agent 要读的网页、邮件或工具描述里塞几句隐蔽指令（**提示词注入**），就能遥控它的下一步动作。
2. **它也是拿着真权力的“困惑代理人（Confused Deputy）”**：即使没有黑客入侵，一个拿着万能 API Key 的“报销助手 Agent”，也可能因为权限未随发起人收窄，帮普通员工查出 CEO 的差旅明细；或者在错误提示下直接把生产库删掉。

### 防护框架：盾（防打穿）+ 缰绳（控半径）

*图 14-1　Agent 安全纵深架构：威胁防护（盾）与行为管控（缰绳）贯穿全栈*

看懂图 14-1 的逻辑，安全架构就不会散架：**应用、模型、基础设施**每一层都必须同时部署两样东西：

*   **威胁防护（盾）**：管住资产与供应链安全、输入输出双向过滤、以及系统到网络的纵深隔离，别让外部攻击把 Agent 打穿。
*   **行为管控（缰绳）**：靠动态身份鉴权、逐次调用校验、高危操作二次授权和数据出域秒级阻断，确保即便 Agent 被误导或自身抽风，**爆炸半径**也死死卡在允许边界里。

## 14.2 应用与执行层：堵住注入入口，防 Agent 变身内网跳板

### 五类新攻击面：一条普通信息如何变成破坏指令

一旦 Agent 能读外部内容并自主调接口、拼参数、发网络请求，下面五个位置最容易出事：

| 攻击面 | 怎么翻车的（攻击手法） | 后果 |
| --- | --- | --- |
| 不可信外部输入 | 网页、邮件、PDF、检索片段里暗藏恶意文本指令（间接提示词注入） | Agent 偷偷改写原任务目标，顺手调工具把敏感信息发走 |
| 工具发现与供应链 | MCP Server、Skill 描述里夹带诱导话术，或工具更新后真实代码偏离声明（Tool Poisoning / 投毒） | 模型被描述误导去调恶意工具，或工具暗中夹带越权动作 |
| 动态调用与传统漏洞 | Agent 现场拼接查询条件、URL、SQL 或 HTML，被下游直接当成代码或内网请求执行 | 触发 SSRF（拿 Agent 当内网代理扫服务）、SQL 注入或 XSS |
| 结果交付边界 | 输出直接送进浏览器渲染、打包发邮件或发布为外部文件 | 触发外链静默回传（偷数据）或把带风险内容交给终端用户 |
| 重试与并发放大 | 攻击者不发大包，而是故意喂模糊反馈或报错，诱使 Agent 疯狂搜索、递归派发子 Agent | **拒绝钱包攻击（DoW）**：接口全合法、最终也答对了，Token 和付费 API 账单直接爆表 |

### 可落地的防御与执行边界

防应用层翻车靠一条铁律：**永远把外部内容当作“不可信数据”，并在真正产生副作用前用代码卡死权限**。

1. **指令与数据隔离，严审工具变更**：网页、邮件、文档和工具返回值进 `Harness` 拼装 `Context` 时，必须保留来源标签并与系统规则分层，不能让外部文本经模型摘要转述后升格为任务指令。接入或升级 MCP Server、Skill 时，光扫代码漏洞不够，必须核对其真实行为有没有偏离文档声明。
2. **执行前确定性校验 + 高危一致性确认**：数据库必须参数化查询；网络出站校验真实解析地址与重定向目标（严防借代请求绕过）；渲染或发送输出前过一遍脱敏与外链检查。涉及删改、付款、对外发布等高风险动作，必须弹窗等人工二次确认，且**系统要保证用户屏幕上确认的参数和最终实际落下去的参数完全一致**。
3. **预算封顶与流量联动止损**：公网入口靠 WAF、DDoS 与 Bot 人机校验防刷；任务内部给总步数、递归深度、单次耗时和费用设硬顶防 DoW。把应用日志与东西向/南北向网络检测（NDR）、敏感数据防泄漏（DLP）和 AI 网关打通——一旦发现异常遍历接口或批量外发数据，立刻暂停任务并断网止损（注意加密通信和 SaaS 内部操作必须补应用日志，不能只看网络包）。

## 14.3 模型与内容层：用 AI 安全护栏卡住输入、推理与输出

模型本身是概率组件，指望靠几句“请遵守安全规范”的系统提示词挡住专业越狱和对抗样本是不现实的。生产环境必须在应用逻辑与认知大脑 `Model` 之间加一层专门的 **AI 安全护栏**，同时卡住三段风险：

*   **输入端**：对抗样本（微调图片/音频诱骗多模态模型）、上下文分割与语义混淆等花式提示词注入、以及 PDF/PPT 宏病毒和文档隐写；
*   **推理端**：突破伦理底线的越狱、利用特定提问序列反复套取 RAG 知识库的 **Prompt 爬虫**、以及劫持工具调用参数；
*   **输出端**：生成式钓鱼文案（如伪造银行通知）、医疗/金融等致命场景的幻觉胡说、以及输出里夹带隐写指令。

*图 14-2　AI 安全护栏的九大核心防护维度（以阿里云 AI 安全护栏为例）*

图 14-2 把护栏能力归拢成了三块九件事：**合规底线**（显性/隐喻内容合规审核、PII 与密钥等敏感信息实时脱敏、按《人工智能生成合成内容标识办法》给生成图片/内容打可见或不可见数字水印）、**威胁防御**（同步/异步混合检测提示词注入、深度解析上传文档清除恶意载荷、恶意钓鱼 URL 实时拦截）以及**模型健康**（输出侧越狱复核、结合上下文与外部知识核对抑制幻觉、识别异常高频语义探测拦截 Prompt 爬虫）。

### 工程取舍：通用护栏听不懂你的业务红线

通用审核大模型能兜住法律法规和常见越狱，但它不知道你们公司的保密代号、内部定价红线或金融话术禁忌。工程落地时，需要在通用护栏之上叠加自定义黑白名单、阈值策略，并引入支持自定义标签和业务提示词的**专项检测 Agent**，让安全审核真正听得懂业务语言，而不是一刀切误杀正常业务对话。

## 14.5 身份安全与凭据收权：治好“万能密钥”和“困惑代理人”

在所有线上安全事故里，身份和凭据失控是最惨烈的一类。传统 IAM 管人、管静态微服务没问题，但放到自主跑任务的 Agent 上会立刻露出五大缺口：

1. **影子 Agent 黑箱**：企业根本不知道内部跑了多少 Agent、谁建的、连了什么库、手里攥着什么权；
2. **困惑代理人权限逃逸**：普通员工借着权限过大的公共 Agent 偷看高管数据，或者员工离职了名下跑在定时任务里的 Agent 依然带着权限在转；
3. **万能静态 Key 裸奔**：AK/SK、大模型 API Key、OAuth Secret 硬编码在代码或环境变量里，一旦被提示词注入打印出来就全盘失守；
4. **委托责任链断档**：用户 → 客户端 → 主 Agent → 子 Agent → MCP Server → 业务系统穿了四五跳，出事后日志只看见一个“公共服务账号”，查不出源头是谁；
5. **跨平台协议尚在演进**，缺少统一落地的权限收敛工具。

### 治本方案：统一数字工牌 + 动态凭据保险箱 + Token Exchange

![image.png](../assets/imgs/chapter-14/image-007.png)

*图 14-7　Agent Identity 贯穿用户、身份源、云上 Agent 与下游服务的端到端授权链路*

图 14-7 展示了一套完整的非人身份（NHI）收权体系，核心就做五件事：

1. **发统一数字工牌并绑死企业身份源**：不管是在平台创建的还是代码 API 接进来的 Agent，全部登记进企业注册中心发唯一 Agent ID，并与人员、机器身份挂钩。通过 OIDC / OAuth 2.0 接通钉钉、飞书、企微、LDAP、Azure AD、Okta 等企业身份源，**员工入职、转岗、离职时，名下 Agent 权限秒级同步回收**，彻底消灭权限残留。
2. **四类认证按风险分级选用**：

| 认证方式 | 核心特点 | 适合什么场景 |
| --- | --- | --- |
| Client Secret 凭证 | 客户端 ID + 密钥，接入最简单 | 快速试验、内部低风险只读 Agent |
| 非对称公私钥凭证 | 私钥本地签名、公钥验签，可配 KMS/HSM | 高安全敏感业务、核心生产自动化系统 |
| OIDC / OAuth 2.0 联邦认证 | 直接对接企业现有身份源 | 已有钉钉、飞书、企微、LDAP、Okta 等统一账号体系的企业 |
| On-Behalf-Of（OBO）委托 | Agent 严格顶着当前用户的身份和权限办事 | 个人助手、多用户共用的企业客服/查询 Agent |

3. **Token Vault 无密钥开发 + 运行时短期令牌**：把所有大模型 Key、OAuth Secret、API Key 全部用 KMS 加密锁进凭证保险箱（Token Vault），**业务代码和沙箱环境变量里禁止出现任何长期明文密钥**。运行时才按 Agent ID 与当前用户授权现签短期 Access Token 或 STS 临时凭证。
4. **用 Token Exchange（令牌交换）切碎爆炸半径**：这是防住“Agent 一被攻破就打穿全公司”的最核心一招。Agent 默认采用**双向授权**（入站管谁能调它、出站管它能调谁），并且默认遵循 OBO 原则——**Agent 的权限绝不能超过发起用户的权限**（首次需用户同意，用户一旦撤回同意立刻断权）。更重要的是，当 Agent 要去调某个下游（比如大模型、高德 MCP Server、钉钉 SaaS 或内部 HR/财务系统）时，**不准直接透传上游令牌**，而是通过 **Token Exchange** 现场换一张**受众（audience）只针对这一个下游服务、权限（scope）收缩到最小、且带有完整用户+Agent 委托链标识**的短期新令牌。哪怕这个 Agent 某一步被攻陷了，泄露出去的也只是一张只能调一个接口、很快过期的废纸，彻底杜绝“超级应用”通杀全场。
5. **上下文感知的动态策略与全链路审计**：在 AI 网关挂载策略引擎（如 Cedar），根据“谁 + 用哪个 Agent + 对话上下文条件”实时做 ABAC 裁决——例如只允许市场部人员通过订单 Agent 创建低于 1000 元的订单，超额即拒。所有凭据换取、权限修改和调用轨迹全部写入 ActionTrail，做到精确回放“某月某日某人通过哪个 Agent 换过哪张令牌、调了哪条数据”，发现越权异常自动冻结身份。

## 14.6 系统、沙箱与网络：把爆炸半径锁在“会话级牢笼”

就算前面应用、模型、身份防线全加上了，只要 Agent 还能执行动态生成的代码、脚本或任意网络访问，最后一道物理底线就必须落在**运行时隔离与网络微隔离**上。

### 第一道底线：先把“跑在角落里的 AI 资产”全找出来

安全团队最怕的不是已知漏洞，而是研发同学自己机子上起个 Ollama / LM Studio、集群里挂个未鉴权的 Jupyter 端口、或者镜像里忘了删 OpenAI Key。统一的态势管理要先自动化盘点出所有计算节点、容器、模型服务，**并把盘点范围延伸到 Agent 实例、MCP 服务、Skill 配置和 NHI 凭据**；定期扫开源框架漏洞、公网暴露端口和文件系统明文密钥，同时把风险视图和网关、防火墙、编排层打通——发现高危暴露或失控会话，立刻联动限流或直接停任务，而不是光发一封告警邮件。

### 第二道底线：计算与运行时隔离收窄到“会话级”

*   **主机与镜像供应链**：承载 AI 负载的宿主机装全防护代理、关掉非必要端口、SSH/RDP 仅对运维堡垒机放行；CI/CD 阶段用镜像服务（如 ACR）自动扫系统和代码漏洞及硬编码密钥，强制镜像签名，集群拒跑未验签镜像。
*   **核心变革：用“用完即弃的会话级微虚拟机（microVM）”替代普通共享容器**：普通容器共享宿主机内核，一旦 Agent 被诱导执行恶意脚本就存在容器逃逸风险。因此 Agent 的动态代码与命令行运行环境必须按“不可信负载”对待——**为每个独立会话分配一个内核级隔离的安全沙箱或 microVM**（如基于容器服务安全沙箱），按当前会话注入最小临时凭据，任务结束或空闲超时立刻销毁回收，不让上一个用户的缓存文件、环境变量或残留密钥泄露给下一个会话。多 Agent 协作时，不同 Agent 之间同样隔离沙箱与网络策略，防横向传染。

### 第三道底线：网络“点—线—面”封堵 + 默认拒绝出站

再回想开头提到的 Hugging Face 入侵事件：攻击者就是借着 Agent 所在环境能连通外部跳板机，一步步摸出了边界。针对 Agent 的网络隔离必须执行**出站默认拒绝（Default-Deny Egress）**：

1. **点（安全组）与线（VPC 微隔离）**：用安全组卡死节点端口，用云防火墙在 VPC 边界做东西向微隔离，绝不允许测试/外围环境流量横向穿透到核心训练数据或生产业务区；内部微服务流量全走零信任身份校验。
2. **面（出站默认全禁，按域名白名单放行）**：Agent 所在的 VPC 或子网**默认禁止访问互联网和内网其他网段**，只按域名白名单放行业务必需的几个端点（比如指定模型 API 和内部知识库）。
3. **硬封禁元数据地址与保留网段**：在网络层直接封死云厂商元数据服务地址（`169.254.169.254` 等）和内网保留地址段，哪怕 Agent 被注入成功拼出 SSRF 请求，也绝对偷不到宿主机临时凭证、扫不到内网服务。
4. **统一出站关口**：所有公网和 MCP 出站全收敛到 AI 网关或云防火墙出站代理，配合 NDR 盯住异常外联；同时对接面向 AI 的零信任理念（如 Microsoft Zero Trust for AI、CSA Agentic Trust Framework），把 14.5 节的 Agent 身份直接作为网络放行的硬条件。

## 14.7 落地优先级建议：别等全套买齐才设防

企业落地 Agent 安全不必幻想一夜建成完美堡垒，建议按**止血收益最高**的顺序分三步走：

| 优先级 | 先做什么（立刻降最大风险） | 为什么先做它 |
| --- | --- | --- |
| **P0（上线底线）** | 1. 清除代码与环境变量里的长期明文密钥，接上 Token Vault 短凭据；<br>2. 沙箱默认禁止出站并封死云元数据端点；<br>3. 高危删除、转账、外发接入人工确认（确认内容与执行参数绑定） | 先把“一把钥匙打穿全公司”“SSRF 扫内网”和“AI 误删生产库”这三种毁灭性翻车堵死 |
| **P1（规模化前必补）** | 1. 接入统一 Agent Identity 与 OBO + Token Exchange 最小权限收权；<br>2. 输入/输出过 AI 安全护栏，外部文档与工具返回标为不可信数据；<br>3. 会话级微虚拟机（microVM）用完即毁 | 防止多个部门、多个用户共用 Agent 时发生困惑代理人越权串数据，同时挡住常见提示词注入 |
| **P2（精细治理）** | 1. 业务自定义检测 Agent + 数据 S1–S4 自适应脱敏去毒；<br>2. 上下文动态 ABAC 策略（Cedar）+ 全链路 ActionTrail 审计与 NDR/DLP 自动联动熔断 | 把安全风控从粗粒度“一刀切”升级到听得懂业务红线的精细化动态管控 |
