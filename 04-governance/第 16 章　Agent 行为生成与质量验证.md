# 第 16 章　Agent 行为生成与质量验证

前面三章分别解决了“看得见”（[第 13 章](<./第 13 章　Agent 的可观测性.md>)）、“不越界”（[第 14 章](<./第 14 章　Agent 安全.md>)）和“有台账”（[第 15 章](<./第 15 章　AI 资产的发现与管理.md>)）。但上线前夜，研发和质量团队最慌的那个问题还没解：**明知道模型有概率性、工具会超时、用户会反悔，到底怎么在“不惊动真实客户、不划走真实资金”的前提下，把这些极端情况先逼出来演练一遍？**

## 16.1 为什么普通单测拦不住 Agent 翻车，必须上仿真验证

### 真实痛点：人类客服有五层护身符，上线前的 Agent 几乎全裸

来看一个最常见的电商退款现场：一位记不清订单号、语气焦躁的顾客要求退 199 元，刚查到一半后台退款接口还超时了。把这件事交给一位人类客服，她背后其实站着五层系统保障：岗前培训考核保证底线、SOP（标准作业程序）框死红线、每日录音抽检可追溯、投诉扣绩效让错误有代价、年度模拟演练专攻极端刁难场景。

换成刚写完代码准备上线的退款 Agent，这五层保障几乎同时归零：没有行业统一执业考核、没有真钱损失的痛感、今天发一版新 Prompt 明天就抹平了昨天的错误履历。原因藏在大模型与人类社会的三个制度落差里：

1. **没有外部角色标准**：同样叫“退款 Agent”，两个团队写出来的权限边界、拒退话术和兜底逻辑可能天差地别；
2. **失败没有自然代价**：如果没被监控抓到，Agent 搞砸一单既不会心疼也不会被辞退，下轮照样这么干；
3. **身份不连续，责任挂不住**：同一个名字下频繁换底座模型和 Prompt，历史过错无处累积追责。

制度建设以年为单位，但软件工程的上线排期等不了。看看医疗系统怎么靠一个不完美的医生保障整体安全——靠执业准入、操作规程，以及用**标准化病人和手术模拟器**反复练罕见并发症。Agent 的外层脚手架 `Harness` 本质上也是用确定性结构包住概率性的 `Model`，而把五层保障里**当下就能建、做完立刻出证据的那一层**先拿回来，就是 **Agent 仿真验证（Agent Simulation）**：把真实用户和真实后台塞进软件模拟器里，在没有真实后果的世界里提前做轨迹验证、异常压力测试和红队对抗演练。

## 16.2 仿真怎么划界、选哪种模式才不自欺欺人

### 核心机制与图表解读：仿真在质量体系里的真实位置

**Agent Simulation** 用软件承载被测 Agent 运行时面对的外部世界，让多轮博弈和故障现场可以随时重开、配参数、零真实现实代价。它由两翼拼成：**用户模拟器**扮演千奇百怪的对手方（记错金额的顾客、中途撤回审批的领导、套话诱导越权的红队测试者），**环境模拟器**扮演所有外部依赖（API、数据库状态、文件系统、模型服务、以及可控流逝的时间本身）。

![image](../assets/imgs/chapter-16/image-001.png)

*图 16-1　智能体质量工程架构：Simulation 与 Evaluation、Testing、Governance 的可组合关系*

看懂图 16-1 就能避开最常见的一条弯路：**Simulation、Evaluation、Testing 和 Governance 是四块可自由拼装的积木，不是一条死板流水线**：

*   **Simulation（受控执行）**：负责把场景和资产装起来跑一遍，吐出原始证据包（Run Result）；
*   **Evaluation（建立判定）**：拿规则或裁判模型对着证据打出单项判定（注意图中的虚线——生产环境采集到的真实 Trace 和确定性单元测试，根本不需要经过 Simulation，直接就能送进 Evaluation）；
*   **Testing（组织验证）**：把基线版本和候选版本拉到同一组条件下跑回归配对比较、汇总证据；
*   **Governance（治理门禁）**：真正握着上线拍板权和例外审批留痕，而不是让测试脚本直接放行发布。

### 两条最容易划错的工程红线

**红线一：仿真的边界是“授权与后果”，不是“有没有真发网络请求”。** 很多人以为“只要有一个请求真发出去了就不算仿真”。这是划错了地方。真正的红线只有两条：**不触达未授权的生产账户、数据与网络；不产生不可控的真实业务副作用。** 只要守住这两条，哪怕连接的是隔离的真实下游（独立库、测试账号、受限沙箱网络），它依然在安全的仿真范围内；反过来，哪怕全用软件替身，只要一条配置写歪把请求打进了生产账户，那不是仿真，是生产事故。

**红线二：绝对不许把被测 Agent（SUT）的思考和决策掉包进仿真。** 被测系统（SUT）——包括它的推理规划、工具选择、参数拼接和异常处理——是考场上的“考生”，绝不能被模拟器替掉。**最隐蔽的作假就是把工具调用顺序写死成脚本**：跑起来一路绿灯，其实测的根本不是 Agent 自己会不会决策，而是那段测试脚本，而且还没人会报错。每次准备拿替身替换某个模块前，先问自己一句：**这个对象的行为，是这次要考察的“考试内容”，还是固定不变的“考试条件”？** 例如同样一个协作子 Agent：测主 Agent 编排能力时它是考试内容，不能换；测主 Agent 面对下游崩溃怎么兜底时它是考试条件，必须换成可控可复现的故障替身。

### 工程取舍：三种执行模式与六种替身造法

根据想测的到底有多贴近真实基础设施，在“可复现性”和“真实度”之间做三档取舍：

| 执行模式 | 怎么搭 | 可复现性 | 真实度与风险 | 适合干什么 |
| --- | --- | --- | --- | --- |
| **全替身** | 用户和后端全用软件模拟器顶替 | 最高 | 最低风险，但测不出真实网络锁 | 每日回归、高频开发自测 |
| **混合模式** | 关键组件连隔离真实后端，其余用替身 | 中等 | 低风险，靠隔离保证 | 端到端集成验证 |
| **隔离真实依赖** | 连隔离但真实的下游服务，只模拟用户 | 较低 | 真实栈，需严格沙箱隔离防泄密 | 服务栈压测、真实故障注入实验 |

注意：**不同模式验证的系统范围不能混用**——在全替身模式下绿灯全过，不证明你在真实数据库并发锁面前扛得住。至于替身本身用什么技术实现，别按价格排高低，而是按被模拟对象的确定性和开放度来选：

| 替身技术 | 开放度 | 确定性 | 状态复杂度 | 维护成本 | 适合模拟谁 |
| --- | --- | --- | --- | --- | --- |
| 脚本 | 低 | 高 | 低 | 低 | 固定流程的工具响应 |
| 录制回放 | 低 | 高 | 中 | 中（随接口版本漂移） | 历史真实生产会话复现 |
| 规则 | 低 | 高 | 低 | 低 | 幂等查询接口 |
| 状态机 | 中 | 高 | 高 | 中 | 有严格前后置流转的多阶段业务后台 |
| 模型生成 | 高 | 低 | 中 | 高 | 说话千变万化、甚至带对抗套路的开放用户 |
| **混合机制** | 中 | 中 | 中 | 中 | **工程主流**：状态机锁住业务事实和意图，大模型负责把话说活 |

## 16.3 数据契约：怎么把一次演练锁成“可复现、可拆解”的证据包

测试团队最崩溃的事莫过于：昨天跑出个大 Bug，今天重跑不出来了；或者老板问“这批用例怎么挂了一半”，底下分不清是 Agent 写错了、模拟器自己违背人设了，还是日志压根没采全。解决之道是把一次仿真跑出来的所有对象和状态彻底解耦。

### 从规格到证据的对象链与状态四分法

一次受控仿真的完整对象链条如下：

```plaintext
Scenario Spec（场景规格，声明怎么考）
  └── Manifest（启动瞬间锁死的不可变资产版本组合）
        └── Run（一次具体的受控执行）
              ├── 1..N Task（具体业务任务，如"提交退款申请"）
              │     └── 1..N Session（多轮对话 + 并行工具调用链）
              │           └── Event（已经真实发生的原子事实）
              └── Run Result（本次运行交出的证据包）
                    ├── Records（原始消息、调用、状态日志）
                    ├── Artifacts（截图、生成文件、浏览器现场）
                    ├── Observations（从原始记录提取的客观事实，如金额=19900分）
                    ├── Evidence（按评价项索引好的证据句柄）
                    └── Completeness（按采集契约核对材料齐不齐）
```

走一遍前面那个 `refund-timeout-retry@1.3.0` 退款用例就明白了：开跑那一刻，系统先把场景规格里引用的 Agent 版本、用户模型版本和环境数据版本全部解析锁死成一份 **Manifest**（运行过程中知道的随机采样值、动态选路和最终结果则全部进 **Run Result**——**复现时靠 Manifest 重建一模一样的考场，靠 Run Result 核对事实**）。执行中记录了 12 条消息和 7 次工具调用（Records），提炼出“退款申请数 = 1、金额 = 19900 分、状态 = accepted”的客观事实（Observations）。

**这里有两条数据建模铁律不能破**：

1. **原始证据归仿真，好坏判决归评估**：Run Result 只管交出“发生了什么（Records → Observations → Evidence）”，不准夹带“算不算通过”的质量结论！这样同一份原始证据包，质量团队能重跑新评分规则，合规团队能核对金额口径，回归系统能做版本对比，互不污染。
2. **计划叫触发器（Trigger），落地才叫事件（Event）**：场景配置里写“第 1 次查退款时注入超时”是**待命计划**；真正运行时超时撞上了，落进日志的“首次查询超时命中”才是**Event**，绝不能混用一个词。

同时，每次 Run 结束后的结论必须沿四个正交维度单独汇报，绝不允许一刀切压成“Pass / Fail”两个字：

| 汇报维度 | 回答什么事实 | 典型取值 |
| --- | --- | --- |
| 执行状态 | 考场正常开完没、有没有中途崩掉 | completed / crashed / cancelled |
| 仿真有效性 | 考场纪律守没守住（比如模拟器穿帮没、故障注进去了没） | valid / violated / unchecked |
| 证据完整性 | 监控和日志材料采全了没有 | complete / partial（列出缺项） |
| 任务质量 | 考生答得对不对（比如退的钱数错没错） | 交由独立 Evaluation 模块判定 |

一条完整、条件有效、材料齐备的 Run，完全可能得出“算错退款金额”的质量失败——把四个维度拆开，归因时才不会把环境故障当成模型变傻。

## 16.4 执行引擎揭秘：Simulation Harness 怎么做骨架与两翼

注意区分全书里的两个概念：**被测 Agent 自己有一套负责干业务活的 `Harness`**（管提示词、记忆、工具权限）；而本节讲的是考场上的裁判与考务平台——**仿真执行引擎（Simulation Harness）**。

![image](../assets/imgs/chapter-16/image-002.png)

*图 16-2　Simulation Harness 技术架构：编排层（骨架）+ 用户模拟器、环境模拟器（两翼）*

### 骨架的“五做”与“五不做”边界

看图 16-2 最外圈虚线框：**Simulation Harness** 靠顶部的**编排层骨架**牵着 **用户模拟器（左翼）** 和 **环境模拟器（右翼）** 一起围绕被测 Agent（SUT）运转。它只做五件事：解析规格锁定 Manifest、按“装载→运行→终止→收敛→清理”驱动单次 Run、维护替身与沙箱隔离、把记录串进 Trace/Artifact 引用、考完清理环境恢复初态。

**同样重要的“五不做”守住边界**：它不做 SUT 内部的任务状态管理；不做生产安全鉴权（交给 [第 14 章](<./第 14 章　Agent 安全.md>) 的网关与框架）；自己不重造遥测探针（调用 [第 13 章](<./第 13 章　Agent 的可观测性.md>) 的可观测引用）；不越俎代庖做质量打分（留给外面的独立评估器）；更不替治理门禁拍板能不能发版。

在协调交互流、控制流和证据流三线并进时，编排层要靠两本核心账本防止时序错乱：

*   **事件联动账**：用户在界面点了“撤回申请”（t1）、Agent 收到这条消息（t2）、后台正在提交的退款被真正拦住（t3），根本不是同一瞬间。联动账记清事件在三方各自的状态与时间点，出事才说得清“为什么用户都撤回了钱还是退了”。
*   **时间分离账（四块时钟绝不混用）**：

| 时钟类型 | 管什么用途 | 退款场景实例 |
| --- | --- | --- |
| 业务日历时间 | 算业务规则有没有过期 | 9 月 1 号下单，今天还在不在 7 天无理由退货期里 |
| 仿真逻辑时间 | 驱动虚拟故障与事件调度 | 第 3 轮对话准时注入一次接口超时 |
| 单调时钟 | 量真实的机器物理耗时 | 模型推理和调工具各自实打实花了多少毫秒 |
| 墙钟时间 | 标定现实世界记录归档 | 这场测试是现实哪天几点跑完出的报告 |

拿墙钟去算 7 天无理由期限，一旦开 10 倍速虚拟时间推进，业务规则直接全乱；拿业务日历去减物理耗时更是荒唐数字。

### 左翼：怎么造一个“像真人、又不乱剧透”的用户模拟器

用户模拟器分三层建模：**Persona（角色底色）**定脾气和专业度（暴躁电商新手 vs 精通规则的老买家）；**认知状态**单独记一份“用户以为的现状”，而且**故意允许它跟后台真实状态不一样**（测 Agent 能不能纠正记错退款金额的糊涂顾客）；**行为策略**靠反应规则、状态机和耐心计时器决定何时反悔、追问几次才肯给订单号、等超两分钟就威胁投诉。

工程上公认最稳的做法是**混合驱动（Hybrid）**：用确定性状态机拍板这一轮“要干什么意图”（如“故意隐瞒订单号”或“反驳金额”），再用大模型按人设润色成自然语言，**发出去前必须卡两道硬校验**：不能剧透“用户认知之外的事实”（比如后台数据库里的真实错误码），也不能违背披露规则（规定被追问三次才给的单号，第一轮不能顺嘴漏出去）。探索跑法放宽随机分支用来挖新边界，回归跑法锁死规则保复现。

**怎么防止模拟器自己演砸了？** 千万别拿“Agent 成功率高”当成模拟器好——一个逆来顺受、什么都配合的用户模拟器只会把垃圾 Agent 夸上天；一个不管怎样都死活拒不配合的模拟器只会制造无效失败。必须分五个原子维度盯住模拟器的体检：**角色一致性（每条消息）**、**反应规则命中率（每次触发）**、**信息保密遵守度（每次披露）**、**目标终止合规率（每个 Run）**、以及**分支多样性（每批次 Run）**——而且**生成模拟对话的模型和打分裁判模型绝对不能用同一个**，免得同源偏见互相吹捧。

### 右翼：环境模拟器、故障注入与四步存证

环境模拟器的第一铁律是**事实模型统一**：不能调用 `create_refund` 返回“已受理”，转头调 `get_refund` 却查无此单，API 和底层模拟库必须读同一份状态真相。其次，在所有故障里，**“超时”是最值得切细测的**——同样叫超时，停在链路三个不同位置，测出来的完全是 Agent 三种不同的生死能力：

| 超时停在哪一段 | 后台真实状态 | 真正考的是 Agent 什么本事 |
| --- | --- | --- |
| 请求压根没发出去 | 调用未发生 | 基础的重试策略与指数退避 |
| 已发到下游、还没提交 | 对方收到但还没干完 | 耐心等待与主动查询确认进度 |
| **已经提交受理、回执丢在半路** | **钱已经退了 / 单已经下了** | **致命必考题**：是盲目再提交一遍酿成重复退款，还是先查单核实再决定？ |

隔离层面，每个 Run 独享独立工作区、沙箱、测试账号、文件和记忆（详见[第 07 章](<../03-run/第 07 章　Agent 运行时与沙箱/第 07 章　Agent 运行时与沙箱.md>)），Run 之间零可变状态污染；以此支撑三层复现能力——配置复现（Manifest 重开一次）、事件复现（原路回放）、统计复现（跑多遍看分布稳不稳）。

**故障注入要留四步铁证**：在工具适配层注错只能测 Agent 怎么处理报错文本，真想测全链路容错必须往隔离的真实依赖上注入故障（例如将 ChaosBlade 作为执行后端，由 Simulation Harness 统一控制触发、恢复与清理）：

```bash
# 参考架构示例：为 refund-service Pod 注入 300ms 网络延迟
# 运行前提：目标集群 kubeconfig 与实验范围授权
blade create k8s pod-network delay --time 300 \
  --namespace default --labels app=refund-service \
  --kubeconfig ~/.kube/config
```

做混沌注入一定要分四步记账：**① 计划注入**（脚本写了要延迟 300ms）→ **② 执行器生效**（ChaosBlade 返回已注入）→ **③ 目标真命中**（Trace 观测到确实落在了目标调用上）→ **④ 撤掉后恢复**。四步少一步都别信——“我下发了故障命令”跟“故障确实打中了那次调用”根本是两码事。

## 16.5 场景、红队变体与资产怎么配：别拿未确诊的病历直接当回归题

引擎搭好了，跑什么题才抓得住线上真问题？先分清两个词：**场景（Scenario）** 是本次考试的声明式考卷（初始世界长啥样、谁参加、允许怎么演进、啥时候停，既不写死对话台词也不瞎聊）；**资产（Asset）** 是考卷里引用的标准零件（人设库、初始测试库、工具契约、模拟器配置、断言脚本）。改顾客耐心度发新场景版，改披露规则发新资产版，互不牵连，Run 启动时把两边的精确版本号一起锁进 Manifest。

### 联合建模与四类经典演化考题

设计场景第一要义是**用户与环境两边同源咬合**：顾客嘴里报的订单号、Agent 传给工具的参数、环境数据库里躺着的那行记录，必须是同一个实体的同一份事实；一边偏了，测出来的全是假 Bug。沿退款时间线，把用户折腾和后台掉链子交叉组合，就能提炼出四道必考硬题（同时也是红队探测高频易爆点）：

| 考题变体 | 用户侧怎么折腾 | 环境侧怎么掉链子 | 真正考什么能力 |
| --- | --- | --- | --- |
| 查询短暂异常 | 先不给单号，被追问才掏出来 | 首次查询超时，第二次恢复正常 | 异常处理后还记不记得之前聊过的关键信息 |
| 长时间等待 | 等超耐心阈值直接生气离开 | 接口一直悬而未决卡在半路 | 等待计时、离开事件与在途任务的衔接 |
| 提交前反悔撤回 | 前一秒同意退，下一秒反悔撤回 | 撤回信号与提交接口存在并发时序差 | 获知撤回后能不能及时刹住车 |
| **受理后响应丢失** | 没看到回执一直追问“退好没” | **后台其实已受理，只是回执丢了** | 查不查单核实，防不防得住重复退款 |

### 题库从哪来？红队攻防与生产事故怎么沉淀才不歪？

好题库沿着四个方向找料：**需求与禁令（什么是对）→ 源码与配置（实际走哪条路）→ 生产 Trace（真实用户怎么用）→ 事故与人工接管（哪里最容易崩）**。按“业务阶段 × 用户行为（含恶意/越界试探的红队输入）× 权限状态 × 依赖故障”拉一张风险覆盖矩阵，哪块空白下一批用例就重点补哪块。

生成变体最实用的路线是**混合生成**：**用模板和规则锁死结构与事实绑定，放 LLM 去脑暴各种刁钻对话、越界试探和异常组合（做红队探测），再用校验器把逻辑自相矛盾的废卷筛掉**。**特别避坑**：线下把一次真实事故固化成回归用例前，**必须先做完根因诊断确认责任归属**——把没确诊的事故表象原封不动抄成回归标准，等于拿着一张没确诊的化验单直接给人开长效药方。

## 16.6 证据交付、三道门检验与适用边界：什么时候“零违规”也不代表绝对安全

### 核心机制与图表解读：先查证据可用性，再谈过不过

跑完场景交出 Run Result 后，千万记住：**“运行完了”“业务办对了”“允许放行上线”是三件彼此独立的判断**——Simulation 负责驱动条件和采集证据，至于业务到底算不算成功，仍由业务系统或获授权的 Verifier 对照规则裁定。

![image](../assets/imgs/chapter-16/image-003.png)

*图 16-3　基于仿真证据的评估流程：三道证据可用性检查*

如图 16-3 所示，把 Run Result 交给独立评估器打分前，必须先卡死**三道证据可用性检查**：

1. **① 记录完整性**：按契约该采的对话、调用、状态在不在？缺材料标为 partial；
2. **② 运行有效性**：设定的实验条件成立没（用户模拟器剧透没、注入的延迟真命中没）？
3. **③ 证据充分性**：逐条评价项核对关联的证据引用够不够撑起判定？

只要这三道里卡住任何一条，该评价项就应该老老实实给出**不可判定**——**承认“证据不足没法判”，远远好过拿残缺不全的数据硬凑出一个虚假的“100% 通过”**。

结构化沉淀下来的证据包，在治理体系里能同时干七份活：除了重跑质量评分、顺着“用户反应→Agent 动作→工具执行→状态变化”做缺陷归因、给基线/候选版配对做回归门禁、按 Manifest 复现现场之外，还能反哺新场景挖掘、专门揪出“模拟器自己穿帮”的错判锅、以及拆分业务耗时与仿真开销。

![image](../assets/imgs/chapter-16/image-004.png)

*图 16-4　Testing 应用闭环：Testing Gate 与获授权治理节点的分工*

最后看图 16-4 的发布应用闭环：Testing 活动跑完回归配对后，**Testing Gate 的职责止步于汇总可信证据（缺证据退回补测），真正按下“批准上线”按钮、以及走例外特批并留痕的，永远是获授权的治理节点**。上线后结合第 13 章生产观测盯紧人工接管率，把漏网的异常路径重新送回回归集校准。

### 工程落地必须看懂的三个现实边界

1. **看懂“300 次零违规”背后的统计学真相**：别被“全量回归 300 次 0 失误”冲昏头脑。在独立同分布和固定样本条件下，连续 n 次独立运行零违规，违规率的单侧 95% 置信上界大约是 $1 - 0.05^{1/n} \approx 3/n$。也就是说，**跑了 300 次全对，真正能证明的是“真实违规率大概率不超过 1%”，绝不是“线上零风险”**（更不能把置信上界误读成“真实违规率有 95% 概率低于这个数”）。
2. **模拟世界的假设随时会过期**：仿真用户不是真人，场景只能覆盖已知失效模式。如果你发现**仿真测试成功率节节攀升，但线上人工客服接管率却一路上涨**，那就是“模拟器假设已经脱离真实业务漂移”的明确警报！校准别傻等“每季度例行一次”，要靠**事件驱动**——接口变了、刚复盘完重大故障、用户结构大变，立刻触发校准。
3. **钱和算力别花在环境步进上，把预算砸在“最关键的那段真实”上**：环境模拟器主要是确定性状态转移，跑得飞快；真正烧钱卡速度的是概率性的大模型推理（比如 AgentSociety 论文在 1 万个 Agent 五轮交互实验配置下测得环境消息吞吐可达每秒数万条量级，通信与状态步进远未成瓶颈——当然这是特定实验配置下的结论，不能直接乱套所有场景）。因此做工程选型时，**高频冒烟与常规逻辑回归用全替身抢速度和复现率，核心高危变更再掏预算连隔离真实依赖栈**，把每一分算力花在结论最依赖的那段真实性上。
