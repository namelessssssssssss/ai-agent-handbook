# 深入浅出推理框架

继 Model、Harness 之后，DeepSeek 开源推理框架 DeepInfer，又把「推理框架」推到了台前。很多做 Agent 开发的工程师天天调模型 API，却很少往下看一层：到底是什么在决定你账单上的价格和用户的等待时间？

你一定见过这两个让人困惑的定价数字（以 DeepSeek 当前定价为例）：**为什么输出 Token 的价格是输入 Token 的 4 倍？为什么缓存命中后的价格，能直接降到未命中的 1/50？** 搞懂推理框架，不仅能直接回答这两个问题，还能让你知道怎么设计 Agent 的上下文顺序来直接砍掉一大半调用成本。

这篇文章从 Agent 开发者的视角出发，按三步把推理框架讲透：**先看 Agent 场景到底把推理框架逼到了什么墙角，再跟着一个请求走完内部核心机制（KV Cache、PagedAttention、PD 分离、投机解码），最后梳理当前开源生态和工程选型取舍。**

## 17.2.1 痛点：为什么 Agent 把推理成本和等待时间成倍放大

### 模型上线之后，比拼的是每调用一次花多少钱

一个大模型从零诞生通常走四步：预训练学语言知识 → 后训练（SFT、强化学习、蒸馏）学听话和用工具 → 评测过线 → 部署上线接流量。模型一旦训练完成，「推理」就是拿着固定不变的模型权重，吃进输入、算出输出的过程；**「推理框架」就是把这件事在 GPU 或国产算力卡上跑稳、跑快、跑省的中间件。**

推理框架不仅管线上 API，也深度参与后训练：比如做强化学习时最耗时的是让模型批量试跑生成轨迹，评测和合成数据也要批量跑题，主流 RL 框架底层都直接嵌着推理引擎。但两者有笔根本不同的账：**训练是一次性投入，训完就结账；推理是持续性出血，模型每被调一次都在烧卡。** 模型本身决定 Agent 聪明到什么上限，推理框架决定这份聪明每次调用要花多少钱、让用户等多久。

把推理框架「做好」，绕不开五个互相打架的目标：

- **快**：发出去很快吐出第一个字，后面吐字流畅不卡顿（对应首字延迟与生成速度）；
- **多**：同一批卡同时扛住尽可能高的并发请求（对应批处理与吞吐）；
- **省**：把显存和算力抠到极致，算过的前文不重复算（对应显存管理、量化和缓存）；
- **稳**：流量打满、遇到超长上下文或某张卡坏了，服务不雪崩（对应集群调度与容错）；
- **准**：部署后智商不缩水，格式严丝合缝，必要时能完全复现（对应模板、采样与结构化输出）。

这五个目标天生互相扯后腿：一次塞进更多请求能提升「多」，单人吐字就会变慢；把数值精度压太狠能做到「省」，输出就可能变傻影响「准」。推理框架干的所有优化，本质都是在业务可接受的延迟底线内，把有效吞吐（Goodput）和性价比拉到最高。

### Agent 负载的三个要命特点

如果说普通聊天是一问一答，Agent 干一件事更像连着打十几通长电话。拿线上故障排查 Agent（例如阿里云 STAROps 的诊断场景）来说：用户一句话描述报错，Agent 先列计划，调日志工具看结果，再调监控工具，再查链路和变更……一件事做下来，模型动辄被调用十几次甚至几十次。

而且每一轮调用，Agent 都得把**系统提示词 + 一堆工具定义 + 前面全部思考和工具返回 + 本轮最新进展**打包发给模型。这就给推理框架甩来三个极端的负载特征：

1. **输入极长，输出很短**：每次读几千上万 Token 的背景和工具结果，只吐几十上百字的下步工具调用。
2. **前后请求高度重复**：第 10 轮请求里 90% 的前文内容，在第 9 轮刚算过一遍。
3. **耗时直接累加**：单步慢 500 毫秒，30 步下来用户就多干等 15 秒。

聊天机器人比拼的是单次算得多快；到了 Agent 时代，**比拼的是「算过的内容能不能记住、直接跳过不重算」**。这也是为什么同样做 Agent，有的人每月 API 账单少一半、首字秒出，有的人慢得像死机。

### 推理框架不是「把训练框架拿来跑前向」

很多研发第一反应会把推理框架类比成 PyTorch、Megatron-LM 或 DeepSpeed。虽然都操作 GPU，但两类系统的工程性质完全不同：

| 对比维度 | 训练框架 | 推理框架 |
| --- | --- | --- |
| 核心目标 | 把模型练出来 | 把模型用起来 |
| 计算内容 | 前向计算 + 反向传播，更新权重 | 只做前向计算，权重固定不变 |
| 负载特点 | 数据批量准备好，按计划跑完 | 请求随机到达，长短不一，随时进出 |
| 时间要求 | 一次训练跑几天、几周都可以接受 | 每个请求要在秒级甚至更短时间内响应 |
| 显存主要用途 | 权重、梯度、优化器状态、中间激活 | 权重、KV Cache（下文详述） |
| 关注指标 | 训练吞吐、收敛效果、算力利用率 | 首字延迟、生成速度、吞吐、单位成本 |

训练像闭关写书，离线排好批次算完就行；**推理更像高并发数据库和 Web 服务器**，请求随时突袭、有长有短、要求毫秒级响应，只是它调度的不是 CPU 和磁盘，而是极贵的 GPU 算力和显存。

在整套系统栈里，位置非常清楚：最上层 Agent 的 Harness 负责组提示词、管状态和工具，往下调模型服务（API 或自建），模型服务底层跑的就是推理框架，推理框架下面才是硬件卡。

### 先理清五个常被混用的名词

看资料时经常看到推理引擎、推理框架、推理服务、MaaS 混着叫，用开客运公司打比方一眼分清：

| 名词 | 指什么 | 典型形态 |
| --- | --- | --- |
| 推理引擎 | 在一台或几台机器上把模型跑起来的核心程序，负责请求调度、显存管理和计算执行 | 一个可以在服务器上启动的程序或 Python 库 |
| 推理框架 | 日常用法中常与推理引擎混用；更完整的含义还包括 API 接入、分布式部署、缓存系统等配套组件 | 一套开源软件，通常以推理引擎为核心 |
| 推理服务 | 把推理框架部署起来，对外提供的在线服务，额外包含网关、鉴权、计费、监控、扩缩容等 | 企业内部的模型服务集群 |
| 模型服务平台（MaaS） | 云厂商把推理服务做成产品，用户按调用量付费，无需关心底层 | 各家云厂商和模型厂商的模型 API |
| 本地运行工具 | 把推理引擎、模型下载和简易 API 打包在一起，面向个人电脑 | 一条命令就能在笔记本上跑起模型的桌面工具 |

一句话串起来：引擎是发动机，框架是整套动力总成，推理服务是上路运营的车队，MaaS 是直接对外卖票的客运公司。下文统称「推理框架」。

## 17.2.2 核心机制与请求旅程：搞懂推理内部发生了什么

想要一次看懂 KV Cache、PagedAttention、PD 分离和投机解码，先记住四个前置零件，再跟着一个真实的 8000 Token 客服 Agent 请求走一遍后台全程。

### 先搞懂四个底层零件

**零件一：Token 与 Prefill / Decode（先读题、后作答）**

模型看不懂整段文字，先把输入切成数字编号的 Token（英文约 1 个 Token ≈ 3/4 个单词，中文因分词器而异）。处理一次请求必定分成脾气截然不同的两个阶段：

1. **Prefill（预填充，相当于「读题」）**：把你发过去的全部输入一次性吞进去，所有输入 Token 可以高度并行计算，把 GPU 算力单元吃满。算完这一步，吐出第一个输出字——决定 **TTFT（首 Token 时延，用户等多久看到第一个字开口）**。
2. **Decode（解码，相当于「作答」）**：从第二个字开始，模型一次只能蹦出一个 Token，拼到末尾再算下一个。**要命的是：每蹦出一个字，GPU 都得把整套几十上百 GB 的模型权重从显存里搬出来过一遍，实际计算量却很少**——就像为了写一个字，把整本大辞典从头翻到尾。因此 **Decode 的瓶颈根本不在算力，而在显存带宽（「翻书」速度）**，它直接决定 **TBT / TPOT（Token 间时延，模型说话的语速）**。

这就直接解开了开篇的第一个谜题：**为什么输出价格比输入贵 4 倍？** 因为输出必须一个字一个字串行「翻书」，单位时间内占着 GPU 显存带宽的时间远远高于一次性并行的读题。

既然「翻书」最费功夫，那翻一次书顺便帮 64 个请求各写一个字，是不是就值回票价了？这就是**批处理（Batching）**：1 个请求和 64 个请求合批做一步 Decode，耗时差不了太多，产出却翻几十倍。早期静态批处理要等批次里最慢的那个写完才放行整批；现代框架全标配了**连续批处理（Continuous Batching）**，每吐出一个 Token 就调度一次，谁写完谁立刻下车，新请求随时插队上车，像一趟不停站随上随下的环线公交。

**零件二：KV Cache（模型的草稿纸）**

模型每生成新 Token，都要回头看前面所有内容算注意力关联。如果不存中间结果，写第 1000 个字就把前 999 个字重新算一遍，算力直接爆炸。

**KV Cache** 就是把前面每个 Token 算好的 Key 和 Value 中间矩阵存下来。后面写新字时直接查这张「草稿纸」，只算新字本身。但草稿纸极吃显存，大小同时跟**上下文长度**和**当前并发数**成正比——生产里最先爆掉的往往不是模型权重，而是塞满显存的 KV Cache。常用的瘦身招数是**量化**：用 8 位（FP8/INT8）甚至 4 位精度存权重和 KV Cache。降到 8 位多数场景几乎无损，降到 4 位压缩极狠但容易伤准确率，得拿业务集实测；另外许多新模型（如采用压缩注意力结构的模型）从网络结构源头上就把草稿纸做薄了。记住一句口诀：**模型能不能跑起来看权重显存账，同时能服务多少人主要看 KV Cache 的账。**

**零件三：TTFT、TBT 与有效吞吐的三角平衡**

把更多请求塞进同一批次，总吞吐上去了，可大家抢时间片导致单人语速（TBT）变慢；优先插队给新请求做 Prefill 降了首字等待（TTFT），正在吐字的老请求就会瞬间卡顿。行业用 **有效吞吐（Goodput）** 衡量真本事——也就是**在不突破业务延迟红线的前提下，最多能扛多少流量**。

**零件四：MoE（混合专家）的显存账**

像 DeepSeek-V3 总参数 6710 亿，每个 Token 实际只唤醒大约 370 亿参数的几个「专家」计算——算得快、知识量大，代价是**全部 6710 亿参数的专家都得常驻显存**，单机根本塞不下。于是必须拆到多张卡上，卡间频繁传数据、热门专家堵车就成了集群推理的新难题。

---

### 跟着一个 8000 Token 的 Agent 请求走完六站

假设企业内部客服 Agent 把系统提示词、十几个工具定义、前几轮对话记录和最新提问打包成 **8000 Token** 发给模型服务，它在推理框架内部要经过六站：

#### 第 1 站：入口层（协议转换、对话模板与防逃逸）

接入层先把外部 API 请求套进该模型专属的「对话模板」，用特殊控制符区分谁在说话、哪里是工具参数，再由 Tokenizer 切成 Token ID。**注意两条隐形雷区**：第一，模板拼错一两个换行或特殊符号，模型照样吐字但能力大跌、工具调用狂出错；第二，如果用户输入或工具返回的脏文本里刚好混入了模型特殊控制符，入口层必须当普通文本转义，否则黑客直接靠一段网页文本就能伪造系统指令注入。请求算完后，再由入口层把 Token 还原文字、拆出思考过程和工具 JSON 流式吐给前端。

#### 第 2 站：调度层（连续批处理、分块预填充与前缀路由）

Token 排进等待队列。这 8000 Token 立刻给调度器出了个难题：如果一口气跑完这 8000 字的 Prefill，同卡上几十个正在流畅吐字的请求就得全停下来干等，用户端明显一卡一卡的。

现代框架的解法叫**分块预填充（Chunked Prefill）**：把 8000 Token 切成比如每块 512 或 1024 Token，每一步只算一小块，和其他老请求的 Decode 混在一锅算——新请求不用干等太久，老请求也不会卡顿。如果 KV Cache 爆了，调度器还会忍痛暂停低优请求、把它们的草稿纸换出到主机内存甚至丢弃重算；同时靠**异步调度**让 CPU 在 GPU 算当前步时就把下一步输入备好，不让 GPU 傻等 CPU。多机场景下还有上层负载均衡器（例如阿里云 PAI-EAS 智能路由），专门把相同前缀的请求优先派往已经存着对应 KV Cache 的机器。

#### 第 3 站：执行层（四种并行、底层算子与图录制）

调度器拍板这一步算谁之后，交给执行层上 GPU 真算。单卡放不下就拆卡并行，四种切法各有用途：
- **张量并行（TP）**：把每一层的大矩阵劈开分给多张卡同时算，适合单卡装不下、追求单请求低延迟（要求卡间高速互联）；
- **流水线并行（PP）**：把不同网络层像工厂流水线一样分给不同机器接力；
- **数据并行（DP）**：每套副本完整放模型，各接各的请求拼总吞吐；
- **专家并行（EP）**：专门服务 MoE，把不同专家拆到不同卡上——大规模 MoE 的 Decode 经常用「几十路 DP + EP」扛超大吞吐，遇到热门专家排队拖慢全队时，框架还会把热门专家多复制几份均衡负载。

到了每张卡最底层的算子（Kernel），比如 FlashAttention 通过减少显存来回搬运把注意力算飞起；又因为 Decode 每步计算量小、CPU 启动 GPU 算子的固定开销占比很高，框架还会用计算图录制（如 CUDA Graph）把整步调用录下来一次性回放，挤干硬件空档。

#### 第 4 站：缓存层（PagedAttention 与多级前缀复用）

回到那道账单谜题：**为什么缓存命中价格能打到未命中的 1/50？**

前面说过，8000 Token 里绝大部分（系统提示、工具列表、前面多轮对话）在上一次请求里刚算过。早期框架为防对话变长，只能给每个请求预留一整块连续的「最大长度」显存，结果实际只用了两三成，其余全空耗着，还很难跨请求共享。

**PagedAttention 的破局灵感直接抄自操作系统内存管理**：不再一整块连续划地盘，而是把 KV Cache 切成固定大小的 **「页（Page / Block）」**，用一张页表记录映射，物理显存里东一块西一块散着放也无所谓，写多少页才申请多少页——显存浪费瞬间压到极低，并发立刻翻倍！更重要的是，只要两段请求的开头前缀 Token 一模一样，它们就可以直接指向物理显存里 **同一批 KV Cache 页**，实现零重复计算的 **前缀缓存（Prefix Caching，如 SGLang 的 RadixAttention）**！

显存装不下所有热前缀时，现代架构还会做**显存 → 主机内存 → 本地 SSD → 分布式缓存池**的多级卸载与池化共享（例如阿里云 Tair KVCache 就是把多台 GPU 机器的显存和内存池化，适配 vLLM/SGLang/TensorRT-LLM 共享复用）。

> **给 Agent 开发者的一条立省大钱的实战原则**：一定要把**固定不变的系统提示词、工具定义、共享背景知识放在输入最开头**，把每轮新对话和动态变量追加在最末尾！千万别为了省事在系统提示词第一行插入「当前精确时间：2026-11-21 20:05:31」——只要开头第一个字变了，后面几千上万 Token 的前缀缓存全部失效，直接错过一两折的缓存折扣和首字加速！

#### 第 5 站：集群层（PD 分离与大规模弹性容错）

单机扛不住时，推理框架进化成分布式集群，这里最关键的架构革命叫 **PD 分离（Prefill-Decode Disaggregation）**。

前面讲了，Prefill 极度吃算力、Decode 极度吃显存带宽。过去把两者塞在同一批 GPU 卡上算，长文档一进门做 Prefill，整张卡算力被抽干，旁边所有正在吐字的用户全部卡死。**PD 分离干脆把机器拆成两支专业队伍：一组机器专门做 Prefill（配高算力卡和小并行），读完题把产出的 KV Cache 通过 RDMA 高速网络甩给另一组专门做 Decode 的机器（配大显存带宽和适合大吞吐的并行）继续吐字，两者互不打架！** 多模态模型还可以把图片/视频编码器再拆一层独立扩容。

以阿里云 PAI-EAS 部署 MoE 模型的 PD 分离模板为例：Prefill 实例默认采用 8 卡张量并行（TP=8）把长读题压到最短；Decode 实例则默认采用 8 路专家并行加 8 路数据并行（EP=8 + DP=8）稳稳撑高并发吐字，平台还能按输入输出长度自动推荐实例配比。当然，上百张卡拼成一个大实例后硬件坏卡是常态，集群编排层必须能及时把受影响请求切走、靠冗余实例弹性缩扩容顶上。

#### 第 6 站：采样与输出（确定性、结构化约束与投机解码）

模型每步算出来的其实不是某一个字，而是整个词表上几万个 Token 的概率分布。最后一步 **采样（Sampling）** 决定从中挑哪个字（Temperature 越高越随机发散，Top-p/Top-k 卡住候选池范围）。

这里解开很多工程师的另一个大困惑：**为什么我把 Temperature 设为 0，同一句输入调两次 API，偶尔还是会吐出不一样的字？** 原因在于 GPU 浮点加法不满足严格结合律——你的请求这次和 A 拼在一个批次里算、下次和 B 拼在一起算，算子并行归约顺序微小变化带来十万分之一的浮点误差，恰好在某一步把两个并驾齐驱候选词的概率反超了，后续整段回答跟着分叉。为了保证评测和强化学习训练可复现，部分框架开始支持「批不变（Batch-invariant）」的确定性推理模式，代价是牺牲一部分调度灵活性与性能。

采样这站还能顺便解决 Agent 的两个老大难问题：

1. **结构化输出（防 JSON 解析崩盘）**：Agent 调工具最怕模型少写半个括号导致程序报错。推理框架可以把 JSON Schema 或正则编译成语法状态机，在每一步采样前把违反语法的非法 Token 概率直接清零（Mask），从物理层面上保证 100% 吐出合法格式。
2. **投机解码（Speculative Decoding，白嫖闲置算力提速）**：既然 Decode 每次翻完整本大字典却只写一个字，GPU 算力单元其实大多在发呆。投机解码找一个极小极快的「草稿模型」（比如上一篇说的拿 KL 蒸馏出来的小模型，或者主模型自带的轻量预测头如 EAGLE），一口气连续猜出后面 4~5 个字，再送给大模型**一次性并行前向验证**这 5 个字——猜对了 4 个就直接一次性收下 4 个字，猜错的从出错那个位置按拒绝采样重选。因为经过严格数学拒绝采样校正，**最终生成出来的概率分布和老老实实逐字生成一模一样、毫发无损，生成速度却能显著加快**！

最后，采样出来的 Token 回到第 1 站转成流式文本返回给你，并结算清楚总输入 Token、缓存命中 Token 和输出 Token。下表帮你一图兜底这六站脉络：

| 环节 | 主要工作 | 解决的问题 | 主要影响 |
| --- | --- | --- | --- |
| 入口 | 协议转换、对话模板、分词、输出解析 | 让请求以正确的格式进入模型 | 效果一致性、安全性 |
| 调度 | 连续批处理、分块预填充、显存准入、负载均衡 | 下一步让 GPU 算什么 | 吞吐、首字延迟、卡顿 |
| 执行 | 并行策略、算子、低精度计算 | 每一步算得多快 | 单卡性能、硬件利用率 |
| 缓存 | 分页管理、前缀复用、多级缓存 | 算过的不再算 | 成本、首字延迟 |
| 集群 | PD 分离、大规模并行、扩缩容与容错 | 规模化之后如何稳定高效 | 整体吞吐、稳定性 |
| 采样与输出 | 采样策略、确定性推理、结构化输出、投机解码 | 输出是否可控、可复现、足够快 | 可靠性、生成速度 |

## 17.2.3 开源版图与工程落地取舍

### 开源推理框架的四条演化脉络

从 2023 年算起短短三年多，开源推理界已经演进出四条清晰阵营（下述 GitHub 星标数统计截至 2026 年 10 月，仅作社区热度参考，不作优劣排序）：

**1. 服务器端通用推理引擎（主力底座）**

| 项目 | 发起方 | 首次公开 | 主要特点 | GitHub 星标 |
| --- | --- | --- | --- | --- |
| vLLM | 加州大学伯克利分校 Sky Computing Lab | 2023 年 6 月 | 提出 PagedAttention 分页管理 KV Cache；2025 年 5 月成为 PyTorch 基金会托管项目 | 约 9.4 万 |
| SGLang | LMSYS | 2024 年 1 月 | 提出 RadixAttention，自动复用请求间的公共前缀；重视结构化生成 | 约 3.7 万 |
| TensorRT-LLM | 英伟达 | 2023 年 10 月 | 面向英伟达 GPU 深度优化 | 约 1.5 万 |
| LMDeploy | 上海人工智能实验室 InternLM 团队 | 2023 年 | 集模型压缩、部署和服务于一体 | 约 0.8 万 |

老牌先驱 Hugging Face TGI（Text Generation Inference）自 2022 年登场后，已于 2025 年 12 月正式转入维护模式，官方建议用户转向 vLLM、SGLang 等新一代引擎。回看演进能发现两个规律：一是**学术到生产极快**（2022–2024 年间的 Orca 连续批处理、PagedAttention、FlashAttention、投机解码和 DistServe/Splitwise PD 分离论文几乎落地即主流）；二是**单机特性已高度趋同**，大家现在拼的是新模型发布当天能不能跑起来（例如 2025 年 9 月 DeepSeek-V3.2-Exp 发布当天、Qwen3-Next 发布次日 vLLM 就宣布支持）、国产芯片生态好不好接，以及大规模集群里稳不稳。

**2. 本地与端侧运行（个人电脑与消费级设备）**

`llama.cpp`（2023 年 3 月，C/C++ 实现，推出普及极广的 GGUF 量化格式，星标超 13 万）和 `Ollama`（一条命令本地拉起跑，2025 年起逐步转向基于 GGML 的自研引擎，星标超 18 万），再加上靠编译技术跑进手机和浏览器的 `MLC-LLM`，共同撑起了本地开发调试和端侧隐私推理生态。

**3. 集群编排层（2025 年后的真正分水岭）**

当单机引擎优化撞到天花板，行业开始在引擎上面再架一层专门管多机调度、PD 分离和跨机 KV Cache 传输的分布式编排层：包括英伟达 2025 年 3 月推出的 **Dynamo**（支持对接 TensorRT-LLM/vLLM/SGLang）、红帽联合 CoreWeave/谷歌云/IBM/英伟达发起的 K8s 原生方案 **llm-d**，以及月之暗面 2024 年公开、凭以 KV Cache 为中心的 PD 分离架构摘得 FAST 2025 最佳论文的 **Mooncake**（已陆续开源数据传输引擎与存储组件）。**单机比谁算得快，集群比谁调度得好。**

**4. 模型厂商与大厂自研开源系统，以及硬件多元化适配**

头部玩家越来越发现模型架构和推理系统必须协同设计：DeepSeek 在 2025 年 2 月开源周放出了 FlashMLA、DeepEP、DeepGEMM、EPLB、3FS 等核心底座组件（其内部引擎最早脱胎于早期 vLLM 分支），并于 2026 年 10 月正式开源完整推理框架 **DeepInfer**；同期还有专注国产芯片支持的京东 **xLLM**、阿里 **RTP-LLM**、百度 **FastDeploy 2.0**。

在硬件多元化上，推理框架越来越成为「模型 ↔ 芯片」之间的关键翻译层：vLLM 在 2025 年推出硬件插件机制后，衍生出华为昇腾 `vllm-ascend`、百度 `vLLM-Kunlun`、沐曦等适配，DeepInfer 也同时支持英伟达 GPU 与华为昇腾 NPU；模型侧同样开始反过来迁就硬件特性（如 DeepSeek-V3.1 采用针对下一代国产芯片设计的 UE8M0 FP8 数值格式），再加上 Triton、TileLang 等高层算子语言降低了移植成本。不过选型时务必要实测——**不同芯片配不同引擎版本，支持的模型范围和吞吐差异依然很大，切忌看纸面宣传盲目上线。**

### 五类团队怎么对号入座用推理框架

1. **模型厂商与云厂商**：算力利用率直接决定毛利和 API 报价，通常养专职推理团队深度魔改开源引擎或自研。
2. **金融/政务/医疗/制造等私有化企业**：数据不出域，需要自建机房或跑在国产芯片上；要么采买推理一体机省心，但做容量规划和选型时必须算得清显存权重账与 KV Cache 并发账。
3. **Agent 与 AI 应用团队（绝大多数读者）**：虽然日常直接调模型 API，但**处处都在吃推理框架的红利或亏**——选供应商要看清 TTFT、TPOT 和缓存命中价；写 Prompt 要死守「固定前缀放最前、动态信息放末尾」保缓存命中；调工具要盯牢结构化输出支持度；还要靠可观测工具（例如阿里云 AgentLoop）逐层把每次调用的 Token、缓存命中和耗时拉出来看清钱到底花在哪一步。如果打算把意图分类、信息抽取等高频环节拆出来自己部署小模型，也会立刻直面推理框架选型。
4. **后训练与科研团队**：做 RL Rollout、蒸馏采样和大规模评测，最看重离线高吞吐以及**推理采样概率与训练引擎数值对齐**。
5. **个人开发者**：看重一条命令装好、能在笔记本或消费级显卡上跑得动隐私数据。

## 结语

总结成一句话：**Model 决定 Agent 能做多聪明的事，推理框架决定这份聪明每次干活要花多少钱、让用户等多久。** 智能体越普及，单次任务的调用轮数越多、每轮上下文越长——在这道乘法题里，推理层省下来的每一分算力和每一毫秒延迟，都会被调用规模成倍放大。
