# 第 21 章　Agent 黄金数据集

客服团队发现 Agent 老在回复里漏掉一个关键步骤，研发补了两句提示词上去，当场再问一遍——答全了。可兴奋不过三秒，三个新问题马上砸过来：**用户换个说法还灵不灵？改完这句，别的原本答得很好的题有没有变蠢？下个月切换新模型，这个老毛病会不会悄悄复发？**

每次出事都现翻日志、靠人工肉眼凭印象“感觉好多了”，团队迟早会被压垮。**黄金数据集要干的事，就是把业务认账的“考题”和“怎么算答对的尺子”一起冻成题库资产。** 以后不管是改提示词、加 Skill、换知识库还是切模型，全都拉到同一张考卷上考一遍，行不行拿分说话。

在平台里，Dataset 就是管这张考卷的地方。上一章把线上轨迹源源不断加工进了候选表，这一章讲怎么挑题、定死标准、建成黄金集，并让它真正在日常迭代里守住底线。

## 21.1 黄金数据集到底是什么，值不值得专门花精力建

**黄金数据集不是什么高深格式，就是一组经过业务拍板的任务清单：每条既有“题目”，也有“怎么判及格的标准”。** 纯知识问答主要靠参考答案和必须覆盖的要点；退款、订票这类操作任务还得写明业务系统最终该变成什么状态；代码任务则配上测试用例和验收命令。

“黄金”二字指的是**题目真实、判据靠谱**，绝不是非要挑那些本来就答得漂亮的高分样板。恰恰相反，**线上曾经翻过车、被业务补齐了正确答法和扣分细则的错题，才是黄金集里最值钱的压箱底考题。**

| 团队想解决的问题 | 黄金集怎么帮上忙 | 带来的实际改变 |
| --- | --- | --- |
| 扯皮“到底算不算答得好” | 让业务一次拍板这批题的参考答案与评分标准 | 运营、研发、测试对准同一把尺子，少在群里口水仗 |
| 选型新模型或新 Agent 方案 | 让几个候选方案在同一张考卷上跑结果、耗时和费用 | 按自家真实业务选型，不盲信外部通用榜单 |
| 确认某次改动值不值得发 | 保留修改前后逐题的回答和分数对比 | 一眼看出想修的问题好没好、有没有把原本正常的题改坏 |
| 防止修好的老毛病复发 | 把历史故障和主干题收进回归范围，上线前必跑 | 每次投诉和线上事故都变成长期防线 |
| 检验自动评估器靠不靠谱 | 拿人工早定好分数的样本去测试机器评估器 | 让自动打分尽量贴合业务专家口味，减少误报垃圾告警 |

拿产品客服举例，“有哪些功能”看重能力说全没说全，“如何做评估”看重步骤照着能不能走通。把这两类题和各自标准留进黄金集，以后产品每升一次级，只需要顺手更新对应那几行的标准，就能一直盯住客服有没有说错话。

记住一点：**一套锁在抽屉里从没进过评估、实验或发版门禁的数据集，整理得再精致，对 Agent 也没有产生一分钱价值。**

## 21.2 Dataset 日常都能拿来干嘛

进对应 AgentSpace 的「数据中心 → 数据集」，你可以把它当成一张专门服务评估和调优的业务表：一行一道考题，一列一个字段。表建好了还能随时添行、加列、人工复核、打版本快照。

| 当你想干这件事 | 在界面上点哪里 | 最适合什么时候用 |
| --- | --- | --- |
| 把手头现成题库导进来 | 创建数据集时选上传 CSV / Excel / JSONL | 团队原本就有 FAQ、测试用例或整理好的 Excel 表 |
| 从线上真实运行里挑题 | 从 Trace / 轨迹导入，或在单条轨迹点「加入数据集」 | 把真实投诉、报错任务和奇怪问法收进候选池 |
| 从零手写几条摸索流程 | 创建时选「从空白开始」，建完字段自己填 | 冷启动期没流量，或者请专家直接出典型边界题 |
| 补参考答案、场景和评分细则 | 「字段管理」加列，进「数据详情」逐条编辑 | 题目有了，得把怎么判分写清楚 |
| 人多题多，先预分类再逐条审 | 「AI 标注」和「标注管理」 | 批量打场景标签、初筛嫌疑样本，再分发人工复核 |
| 重要对比前冻结一份题库 | 版本管理里的「创建版本」 | 上线大版本、正式评测或规则大改前留个只读快照 |
| 真正跑起来看分 | 「发起评估」和「发起实验」 | 评估查历史已有回答，实验让新改的 Agent 重新做一遍 |
| 导出去给外部系统用 | 导出当前筛选结果，或离线全量下载 | 做外部分析、拼微调训练集或离线归档 |

第一版题库千万别贪大，先把团队最头疼、最核心的二三十道题放进来把标准立住，后面缺啥再添。

## 21.3 实战搭建：从零攒出一份产品客服黄金集

继续用演示里的两道经典考题走完整套动作：“Agent 观测与优化有哪些功能”和“Agent 观测与优化如何做评估”。目标很实在——看客服能不能既把产品能力讲全，又给出用户照着就能上手的操作步。

### 第一步：先建“候选集”，把值得考的题先拢起来

点「创建数据集」，起名 `customer_service_candidates`，备注写清这是“产品客服候选题库：收真实咨询和低分回答，等产品专家复核”。手头有 FAQ 表格就直接传（预览一定看清列有没有错位）；线上有流量就从轨迹详情挑选加入，或者让上一章的 Pipeline 每天往里喂；连流量都还没有，就请产品和客服先手写几条高频题和红线边界题，在来源列标好出处就行。

### 第二步：设计几个精简够用的字段，把“考什么、怎么判”说死

去「字段管理」加好这六列基本盘，全用文本字段就能跑起来：

| 列名 | 示例字段名 | 实际填什么 |
| --- | --- | --- |
| 题目 | `input` | 用户原始提问；如果是多步操作，把必要前提条件写在这里 |
| 原回答 | `actual_output` | 当时线上 Agent 怎么回的，方便复核时对照挑刺 |
| 参考答案 | `expected_output` | 业务认可的标准答案或最终应达成的结果 |
| 评分要求 | `rubric` | **核心尺子**：必须覆盖哪些点、怎么算分、踩中哪些底线一票否决 |
| 场景 | `scenario` | 功能介绍、操作指导、异常处理等，用来统计覆盖面 |
| 来源 | `source_ref` | 原轨迹 ID、产品文档版本号或专家编写人 |

**为什么“参考答案”和“评分要求”最好一起配？** 参考答案是给一个“长这样就算合格”的范本，而评分要求是划清“哪些要点必须做到、允许换什么措辞表达”。对开放式问答，千万别按字面一字不差死抠！

| 题目 | 参考答案要给什么重点 | 评分要求（Rubric）该盯什么 |
| --- | --- | --- |
| Agent 观测与优化有哪些功能？ | 讲清观测、数据处理、评估实验、经验使用等核心能力及各自用途 | 覆盖用户关心的能力了吗？讲清能解决什么问题了吗？有没有胡编不存在的承诺？ |
| Agent 观测与优化如何做评估？ | 串起准备数据、建评估器、配任务、看结果与改进的完整路径 | 给出功能入口了吗？提到输入输出字段映射了吗？说明低分怎么拿去改进了吗？ |

演示里踩过一个很实在的坑：最开始把这两道题的标准揉在同一个评估器里，结果跑完根本看不清错在哪；后来干脆在数据集里加了一列逐题 Rubric，每道题各写各的判据，低分马上能对应到具体漏了哪一步。下面就是“如何做评估”的逐题 Rubric 范本，业务同学直接拿去微调权重就能用：

> 按四项检查，每项满足得 0.25 分，否则得 0 分：①说明如何准备并选择评估数据；②说明如何选择或创建评估器；③说明用户输入、Agent 输出与轨迹的字段映射；④说明如何运行评估、查看解释并处理低分样本。输出逐项得分、总分及缺少的内容。若编造产品能力或操作入口，另标记为不通过并说明具体问题。

### 第三步：先凑一起手工对齐几条，再放 AI 批量预整理

进「数据详情」，挑几条典型题拉着业务和研发当场对一遍——**很多分歧都是这时候吵出来的**：比如介绍功能到底要不要顺便给使用建议？操作指导是不是必须写出具体点哪几个菜单？先把这几条规矩定死、补进参考答案和评分要求，再放手批量整理。

题目攒到几十上百条，手工贴标签太累，就开「AI 标注」，勾选题目、原回答等关注字段，让它先按“功能介绍、操作指导、异常处理”归类，或者初步标出“疑似漏步”的样本。**一个小提醒**：只想给新进来的题补标签，就选“跳过已有结果”；只有分类体系推翻重来时才选“覆盖重标”。任务跑完一定要抽查几条确认 AI 没理解岔。**AI 预标注只负责省力气，黄金题目的合格标准必须由业务人员最终拍板。**

### 第四步：复核定稿，正式搬进黄金集

多人一起审题时，在「标注管理」配好模板，把题目、原回答、参考材料展示出来，把“答案对不对、缺了哪块、要不要补证据”做成固定填写项，大家一条条过完，有争议就翻原轨迹对齐。

**注意一个特别容易漏的细节：最终实验要用的参考答案和 Rubric，必须实打实填进约定的数据列里，评估器才读得到。** 如果你只随手在讨论区批注了一句“这题以后应该这么答”，自动化实验是看不见的。

复核通过的这批样本，筛选勾选后点「加入数据集」，送进新库 `customer_service_gold_v1`（或者导出再导入新集）。**所谓“黄金集”不是一种特殊的数据集类型，而是团队给这批“标准已确认”的样本赋予的用途身份。** 证据不全或还在吵架的题，老老实实留在候选集里等补齐；已经坐实有问题并补好正解的，就成了团队正儿八经的 Badcase 资产。

## 21.4 题库怎么挑，才不会测出个“虚假繁荣”

只收低分翻车题，改完之后根本不知道正常能力有没有退化；只收高频大白话问题，上线后一遇高风险边缘场景照样出大事。挑题时让运营、专家和研发一起照着下面这张五类拼盘对照着补：

| 必须留的五类题 | 为什么不能少 | 客服场景举例 |
| --- | --- | --- |
| 高频常规问题 | 决定了绝大多数用户的日常体感 | 功能介绍、怎么接入、常见配置怎么改 |
| 曾经翻过车的故障题 | 专门盯着修过的 bug 别死灰复燃 | 回答漏操作步骤、引用早下线的旧功能 |
| 高风险与业务红线边界题 | 防住“概率低但一旦做错代价极大”的事故 | 没权限的越权操作、胡乱承诺不存在的能力、泄露敏感信息 |
| 原本答得好好的正常题 | 当警报器，第一时间揪出“修一处坏三处”的退化 | 过去一直能答全的标准操作问答 |
| 换种说法与多轮追问 | 验证是不是死记硬背了某种问法 | 简称、口语化提问、回答中途突然补充新条件 |

按“场景”这一列做个透视，哪一栏密密麻麻全是相似题、哪一栏还是零，一目了然。**永远优先填空白场景，别在一个高频问法上凑十道差不多的题。** 不过如果同样一句话，因为用户账号权限、产品版本或前面聊过的上下文不同，正确答案也跟着变了，那它们就不是重复题，必须各自保留并标清前提。

碰到还要实际干活的操作题（比如退款或改配置），**一定要在题目里把起始条件写死**：新实验该从“订单已满足退款条件”这个干净状态起步，而不是直接照搬当年报错时的历史残局；除非你测的就是“失败中断后能不能正确恢复”，那才需要专门把那个失败检查点原样搭出来。

第一批黄金题哪怕只有二三十道也完全够用，关键是**每一道题团队都有人能讲清：为什么留它、怎么算对**。以后线上每处理完一类新故障，顺手往里添一两道代表题、淘汰过时的旧题，题库自然就活起来了。

## 21.5 建好之后怎么真正派上用场

**1. 当校准题，先验评估器准不准**

挑几条人工早已定性的好回答、坏回答和擦边回答，直接点「发起评估」，把字段接给评估器跑一圈。如果连你明明标成“坏回答”的样本都被机器打了高分，别急着上线自动告警——先查是不是字段接错了、或者标准条款写得有漏洞，调到机器打分和专家判断大致对齐为止。

**2. 当标尺，对比两个版本的真本事**

点「发起实验」，同一批题先让现在的线上版本（Baseline）做一遍，再让改完的新版本（比如刚加了一门评估操作 Skill）做一遍，对比新生成的答案和轨迹。**看成绩一定先看逐题变化，别被平均分蒙蔽了**——如果平均分涨了 10 分，可“如何做评估”这道核心操作题照样少关键一步，这次改动就还不能放行；同时盯紧“有哪些功能”等正常题的得分、总耗时和 Token 成本有没有崩。

**3. 当长期回归防线，发版前自动跑**

挑出历史故障、核心主干流程和一部分正常题作为长期回归范围，每次换模型、改提示词、升级 Skill 或刷知识库前跑一遍，甚至交给调度定时跑。**黄金题和回归题完全可以是同一份数据，不需要为了两个称呼复制出两份一模一样的库**（除非需要独立的权限隔离或发版节奏）。

## 21.6 题库要跟着业务变，但做实验时别晃尺子

正式开始对比前，去数据集的「版本管理」点「创建版本」，写清版本号和快照说明（比如“v1.0，产品客服操作指导，按本月产品文档口径确认”），方便以后翻旧账查当时用的哪一版考题。

需要注意控制台的一个操作特点：**历史版本只能作为只读快照查看，发起评估和实验跑的是数据集当前的最新数据。** 所以最稳的实战习惯是：这轮对比直接拉一个独立的黄金集，审定封版后做完版本留档，**对比实验期间谁都不许再往里增删改**；日常流水线新捞出来的样本继续进候选集，等下个周期复核完再统一出 v2.0。

产品规则改了、文档更新了，别忘了同步修订受影响考题的参考答案与评分标准，顺带记清对应的文档版本，外部附件也要留可重取的副本。导出交给别人时，看清界面导的是当前过滤出来的子集还是全量。

最后一条极其关键的工程纪律：**千万别用同一批题“既指导改 Prompt / 写 Skill / 挖经验，又拿来宣布最终验收通过”。** 就像不能拿平时刷过答案的模拟卷当高考真题一样——拿一部分题去诊断和调优，另留一批从没参与过本轮修改的黄金题专门做独立验收；一旦哪道验证题被研发反复拿去对照着调提示词，它就已经失去盲测资格了，得抓紧再留一批新验证题。

这样跑顺之后，每次用户吐槽和故障排障都不再是一锤子买卖：业务添进真实要求，研发拿它验真伪，测试盯着回归防线，整个团队手里就真正攒起了越滚越厚的工程资产。
