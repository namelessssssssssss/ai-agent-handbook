# Agent 调优总览

模型调优改的是模型权重本身；智能体调优管的是一个已经上线的 Agent，怎样把模型、工具和业务规则配合好，把同类任务一次次做稳做对。从第 18 到第 23 章，全都在讲同一条闭环主线——**数据飞轮**：把真实运行留下的日志和现场，整理成可复用样本、可执行判据和可对照实验，再把验证有效的改动稳妥带回线上环境，让系统越跑越靠谱。

这一章先搭好整套数据飞轮的全景骨架，说清楚 Agent 上线后为什么还得持续盯着「办得对不对、花了多少钱」，以及后续几章各自接哪一棒：第 19 章把零散日志穿成可读轨迹（Trajectory），第 20 章用声明式 Pipeline 批量洗出业务样本，第 21 章沉淀出带判据的黄金数据集，第 22 章靠持续评估和对照实验抓住 Badcase，第 23 章把验证过的好做法收进 Skill、经验和运行机制做受控自进化。

动手落地时，不用等把六章全吃透再开工。最务实的姿势是从团队眼下最痛的点切入——排障太慢、账单太贵，还是业务质检跟不上——先顺着「找到问题 → 定清标准 → 验证改动」把第一圈小闭环跑通，再把自动化一环环补上。

## 18.1 Agent 上线以后，还要持续回答哪些问题

写传统后端代码时，条件分支、接口入参和状态流转都是写死的：输入和依赖一致，每次跑出来的路径基本可预测、可复现，单测和集成测试卡住接口契约就稳了一大半。

Agent 把一部分决策权交给了概率性的 Model：你定好目标、给齐工具和规矩，具体先查哪个接口、参数怎么拼、报错后怎么绕弯，全靠模型在运行时自己看现场决定。拿退款举个例子：接口只管按订单状态和规则吐出能不能退；Agent 却得先从含糊对话里认清用户说的是哪笔单，挑对规则去核验，选准操作，最后还得核实钱是不是真的退下去了。**对话聊得客客气气、后端接口也没报 500，完全不代表这件事真办对了。**

| 关注点 | 传统应用中的确定性业务逻辑 | Agent 应用新增的要求 |
| --- | --- | --- |
| 执行路径 | 检查代码规定的分支 | 检查模型为什么选择这条路径，以及中间反馈怎样影响后续行动 |
| 正确性 | 验证接口契约和状态转换 | 同时验证目标达成、业务约束和交付结果 |
| 故障定位 | 查找代码或依赖的异常 | 进一步区分理解、上下文、工具使用和恢复策略的问题 |
| 变更验证 | 检查功能和历史场景 | 还要观察重复执行是否稳定，以及质量、成本、延迟怎样变化 |

因此，Agent 的执行即便零技术报错，照样可能彻底跑偏业务目标；而且同一套题，今天跑对了一次，明天换个问法或重跑八遍，未必次次都对。

### 18.1.1 Benchmark 提醒我们：会做、做完和稳定交付是不同层次

下面几组带明确测试日期的公开评测快照，最能说明「模型很强」和「业务能交付」之间隔着多远：

| 测试场景 | 公开实验快照 | 需要关注的问题 |
| --- | --- | --- |
| SWE-Bench Pro（Public），软件工程任务 | OpenAI 2026-03-05 报告：GPT-5.4 为 **57.7%**，研究环境、默认 xhigh 推理设置。[原始报告](https://openai.com/index/introducing-gpt-5-4/) | 在该任务与配置下，端到端完成仍有改进空间。 |
| OSWorld-Verified，桌面操作 | 同一报告中，GPT-5.4 为 **75.0%**，GPT-5.2 为 **47.3%**；报告引用的人类成绩为 **72.4%**。[原始报告](https://openai.com/index/introducing-gpt-5-4/) | 能力进步很快，业务交付仍要逐项确认是否完成。 |
| OSWorld 2.0，长流程任务 | 2026-07-13 论文 v2，108 个任务、500 步预算、最高思考水平及批量动作配置：Claude Opus 4.8 的 **严格完成率为 20.6%**，部分得分为 **54.8%**。[论文表 3](https://arxiv.org/html/2606.29537v2) | 完成许多中间步骤，并不等于交付了完整结果。 |
| τ-bench，业务规则下的工具与用户交互 | 2024-06-17 原论文：GPT-4o 原生工具调用在零售任务上的 **pass¹ 为 61.2%**，**pass⁸ 低于 25%**。[原论文](https://arxiv.org/html/2406.12045v1) | 一次做对之后，还要检查重复执行的可靠性。 |

注意两处容易看岔的细节：OSWorld 2.0 的「部分得分」高出「严格完成率」一倍多，说明走完很多中间步骤离完整交付还差得远；τ-bench 的 `pass⁸` 指的是同一任务连跑八次**八次全对**（区别于八次里蒙对一次就算的 `pass@8`），直接暴露出一次做对与反复稳定交付之间有多大落差。并且这些只是各自实验条件下的快照，不能直接换算成自家业务成功率。

所以上线后的团队永远要同时盯紧两个问题：**事办成了没有？办成花了多大代价？** 一条回答正确的轨迹可能来回查了五遍相同资料；一次 Token 暴降的优化也可能省掉了最关键的校验步骤。只看评估没有调优，手头只有分数不知道改哪；只改 Prompt 不做固定评估，改完永远只能凭感觉说「好像变好了」。

## 18.2 数据飞轮怎样把运行经验变成改进

很多团队的日常是「救火式排障」：今天线上有人吐槽，研发翻半天散落的日志找到原因，把 Prompt 改了两句就当结案；几周后用户换个问法踩进同一个坑，由于当时的现场轨迹没沉淀成题库、判定标准也没固化，新接手的同学又得从头摸黑查起。

数据飞轮解决的就是这种断点：它把每次运行留下的事实变成可复用题库，拿统一标准跑出低分问题，拿对照实验检验修改到底管不管用，再把验证通过的方案送回生产环境。里面有两条必须齐头并进的反馈线：

- **一条线打磨「标尺和数据」**：比如演示里客服 Agent 面对「有哪些功能」和「怎么配置评估」两类问题，标准完全不同。团队最初偷懒把标准全写进同一个通用评估器，跑完实验才发现判不准，于是倒逼自己在数据集里补出「题目级 Rubric」，逐题定细则、重配变量映射再测——运行结果反过来校准了你的评测尺子。
- **另一条线打磨「Agent 自身行为」**：评估抓出操作步骤漏了，去补一条 Skill；工具老被误用，去改清晰工具描述；发现接口超时后反复重提交，去修状态查询和幂等逻辑。所有改动先当「候选方案」，放到固定数据集上跟现网版本同台跑完实验再决定发不发。

也就是说，数据在飞轮里既帮你**找准该改哪**，更帮你**拦住那些「感觉有效、其实让别的题退步」的瞎改**。

## 18.3 围绕同一任务连接各个模块

![image](../../assets/imgs/chapter-18/image-001.png)

其中 **Pipeline 是整个体系的数据生产车间**。原始 Trace 是按单次 API 和工具调用打散的，评估看重完整任务轨迹，实验需要输入和预期答案，成本分析又盯着各节点 Token 与耗时——Pipeline 负责按不同用途去重、筛选、抽字段，把每天源源不断的运行记录自动洗成能直接喂给下游评估与实验的结构化样本；进库样本还能单独触发 AI 标注任务补全标签。

从实际工作视角看，六个核心模块各自帮你干一件事：

| 模块 | 用户怎样使用 | 帮助业务完成什么 |
| --- | --- | --- |
| Trace 与 Trajectory | 按应用、问题、工具或耗时搜索任务，展开步骤，选入数据集 | 找到答错、反复操作或耗时过长的原因 |
| Pipeline | 选择数据源和模板，配置业务字段、过滤与标注，预览后持续运行 | 把每天的运行记录变成质检人员和评估器能直接使用的样本 |
| Dataset 与人工复核 | 导入真实问题，填写参考答案与评分要求，确认后保存题库版本 | 积累可重复使用的业务验收题，减少每次升级重新准备测试的工作 |
| Evaluator 与持续评估 | 配置标准，用真实样本试评，再对指定范围持续检查 | 发现哪些场景需要改进，将人工阅读精力集中到值得处理的问题 |
| Experiment | 让当前方案与候选执行同一批题，比较逐题结果、成本和耗时 | 决定是否换模型、采用新 Prompt 或上线改动 |
| Trace2Optimizers | 从问题改进 Skill、工具与运行机制，或把历史方法送入经验召回 | 减少重复犯错与重复探索，使验证有效的方法参与后续任务 |

这六个模块不是一条单向死流水线：评估结果可以写回数据集让人工复核，复核可能推翻样本、也可能反手改掉不合理的评估器；优化方案必须回实验台做回归；新上线的 Skill 或经验又会改变下一批产生的线上轨迹。

拿「退款超时导致重复扣款/提交」这个经典现场来看边界就更清楚了：Agent 看到工具返回超时于是重新发起退款，其实后台数据库里第一笔已经成了。只有把业务结果状态补关联回 Trace，Pipeline 才能拼出完整真相；评估标出「结果核实缺失」，人工定清标准动作，研发再去评估是补查单工具、改操作 Skill 还是把接口改成幂等；最后实验必须同时测通成功、失败和超时不确定三种局面，才能放心上线。各管一摊、产物互认，出事才追得回原因，改完才算得清收益。

## 18.4 从一个业务问题开始，把第一轮做完

第一次建飞轮，千万别一上来就贪大求全。挑一个团队最疼、边界最清、结果好核实的小切口——比如「客服老答对概念却漏操作步骤」「排障 Agent 反复读同一批日志」「报告 Agent 引用过期数据」。以「产品客服漏掉操作步骤」为例，第一轮小闭环按六步就能跑完：

1. **捞出真实现场**：在「数据中心 → Agent 轨迹」筛出客服应用的操作咨询，专挑用户还在追问的那几条，看清原始输入和到底漏了哪一步。
2. **接上持续收数**：零散几条手动点加入数据集；如果想做成日常质检，配一条 Pipeline 抽出问题、答复和轨迹 ID，预览没错后定时跑进候选集。
3. **把业务要求写成题库**：拉产品或客服同学把标准答案和评分细则（Rubric）写进题目里选入黄金集——比如「如何做评估」必须说全准备数据、选评估器、配字段映射、看结果四步。
4. **先校准尺子再盯盘**：配好评估器后拿几道已知好坏的题试跑，确认它真能揪出漏步骤的回答，再挂成持续任务去线上抓新问题，挑典型题补回题库。
5. **改完让新旧版本同场做题**：补一条操作 Skill 或改掉 Prompt，拿同一份黄金集让旧版和新版各跑一遍，盯紧操作题分涨了没有、常规概念题有没有退步、耗时和费用扛不扛得住。
6. **上线并继续吃反馈**：通过后走应用发布流程确认真实生效，后续所有线上流量继续流过同一套轨迹与评估，把新冒头的问题送进下一圈。

一轮跑通之后，你手里攥着的不只是一份改过的 Prompt，而是一套可反复使用的业务验收题库、一份白纸黑字的评分细则、改动前后的硬对比账单，以及一条自动收数的管道。以后每次换底座模型或大版本升级，这些资产直接就能拿出来做回归拦截，省去从头踩坑。
