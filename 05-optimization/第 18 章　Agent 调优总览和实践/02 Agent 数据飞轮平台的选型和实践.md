# Agent 数据飞轮平台的选型和实践

宙斯是 1688 探索企业 AI 自主经营的组织经营大脑，把业务知识、数据和多角色 Agent 串起来，目前已经在 1688 即时零售、商业发展等业务线落地。本文记录的是宙斯团队在选型、接入和跑通 Agent 数据飞轮平台过程中的一线实操：怎么挑平台、怎么接探针、踩过哪五个坑、抓出了什么典型 Badcase，以及最后量化的提效数字。

## 一、接入前的痛点：盲人摸象式调优

对于研发和测试来说，只看「这一次 Agent 最终答没答对」远远不够——你必须知道答案是怎么一步步推导出来的、哪一步踩偏了、改完之后同类题能不能稳定全过。Agent 把模型推理、工具调用和多轮重试搅在一起，同样一句话发过去可能走出完全不同的路径。在接入飞轮平台前，宙斯团队主要卡在三个痛点上：

- **痛点一：出问题了不知该动哪一层。** 输出跑偏可能是 Prompt、Skill、工具参数或检索策略的问题，手头排查信息太碎，改完一处全靠肉眼盲猜「是不是改对了」，经验很难留下来。
- **痛点二：改完没法定量证明「真的变好了」。** 改了 Prompt 或 MCP 配置，手动测几条看似通过，既证明不了同类问题全修好了，也不知道有没有把别的场景改坏，发版全凭经验拍板。
- **痛点三：历史故障留不住，版本一变就复发。** 失败案例散落在日志和聊天记录里，没有沉淀成可重复跑的回归集。每次切模型或升级工具，研发又得重新人工过一遍，旧问题在不同版本里反复诈尸。

![image](../../assets/imgs/chapter-18/image-002.png)

_图 1-1：接入前的工作流_

为了打破这种「改一处、祈祷别处别坏」的局面，团队决定把执行观测、自动评估和样本回归真正连成闭环。

## 二、为什么选型 AgentLoop，它能接住哪些环节

### 2.1 三套方案对比与选型结论

团队对比了 AgentLoop、开源的 DeepEval 以及集团内部评测平台，核心考察与现有框架的适配度、运行观测深度和回归闭环成本：

| 方案 | 主要特点 | 优点 |
| --- | --- | --- |
| AgentLoop | 连接线上 Trace、质量评估、数据集和实验 | 观测、评估、回归一体化；通过 ARMS 探针无侵入采集 Trace，接入成本较低 |
| DeepEval | 通过测试代码维护用例、指标和回归流程 | 开源、代码化、接入灵活；适合纳入 CI 自动回归 |
| 内部评测平台 | 统一管理数据、任务和结果 | 一站式平台；部分应用免埋点或少量埋点；支持多类数据集、指标和实验对比 |

宙斯最终选定了 AgentLoop：它能用 ARMS 探针做到业务代码零改造接入，而且观测、自动评估和样本回流都在同一个工作台里，刚好接住团队当时的缺口。

### 2.2 核心三件事：看清过程、按业务打分、让错题进回归

把平台接进来主要靠三板斧：

1. **观测（先看清过程）**：平台把请求拆成 Session（多轮会话）→ Trace（单轮请求）→ Span（单次模型或工具调用），进而还原成结构化的 Agent 轨迹（图 2-1）。注意一点：能还原出多细的「白箱」，完全取决于探针和框架实际吐出了什么——**验收接入千万不能只看控制台冒出一条 Trace 就收工，必须点进去确认关键步骤都在**。

![image](../../assets/imgs/chapter-18/image-003.png)

_图 2-1：AgentLoop 执行链路观测_

2. **评估（调用成功不等于把事办妥）**：工具接口返回 200 只代表没挂，不代表满足了业务需求。平台支持把采集来的用户输入、推理步骤、工具调用和最终输出洗成数据集，配三种裁判打分（图 2-2）：明确规则用 **Code 评估**、常规语义用 **LLM 评估**、需要查业务知识库和核实多步证据的复杂判断，则让 **Agent-as-a-Judge** 挂载 Skill 或 MCP 自己查完事实再给分。

![image](../../assets/imgs/chapter-18/image-004.png)

_图 2-2：AgentLoop 任务评估_

3. **回归（让线上错题变成下一次发版的门禁）**：从线上抓到低分 Trace，人工复核确认问题后直接存进测试集；修改 Prompt、Skill 或模型配置后，用测试集重新真实请求新版 Agent，在尽量一致的业务条件下对比结果（图 2-3）。先围绕一个具体错题把这条路跑通，再把线上撞不到的低频边界场景人工补进来。

![image](../../assets/imgs/chapter-18/image-005.png)

_图 2-3：失败样本回归验证流程_

## 三、接入实操与五个避坑指南

### 3.1 为什么挑 ARMS GenAI Java Agent 探针

AgentLoop 支持 eBPF、LoongSuite 插件和语言框架探针三种接法。宙斯是基于 **AgentScope2** 开发的容器化 Java 应用，因此直接选了 **ARMS GenAI Java Agent 探针（jar 5.2.0-genai-1.0）** 配独立 AgentScope collector 上报到单独的 SLS workspace，与公司现有日志链路物理隔离。好处很直接：字节码自动插桩生成模型和工具语义 Span，业务代码零改动，通过启动参数一键挂载，且能靠开关剪掉非 Agent 相关噪音。

### 3.2 三步跑通接入与评估配置

**第一步：开 workspace 并挂载启动参数。** 在控制台开好 workspace（生产与预发务必分开命名），把 `licenseKey`、`appName` 和 `workspace` 写进应用启动参数（`licenseKey` 为空时只会打 WARN 跳过挂载，不影响主服务启动）。

![image](../../assets/imgs/chapter-18/image-006.png)

_图 3-1：ARMS GenAI Java Agent 启动参数配置_

**第二步：按三条硬标准验收 Trace 完整性。** 探针挂上后别急着配评估，先拿复杂请求测三件事（图 3-2）：① **步骤齐全**（每次模型、工具调用都有 Span 且入参出参可读）；② **嵌套正确**（子代理和异步任务不丢父 Span，没有孤儿断链）；③ **染色正确**（业务属性跨步骤传递不丢失）。如果业务代码里已经用了别的基于 OTel Context 的自建追踪系统，一定要给两套链路分配相互独立的 Context Key 和恢复逻辑，防止父子关系互相写乱。

![image](../../assets/imgs/chapter-18/image-007.png)

_图 3-2：AgentLoop Trace 完整性验证_

**第三步：打通「轨迹 → 数据处理 → 数据集 → 评估任务/评估器 → 结果」流水线。**

1. **数据处理与字段映射**（图 3-3）：从 OTel 轨迹里按时间、应用和状态筛出目标请求，抽取并映射到 `input`、`output` 和中间过程变量；
2. **沉淀数据集**（图 3-4）：主渠道靠真实轨迹自动转化，冷启动和低频异常靠人工补充，按用途拆进测试集、回归集和基准集；
3. **建评估任务、选评估器与运行**（图 3-5、图 3-6）：选定数据集和评估维度后，搭配三类裁判——**Code Judge**（Python/JS 沙箱判格式、关键词、阈值，零模型成本）、**LLM Judge**（Prompt 直评语义相关性，轻量见效快）、**Agent Judge**（可接私域知识、Skill 和 MCP 先查证再判，专啃业务合规与证据核验）——完成变量映射即可跑出 0~1 分的结果，低分样本直接点回原 Trace 追因并沉淀成测试集。

### 3.3 踩坑清单（接探针前先对照看一遍）

1. **生产和预发环境没隔离**：两个环境共用 `appName` 或 `workspace`，导致预发测试脏数据混进线上评估，分数失真。**解法**：按环境拆独立应用标识，并在评估任务筛选条件里按环境过滤。
2. **探针插桩开得太宽**：默认把数据库查询等海量基础设施 Span 全报上来，直接淹没真正的模型与工具链路（图 3-7）。**解法**：在探针开关设置里只开 AgentScope 所需组件，显式关掉数据库等非必要埋点。

![image](../../assets/imgs/chapter-18/image-012.png)

_图 3-7：AgentScope 探针开关配置_

3. **`user.id` 在异步调用后跟丢了**：只在入口 Span 设 Span Attribute，碰到异步子任务新建 Span 时不会自动继承，导致后面按员工查不到链。**解法**（图 3-8）：入口就把用户标识写入 OpenTelemetry Baggage，并在切异步线程前先捕获传递上下文。

![image](../../assets/imgs/chapter-18/image-013.png)

_图 3-8：用户标识的链路传递_

4. **多套链路追踪组件互相覆盖**：公司内部追踪 SDK 和 ARMS 探针共用同一个 OTel Context，导致子任务挂错父 Span 或整链断开。**解法**：为两套系统设置互相隔离的上下文键与父链路恢复逻辑，并用带异步子任务的请求专门验收父子嵌套。
5. **跨系统 TraceId 对不上**：内部日志系统、业务链路和 AgentLoop 各自生成自己的 TraceId，排障时没法用一个 ID 串到底。**解法**：在入口和关键节点日志里把两边的 TraceId 一起打印出来建映射，排障先凭任一 ID 找到日志再跳转另一侧查全链。

## 四、真实跑出来的效果与典型 Badcase 复盘

### 4.1 三个日常核心用法

接入跑顺后，宙斯把平台能力固定到三个常态动作里，串成「线上发现 → 实验验证 → 上线准出 → 持续盯盘」的闭环：

- **线上巡检**：通过 Pipeline 定期把线上轨迹喂给评估任务。在其中一轮巡检中，共覆盖 **2080 条评估记录**、横跨执行步骤效率、回答证据支持度、任务完成度、工具调用成功率和工具选择合理性 **5 个维度**；筛出任务完成度 ≤ 0.6 的 **72 条候选样本**送进人工复核，分清哪些是真能力缺陷、哪些是数据或裁判误判（图 4-1）。

![image](../../assets/imgs/chapter-18/image-014.png)

_图 4-1：线上巡检评估结果_

- **实验验证**：锁定 Badcase 后把代表样本存成实验数据集，围绕「加数据路由、改 Prompt、改 Skill、换模型或调工具」做多方案同场对照（图 4-2），盯着任务完成度、证据支持度、工具选择、延迟、Token 和成本六项指标，**绝不允许只修好一道题却把别的题弄退化**。

![image](../../assets/imgs/chapter-18/image-015.png)

_图 4-2：Bad Case 实验验证_

- **发布准出**：版本发版前用固定回归集检查历史问题有没有复发、用基准集检查整体大盘有没有掉分，全过门槛才放行灰度（图 4-3）。

### 4.2 抓出来的两个典型翻车现场

这两个 Case 最有代表性：**表面上看 Agent 没报错、也输出了像模像样的答复，靠传统监控根本发现不了，但放到轨迹和评估器下面立刻原形毕露。**

#### Case A：用户要求重读在线文档，Agent 却拿旧记忆糊弄（图 4-4）

- **现场**：用户明确说「重新读取这份在线文档，按最新内容回答」。结果 Agent 直接凭前面几轮对话里的旧缓存瞎讲了一通变化说明，压根没调文档读取工具。
- **风险与改法**：回答看着头头是道，实则拿旧内容充数。现在要求一旦出现「重新读取、刷新、最新」指令，必须强制触发本轮读取并绑定本次文档版本作答；真读失败就老实报错，不准靠脑补兜底。

![image](../../assets/imgs/chapter-18/image-017.png)

_图 4-4：Case A，文档读取未刷新_

#### Case B：子 Agent 查回了全部数据，主 Agent 却回报「全没查到」（图 4-5）

- **现场**：用户让主 Agent 派一个只读子 Agent 查 6 个研发工作项的标题、状态和负责人。翻看底层执行轨迹，子 Agent 规规矩矩调了 6 次查询而且全部成功返回了详情；偏偏子 Agent 最后吐给主 Agent 的摘要里自己写着「既开始了查询又没收到 ID」，主 Agent 看都不看工具明细就信了摘要，向用户汇报「6 项都没查到真实数据」，任务完成度直接跌到 **0.25 分**。
- **风险与改法**：这类「底层工具全成功、但主流程把结果弄丢」的 Bug，光盯接口成功率绝对抓不到。改进方式是要求主 Agent 在子任务结束后直接核对结构化工具返回、逐项数齐必填字段，摘要与真实轨迹冲突时以真实结构化返回为准。

![image](../../assets/imgs/chapter-18/image-018.png)

_图 4-5：Case B，子 Agent 结果未回传_

### 4.3 错题怎么留下来：四类数据集的分工

抓完 Badcase 不是修完就扔，而是按图 4-6 的路径流转沉淀：刚抓到的低分样本进**测试集**复现并验证修复；确认修好后升入**回归集**当每次上线前的拦截门禁；长期稳定、人工复审通过的典型黄金样本沉淀进**基准集**，专管切模型、大版本升级时的大盘横评；其中特别干净优质的多步轨迹或人工标样本，再加工进**后训练集**用于后续 SFT/RL 或偏好对齐。至于每次实验临时冻结的那一撮切片，只是取数视图，不用单开长期库。

### 4.4 跑出来的量化收益账单

在宙斯特定业务场景、固定数据集和对应评估口径的一段真实运行期里，拿到了下面这组对比结果（注意：这组数字反映的是该场景条件下的实测效果，不能直接套成其他团队接入后的预期保证）：

- **排障和回归效率**：单次问题定位从平均约 **55 分钟**降到 **15 分钟**（效率提升约 **73%**）；完整回归从 **1.5 人天**压到 **3 小时**（耗时降约 **75%**）；评估覆盖量从人工抽查 **200 条/轮**扩大到日均自动跑 **2000+ 条、5 个维度**（覆盖量翻约 **10 倍**）。
- **质量指标**：从任务完成度 ≤ 0.6 的 72 条候选里人工确认为 **31 个有效问题**，其中 **26 个**已完成修复并通过回归（修复通过率约 **84%**）；固定回归集上，任务完成度均值从 **0.62 升至 0.82**，证据支持度从 **0.66 升至 0.85**，历史问题复发率从 **16% 降至 5%**。
- **研发节奏**：团队从等用户骂上门的「救火」转成「线上巡检 → 复核 → 沉淀回归 → 发布准出」的「防火」节奏，问题在上线前被拦下来的比例从 **约 30% 提至 75%**，月均紧急排查从 **8 次降到 3 次**。

## 五、两条实用建议与后续计划

1. **起步别贪大，先跑通最小闭环**：挑一个高频、结果好验真的核心场景，先把「探针采集 → 轨迹核验 → 自动评估 → 人工复核 → 回流测试集 → 版本回归」走完一圈，确认模型调用、工具、异步子任务和业务 ID 全都没丢，再扩覆盖面。
2. **往业务深处和自动进化延伸**：后续团队一方面会在通用指标之外挂上能连业务知识库和 MCP 的**专职业务评估器**（主动查最新规则再判对错）；另一方面等回归闭环彻底稳固后，再挑低风险、好验真的场景小范围试点平台自带的**经验库**和**记忆库**，用固定测试集验证真有正向收益再放量。
