抓出 Badcase 之后，改一版 Prompt 或换个模型，到底有没有真修好、有没有把老题目搞砸？感觉不算数，要拉回同一个题库做**对照实验**才算数。这一篇围绕三个工程现实问题展开：实验计划怎么配、部署在公司内网的 Agent 怎么在不把数据搬出内网的前提下跑实验、以及怎么靠题目级 Rubric 让实验分数真正指导调优。

## 一、实验计划：绑定数据集、评估器与变量映射

演示数据集里存着前面评估抓出来的两道低分题：『AgentLoop 如何做评估』和『AgentLoop 有哪些功能』。创建实验计划时选好这个数据集和对应评估器（图 1），再配好 **变量映射**（图 2）：

![AgentLoop 数据飞轮实践（四）配图 1](../../assets/imgs/chapter-18/image-052.png)

*图 1：实验计划：指定数据集与评估器（视频 34:02）*

![AgentLoop 数据飞轮实践（四）配图 2](../../assets/imgs/chapter-18/image-053.png)

*图 2：变量映射：内置变量与数据集字段对应（视频 34:18）*

变量映射就是告诉评估器去哪取数：一边接**实验内置变量**（本轮实验跑出来的 `input`、`output` 和轨迹），另一边接**数据集里原本存的参考字段**（比如 `expected output`，让评估器能拿着标准答案做对照）。另外千万别忘加上**自定义变量**标记版本号（例如版本 Tag、实验记录 ID），不标版本，后面大盘里就没法对比「V1 和 V2 到底差在哪」。配完之后，就能拿到底部的本地执行入口。

## 二、离线实验平台：部署在内网，数据不出域

很多企业 Agent 跑在公司内网隔离环境，云端控制台根本访问不到；把线上数据全搬出来跑测又不合规。AgentLoop 的解法是把 **离线实验平台** 直接部署在客户自己内网里（图 3、图 4）：内网平台一边向内直连本地 Agent 跑测试题，一边主动出网把实验分数和轨迹记录交回云端大盘，做到业务数据不出内网。

![AgentLoop 数据飞轮实践（四）配图 3](../../assets/imgs/chapter-18/image-054.png)

*图 3：离线实验平台：部署在客户内网（视频 35:32）*

![AgentLoop 数据飞轮实践（四）配图 4](../../assets/imgs/chapter-18/image-055.png)

*图 4：离线实验平台架构：云端控制台 ↔ 内网实验平台 ↔ 本地 Agent（示意图，依据演示内容整理）*

### 1. 连上云端 AgentSpace

先在内网平台配置绑定信息（图 5）：指定目标 AgentSpace 与所在 Region（endpoint 和 VPC 跨区时再改），填入专用 `AK / SK`——需要具备 **AgentLoop FullAccess（读写）权限**，建议专门单独申请一个只服务离线实验的专号 AK，权责隔离好排查。填好点测试链接确认连通。

![AgentLoop 数据飞轮实践（四）配图 5](../../assets/imgs/chapter-18/image-056.png)

*图 5：配置 AK/SK 与 AgentSpace 绑定（视频 36:05）*

### 2. 注册并适配本地有状态 Agent

接着新建一个本地 Agent 连接（演示命名为 **Test1**，图 6；一个离线平台可以同时挂好几个 Agent 对比着测）。

这里有个高频实操细节：**默认调用代码假设 Agent 是无状态的一问一答 API，但绝大多数真实 Agent 是有状态的！** 比如这个基于 Claude Agent SDK 的客服 Agent，必须**先建一个 Session 拿到 Session ID，再往这个 Session ID 里发问题取响应**。直接在调用代码里按自己的通信方式改好这段胶水逻辑即可。

保存后先发一道**单题连通测试**（比如问『我的位置在哪里』，图 7），看到 Agent 正常回出『我无法获取您的实际位置信息』，就说明整条内网实验链路彻底打通了。

## 三、定时调度与 Launch History：让回测变成日常回归

单次实验测当前修改，**定时调度**则把回归做成日常习惯：演示中把计划配成每 5 分钟自动跑一轮回归（实际生产一般按每天一次配）。打开 **Launch History**（图 8），可以看到 51 分、56 分准时触发的记录，且本地平台和云端控制台同步一致。

![AgentLoop 数据飞轮实践（四）配图 8](../../assets/imgs/chapter-18/image-059.png)

*图 8：Launch History：定时调度触发记录（视频 43:41）*

点开该轮回测成绩：两道题分别只拿到 **0.25 分**和 **0.5 分**（满分 1）——第一题『AgentLoop 有哪些功能』漏掉了 Rubric 要求的好几个核心能力项，第二题『AgentLoop 如何做评估』漏掉了若干评估步骤细则。分数低反而是好消息，因为明细里逐条列出了「命中了什么、缺了什么」，下一轮改 Prompt 或补知识库直接照着清单补就行。

## 四、实验大盘与分数分析三步法

每个实验计划都会自动生成一张 **实验大盘**（图 9），看整体均分、版本趋势，还能下钻到每一道单题上看它改前改后涨了还是跌了。为了烫平评估器单次打分的随机抖动，可以切出**按时间窗口算均值**（比如 5 分钟或 1 小时窗口，图 10）。

![AgentLoop 数据飞轮实践（四）配图 9](../../assets/imgs/chapter-18/image-060.png)

*图 9：实验大盘：整体分数与变化趋势（视频 44:34）*

![AgentLoop 数据飞轮实践（四）配图 10](../../assets/imgs/chapter-18/image-061.png)

*图 10：按时间窗口计算均值（视频 45:13）*

看实验大盘记住一条极重要的排查顺序，避免冤枉模型或白改代码：
1. **分数往下掉先别急着下结论**；
2. **先盯紧同一个版本重复跑稳不稳**：如果代码和模型没动、同一批题连跑几次分数自己上下乱跳，毛病不在 Agent 退化，而在 **Rubric 评分标准写太模糊**——尺子不准，先回头修评估器；
3. **确认同版本跑分稳如泰山后**，不同版本之间拉开的分差，才是你这次优化改动带来的真实效果差异。

## 五、关键实践：把 Rubric 细化到「题目级别」

跑通上面流程后，演示做了一次很关键的架构纠偏。

为什么之前在线评估时用一个大一统通用 Rubric 勉强够用，到了实验阶段却非改不可？因为**线上流量问题千奇百怪，只能拿通用标准框住大方向；可进了实验数据集，每一道题目问什么已经完全定死了！** 『有哪些功能』和『如何做评估』要核对的知识清单风马牛不相及，硬塞进同一个公共评估器里写死规则，最后分数必然互相打架、改了东墙塌西墙。

正确做法是**把 Rubric 下沉到数据集的每一道题目上**（图 11），改造只需四步：

![AgentLoop 数据飞轮实践（四）配图 11](../../assets/imgs/chapter-18/image-062.png)

*图 11：题目级 Rubric：按题目绑定评估标准（视频 48:07）*

1. **逐题整理标准**：把『有哪些功能』『如何做评估』各自对应的功能清单、原子能力点、概念边界和扣分项分别写清楚；
2. **数据集 Schema 加一列**：在数据集字段管理里新增一列 `rubric`（`text` 类型），保存 Schema 后把每道题自己的评分细则和计算公式填进去；
3. **改造评估器接动态标准**：给评估器新增一个 `rubric` 输入变量，让它按传入的当题标准打分，并强制返回结构化 JSON（包含 `rubric_id`、`score`、`reason`、`item_scores` 字段）；
4. **实验里绑定字段**：把实验计划里的 Rubric 变量映射改为直接读取数据集里的 `rubric` 列。

改完之后，一百道题就有一百把严丝合缝的专属标尺，哪道题掉分、缺哪条原子能力一目了然。

## 六、小结

| 环节 | 关键点 |
| --- | --- |
| 实验计划 | 数据集 + 评估器 + 变量映射（内置变量 ↔ dataset 字段），可加版本号等自定义变量 |
| 离线实验平台 | 部署客户内网；AgentSpace/region/AK·SK 配置；连接本地 Agent |
| 调用代码 | 有状态 Agent 先建 Session 再发消息 |
| 定时调度 | 每 5 分钟/每天回归；Launch History + 平台侧同步 |
| 实验大盘 | 总分、趋势、窗口均值、按题目下钻 |
| 分数方法论 | 分数低先查 Rubric 定义，稳定后再比版本差异 |
| 题目级 Rubric | rubric 绑定到数据集题目，评估器输出结构化 JSON |
