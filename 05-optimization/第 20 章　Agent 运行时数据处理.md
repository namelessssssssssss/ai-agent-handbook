# 第 20 章　Agent 运行时数据处理

客服负责人提了个很实在的需求：每天抽一批退款对话，专门抓“工具压根没退成，Agent 却跟用户说已经办好”的假成功案例；研发改完提示词后，还得拿这批真实案例回头复测，确认毛病真少了。

后台接入了运行日志，单条轨迹也能点开看了，可质检人员真正要的是一张打开就能用的表格：用户问了啥、Agent 怎么答的、工具到底干了啥、出事的记录从哪条追踪号来的。数据量一大，还得按业务自动分类、抽样，每天定时把新数据添进去。如果每次都得找研发导日志、改 Python 脚本、拼 Excel 表，这种质检撑不过三天。

**Pipeline（数据处理流水线）干的就是这个活：把一次摸索出来的整理套路存成自动化任务，按约定持续往 Dataset（数据集）里吐干净样本。** 研发把源头字段接对，业务负责人盯着预览拍板“这张表我能用”，后面的评估、人工复核和回归实验就全部吃同一套标准字段，彻底省掉来回对口径、找日志的拉扯。

## 20.1 先盘点一下，Pipeline 能替业务省哪些麻烦

不用把 Pipeline 想成一套必须全部点亮的复杂引擎，需要什么结果就拼哪几步。

| 业务想要的结果 | 对应的处理模块 | 实际解决了什么问题 |
| --- | --- | --- |
| 把晦涩日志变成人能读懂的表 | 字段投影、字段扩展、条件过滤 | 抽出问题、回答、模型、耗时等关键列，直供质检、分析和评估 |
| 把零碎事件拼成完整任务样本 | 实例构建 | 按确认过的任务或会话 ID 组装记录，适合源数据还是碎 Span 的应用 |
| 从海量相似对话里淘洗题库 | 精确去重、近似去重、语义去重 | 剔除撞车和微调改写的废题，省下题库维护和重复打分钱 |
| 人手有限，尽量覆盖全貌 | 随机采样、分组采样、向量生成、语义聚类 | 按条数、比例或业务分桶抽样，支撑人工抽检和盲区排查 |
| 原始记录没有业务分类标签 | LLM 调用、智能体调用 | 自动打场景分类、抽摘要或做候选标注，方便按类别筛选 |
| 揪出上下文爆炸、死循环长文本 | 文本统计、条件过滤 | 算字数长度特征，捞出超长输入或啰嗦的工具返回做成本排查 |
| 从临时盘点变成每天自动运行 | 单次执行、周期执行、运行历史 | 先补一段历史老账，再按小时或天稳定交付新样本 |

同一份底层轨迹，完全可以拆出几条流水线各取所需：客服质检只要问题、答复和工具状态；研发排障要看完整步骤和入参；算账的团队盯着模型和 Token 开销。共用底层来源，各自配各自的输出集就行。

**动手前一定先拍板一件事：输出结果里的“一行”到底代表什么？** 做退款质检，按“一次任务一行”最顺手；想排查用户为什么老是多轮追问，就得把连续多轮留在一行；要对比多个并行子 Agent 的发挥，就要把不同路径拆开存。这个粒度一旦定偏了，后面的分组、抽样和打分全都会拧巴。

## 20.2 挑对入口起手，不熟字段就让 Loopie 先搭草稿

进到对应的 AgentSpace，点「数据中心 → 数据处理 → 创建 Pipeline」，就能在同一个向导里把来源、模板、输出和调度一次配好；如果已经在建 Dataset，也可以直接点「从轨迹数据导入」拉起流程。

选数据来源看这三条判断：

- **已经整理出 Agent 轨迹、准备直接做评估**：选**轨迹数据**，直接套用推荐的「Agent 轨迹样本提取」方案，把输入、输出、会话和完整轨迹一次拎出来。
- **底层只有调用日志、需要现拼业务字段**：选**Trace 数据**，先跑推荐的问答提取模板，缺哪列再往流水线上挂模块。
- **只关心一问一答的文本效果**：优先走问答提取；但只要任务里要查工具用对没有、失败后怎么恢复，**务必把完整过程轨迹一起带上**，省得质检看一半还得回头捞原始日志。

选完模板，编辑器左边是流水线上的各个处理模块，熟门熟路的研发可以直接点模块改配置；要是不熟悉原始日志长啥样、或者需要一长串加工动作，直接用大白话跟助手 Loopie 提需求，让它生成管线草稿再微调：

> 整理退款客服最近一天的运行轨迹，一次任务一行。保留用户问题、实际答复、完整执行过程和来源 ID，输出到退款质检数据集。先给我看真实样本；没有最终答复的任务也保留，方便检查中断问题。

Loopie 生成草稿后会直接展现在编辑器里，你对着真实预览样本继续追着提要求就行——比如“这里抽出来的是系统包装过的提示词，帮我换成用户进门时说的原话”，或者“加一列区分是申请退款还是查进度”。来回两轮对话，比自己对着 JSON 结构摸索快得多。

## 20.3 实战演示：跑通第一条退款质检 Pipeline

假设退款 Agent 已经接入了标准轨迹，我们先建一条管线，把昨天的数据整理到新数据集 `refund_review_samples` 里。第一轮先把每条真实任务原原本本留下来，这样才能看清同样一个问题，成功时怎么走、失败时卡在哪。

### 第一步：定来源、配好这几个核心字段

在创建页选「轨迹数据 → Agent 轨迹样本提取 → 选择此方案」。进编辑器后先核对应用范围，如果多个应用混在同一个空间里，让 Loopie 按示例字段加上筛选条件。

这套默认方案会吐出五个最核心的字段，业务看前两列，评估器吃中间的过程，研发顺着后面的 ID 就能一键回查案发现场：

| 输出字段 | 装的内容 | 在退款质检里的用处 |
| --- | --- | --- |
| `input` | 用户输入 | 例如“订单 1001 需要退款” |
| `output` | Agent 最终答复 | 例如“退款申请已经提交” |
| `agent_trajectory` | 完整轨迹内容（由源数据的 `atif_content` 映射而来） | 翻看退款工具传了啥参数、报错没有、后面怎么回的 |
| `trajectory_id`、`trace_id` | 来源追踪标识 | 锁定这一次具体执行，方便复核与排障 |
| `session_id` | 会话关联标识 | 必要时串起用户前后几轮追问 |

如果业务还要按渠道或订单类型拆表，直接在「字段投影」或「字段扩展」模块里添列，并从真实样本里指明取值路径。**核心原则是字段得能支撑你的质检问题**：想查“用户后面补充的退款原因用没用上”，补充输入就不能丢；想查“到底退成功没有”，工具返回和业务结果字段就必须保留。

### 第二步：一定先点“预览”，拿真样本验货

点击输出模块的「预览」，选一个肯定有真实流量的时间段。抽查时别光看正常样本，**刻意挑两条来对照**：一条顺顺利利的普通单，看质检同事能不能一口气读明白；再找一条工具报错、或者压根没吐出最终答复的任务，确认它没有被过滤条件误杀。

比如预览里正好捞出一条：工具返回报错“缺少退款原因”，可最终答复写着“退款已经提交”。**这正是整条流水线要抓的活靶子！** 如果预览里只剩最后一句话、看不到工具报错，或者因为没有终态输出整行被过滤掉了，当场点开对应模块把条件改回来重新预览。

预览也是业务和研发拍板形态的好时机：长轨迹收在结构化字段列里，表格首屏只亮出问题、答复和渠道标签。业务负责人看这几行样表点头说“收到这种表我就能开始干活”，再往下正式启动。

### 第三步：正式运行并去 Dataset 验收入库

点「创建并启动」，在「任务信息与调度策略」里填好名字和说明，选「单次执行」，把处理时间窗明确设为昨天，输出目标填 `refund_review_samples`。**这里最容易踩一个小坑：你在编辑器里点预览选的时间窗，和正式调度要跑的时间窗未必会自动同步，提交前务必再核对一遍正式时间范围。**

再次确认启动后，任务进队列执行。去「运行历史」盯一下数据窗口、状态、输出行数和耗时；显示成功后，点输出卡片上的跳转图标直接进 Dataset 详情，拿昨天已知的一条追踪号搜一下，点开确认每列都能读出来。

万一跑出来是空表，八成是两件事：要么所选时段里压根没数据（或应用过滤写太严），要么字段提取路径写偏了导致大面积空值。第一轮专门框定一个已知的短时间段来跑，能最快分清到底是没数据源还是规则写错了。

## 20.4 人看不过来、还没业务标签？加上采样、去重和 AI 打标

第一条线跑通之后，再按团队人手和分析痛点往上挂模块，千万别第一天就叠成十层汉堡。

### 控量抽样与题库去重

假设质检同学一天最多精读 100 条，就挂一个「随机采样」模块，按条数限制 100；怕冷门场景全被高频问题挤掉，就在分组列里填上业务类别，改成按类别每组抽固定条数。

如果连线上到底有哪几类问题都摸不准，先挂「向量生成 + 语义聚类」把相似提问聚成几堆，再按聚类挑代表样本——比如同样问“进度怎么查”，抽几条看看就够，把宝贵的阅读时间留给奇葩长尾问题。（注：如果目的是估算线上总体故障率，仍应保留严格随机或按真实流量比例的代表性抽样，别让聚类抽样扭曲分母。）

做回归题库遇到重复提问时，可以用去重模块：一字不差用精确去重，改了几个词用近似去重，换了种问法用语义去重。**唯一要注意的是：去重键千万别只选提问文本！** 同一句话今天答对了、昨天答错了，或者 VIP 和普通账号规则不一样，带着结果和场景差异一起去重，才不会把宝贵的失败案例当成重复题给洗掉。

### 没标签就先让模型打一版，但别拿它当最终质检分数

原始数据如果没有业务分类，就在提取字段后加一个「LLM 调用」模块，把输出格式设为 JSON、输出列名设为 `scenario_label`，写一段清晰短提示词：

> 根据用户输入 {{input}}，将本次任务归为“申请退款”“查询进度”“退款被拒”“其他”之一。只根据输入判断，不推断办理结果。返回 category 和 reason 两个字段；reason 简短说明分类依据。

预览确认比如“已经申请三天了怎么还没到账”能正确落进“查询进度”，再挂一个字段扩展把 JSON 里的 `category` 拆成独立筛选列；分类有歧义就往提示词里补两句定义和正反例。如果有些判断必须查知识库或调外部接口才能定性，把模块换成「智能体调用」。

这套手段也能用来做**数据增强**——比如手里只有“直接申请退款”的单轮样本，想补“先问到账时间、再转成申请退款”的多轮边界案例，可以让模型按固定业务事实改写生成。**两条铁律得守住**：合成数据必须标明来源、先进候选池经人工确认再用；大模型打出来的标注只用来筛选和预分类，**正式的质量评分还是要交给后面可校准、可对比的评估器**。

顺手算笔省钱账：管线排序按**“能用确定性字段先过滤 → 能先采样缩量就先采样 → 最后才过 LLM 处理”**来排（除非采样分组本身要依赖模型刚打出来的类别）。多加的每一个模块，都要能说清“它替业务省了什么人工、补出了什么新信息”。

## 20.5 从一次性排查升级成每天自动吐样本

昨天的老数据验完确认好用，就可以把同一套配置复制成日常任务：选「周期执行」，比如按小时增量补数或按天定时汇总，输出统一写进固定数据集 `refund_review_daily`。接好历史补数和周期起点后，业务同学每天固定点开这一个地方就能看新样本；应用一旦上了新渠道或改了交互形态，记得回来同步改管线提取规则。

紧接着把 Dataset 接进评估任务：把刚才产出的输入、输出和完整轨迹列映射给退款质检评估器，跑一轮打分和归因，那些“工具失败却给用户报喜”的案例就会成批浮出水面。研发顺着轨迹修完代码或提示词，进实验拿这批题重跑一遍验证；线上的新流量同时源源不断流进日常管线，真正把“干活 → 看数 → 改错 → 验证”串成闭环。

在后面的实操演示里，团队也遇过一个典型调整：起初两道客服题共用一套评估细项，跑起来才发现“有哪些功能”和“如何做评估”的得分点完全不一样，于是直接回到 Dataset 加了一列逐题 Rubric，再改一下映射就接上了——**数据底座够干净，后面改标准才不用推翻重来**。

## 20.6 第一步只求有人天天打开用

第一次上手，最忌讳追求大而全。照着这个最小节奏跑通就行：**轨迹提取 → 落成 Dataset → 跑通一批评估 → 叫上真正做质检的人看一遍结果**。确认列都对、人真看懂了，再往上加自动标签、分组抽样和周期调度。

长期合作下来，业务和研发守住三条朴素约定：一行代表什么粒度、核心字段到底啥口径、这张表用来干嘛。至于管线搭得值不值，不用看加了多少花哨算子，就问三个真问题：

1. 质检同事还用不用每天去翻底层原始日志？
2. 业务新加了一个场景，能不能加个字段或改条规则就收进来？
3. 研发接到一个 Badcase 单子，能不能一跳钻回当时的执行现场？

只要这三条全打通了，你手里就有了一份真正能喂给评估和实验的“活数据”。下一章，我们来看看怎么把这些经过挑拣的样本，沉淀成团队长期信赖的**黄金数据集**。
