# 第 23 章　受控自进化

一个排障 Agent 上周刚修好过一次某类告警，这周再碰到一模一样的故障，还是从头瞎查日志、传错参数，甚至把上次千叮万嘱的关键核对给忘了；一个代码 Agent 逻辑改得飞快，却老是在某类任务里写完代码直接收工不跑单测。

团队最想要的状态其实很简单：**怎么把已经跑通的门道稳定留下来、让反复踩的坑越来越少，同时别让 Agent 在“自己进化”的时候改野了、花冤枉钱？** 这就是本章要讲的“受控自进化”：一边靠经验库、Skill 和 Harness 沉淀积累，一边靠实验对比和回滚机制把每一步改变关在笼子里验收。

## 23.1 先挑对一类任务，选准该动哪一层

第一轮别搞全平台自动化，先找一个目标清楚、天天重复发生、结果容易验证的场景。业务负责人定好“什么算做好”，研发从 Trace 里拎出几条成功样本和几条失败样本一对比，很快就能看出问题到底该归哪一层去治：

| 你在业务里看到的毛病 | 先动哪一层最见效 | 期望换回什么改变 |
| --- | --- | --- |
| 每次遇相似故障都要重新瞎试，门道只在特定前提下管用 | **经验库**：在任务开局或卡壳时按需召回 | 少走冤枉弯路，更快摸到有效路径 |
| 老是漏掉前置检查、单测或结果核对 | **Skill**：把检查步和口诀补进技能规范 | 同类任务稳定执行完必要步骤 |
| 天天重写的统计查询、分页翻页或数据清洗逻辑 | **SQL 模板 / Script / 工具**：把算子封装死 | 少临场瞎写报错，业务口径全组统一 |
| 固定套路老得人盯着一步步催 | **Workflow**：把固定衔接和异常分支编进流转 | 前置检查、执行和验收按约定自动推进 |
| 重复提交、中断恢复后状态乱套、长任务忘了初始约束 | **Harness**：直接改执行控制与上下文管理机制 | 从底座上消灭重复动作和中断丢状态 |

比如排障 Agent 一查日志就把全天几百万条拉出来导致超时，如果是缺方法，往 Skill 里补一条“按故障时间窗和对象缩小范围”；如果连查询工具本身都不支持按时间过滤，那就别逼提示词了，直接找工具维护者把参数加上。

## 23.2 建好经验库：别只存答案，要存“遇事怎么查”

经验库最怕沦为错题答案合集。对排障来说，“上次那个订单是库挂了”几乎没法复用，真正值钱的是**“遇到日志里全在报重试时，顺着时间往前找首次异常”**这种可迁移的操作套路。

建一套靠谱的经验库分三步走稳：

1. **先确认轨迹里真有干货**：打开选定 AgentSpace 下的一条真实轨迹，确认用户目标、关键工具调用和工具返回都能看全。如果轨迹里光秃秃只剩最后一句总结，先回头把埋点补齐，没过程根本挖不出好套路。
2. **挑相近任务和时间窗建库**：去经验库入口填名字和说明，选定应用与挖掘起始时间。第一批挑最近一段业务规则稳定、任务类型相近的数据即可，**别为了凑条数把半年前规则早作废的陈年老账全倒进来**。应用和起始时间建库提交时就定死了，点提交前一定核对清楚。
3. **打开挖出来的经验，对照原始 Trace 验货**：专挑最常碰到的几条经验，逐条拷问三件事——**它要解决什么问题、建议干什么动作、在什么前提下才算数**，然后点回来源 Trace 确认当时真是这么跑通的。

**最容易踩的误用坑**：比如有条经验写着“查不到日志就扩大时间窗口”。排障同学审这一条时必须追问一句：当年那条轨迹是因为时间窗设窄了，还是那台机器根本没接日志采集？**只有把来源和“不适用条件”一起盯牢，才不会把一次权宜之计变成误导所有人的死规矩。** 如果挖出来全是“仔细分析问题、正确使用工具”这类大空话，说明喂进去的轨迹太杂或过程信息不够，先补好轨迹代表样本再重挖。

_图：经验随着真实反馈不断修订；人重点审内容、适用边界和来源证据，再决定哪些可以放去试用。_

## 23.3 把经验接进 Agent，亲自看它查没查、用没用

经验库攒出一批靠谱条目后，就按经验召回页面的指引把它接进目标 Agent（以支持 Skill 的排障或研发 Agent 为例）：

1. **装上召回 Skill**：在 Agent 工程目录执行页面给的安装命令装好 `alibabacloud-agentloop-experience`，确认 Agent 列表里能扫到这门技能。装的只是“去经验库查资料的能力”，具体条款都是跑起来才按需拉的。
2. **配好库地址和凭证**：从召回页面抄来当前经验库地址、API Key 和开启开关。如果本地用的是项目级配置文件，**核对清楚 Agent 实际跑在哪个工作目录、吃的是哪份配置**，别一不小心连到测试库或别的项目库。
3. **放开必要的工具权限**：按你使用的 Harness 要求，把 Skill 白名单和所需的会话执行权限开齐。
4. **发一条真实问题现场抓包验收**：挑一条你刚才亲自验过货的经验，用相近的故障场景去问 Agent（例如说明症状、时间段和已知的重试现象，要求它先查经验）。**验收绝不能只听 Agent 嘴上说“我参考了历史经验”，必须点进 Trace 看清三件事：真的发起了召回工具调用、返回里确实命中了那条经验、后面的动作也真照着去查首次异常了。**

![目标 Agent 在运行时召回并评估经验](../assets/imgs/chapter-23/image-002.png)

_图：Agent 在执行时主动发起召回取回候选经验，再结合手头实际条件决定用不用。_

接线要是不顺利，对照下面四个环节一眼定位，别一上来瞎调相似度阈值：
- **根本没发起查询**：查 Skill 启没启用、触发说明写清没、权限放开没；
- **查询直接报错**：查库地址、AgentSpace、库名和 API Key 填对没；
- **查通了但返回空**：先看库里有没有对应经验，再看查询词和过滤条件是不是卡死了；
- **命中了经验却没照做**：检查返回内容进没进上下文、以及是不是因为当前前提不符被 Agent 合理跳过了。

## 23.4 经验不是越多越好：用实验定召回策略和预算

查一次经验要多一次检索耗时、多塞几百上千 Token 进上下文。对一句简单问答来说，查经验可能纯粹白费钱；对兜兜转转二十步的复杂排障来说，开局命中一条老套路就能省掉一半试错。值不值得查、每次给几条，靠实验数据拍板。

先拿“不开经验召回”跑出一批基准成绩（Baseline），再用完全相同的模型、工具和题目测不同的召回配置。**关键铁律：每次对比必须换全新的 Session ID，把任务依赖的外部文件或业务状态全部重置清零**，防止上一轮留下来的半成品帮下一轮“作弊”。

| 可调节的开关 | 怎么设计对比实验 | 用什么标准判断是否合适 |
| --- | --- | --- |
| 召回阈值 | 比一比“门槛卡严一点”和“门槛放宽一点” | 塞进来的废话经验少没少、真正有用的线索漏没漏 |
| 返回条数 | 比一比只给 1 条和给 3～5 条 | 多出来的条数是补齐了适用条件，还是纯粹加重阅读负担 |
| 触发时机 | 比“开局规划前先查”和“工具失败卡壳后再查” | 决策前就避坑了吗？有没有出现每轮死循环重复查？ |
| 位置和长度 | 调当前任务、说明和经验在上下文里的排布，砍掉啰嗦字 | 关键前提保留住没、Agent 读完到底用没用上 |
| 约束口吻 | 明确写明“经验仅作历史参考，不符现状立刻放弃” | 条件变了时能不能果断丢掉老经验继续自己查 |

算总账时一定别只看“召回后准不准”：排障盯根因和证据链完整度，代码盯需求完成和单测通过，统计报告盯数字口径——**然后把召回本身吃掉的耗时、Token 和费用一并算进总账**，再顺手拿一组“压根用不着经验的普通题”验一遍，看是不是平白无故给简单任务拖了后腿；最后别忘了再用一批没参与本轮经验挖掘的新任务做盲测。

如果发现某条经验老把 Agent 带沟里（比如一遇到问题就教条地扩大范围或照抄旧参数），先收窄它的生效范围或者直接停用，顺手把出事的任务收进回归集。这样团队修的是具体的策略与条目，不会动不动全盘否定“经验到底有没有用”。

## 23.5 摸透了的稳定套路，别总靠临场生成：直接固化成硬资产

经验库适合处理“看菜吃饭”的场景提示；一旦某项工作的套路已经被摸得清清楚楚、容不得模型临场发挥写歪，就该果断升级成确定性更高的资产。拿“定期统计 Agent 失败率”来说，业务先定死“一次任务”和“算不算失败”的口径，研发把跑通的轨迹拎出来拆成四样东西：

- **SQL 模板**：把去重、计数、分组逻辑写死，只把应用名和时间窗留成参数，顺便注清楚字段含义、时区、空结果怎么解释和明细怎么核对。
- **Script 或工具**：把分页拉取、JSON 解析、去重汇总打包成一个黑盒脚本，给短参数就吐干净结构体，再也不用每次让大模型现写十遍清洗代码。
- **Skill**：专管“什么时候拿这套算法、先找人对齐什么口径、参数怎么填、算完怎么交叉核对报告”。
- **Workflow**：把“定范围 → 跑统计 → 核明细 → 出报告”串成硬步骤，顺手把空数据、超时和口径不匹配分支安排好。

**千万别第一天就想把这四样全堆齐。** 哪块最疼先治哪块：天天写错复杂 SQL 就先交付模板，老漏最后一步校验就先改 Skill，等步骤和异常处理完全定型了再封装 Workflow。写这些资产可以让 Agent 帮着起草，但上线前必须由懂业务的人审一遍，并用换参数、空表、重复行和字段变动用例实测，最后还要**从头新发一个普通任务验证 Agent 自己找得到、调得通**，才算真落地。

## 23.6 拿失败 Badcase 做局部微创：改 Skill 甚至改 Harness

碰到线上实锤的 Badcase，别一拍脑袋就把整份 Skill 推倒重写成三千字“注意事项全集”。把原来的 Skill、失败轨迹、几条相近的成功轨迹和期望行为打包交给优化助手（比如 SkillForge），让它对照执行证据生成精准的局部补丁，人只管确认没弄丢原有好习惯、再拿去跑实验对比。

看一个典型的表格 Agent 实操案例：系统发现它两次翻车，一次是不查表名直接往不存在的工作表里写数据、报错后才去查列表，另一次是公式少敲半边括号写入失败。对照证据改 Skill 只加了精准的三句话——**写入前先核对目标表名、提交前检查公式括号配对、写完必须回读目标单元格确认落盘**。每条改动都能在轨迹里找到对应病灶，干脆利落。

![依据失败与成功轨迹生成局部 Skill 补丁并实验验证](../assets/imgs/chapter-23/image-003.png)

_图：把失败和成功轨迹交给优化助手生成局部修订候选，人拍板挑一版进实验跑测试。_

代码团队也一个思路：Agent 老写完代码就宣布结束，先顺着轨迹看它加载对应 Skill 没、测试命令在不在、环境通不通；缺步骤就补“改完必跑对应测试并核对结果”，环境坏了直接修环境，最后用**目标失败题 + 原本正常的题 + 不该触发这门 Skill 的无关题**三拨数据一起验，防止为了治一个病把正常题带歪。

而有些底层毛病，改 Skill 根本兜不住，必须由负责运行环境和 Harness 的团队改代码：
- **比如“工单已经提交出去，半路断网恢复后系统又重发了一遍”**：业务拿出重复提交记录，研发顺着 Trace 找准中断点，在 Harness 的恢复逻辑里把状态拆细成“尚未开始 / 已开始但结果未知 / 已完成”——**只要状态处于“结果未知”，恢复后第一动作必须是反查业务系统现状，绝不能直接重新调工具**。
- **又比如“长任务触发上下文压缩后，忘了开局叮嘱的限制条件”**：改压缩规则和外置任务状态保留逻辑。

动了这种底层恢复机制，验收不能只拿普通问答糊弄：要在可控环境里故意掐断“提交前”“提交后结果未落盘”这几个时刻，或者用真能触发压缩的长任务跑到底，亲眼看到重演现场确实被新逻辑兜住了，才能放行。

## 23.7 自动化逐步放手，人永远留着最后四道关

从完全人盯人到把重复活交还给系统，团队按自身成熟度一格格往上走就行：

| 进化方式 | 人和系统各管哪一摊 | 这一轮走完拿到什么 |
| --- | --- | --- |
| 手动调优 | 专家挑题看轨迹，研发动手改某一条 Skill、查询模板或配置 | 一项明确改动，加对应任务的验证记录 |
| 半自动调优 | 系统自动聚失败模式、挖经验、出 Skill 补丁草稿；人比对方案、拍板上线 | 审过的候选清单、实验分差和明确采用范围 |
| 受控自动调优 | 在提前圈定的安全边界内，自动接实验和检查，达标自动生效，异常转给人 | 合规留痕的自动改进和可回查的运行看板 |

![从人工闭环走向受控自动调优的演进节奏](../assets/imgs/chapter-23/image-004.png)

_图：系统扛走越来越多重复的整理与试错工作，但业务目标、采纳门槛和异常兜底必须人提前定死。_

挑先自动化的环节，优先找高频、边界死、结果好验的块——比如“经验自动挖掘 + 运行时召回”可以先接通，“Skill 自动生成补丁”先保留人工点确认；至于跨资产全自动实验发布，则挂进团队既有的 CI 和发布流。

不管自动化到哪一步，**每次决定采用新改动前，负责人死守这四道检查**：
1. 原本瞄准的 Badcase 真改善了吗？
2. 以前好好跑着的常规任务退化了吗？
3. 多掏出来的耗时和 Token 账单业务能接受吗？
4. **进 Trace 确认目标 Agent 真的用到新资产了吗？**（很多次分数没变，是因为压根没加载上！）

同时留好旧版快照、改动差异和随时一键切回的应急方案。这里有个特别要命的坑：**如果发现经验库把线上的任务带偏了，千万别以为点个按钮停掉“经验挖掘任务”就万事大吉——之前早就挖进库里的旧经验依然会在运行时继续被召回！** 出了异常必须直接调整召回开关或把有毒条目下线停用。

![从发现问题、实验对比到发布回滚的全链路关联](../assets/imgs/chapter-23/image-005.png)

_图：让每一处改动都能往回追到具体 Badcase 和实验数据，出退化时一秒定位回滚。_

每一次采纳之后，新跑通的好方法留下继续复用，新揪出来的反例继续塞回第 21 章的黄金集和第 22 章的评估循环。所谓数据飞轮，最后拼的不是多酷炫的自进化口号，而是团队敢说：**线上每一轮跑得比上一轮更稳，而且每一处变好，我们都说得出是哪一行数据、哪一次实验验证出来的。**
