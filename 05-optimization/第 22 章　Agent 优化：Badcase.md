# 第 22 章　Agent 优化：Badcase

上一章把考题和判分尺子冻进了黄金数据集。接下来要干两件配合着转的事：**用评估（Evaluation）持续从线上或历史执行里抓 Badcase，再用实验（Experiment）让改完后的 Agent 重新做这批题，拿新答案和新轨迹验明正身。**

本章继续沿着产品客服 Agent 的实操走下去：用户会问“Agent 观测与优化有哪些功能”“如何做评估”，团队既要回答准确，更要给出照着就能点下去的操作步骤。先分清一个基本概念：**评估审的是已经发生过的旧执行；实验测的是修改之后现跑出来的新执行。**

![从轨迹评估发现 Badcase 到实验对比验证的闭环](../assets/imgs/chapter-22/image-001.png)

## 22.1 先挑一个最痛的问题，做出第一版能用的评估器

刚开始建评估，最怕贪大求全，想一张网把所有业务毛病全兜住。正确的起手式是**只盯一个最高频的痛点**——比如产品客服最常挨骂的“说了一堆概念，却没解决用户眼前的问题”。把几条专家拍板的好回答和几条明显翻车的回答放桌上，对比差在哪。

同是产品客服题，“有哪些功能”看重能力说全没说全、“各自干嘛的”；“如何做评估”看重准备数据、配标准、跑任务、看结果这串步骤连没连起来。虽然都要求准确，但及格线长相完全不同。团队先定一套通用评估框架，等样本进实验集后再挂各自专用的 Rubric，录入方法见上一章。

第一版通用评估器其实只要查清三件事：
- 有没有正面回应用户的真实需求；
- 关键说法有没有材料支撑，别顺嘴编功能；
- 需要动手做的任务，给的步骤够不够用户往下继续点。

每项都写死“满足、部分满足、不满足”三档条件，并逼着评估器输出**扣分原因**。如果任务还会动后台数据（比如退款、改权限），一定补上业务状态核对——千万别因为客服语气礼貌就给满分。

进控制台「评估 → 评估器」，先翻一眼预置评估器（比如现成的任务完成度）够不够用；需要塞入自家产品口径再建自定义评估器。在 Prompt 里写清规则、声明要读取的输入、输出和轨迹变量，在输出定义里配上分数、结论和解释字段。场景分类、分项得分这些字段按需要再加，别一上来把用不上的列全堆上去。

| 你想让它判断什么问题 | 挑哪种评估器最省事 |
| --- | --- |
| 输出是不是合法 JSON、必填字段漏没漏 | **Code 规则**：确定性条件先用代码硬卡，又快又省钱 |
| 回答切不切题、要点全不全、有没有胡编 | **LLM 评估**：把参考材料和评分细则喂齐，看语义质量 |
| 多步任务真做完没、工具返回和嘴上说的对不对得上 | **Agent 评估**：连着轨迹一起查；懂特定业务再挂载领域 Skill |

同一条任务可以同时挂多个评估器——比如把“回答写得像不像样”和“业务到底办没办成”拆成两个分来看。真要合出总分，也在标准里写明权重公式，**切忌图省事直接把几个评估器分数取平均**，一旦平均分糊在一起，出事根本看不出是哪头掉了链子。

## 22.2 先拿几条真样本试评，再跑第一批历史评估

评估器保存完，进「评估 → 评估任务 → 创建评估任务」。这一步最核心的目标不是赶紧出个平均分，而是**确认评估器真的看见了完整的问题、回答和执行过程**。

### 1. 选对数据源和时间窗

评估刚接入不久的新 Agent，直接选「Agent 轨迹」；如果上一章已经用 Pipeline 清洗组装好表了，直接选对应的 Dataset。选轨迹或 Trace 来源时要区分「单轮对话」还是「多轮对话」——多轮必须配置“对话结束判断”，等整轮事情聊完再评；用 Dataset 时由于前面已经按行定好粒度，界面不会再让你选单多轮开关。

第一把建议开「基于历史数据评估」，挑一段确认肯定有目标业务流量的时间（比如最近四小时），点「数据预览」亲眼验一眼：里头是不是真有你要查的那类题，有没有混进别的应用。要是多轮会话预览是空的，多半是那几个小时里的对话还没满足你设的结束条件。

### 2. 把试运行规模压到人能逐条看完的量

在「采样配置」里定采样比例和最大条数。演示里用的是 100% 采样、上限 100 条——注意，这卡住的是**送去评估的候选样本上限**，不代表跑完一定给你捞出 100 条 Badcase。第一次试水完全可以先抽个二三十条，让业务同学逐条看一遍扣分解释再放量。

### 3. 接好字段映射，拿三条样本现场试评

选定评估器后，对着预览样本配「字段映射」：用户提问接输入变量，最终答复接输出变量，要查步骤再把完整轨迹接上去。**变量名随你起，内容千万不能串**——最常见低级失误，就是把“最终回答”误接到了中途某一步工具调用的输出。

![评估任务字段映射与单条测试预览](../assets/imgs/chapter-22/image-002.png)

_演示示例：把评估器需要的输入、输出和完整轨迹变量，逐一接到预览样本的对应字段再做试测。_

点「运行测试」，用「换一条」至少把三类样板试过一遍：**一条公认好回答、一条公认坏回答、一条信息残缺的样本**。对着评估器吐出来的分和理由问三句：它引用的扣分原话，回答里真这么写的吗？工具返回引对了吗？证据缺失的时候，它老实标“无法判断”了吗？

如果坏回答居然得了高分，先看它拿到的入参全不全，再查是不是条款太松——比如标准里只写了“是否提到评估器”，那糊弄两句概念照样拿高分，得改成“是否写明能让用户迈出下一步的具体动作”。改完标准重跑同一批试评样本，确认没把原本的好回答误伤。如果任务还带图片、音频或文档附件，也得按这顺序先看评估器读不读得懂附件，再查它引的页码、票据金额和填报结果对不对（图 22-3）。

![多模态与附件材料评估试测检查](../assets/imgs/chapter-22/image-003.png)

### 4. 配好结果回写，跑出第一批全量历史

正式点「保存并运行」前，别忘了打开「写入评估结果数据集」并透传源数据里的原问题、原回答、场景等字段——**结果数据集在任务创建后就不能再改了**，务必一次配齐。跑完先看实际处理总数和失败记录数，别一上来直奔平均分。单条预览只能证明线接通了，第一批跑下来才会暴露诸如范围圈错、部分样本缺字段的真问题。

## 22.3 从结果里淘洗出真值得修的 Badcase

进评估结果页先扫整体分布，需要跨多次任务拉齐看，去「分析洞察」按评估器、数据源和分数段筛选。**对比低分一定带上任务名和时段**，别把两套标准或两拨完全不同业务的分混在一起比高低。

**看到低分千万别条件反射直接去改 Prompt！** 每条结果都要把四个东西摆一起读：原始问题、Agent 回答、分项结论和扣分理由、以及执行轨迹。总分只是指示灯，解释告诉你哪错，轨迹才告诉你为什么错。

| 你在评估结果里看到的现象 | 接着追查什么 | 这一轮该怎么处理 |
| --- | --- | --- |
| 回答只介绍概念，少了运行和看结果的步骤 | 条款是不是真要求操作步骤，回答真漏了吗 | 坐实是回答完整性问题，收进调优样本 |
| 回答明明写了关键步骤，评估器偏说没有 | 输出映射截断了没？是不是串用了另一道题的标准？ | 错不在 Agent，先修评估器或字段映射再重评 |
| Agent 嘴上说操作成功，轨迹里工具报错失败 | 报错后怎么处理的、业务系统真改了没 | 归为任务执行缺陷，交给负责该行为的团队修 |
| 结果报错或材料缺了一半 | 任务异常、漏采集、附件没传进去 | 先补齐采集或运行条件，暂不算 Agent 的锅 |

演示里有次实验回测很有代表性：“有哪些功能”拿了 0.25 分，“如何做评估”拿了 0.5 分。数字本身只是一张门票，真正值钱的是逐项扣分理由直接标出了漏掉哪几个功能点——研发和业务一眼就能分清到底是知识库没写、回答结构散了，还是题目标尺没写清楚，不用盲猜“是不是模型不够聪明”。

复核过滤完的样本落进数据集，挑几条有代表性的错题留下，**同时记得搭上边界样本和几条原本答得正常的题目**；千万别忘了把**评估器判错的样本专门留作校准材料**，高分样本也要顺手抽检几条防“评估器放水”。等历史回溯判得够稳了，再开「基于新数据持续评估」配好采样率——高并发场景抽个低比例看趋势，重点场景拿专项历史评估捞深水区。

## 22.4 把 Badcase 拉进实验：让改过的版本现做一遍

现在手头有了“有哪些功能”和“如何做评估”两道真题，团队提出一个具体改动（比如补齐产品知识，并在提示词里要求操作问题给出步骤）。动刀原则是：**先拿线上当前版跑出一份 Baseline 成绩，候选方案第一轮尽量只改最有把握的那一项**——如果你同时换了模型、重写了 Prompt 又挂载了新 Skill，分数哪怕涨了，你也不知道到底是谁立的功、谁在拖后腿。

去「实验 → 实验计划 → 新建计划」，挑好数据集选实验类型：「在线实验」是在平台上直接配好模型开跑（注意这叫离线实验，**不是把线上真用户拿去做生产 A/B 分流**）；要测自家部署在内网的真 Agent，选通过 SDK 触发的「本地实验」。

实验和前面评估最本质的区别就在这里：**被评估器打分的，是本次实验现跑出来的全新回答和新轨迹。**

| 评估器声明的变量 | 实验里必须接入的内容 |
| --- | --- |
| 用户输入 | 本次实验实际发给模型或 Agent 的考题 |
| Agent 输出 | 本次实验现场跑出来的新答案 |
| 运行轨迹 | 本次运行刚关联出来的执行过程 |
| 参考答案或预期行为 | 数据集里对应这一行的标准参考字段 |
| `rubric` | 数据集里专门写给这一行的逐题评分细则 |

前面我们在数据集里加了逐题 Rubric，这时候在评估器里声明一个 `rubric` 变量并连过去。先只跑那两道题验个货，点开评分解释亲眼确认：“有哪些功能”吃的是功能覆盖标准，“如何做评估”吃的是操作步骤标准，而且**评的确实是新答案不是旧缓存**。要是评出来的过程还需要提取特定工具状态或业务结果，把 Pipeline 也挂进实验计划，再用带 `pipeline.` 前缀的字段接给评估器，保证线上质检和离线实验用同一套加工口径。

最后再提醒一次：对比期间锁死一份独立黄金集，创好只读版本快照留档，把模型版本、Prompt、工具和参数全记在实验记录里，保证两轮是在完全同一起跑线上赛跑。

## 22.5 把企业内网里的真 Agent 接进来，先拿一道题试水

真实业务 Agent 往往关在公司内网里，得调内网库和审批接口。选完本地实验计划，点「获取本地实验配置」，按侧栏指引装好依赖，在“通过 HTTP 执行”“执行本地命令”或“自定义执行”里挑顺手的路子，把目标服务地址、鉴权请求头、拼参逻辑和超时接进去。如果要集中管多套连接和定时调度，演示里也展示过客户侧实验平台这种 Web 包装层，但**第一次接入直接拿 SDK 脚本跑最快**，没必要上来先搭管理后台。

实际接线最常踩的一个坑是**有状态的会话接口**：很多企业 Agent 不是无脑“一问一答”，你得改写成“新建 Session → 往该 Session 发考题 → 轮询或等待最终回答”。尤其注意两件事：
1. 异步接口先返回一句“任务已受理”不算交卷，得等真正的终态回答回来；
2. **每一道独立考题必须开全新的 Session**，绝对不能把上一道题的上下文留给下一道题串味。

接好代码后**先只跑一道题**！确认请求发出去了、最终答复回来了、实验记录和新轨迹对得上号，再放几十道题的小批集——这样做，能第一时间把“接口调通没”和“答案写好没”彻底分开排查。只要你改了 Tool、Skill、Workflow 或 Harness，务必把新版本号写进实验上下文，确认服务真切过去了；光留着同一个请求地址，根本没法证明前后两次跑的是不同版本。

## 22.6 逐题比完差异，再拍板到底值不值得上线

实验跑完进「实验记录」，勾选 Baseline 和候选点「对比」。先借「概览对比」扫全局、借「配置对比」核对到底动了哪几项变量，然后一头扎进「样本对比」逐题看。

**阅卷顺序建议反着来：先盯退化题，再看改善题，最后检查核心正常场景。** 盯“如何做评估”重点看配置、运行、看结果这几步齐没齐；盯“有哪些功能”看能力覆盖多没多、有没有现编不存在的功能。**回答字数变长不叫进步，新增的字必须踩在评分要点上。** 要是总分涨了但关键红线条款依然挂掉，不准放行；要是只有这一道题涨分、其他正常题集体滑坡，八成是你把硬塞格式的 Prompt 强加给了所有问题，得拆场景分策略重跑。

![实验记录中的样本级前后对比与扣分详情](../assets/imgs/chapter-22/image-004.png)

拿不准这次涨分是不是运气时，两招拆开查波动：**想查评估器稳不稳，拿同一份固定回答连评三遍；想查 Agent 稳不稳，让 Agent 重跑同一批题。** 分数上蹿下跳时先点开原文和轨迹看差异，别动不动怪 Rubric 不好。

决定要不要上线，除了平均分，死守最后三道门槛：
- **严重错误彻底清零了吗？**
- **原本正常的主干场景掉链子了吗？**
- **多花的时间和钱值不值？**（比如多加一次工具查账虽然多花了 1 秒和几百 Token，但彻底堵死了“退款失败还骗用户成功”的事故，这笔开销值；反过来，删掉必要核验换来的快，绝对不能作为升级理由。）

碰到接口报错、额度耗尽没跑完的样本，老实查明原因；如果是因为环境抽风修好重跑可以，如果是比整套服务交付能力，这些失败本身就是分数。**千万别等结果出来了才改统计口径把失败题剔除。** 小批实验稳了再扩大到全量回归集，最后过一道从未参与本轮调优的独立盲测集，连同数据版本和配置变更一起存档，才算稳妥进发版流。

## 22.7 让这套考卷接着服务下一轮迭代

每一轮实验收尾，都要顺手把资产分流归档：验出有效的新考题塞进回归集，评估器看走眼的案例放进校准集，没解决完的留在下轮清单。接好定时回归（比如演示用 5 分钟展示连续调度，生产按发版频率和预算配成每日或每次发布前触发）后，日常只要盯住连续滑坡或关键题退化就行。一旦真发了问题版本，顺着实验记录一秒找回改了啥、按既定流回退，线上的新轨迹又继续流进评估——这套循环转顺之后，接下来我们就能看第 23 章：怎样让系统把这些成功与失败直接炼成经验、Skill 甚至 Harness 自身的进化。
