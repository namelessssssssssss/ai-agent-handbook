# 第 19 章　Agent 轨迹数据

用户吐槽“回答没解决问题”，研发最怕听到这种模糊反馈——到底是因为 Agent 没听懂需求、知识库检索没找着材料，还是材料找着了却被漏掉没用上？只盯着首尾一问一答根本猜不出来。**轨迹（Trajectory）的价值，就是把用户输入、思考行动、工具入参和返回结果、以及最终输出串在同一条时间线上**，让团队一眼看清问题卡在哪一步。

承接上一章的思路：先把一条真实执行的轨迹看明白、定准问题，再把同类数据交给流水线（Pipeline）批量加工，后面的评估和实验才有抓手。

## 19.1 先跑通一条自己熟悉的任务，确认数据真进来了

第一次看轨迹，别挑线上最复杂的疑难杂症。最稳妥的起手式，是自己给产品客服 Agent 发一条明确问题，比如“如何做评估”，顺手记下发起时间、原话和得到的回答；如果调用方能拿到 TraceID 或 SessionID，也一并抄下来。**拿自己刚跑过的任务去对账，一眼就能看出平台记录对不对。**

登录控制台选定对应的工作空间（AgentSpace），进入「数据中心 → Agent 轨迹」。如果页面提示还没接观测数据，先按引导配好接入；如果还没开轨迹清洗或采集开关，看清页面上的数据处理和计费说明后再打开。**切记：配置完开关千万别默认数据就自动到了，一定要再新发起一条请求做验收。**

回到轨迹列表，把时间范围卡到刚跑完那会儿，核对列表里的输入、输出、Agent 应用、模型、步骤数、Tokens 和耗时。点开对应记录，对照原始提问和回答，如果任务里调了知识检索工具，顺便确认这次工具调用和返回内容也在里面。

![Agent 轨迹列表与详情入口](../assets/imgs/chapter-19/image-001.png)

如果列表空空如也，按顺序排查这四项：**工作空间有没有选对 → 时间范围是不是漏了当前时段 → 筛选条件是不是卡太死 → 采集状态开没开**，最后回到观测页面确认新请求到底有没有报上来。先分清“数据压根没采集上来”和“Agent 执行出了问题”，别一急眼就狂发一堆测试请求瞎试。

第一条正常任务对上账之后，趁热打铁再挑两条典型样本来看：一条**失败任务**，检查报错信息有没有完整留下来；一条**多轮任务**，检查用户后面补充的条件能不能顺着轨迹串起来。做到这一步，团队才算手里握住了日常排障的入口。

## 19.2 查问题怎么筛：条件从少往多加，搜字面和搜意思分开

定位轨迹最忌讳一上来把七八个筛选框全填满，搜出来一片空白也不知道是哪条卡住了。记住两个原则：**有精确标识先用标识，筛选条件从少往多加**；条件加完搜空了，优先撤掉最后加的那一条。

| 你想查什么问题 | 列表里怎么最快捞出来 |
| --- | --- |
| 某次具体用户投诉 | 锁定时间范围，优先配 TraceID，没有就用用户输入关键字 |
| 用户追问了好几轮还是没解决 | 用 SessionID 拉出整段交互，结合首尾输入输出看 |
| 挂了某个工具的任务老翻车 | 筛选对应 Agent 应用、工具名和故障时段 |
| 哪些任务慢得不正常 | 同一应用下按耗时范围筛选，对比步骤数（Steps）和 Tokens |
| 某类业务诉求是不是经常出现 | 在输入侧用语义搜索捞候选，点开逐条核实场景 |

输入和输出框都支持**关键字匹配**和**语义搜索**，但用法完全不同：

- **关键字匹配**：适合手里已经有用户原话、固定产品名或特定报错信息的精准查找。
- **语义搜索**：适合知道意图但用户说法五花八门的情况。比如查“如何做评估”这类操作指导诉求，在输入侧搜这句话，就能把“怎么给回答评分”“怎样建评测任务”一起捞出来。

**注意两个细节**：第一，输入框查的是用户需求，输出框查的是 Agent 回复，别搜反了；第二，语义相似度只负责把相近的问题聚成候选，**相似度高不代表这些任务难度一样、也不代表犯的是同一个错**，先按默认设置翻几条，别拿搜索匹配度当成质量分。

![按关键字与语义搜索定位同类轨迹](../assets/imgs/chapter-19/image-002.png)

捞出一批记录后，先抽读几条代表样本把场景拆开。比如同样问评估，有人只想了解概念定义，有人要的是照着点的完整操作步骤——把这两类混在一起分析，很容易把一个简练得体的概念解释误判成“漏写步骤”，也可能把空洞的介绍当成解决了操作难题。

## 19.3 怎么读一条轨迹：先看首尾定性，再钻关键步骤

点进一条轨迹详情，不用从第一行逐字往下啃。先看右侧的输入和输出概览，搞清楚两点：**用户到底要干嘛，Agent 最后交了什么答卷**。再扫一眼步骤数、工具调用次数、Tokens 和总耗时，心中有数该重点查哪个环节。

接着顺着「执行步骤」往下读，基本脉络就是：用户补充信息 → Agent 下一步动作 → 工具返回 → Agent 组织回复。轨迹太长时，直接用「搜索步骤」搜工具名、报错字眼或关键词跳过去，展开相关工具调用的「入参」和「执行结果」，连同调用身份、耗时和 Token 消耗一起看。

拿产品客服回答“如何做评估”来举例：先找到它的知识检索那一步，重点盯三件事——**检索词写得对不对准评估流程、返回内容里到底有没有操作步骤、最后回答有没有用上这些步骤**。如果检索明明已经把完整操作步骤找回来了，Agent 自己只吐出一段概念简介，那改法和“知识库压根没这篇文档”是完全两回事。

碰到多 Agent 协作的任务，详情页如果关联了子轨迹，要顺着委派关系进去查：主 Agent 到底给子 Agent 交办了什么目标、最后实际收回了什么结果，不能光看子 Agent “运行结束”就放行。界面上并排显示的多步也不一定有先后因果，得结合真实的调用关系来读。

![轨迹详情中的执行步骤与工具入参返回](../assets/imgs/chapter-19/image-003.png)

**写分析结论时，尽量把因果落到一条紧挨着的事实链上**，比如：“用户要求操作步骤 → 知识检索已返回完整步骤 → 最终回答遗漏操作步骤”。这种记录谁来复核都一目了然，后面接评估规则也直接用得上；只留一句干巴巴的“回答质量太差”，下游根本没法下手修。

需要核对底层字段、调用身份或导出结构时，点「查看轨迹 JSON」。要是怀疑平台漏记了步骤或串了关联关系，交给研发拿着标识回查底层采集日志；业务到底有没有办成，永远以真实工具反馈和业务系统状态为准。

## 19.4 把看出来的毛病落成优化动作

看轨迹不是为了写流水账，最终要落到排障、省钱和质检三件具体的事上。

**1. 工具报错了，重点看 Agent 后来怎么圆场**

比如退款任务里，用户给了订单号，退款工具返回报错“缺少退款原因”，Agent 却直接回复用户“申请已提交”。点开工具入参确认确实缺参数后，紧接着往下看它收到报错后的动作：有没有向用户追问原因、有没有改参数重调？

- 明明拿到了错误返回还敢给用户报喜，必须修错误处理逻辑和回复策略；
- 如果工具返回本身模棱两可、看不出失败，工具接口也要一并改；
- 至于这笔钱到底退没退成功，直接去业务系统对账。

另外，**失败后的重试过程不要轻易丢掉**。改了参数重新调通，说明 Agent 有自愈能力；原封不动连着重试好几次报同一个错，就得调重试上限和停止条件——同样出现工具失败，两种情况的改法截然不同。

**2. 耗时或 Token 飙高，专门揪“多出来的重复活”**

按应用、意图和耗时框出一批相近任务，对比它们的步骤数和 Token 消耗，把特别高的几条展开细看：是不是反复查同一份资料？是不是工具一次返回了几万字无关噪音？还是同一个动作失败后在原地死磕？

比如两条都在答“如何做评估”，其中一条把同一份文档来来回回查了好几次。逐次核对入参和返回：如果每次确实拿到了新信息，多跑几步无可厚非；如果入参和结果几乎一模一样，就能直接作为候选优化项——复用前面查到的结果、限制无效重试，或者精简工具返回体积，改完再用实验验证答案有没有缩水。

**切记别一看到总 Token 高就一刀砍步骤。** 复杂任务本来就需要多轮探索、自测和状态确认；而且 Token 数反映的是工作量，最终花多少钱还得看所用模型单价和计费方式，决策时要把质量、耗时和账单摆在一起算总账。

**3. 业务质检，核心盯“嘴上说的”和“手里干的”一不一致**

产品客服最常翻车的两类题，一类是“有哪些功能”漏讲了核心能力，另一类是“如何做评估”给不出可执行步骤。用输入检索捞出这两类记录对照看，分清缺口出在知识库本身、检索召回还是回答组织上，两边各攒几条证据清晰的样本留底。

一旦任务涉及生成文件、提交表单或改动配置，**Agent 回答“已完成”最多算个表态**——工具收到请求、任务进程跑完、业务目标真正达成，这三件事经常不在一个时间点上。证据链不完整时先标“待确认”，千万别把漏采日志直接按在 Agent 头上算 Badcase。每次复盘收尾，都要明确下一步去向：补知识、修工具、改回答策略、调整 Harness 执行流，还是先把埋点数据补齐。

## 19.5 好样本留下当素材，大批量交给 Pipeline 加工

翻到值得沉淀的轨迹，直接在详情顶部点「加入数据集」，或者在列表多选批量入库。首次建候选集，用户问题、Agent 最终输出和完整轨迹这三样必留；想顺手做成本和来源归因，把应用、模型、工具名和 Tokens 也带进去。

往已有数据集里追加数据时，**务必核对字段映射，千万别把最终答案和完整轨迹接反了**。写完打开目标数据集抽查一行，确认题目、回答和过程对得齐、长轨迹关键步骤没被截断。如果只是手工点选太慢、或者想做更细的字段拆解，交给下一章的 Pipeline 来处理。

刚收进来的记录还只是**候选样本**。业务同学得先复核问题成不成立、补齐期望答案，再决定谁进黄金集。建库时记得**成败样本都要留**——比如“功能覆盖”和“操作指导”既留翻车例，也留几条原本答得漂亮的正常例，不然下次一改，投诉题修好了，原本正常的回答反而写歪了。

列表也支持把筛选命中的全部记录一键交给后台任务导入。看到弹窗提示“任务已创建”，只代表任务进了队列，并不代表数据已经写完，记得去跟进任务运行结果和实际落库条数。

单条复盘是在摸规律，Pipeline 是把摸出来的规律跑成流水线。比如把这周的客服操作指导轨迹自动抽成问题、检索结果、最终回答和工具状态，顺便去重、按场景分流、补齐评估字段。进入下一章前，你可以先用一句大白话写清需求——“把这段时间产品客服的操作类轨迹，按每条保留题目、检索材料、最终回答和来源标识的格式写进候选集”，拿几条真实轨迹一预览，看关键判断依据留没留住，流水线就能立起来了。

## 19.6 Trace、Session、Trajectory：别把“记录范围”误当“任务结论”

翻轨迹时一定会反复碰到这三个词，它们各自打包的数据范围不一样，搞混了很容易得出假结论。

| 对象 | 实际装了什么 | 分析时怎么理解、防什么坑 |
| --- | --- | --- |
| Trace | 由追踪上下文串起来的一组调用（模型、工具及上下游服务） | 适合定位单次执行和接口调用毛病；能看见多少，完全取决于埋点采集全不全 |
| Session | 应用侧关联起来的一段连续交互，里头可能包着好几条 Trace | 适合回看用户多轮追问和上下文；**同一个会话里完全可能先后聊了好几个独立任务** |
| Trajectory | 把原始调用整理成用户与 Agent 交互步、工具交换、结果和指标的行为主干 | 适合直接阅读过程和加工样本；依然要核对当前记录覆盖了任务的哪一段 |

一次一问一答的同步对话，往往刚好对应一条 Trace；可一旦遇到多轮追问、异步回调或子 Agent 委派，一次任务就会在后台留下多条零散记录。SessionID 能帮你把相近的交互串起来，但**它不会自动证明这些消息一定属于同一个任务**。应用自身必须传入靠谱的任务标识和关联关系，不能因为时间靠得近、聊的词差不多，就脑补平台已经把完整任务拼出来了。

平台整理轨迹时，会把模型每轮请求里重复带上的长历史剥掉，把工具请求和返回对上号，抽出一条干净的行为主干，省得业务人员去一层层翻底层 Span。但同时，真实发生过的重试、报错、缺失返回和未确认状态都会原样留着，分析时切记区别对待。

底层跨工具交换时，平台使用 ATIF 格式来统一描述步骤、消息、工具调用、观察结果、运行指标和来源扩展，让展示界面、数据处理 Pipeline 和评估器都能吃同一份材料。日常分析不用自己手写 JSON，只有对接外部系统或查字段对齐时才需要看它。

记住一点：**轨迹只忠实记下了“上次运行发生了什么”**；要想拿同一批题反复做实验对比，还需要题目起点、可重复的入口和清晰的判分标准。下一章，我们就用运行时数据处理 Pipeline 把这些原始轨迹加工成真正顺手的业务样本表。
