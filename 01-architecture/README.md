# 架构篇导读

过去一年，做 AI 原生应用的起手式彻底变了。以前是写死业务逻辑，只在某个节点调一下大模型生成文本；现在，模型开始自己拆目标、看环境、调工具，还会根据报错反过来调整下一步。Codex、Claude Code、Qoder 这些 Coding Agent 率先在写代码这件事上跑通了这套模式：它们不再只是代码提示插件，而是能自己翻仓库、立待办清单、改文件、跑终端和测试，并在漫长任务里随时听人指点纠偏。

但模型能自己干活，绝不等于光靠一个模型就能上线。恰恰相反，**任务跑得越久、手头的工具越强、改动的生产环境越真，模型外面那套工程脚手架和底座就越要命**。怎么把上下文喂准、把任务进度存到模型脑子外面、把工具权限卡死、把危险命令关进沙箱、中途挂了能断点续跑、做完了能拿客观事实验收——这些能力组成了包裹在模型外层的 **Harness** 脚手架，再加上底下扛住并发和故障的 **Runtime**（长任务宿主）与 **Sandbox**（隔离运行环境），才真正拼出一个能干活的 Agent。企业架构师要设计的，早已不是一次模型 API 调用，而是一整套跨越认知、状态、执行、风控与持续改进的系统。

架构篇管的是生命周期五阶段的第一关：**在写第一行业务代码之前，先把大方向和生死边界划死**——到底该选哪种应用形态、给它多大的自主权、哪些轮子该业务团队自己搓、哪些能力必须沉到共享平台、做到什么程度才算真的完成。这些问题如果拖到写代码甚至上线之后再补，后面运行、治理和调优全会乱成一锅粥。

| 对应章节 | 主线 | 核心解决什么问题 |
| --- | --- | --- |
| 第 01 章 | 定形态与选边界 | 应用形态怎么演变、Agentic Application 到底指什么、企业成熟度（L1–L4）怎么盘点与克制选型。 |
| 第 02 章 | 搭骨架与划责任 | 系统拆成哪几块、部署在谁的平台上归谁管、怎么从一次性 Demo 变成持续迭代的闭环。 |

**第 01 章先帮你破除“盲目追高”的执念**：Workflow 和 Agent 不是谁淘汰谁，现实里长期共存；Single-Agent 往时间上拉长是 Long-Horizon Agent，往协作上拆开是 Multi-Agent，这两个方向按需单用或组合都行，都不是非走不可的升级梯子。真正决定你该用哪一档的，不是产品名字叫得多响，而是“任务风险有多高、容错空间有多大”——永远选择**成本和风险可接受的最低充分架构**。

**第 02 章再把所有组件放进统一的坐标系里**：用组件视图看别漏掉能力，用平台视图划清团队责任，用生命周期视图管住版本发布和迭代闭环。这三个视角各管一摊、不能混着用：比如同一个状态存储（State Store），在组件图里它是持久化任务事实的模块，在平台图里它归数据与资源面管边界，到了生命周期里它是运行期产证据、调优期拿来复盘的关键账本。先说清自己站在哪个视角聊架构，团队才不会各说各话。

这两章前后咬合，建议按顺序一起读。读完本篇，记住两句硬话就够了：**应用先进不先进，不由起名叫不叫 Agent 决定；做架构的目的不是把系统堆大，而是模型每拿走一分自主权，工程上就得为它配上对等的隔离、观测、权限卡点和验收机制。**
