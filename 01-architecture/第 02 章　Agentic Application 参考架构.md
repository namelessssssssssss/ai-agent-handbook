# 第 02 章　Agentic Application 参考架构

Demo 期把 Prompt、循环脚本、工具函数全塞进一个 Python 文件，跑起来一点毛病没有。但只要任务跑到半小时以上、工具加到几十个、用户变成多租户并发，四颗定时炸弹就会集中引爆：

1. **Model 和 Harness 混写在一起**：换一个新基座模型，原本硬塞进 Prompt 里补旧模型短板的补偿逻辑全成了负作用，整个应用得跟着推倒重写。
2. **编排逻辑和 Runtime 绑定死**：任务进度全挂在单个 Web 进程的内存里，发布重启或者节点缩容，跑了两小时的任务瞬间归零。
3. **Context 和 State 不分**：模型上下文一超长被自动压缩摘要，连“哪三步做完了、订单号是多少”的任务事实也被模型“概括”丢了。
4. **工具描述、沙箱和权限搅成一锅**：以为模型上下文里看到工具说明就能直接调、或者以为进了沙箱就万事大吉，结果模型在合法参数下把生产数据改乱了。

所以企业级参考架构的难点，从来不是堆出一堆高大上的组件名词，而是**把每块职责的边界划清楚**。本章给出一套厂商中立的参考架构：不逼你第一天把所有组件全建齐，而是帮你在看清业务风险后，选出刚好够用的**最低充分架构**，并为后面的构建、运行、治理、调优四篇钉牢同一套坐标系。

## 2.1 架构全景：三个正交视角与五个责任域

### 2.1.1 别拿一张图解释所有问题：先分清三个视角

聊 Agent 架构时团队最容易吵架，往往是因为两个人根本不在同一个维度说话。设计 Agentic Application 时，必须把同一套系统放在三个正交视角里看：

- **组件视图（回答“系统由什么拼成”）**：盘清大脑、脚手架、信息对象、工具连接、Runtime、Sandbox、网关、观测、评估和安全各自管什么、怎么交互，防止遗漏核心环节（比如漏掉结果验收或外置状态）。
- **平台视图（回答“组件跑在哪、归谁负责”）**：划分执行面、数据与资源面、控制面，解决“哪些业务团队自己写、哪些共享平台兜底”，防止责任互相甩锅。
- **生命周期视图（回答“怎么从设计上线并持续变好”）**：把架构决策、发布单元、Trace、策略、数据集和补丁串成闭环，避免把“跑通一次 Demo”误当成“已经能持续运营”。

这三个视角谁也替代不了谁。拿**状态存储**（State Store）举个例子：在组件视图里，它是记录任务事实的持久化模块；切到平台视图，它归数据与资源面管租户隔离和保留期；落到生命周期视图，它又是运行期记下事实、调优期拿来复盘的核心证据。讨论任何组件前先对齐视角，架构才能真正落地。

### 2.1.2 五个能力责任域（组件视图）

图 2-1 从组件视图画出了五个核心责任域。读图时注意线条含义：**粗实线**是从业务目标到任务执行的主干链路，**域内细实线**表示组件间的调用与读写，**虚线**则表示版本、身份、策略、观测、评估和候选变更等横向贯穿作用。图中“层”用来划分责任，不代表必须严格按这个顺序一层一层建。缩写对应：LLM（大语言模型）、API（应用程序接口）、MCP（模型上下文协议）、A2A（智能体间协议）。

顺着图里的五个方框往下拆，每个域的边界一清二楚：

1. **① 业务与应用层**：定目标、定入口、定验收。它决定任务是由对话、API、消息队列还是定时事件触发，决定组织成 Single-Agent、Long-Horizon Agent、Multi-Agent 还是 Hybrid 混合形态，并且把“做到什么算完成”说清楚。它不管底层怎么调度，只对业务价值负责。
2. **② Agent 构建与编排层**：把认知大脑 **Model**、任务控制脚手架 **Harness**（图中标为 Harness 编排层）、五类信息资产（Context、Memory、Knowledge、Skill）以及 Tool/Protocol 连接定义组合成完整的“观察—判断—行动—反馈”循环。**注意一条红线：这一层只“描述和绑定”能干什么，真正动手执行命令、启动浏览器或连外部库，统统交给下一层。**
3. **③ 生产运行层**：用 **Agent Runtime**、**State Store / Workspace / Artifact**、**Sandbox** 和 **AI Gateway**，扛住跨请求长跑、断线断点续跑、文件环境隔离和统一流量路由。
4. **④ 治理与控制层**：管谁能发布、谁能跑、能碰什么资源、版本怎么灰度、行为怎么审计。运行层管“能不能稳稳跑完”，这一层管“准不准它这么干”。策略在这里集中定义，但具体拦截点会落进 Harness、Gateway、Runtime 和 Sandbox 的必经请求路径上。
5. **⑤ 调优层**：把运行期吐出的 Trace、Metrics、Logs、Cost 和用户反馈收上来，通过评估、安全分析、仿真和实验定位病根，产出的补丁和验证证据回流给构建层发新版本，过完治理门禁再进生产——**调优层绝不允许绕过门禁直接热改线上 Agent。** 另外，安全（Security）不是只属于图右下角的某个模块，而是贯穿五层：业务层定风险红线、构建层写防护和校验逻辑、运行层做隔离、治理层管身份审计、调优层（Security Analysis）做红队攻防测试。

### 2.1.3 业界收敛的五条架构铁律

结合 AWS、Google、Microsoft、Anthropic、LangChain 和 OpenAI 自 2025 年下半年以来公开的工程实践，靠谱的 Agent 系统普遍守着五条设计原则：

1. **Model 与 Harness 解耦**：模型是可替换的认知大脑，Harness 是贴合任务和业务规矩的控制脚手架。代码上不能强绑死，但每次升级或切换模型后，必须把模型和 Harness 绑在一起重新做回归评测。
2. **编排逻辑与 Runtime 解耦**：Harness 管“下一步干嘛、什么时候停、怎么拼上下文”，Runtime 管“放哪台机器跑、挂了从哪接上”。两者靠标准任务与状态接口对话，一旦编排代码直接读 Runtime 内存数据结构，后面想换宿主引擎就得全拆重来。
3. **状态全外置，执行实例随时可扔**：计划、待办清单、工具回执、工作区文件都必须落在外部持久化存储里，不能只存在模型上下文或单机内存里。只要实例随时能销毁重建，长任务和分布式扩展才站得住脚。
4. **自主权多大，隔离与校验就得有多硬**：Agent 拿到的工具、外网、数据库和凭证越多，出事时的**爆炸半径**（Blast Radius）就越大。必须用最小权限、短期凭证、出站白名单、Sandbox 隔离、结果硬校验和高危审批把半径锁死。
5. **可观测、安全和评估是上线前提，不是事后补丁**：Agent 的表现是模型、脚手架、工具、上下文、预算和环境共同化学反应的结果。上线不带轨迹记录和评估基线，出了事连复现都做不到，更别提证明改了一版之后到底变好了没有。

这五条不是逼你把系统做大，而是要求：**模型每多一分自由发挥的权力，工程上就必须配齐对等的边界、证据和验证。**

## 2.2 构建与编排：大脑、脚手架、五类信息与受控行动

### 2.2.1 Model：可替换、可路由的认知大脑

Model 负责理解意图、拆解步骤、多模态感知和决定调哪个工具。但在生产系统里，选模型不是立项时签一家供应商就一劳永逸的事，而是按任务特点持续做路由决策。

评估一个模型能不能用，至少看五件事：目标领域的硬能力、长上下文里听不听指挥且抗干扰、工具参数填得稳不稳且报错后会不会自纠、延迟价格配额与区域可用性，以及数据隐私和私有化合规边界。前三项决定“干不干得成”，后两项决定“用不用得起”。

复杂系统很少用一个最贵的大模型从头打到尾——规划和疑难排查走强推理模型，摘要、提取和常规分类切到快而便宜的轻量模型，主模型超时或限流时由路由器自动降级。这里有一个一线极易踩中的坑：**降级模型在协议层照样能按 JSON Schema 吐出合法的工具调用，看起来一切正常，但在多步执行中途偷偷丢了约束条件，最后交出一份格式完美但结果全错的垃圾。** 所以任何路由和降级策略变动，都必须带着完整 Harness 跑回归集验证，绝不能把“协议调通”当成“能力等价”。

### 2.2.2 Harness：把看概率说话的大脑，装进确定性脚手架

**Harness** 就是卡在 Model 和运行底座之间那层任务控制脚手架（LangChain 形容为“模型之外的一切”，Microsoft 称之为让语言模型真正干活的运行时脚手架，在图 2-1 中对应“Harness 编排层”）。

它掌管一个 Agent 最核心的任务语义：**这一轮喂给模型什么信息、能看见哪些工具、循环到什么时候停、哪一步该让人拍板、交付前必须过哪几项验收**。生产级 Harness 通常要包住表 2-2 里的七项核心能力——少掉任何一项，线上都有对应的经典翻车现场：

| 核心能力 | 具体管什么 | 缺了它线上怎么翻车 |
| --- | --- | --- |
| **Agent Loop 与终止条件** | 拼装调用、接住工具返回、重试、预算卡控与停止判断 | 模型死循环反复调同一个报错接口，把 Token 预算烧光都不停 |
| **Instruction 与 Context 工程** | 动态拼装系统指令、目标、压缩历史、记忆与环境现状 | 无关历史塞满窗口，关键业务规则被淹没，模型越跑越偏 |
| **Planning 与 Delegation** | 维护待办清单、拆解阶段目标、派发子任务并汇总 | 复杂任务一团浆糊，跑到一半出错根本不知道卡在哪一步 |
| **Tool 与 Skill 管理** | 能力注册、按需渐进披露、参数校验、超长结果外置截断 | 上百个工具说明挤爆上下文，或者把工具报错误判成模型太笨 |
| **Middleware 与 Policy Hook** | 在调用模型、执行工具、改状态前后插确定性卡点与审计 | 只靠在 Prompt 里写“请不要删库”，遇到注入或抽风照样直接删 |
| **Compaction 与 Continuation** | 上下文超长压缩、重置、文件式交接与跨窗口续跑 | 长任务窗口一满直接报错中断，或者摘要把关键订单号压没了 |
| **Steering、HITL 与 Verification** | 运行中给人留插话纠偏口、高危动作弹窗审批、结束前跑独立测试/Diff 检查 | 高危写操作没审批直接发出，或者测试没过模型自称“已完成” |

表 2-2　Harness 脚手架的核心能力与典型翻车模式

搭建 Harness 时，一线两条公开经验特别值得反复对照：
- **Anthropic 的经验是“定期给脚手架做减法”**：基座模型变聪明后，当年为了弥补旧模型短板硬写进去的复杂引导和繁琐约束，反而会束缚新模型发挥。因此每次大版本换模型，都要重估甚至拆掉过时的脚手架逻辑。
- **LangChain 的经验是“模型不变也能靠脚手架提效”**：在基座模型完全不动的情况下，光靠分析线上 Trace 把高频错误聚类、加上死循环检测（Loop Detection）和交付前独立验收器（Verifier），就能大幅拉高任务完成率。

此外再钉死一次它和 Runtime 的分工：**Harness 管任务语义**（下一步该干嘛、要不要找人批、怎么重建上下文），**Runtime 管物理执行**（放哪台节点跑、排队限流、机器挂了从哪条检查点续命）。两者通过任务事件和持久化状态对话，Harness 代码绝不能直接依赖某个 Runtime 的内存对象。

### 2.2.3 五类信息对象：Context、State、Memory、Knowledge、Skill

很多团队把所有文本一股脑塞进“聊天历史 + 一个向量库”，短期看着简单，上线后必出三种事故：上下文压缩把任务状态压丢了、Agent 上次总结错的经验被当成真理反复召回、普通员工搜知识库顺带搜出了高管的保密文档。要根治这些问题，信息层必须严格拆开表 2-3 里的五类对象：

| 信息对象 | 一句话定位 | 典型内容 | 生命周期与治理要求 |
| --- | --- | --- | --- |
| **Context** | 这一轮调用模型时，摆在它眼前的拼接视图 | 系统提示、任务目标、精简历史、可用工具、检索片段、当前环境 | **单次模型调用级**，每轮现拼现扔，绝不当成事实账本 |
| **State** | 任务已经真发生了什么、挂了从哪接上 | 会话、任务状态、Plan、Todo、检查点、工具回执状态 | **任务级**，必须强一致外置持久化，压缩对话绝对改不了它 |
| **Memory** | 跨任务攒下来的个人/团队交互经验 | 用户偏好、历史拍板、跨会话事实、踩坑经验 | **跨会话级**，由 Agent 写入，重点卡写入门槛、更新冲突与遗忘淘汰 |
| **Knowledge** | 企业原本就有的外部权威文档知识 | 制度规范、产品手册、代码库、RAG 索引 | **跟随源系统**，重点做来源追溯、权限过滤和过期刷新 |
| **Skill** | 某一类成熟任务“具体该怎么干”的操作包 | 操作说明、可执行脚本、模板、检查清单与验收法 | **独立能力资产**，必须版本化管理，支持单独复用、测试和回滚 |

表 2-3　五类信息对象的职责切分

这张表里最不能省的一刀，是把 **Memory 和 Knowledge 硬拆成两套库**。Memory 是 Agent 自己写出来的，最大风险是“记错了一次、次次跟着错”，所以必须设写入审核和定期遗忘；Knowledge 来自企业现有文档系统，最大风险是“员工看到了不该看的机密、或者拿到半年前废止的老制度”，所以必须紧咬源系统的 ACL 权限和更新同步。把它们混进同一张向量表，两边治理都会瞬间失守。

同样，**Context Engineering 的真功夫绝不是“买个超大窗口全塞进去”**，而是靠摘要、大返回值写文件外置、按需查 RAG、Skill 渐进式披露、子 Agent 独立上下文，把宝贵的模型注意力留给眼前这一步决策，同时把唯一真实的任务状态（State）牢牢留在窗口外面。

### 2.2.4 Tool、Protocol 与 Environment：一次受控行动的六道关

工程上常把这三样混着喊，其实出问题的地方完全不同：**Tool** 是具体能力（问题常在描述含糊或缺少参数校验）；**Protocol** 是怎么发现和调用它的通信约定（比如 Function Calling、MCP、A2A，问题常在“让模型发现工具”和“授权模型调用它”混为一谈）；**Environment** 则是工具真正落下去产生副作用的空间（如 Browser Use、Computer Use、Shell、Code Interpreter，这类通用环境把能力从预设 API 放大到整个计算环境，爆炸半径也跟着指数级扩大）。

千万记住三条底线：**模型能看见工具 ≠ 有权调用；参数完全符合 Schema ≠ 动作符合用户真实意图；命令在 Sandbox 里跑通了 ≠ 结果可以安全写回生产库。** 因此，一次真正可靠的受控行动必须串行闯过六道关：

> **选对能力 → 身份与权限校验 → 参数合法性检查 → 隔离环境（Sandbox）执行 → 独立结果校验 → 状态更新与审计留痕**

这六道关分布在 Harness、AI Gateway、Sandbox 和平台控制面上——少掉任意一道，模型大脑里的一个随机想法就可能直接变成生产系统的真实事故。构建这四块的具体工程做法，会在第 03 至 06 章展开。

## 2.3 生产运行与治理控制：平台三平面、Runtime、Sandbox 与网关

### 2.3.1 三个平台面：谁在跑、数据放哪、谁来管

在传统云原生架构里，常把流量转发那一面叫“数据面（Data Plane）”。但在 Agent 系统里，“数据”这个词太容易和业务数据、Memory 混在一起。因此本手册按职责把企业级 Agent Platform 切为三个平台面：

| 平台面 | 干什么活 | 管哪些东西 | 核心要求 |
| --- | --- | --- | --- |
| **执行面** | 真正把 Agent 循环、工具和环境操作跑起来 | Runtime Worker、任务队列、Sandbox、Gateway 数据链路 | 可弹性扩缩、允许随时挂掉重来、强隔离，尽量不存唯一事实 |
| **数据与资源面** | 稳稳存住可恢复事实，并托住外部能力供给 | Task State、事件日志、Checkpoint、Workspace、制品、Memory、Knowledge、Model、Tool、MCP Server | 定义死一致性级别、数据归属、保留期、隐私与租户隔离 |
| **控制面** | 定规矩、发版本、管身份、批配额、抓审计 | 各类 Registry、版本灰度门禁、租户、IAM 身份、Policy 策略、预算、观测与评估大盘 | 集中定义、带版本、可审计、可秒级回滚；具体拦截点分布式下沉 |

表 2-4　企业级 Agent Platform 的三平面划分

这里有一个非常关键的可用性设计：**控制面绝对不能成为每次模型或工具调用的强同步瓶颈**。靠谱的做法是“**策略集中定义，判定点分布式执行**”：控制面统一管策略规则、版本和发布；真正干活时，由 Harness 的 Middleware、AI Gateway、Runtime 和 Sandbox 按已经下发到本地的规则直接放行或拦截，同时把审计日志异步吐回控制面。这样就算控制面临时升级抖动，正在跑的线上任务也不会全线雪崩。唯一需要妥协的是“策略同步延迟”，所以碰到吊销高危凭证、封禁恶意租户这类紧急指令时，必须配上短有效期凭证（短 TTL）、强制刷新推送或关键操作走集中二次校验来兜底。

### 2.3.2 Runtime 与 Sandbox：一个保活，一个防炸

- **Agent Runtime 是长任务的“保命宿主”**：它接住外部请求转成 Task，绑上对应的 Harness 版本、身份、租户、预算和运行环境，管排队、并发、超时、取消、Checkpoint 和故障恢复。对长任务而言，Runtime 天生得按“随时可能被杀进程、随时可能断网”来设计，保证任意环节重启后从外置状态接着往下走，而不是从头重新跑一遍。
- **Sandbox 是限制破坏范围的“防爆笼”**：它死卡文件系统可见目录、进程数、CPU/内存/磁盘、包安装权限、网络出站地址和 Secrets 注入。隔离强度按风险挑：低风险脚本用进程级隔离省资源，通用场景上容器，执行不可信代码或碰高敏数据时果断上微虚拟机或独立账号。但必须清醒：**Sandbox 只负责“技术上碰不到不该碰的东西”，它不知道某个动作有没有经过业务审批、也不知道改完的结果对不对。** 权限判定、人工审批和结果校验必须另配。

### 2.3.3 State Store、Workspace 与三层 AI Gateway

State Store 和 Workspace 把任务从单台机器里解放出来，但里面的东西千万别全塞进同一个存储：
- **Event Log 与 Checkpoint** 必须强一致且按顺序写，否则恢复时状态乱套；
- **Workspace**（工作目录与代码）需要支持快速打快照和一键回滚；
- **Artifact**（最终交付件）需要长期可寻址、防篡改归档；
- **Memory 与 Knowledge** 需要支持向量/关键词检索和权限过滤。

至于跨执行面和控制面的 **AI Gateway（统一网关）**，别把它当成简单的 API 转发代理。按管住的粒度，它承担三层截然不同的治理职责：
1. **LLM Gateway（按每次模型调用管）**：管多模型协议兼容、路由、限流、熔断降级和 Token 账单统计；
2. **MCP Gateway（按每次工具调用管）**：管 MCP Server 注册发现、OAuth/密钥托管（不把真密钥暴露给大模型）、工具级 ACL 权限和调用审计；
3. **Agent Gateway（按整次任务管）**：管多 Agent 路由分发、长会话亲和绑定、租户级并发配额与整任务预算上限。

工程实现上这三层完全可以集成在同一个网关产品里，但在配置模型上**策略粒度必须划清**，否则模型限流、工具鉴权和任务总预算会在一处规则里互相打架覆盖。

### 2.3.4 部署怎么选型：四档拓扑别硬抄大厂

参考架构不是让你第一天就从头造一套平台，表 2-5 给出了四种常见落地形态的取舍：

| 部署拓扑 | 最适合谁 | 最大好处 | 主要代价与坑 |
| --- | --- | --- | --- |
| **应用内嵌 SDK 直连模型工具** | 早期原型、低风险内部小工具、单应用 | 上手最快，几小时跑通，链路短好调试 | 密钥、状态、日志和风控散在各个业务代码里，难复用 |
| **全托管 Harness 与 Runtime** | 希望快速推生产，且数据合规允许上托管平台 | 长跑调度、Sandbox 隔离、扩缩容和观测开箱即用 | 有厂商绑定，深度定制能力受限，数据出域逐项过审 |

## 2.4 生命周期：从一次性 Demo 到可复现的五阶段闭环

### 2.4.1 发布单元不能只是代码：引入 Agent Release

传统后端发版，只要打一个代码镜像哈希就确定了行为；但 Agent 上线后，哪怕代码一行没改，只要后台偷偷改了一句 Prompt、换了一个模型权重、多放开一个 MCP 工具或者调低了上下文截断阈值，Agent 的行为轨迹都可能面目全非。

因此，企业级 Agent 的最小可复现发布单元必须是一个完整打包的 **Agent Release**，把六类要素打上版本号绑在一起：
1. **Model 配置**：具体模型版本、采样参数、推理预算与路由降级规则；
2. **Harness 脚手架**：编排代码、循环上限、Middleware 拦截点与终止校验条件；
3. **信息与能力资产版本**：Prompt 模板、Context/Memory 策略、Skill 与 Knowledge 索引版本；
4. **Tool 清单与权限**：开放的 Tool/MCP/Agent 列表、参数约束和凭证作用范围；
5. **运行环境配置**：Runtime 规格、Sandbox 隔离级别、网络出站策略与数据保留期；
6. **质量门禁套件**：对应的评估数据集、Evaluator 评分器、基线分数和准入红线。

只有这六样东西全部带上版本锁进一次 Release，线上出故障时你才说得清“当时到底跑的哪一版”，改完后也才证明得了“新版本是真的变好了”。如果允许运营人员直接在生产后台裸改 Prompt 不留版本，那所有评测结论在改完那一秒就全作废了。

读懂图 2-2，重点看清图中两条极其关键的**虚线回流机制**：

- **第一条：为什么要把“架构设计”单独拎成第一阶段，且治理和调优都有虚线直接指回“架构设计”？** 一旦第一步选错了形态或放宽了权限边界（比如高危操作没加审批、该用确定性 Workflow 却硬上了自由多 Agent），后面整个研发、运行、治理的成本区间就被锁死了。当线上反复出事故、调优发现靠改 Prompt 怎么打补丁都救不回来时，图里指回“架构设计”的虚线就在提醒你：**病根在形态和权限模型，别再叠补丁了，老老实实退回去重画架构。**
- **第二条：调优层的两条虚线为什么绝对不能混为一谈？** 图右下角的“调优”产出候选补丁后，**必须沿着长虚线回流到“构建”阶段**，经过“准入门禁（离线评估 + 安全检查 + 灰度预案）”重新签发 **Approved Release** 才能再上生产。而调优指向“运行”的那条短虚线，明确标注了“**仅观测，不改变生产版本**”——它只用来做线上流量抽样观察和 A/B 对比实验取证。所谓“受控自进化”，核心就是**任何从线上轨迹自动挖出来的 Prompt、Memory 或 Skill 补丁，绝对禁止绕过构建和门禁直接热更新到生产环境**。

### 2.4.3 治理不是上线后的“事后警察”，而是全链路硬约束

很多团队一听“治理”，觉得那是系统上线跑起来以后安全团队的事。其实恰恰相反：权限模型和数据红线在**架构设计**时就得画死，审批卡点和审计字段在**构建**阶段就得写进代码和策略里，**运行**阶段靠 Sandbox 和网关硬执行，**治理**阶段持续盯盘抓异常，**调优**阶段还要拿红队和仿真去验这些防线漏没漏风。

一个最实用的自检标准：**如果某条合规或安全要求，在架构和代码层没有任何策略接口卡住，只能靠上线后拉个群人工填表补救，那只要流量一上来，这条防线一定会形同虚设。**

## 2.5 本章小结

- **划分边界比堆砌组件更重要**：一套靠谱的参考架构靠三个互相不替代的视角撑起来——组件视图防能力漏项（Model、Harness 脚手架、五类信息、Tool/Protocol、Runtime/Sandbox、网关、观测评估）、平台视图防团队甩锅（执行面、数据资源面、控制面）、生命周期视图防把 Demo 当系统。
- **核心角色各自站稳**：Model 是可替换可路由的认知大脑；Harness 脚手架管上下文拼装、外置进度、工具调度、权限拦截和交付验收；五类信息对象把眼前视图（Context）、强一致进度（State）、跨会话经验（Memory）、企业文档（Knowledge）和版本化做法（Skill）硬拆开；Runtime 保长任务活下来，Sandbox 锁住爆炸半径，AI Gateway 在模型、工具、任务三层把好流量入口。
- **发布必须带完整上下文与门禁**：用绑定六类要素的 **Agent Release** 取代单纯发代码，严格执行“运行产 Trace 证据 → 调优验证改法 → 回流构建过准入门禁 → 再进生产”的受控闭环。
- **最后再提醒一遍**：参考架构是让你做减法的尺子，不是要你全套照搬的清单——永远按照任务确定性和风险等级，匹配刚好够用的最低充分架构。
