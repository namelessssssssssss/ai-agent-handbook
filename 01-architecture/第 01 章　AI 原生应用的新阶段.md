# 第 01 章　AI 原生应用的新阶段

仅仅一年多以前，团队做 AI 应用的起手式还很单一：写几段 Prompt、接一套知识库检索（RAG），再用写死路径的工作流（Workflow）串起几个业务接口，把大模型生成的文本丢给人自己看着办。那时候模型只是个“嘴替”，执行链路和业务状态全握在确定性代码手里。

到了这一阶段，玩法彻底变了。模型不再只是被动吐字的引擎，而是开始接管任务循环——自己看上下文、拆步骤、调工具、改环境，遇到报错还能反过来调整方案。Codex、Claude Code、Qoder 这些编程智能体（Coding Agent）率先把这件事跑通了：它们不只是补全几行代码，而是能自己翻整个代码仓库、列待办清单、改十几个文件、跑终端命令和测试，中间还能随时听人喊停纠偏。

但一线工程团队很快撞上一堵硬墙：**模型能干活，不代表光靠一个模型就能上线。** 恰恰相反，任务跑得越久、手里的工具越猛、改动的外部系统越真，模型外面那套工程脚手架和运行底座就越决定生死。行业里流传着一个核心公式——**Agent = Model + Harness**。其中，**Model** 是负责理解、推理、生成和做决定的认知大脑（但它看概率说话，而且本身不存持久状态）；**Harness** 则是包裹在模型外层的任务控制脚手架，负责拼装上下文（Context）、把任务进度（State / Todo）存到外面、管理 Tool 和 Skill、在危险动作前用 Hook 卡死权限，并在交付前拿独立验收器（Verifier）核对结果；真要推上生产扛住长跑和故障，还得再配上管调度恢复的 **Runtime**、管隔离防炸库的 **Sandbox**，以及观测、评估和安全治理底座。

换句话说，企业要设计的再也不是“一次大模型调用”，而是一个跨越大脑、脚手架、长跑底座和持续改进的完整应用系统。本书把这种与业务逻辑、数据、工具、环境和人机交互紧密咬合、最终交付**可验证结果**的应用形态，称为 **Agentic Application**。

本章解决两个最先拍板的问题：第一，Chat/RAG、Workflow、Copilot、单 Agent、长程 Agent 和多 Agent 各自解决什么问题，怎么避免乱用；第二，企业怎么判断成熟度（L1–L4），用**成本与风险可接受的最低充分架构**把项目落稳。

## 1.1 从“回答问题”到“动手交差”：为什么 Coding Agent 成了分水岭

### 1.1.1 上一阶段的三条天花板

上一阶段的 AI 应用（Chat/RAG、基础 Workflow、早期的 Copilot）大多没走出三条舒适区：

- **交互以单轮或短会话为主**：哪怕挂了函数调用（Function Calling）和 RAG，一次任务也在几秒到几分钟内结束。
- **执行路线由代码事先画死**：模型最多做个意图分类、填个参数，完整流程图早就写死在业务代码里。
- **交付物是“内容”不是“结果”**：回答通不通顺靠人看一眼就行；有没有真把事办成，没法靠系统自动核验。

这套模式在企业里很实用——Chat/RAG 解决了自然语言查文档，Workflow 让模型能嵌进审批和工单流，Copilot 靠人的实时把关兜住了模型的不靠谱。但它死死卡在两个前提上：**要么团队事先能穷举所有分支路径，要么人愿意一直坐在屏幕前盯着接管**。一旦碰上路径没法写死、步骤又长达几十轮的任务，老路子就彻底转不动了。

### 1.1.2 Coding Agent 一次性暴露的六大线上真痛点

Coding Agent 的意义远不止“帮程序员写代码”。它是第一个大规模跑在真实复杂环境里的 Agent 场景，把企业级 Agent 进生产必踩的坑一次性全露了出来：

1. **仓库太大，上下文根本塞不下**：几百万行代码不可能全喂给模型，必须靠检索、筛选、摘要和外置存储，把最该看的切片放进单次调用视图里。
2. **任务动辄几十步，模型一压缩就失忆**：改一个复杂需求要几十轮模型调用，必须把计划、进度和待办清单（Todo）稳稳存在模型上下文之外，不能全靠聊天记录硬撑。
3. **工具真会动文件和跑命令，一个手滑就炸库**：读写文件、执行终端、访问外网都有真实副作用，没有权限分级、Sandbox 隔离和不可逆操作审批，谁也不敢放线上跑。
4. **中间一定会报错，不能挂一次就从头再来**：测试失败、网络抖动、进程被杀是常态，执行底座必须支持错误捕获、重试、检查点（Checkpoint）和断点续跑。
5. **模型特别擅长“嘴上说完成了”**：它改完代码直接自夸“已修复”，结果一跑单测全红。完成与否不能靠模型自评，必须用编译、单测、静态检查、文件 Diff 或独立验收器（Verifier）说话。
6. **人不可能逐字监工，只能在关键节点出手**：用户没耐心看模型吐出的每一个 Token，系统必须在定计划、动高危操作和最终交付这几个卡点，支持随时打断纠偏（Steering）和人工拍板（Human-in-the-Loop，简称 HITL）。

Anthropic 在长时任务实践里，把 Session（事件账本）、Harness（任务脚手架）和 Sandbox（隔离执行环境）拆开，让模型能持续换代的同时保持状态与边界稳定；OpenAI 的长时工作实践同样押注可持久化的线程（Durable Thread）、可审阅的外部记忆、Skill 资产、Steering 引导与人工复核。两家实现细节不同，指向的工程真相完全一致：**长任务绝不是把聊天窗口拉长，而是要把“思考、状态、执行、控制”拆成各自独立的层次。**

### 1.1.3 这套套路很快溢出到了研发之外

只要一个 Agent 能在隔离工作区里读写文件、调工具、保状态、跑长任务并接受人的纠偏，它能干的就绝不只是写代码。行业研报自动调研与数据核对、复杂数据分析、企业 IT 运维排障、多系统客服工单协调、知识库自动巡检更新，甚至高风险业务里先生成“可验证执行草案”给人审批——底层要的都是同一套底座能力：模型路由、上下文组织、工具与协议接入、工作区状态、沙箱与权限、长任务恢复、可观测、评估和持续调优。当这些需求在多个应用里反复出现时，它们就顺理成章沉淀成了通用的 Harness 与平台底座。

| 上一阶段的 AI 原生应用 | Agentic Application |
| --- | --- |
| 生成一段让人看的回答 | 交付一个可验证的环境或业务结果 |
| 单轮或短对话 | 多步骤、有状态，能跨会话异步长跑 |
| 主要靠 Prompt 词和 RAG 撑着 | 靠认知大脑（Model）和外层脚手架（Harness）协同驱动 |
| 业务代码死板调用模型 | Agent 在权限和沙箱围栏内主动选工具、动环境 |
| 只看输入和输出打分 | 同时检验执行轨迹、环境变更和最终状态 |
| 开发完上线基本定型 | 靠运行轨迹、评估和灰度的闭环持续进化 |

## 1.2 应用形态不是升级梯子：单 Agent、Workflow、长程与多 Agent 怎么选

### 1.2.1 别把“并存的工具”当成“代际淘汰”

很多团队一立项就容易陷入误区：觉得 Chat/RAG 太土、Workflow 过时了、Single-Agent 是初级版、必须一步到位上 Multi-Agent 才够先进。结果把一个本来 5 步写死 API 就能跑在 99.9% 成功率的退换货流程，硬改成了几个 Agent 互相发消息踢皮球，延迟涨了五倍、账单翻番、出了错连日志都看不懂。

不同应用形态根本不是“谁淘汰谁”，它们切的是四根完全不同的尺子：**任务循环谁攥着、路径在写代码时定死还是运行时现想、动不动外部系统、任务跨不跨时间与多角色**。其中，Single-Agent、Long-Horizon Agent 和 Multi-Agent 都属于 Agentic Application，后两者既不是所有项目的终点，也不是必经阶梯。

| 应用形态 | 核心价值 | 路径谁定、何时定 | 状态与时间跨度 | 人的角色 | 什么时候选它最划算 |
| --- | --- | --- | --- | --- | --- |
| Chat / RAG | 问答、总结与查知识 | 应用代码事先写死 | 单轮或短对话 | 提问、阅读并自行判断 | 只要输出文本参考，不直接改外部系统 |
| Workflow | 稳定可重复的流程自动化 | 设计期画死，只有局部分支 | 步骤有限，状态结构固定 | 设计流程并在审批节点签字 | 规则明确、路径可穷举、出错代价极高 |
| Copilot | 放大专业人士的实时效率 | 人一直在掌舵决定下一步 | 可跨多轮，但主控权在人 | 亲自驾驶、验收并兜底 | 专业判断没法自动化，只把脏活累活外包局部步骤 |
| Single-Agent | 单个 Agent 围绕目标动态搞定有界任务 | Agent 在运行时现场规划部分或大部分路径 | 多步骤、有状态，一次任务或单次会话内闭环 | 下目标、划护栏、卡高危审批、验收结果 | 路径没法事先穷举、环境有报错反馈、结果可客观验证 |
| Long-Horizon Agent & Multi-Agent | 长程推进跨天任务；多 Agent 分工协作啃硬骨头 | 前者随长期反馈动态调；后者由多个 Agent 移交或评审推进 | 前者跨会话/跨进程且支持暂停恢复；后者维护多角色状态与边界 | 设阶段检查点和例外处理；或划清多角色权限与协作契约 | 只有单个 Agent 确实被任务时长、上下文容量或权限隔离卡死，且新收益能盖住新复杂度时才上 |

### 1.2.2 现实里的主力形态：Workflow 与 Agent 长期混合（Hybrid）

Workflow 的王牌是**确定性强、好测试、审计一清二楚**；Agent 的王牌是**路径穷举不了时，能看环境报错现场应变**。偏偏企业里一条真实业务流，往往两样都有。比如理赔或退款：核对资格、算账入账、资金划拨必须走写死校验规则的 Workflow；但看懂用户拍糊的发票、去多方日志里排查异常原因、动态挑一个诊断工具，最适合交给 Agent。

所以企业里真正跑得通的主流，绝不是“全盘 Agent 化”，而是 **Hybrid（混合形态）**：
- 要么在确定的大 Workflow 里，把不确定那一两步挖个槽嵌进 Agent，框死它的输入、超时和可用工具；
- 要么反过来，让 Agent 做总调度，遇到成熟高频的子流程时直接调用经过单测的确定性 Workflow 或 Skill，省得每回都让大模型重新推理一遍。

Google 在总结 Agent 设计模式时把顺序、并行、协调器、层级分解、评审改进并列，反复强调背后其实是在**延迟、成本、共享状态和失败传播**之间做权衡。归根结底，自主权大小要跟着任务风险走：可逆、低风险的操作（比如只读查日志、本地跑单测）多放权；不可逆、高风险的操作（比如写线上库、转账、发群通知）用确定性规则和人工审批卡死。

### 1.2.3 往时间拉长 vs 往协作拆开：两条正交的扩展线

当单次会话的 Single-Agent 真的不够用时，才有必要考虑往两个互不相干的方向做扩展：

- **纵向拉长成 Long-Horizon Agent（解决“跑得久、不能断”）**：面对几小时甚至跨几天的任务，上下文窗口早晚爆掉，进程也会因为发版、超期被重启。系统必须把计划、进度和账本外置成持久 State，靠检查点（Checkpoint）、调度排队、失败恢复和可审阅外部记忆撑住连续性。它的难点不是“跑得久”，而是**跑了三天后目标别漂移、状态别和外部世界对不上账**。
- **横向拆开成 Multi-Agent（解决“分工与隔离”）**：当一项任务同时撞上多个专业领域、互相冲突的权限域，或者把所有工具和提示词全塞一个大脑里导致注意力稀碎时，才把任务拆给多个边界清晰的 Agent（主从协调、顺序接力、并行汇总、生成与评审互相挑刺）。它的价值绝不是“多调几次模型显得高级”，而是为了**上下文隔离、最小权限切分和独立交叉校验**。

这两个维度彼此独立：单 Agent 一样可以跑长程任务，多 Agent 也可以只配合五分钟。更重要的是，**千万别忽略复杂度反噬**——长程带来状态漂移和补偿难题；多 Agent 带来传话信息衰减（还记得调研里 60% 团队踩的头号坑吗？）、通信翻倍和互相死锁。只要一个边界清晰的 Single-Agent 配合好工具和 Skill 能以更低成本搞定，就别硬拆。

## 1.3 Agentic Application 到底怎么定义：核心公式、六大特征与关键边界

### 1.3.1 核心定义与架构图解

本书对 **Agentic Application** 的定义很实在：**它是以 Model 与 Harness 共同组成的执行主体为核心，接上业务逻辑、数据、工具、运行环境和人机交互，能围绕目标维护状态、动态规划、动手执行并在确定性护栏内交出可验收结果的应用。**

背后的最小架构共识，就是那条公式：

> **Agent = Model + Harness**

**Model** 是概率性的认知大脑，专管理解、推理、生成和拿主意，但它不管自己明天还记不记得进度，也不管怎么安全地连数据库。**Harness** 则是套在模型外层的任务控制脚手架，它负责决定模型这一轮看到什么信息、进度账本存在哪、能调哪些工具和 Skill、什么动作必须被 Hook 拦截或让人拍板，以及做完后拿什么标准验收入库。没有 Harness 的 Model 只是一段会聊天的算法；没有 Model 的 Harness 只是一套写死的脚本。只有两者咬在一起，才算一个能干活的 Agent。

看懂图 1-1 的关键，是顺着从上到下的两层分解：
- **顶层分工**：Agent 由左边的 **Model（认知大脑）** 和右边的 **Harness（外层工程脚手架与约束体系）** 合起来构成。

在实际系统分层里（第 02 章会展开），贴着模型直接控制任务怎么推演的脚手架核心就是 **Harness**，而扛住多进程、断线重连和破坏隔离的底层托盘则下沉为 **Runtime** 和 **Sandbox**，旁边再配观测、评估和权限底座。叫什么名字不重要，重要的是**不能把这六块里的关键职责漏掉或甩给模型自己硬扛**。

### 1.3.2 判断一个应用是不是真进入 Agentic 阶段的六把尺子

别听产品叫什么名，拿下面六条一量就准：

1. **对着可验收结果交差，不是只吐答案**：用户给的是目标，验收标准看的是测试过没过、单子改对没、环境变了没，不是看文案通不通顺。
2. **能看反馈现场改路子**：遇到工具报错或新线索能自己换招试，不是沿着事先画死的一条线闷头跑到底。
3. **真能改变外部环境**：能调 API、查改库、改文件、跑命令、操作浏览器，甚至把子任务派给别的 Agent。
4. **状态跨出单次调用窗口**：任务进度不只活在对话里；跑长了能暂停、换台机器恢复、出错能接着重试。
5. **自主权被确定性护栏卡死**：权限边界、沙箱笼子、Token 预算、中间件拦截、结构化校验和人工审批是硬代码和策略，模型想绕也绕不过去。
6. **靠轨迹和评估持续进化**：系统不只存最终那句话，还把工具调用轨迹、状态变化、开销和人工打回全记下来，靠回归测试和灰度验证发下一版。

这六条不是“必须一天全配齐的豪华套餐”，而是判断系统有没有跨过“聊天玩具”门槛的坐标轴。

### 1.3.3 一张表理清八个容易混用的概念

为了避免开会时开发、算法和运维各说各话，表 1-3 直接把这八个核心词按“它是什么”和“一线最容易踩的误区”对齐。

| 概念 | 一句话说清它是什么 | 一线最容易踩的误区 |
| --- | --- | --- |
| **Model** | 负责理解、推理、多模态、生成与决策的概率性认知大脑 | 以为选个最强模型就是 Agent，结果没状态、没隔离、没验收全在线上翻车 |
| **Harness** | 包裹在 Model 外层的任务控制脚手架，负责拼 Context、管 State/Todo、调 Tool/Skill、做权限 Hook 和完成前 Verifier 验收 | 把它简化成几行 System Prompt 或 `while` 循环，一到长任务和并发就丢状态、无限死循环 |
| **Agent** | Model + Harness 组合起来的完整执行主体，能围绕目标观察、判断、行动并收口 | 把任意调过一次大模型接口的微服务都包装成“智能体” |
| **Single-Agent** | 单个 Agent 掌管任务循环，在一个有明确边界的任务或会话内闭环 | 把单轮无工具对话当 Single-Agent，或以为单 Agent 一定干不了复杂活 |
| **Long-Horizon Agent** | 靠外置 State、检查点、恢复机制和人工引导，跨会话、跨进程持续跑下去的 Agent | 以为“买个 200 万窗口的模型”或者“把一个 HTTP 超时拉长到 3 小时”就叫长程 Agent |
| **Multi-Agent** | 多个边界、角色和权限不同的 Agent，按明确机制移交、协同或互相复核完成任务 | 同一段提示词开五个并发调模型就自称 Multi-Agent，或者用多 Agent 硬拆简单流程 |
| **Agentic Application** | Agent 落进具体业务里的完整应用形态（覆盖单、长程、多 Agent 及混合形态），接通业务规则、数据、工具和用户交互 | 把开源框架 SDK 本身或者底层公共平台当成已经能交付业务价值的完整应用 |
| **Agent Platform** | 给多个业务 Agent 提供共享构建、Runtime、Sandbox、网关、观测与评估的公共底座平台 | 因为买了平台，就逼着所有简单问答或确定性脚本都走最重的平台链路 |

表 1-3　核心概念的工程界定与常见误区

这里有三个坑，一线立项时最容易一脚踩进去，必须单独点透：

- **坑一：买了 Agent 框架 ≠ 有了生产级 Agent**。LangGraph、AgentScope 这类框架给了 Loop、Tool 绑定等开发零件，但你的业务 Context 怎么筛、State 存哪张表、哪几个危险接口要弹窗审批、做完拿什么数据集验，框架替你做不了主。
- **坑二：Long-Horizon 和 Multi-Agent 不是智商勋章**。只要单 Agent 在有界时间里就能用更低成本稳定做完，多加长程状态和多 Agent 通信就是在自己给自己找 Bug。
- **坑三：应用形态和底座平台是两码事**。一个 Single-Agent 可以稳稳跑在企业级 Agent Platform 上享受网关、沙箱和观测红利；反过来，就算你把平台建得像航空母舰，简单场景该用单 Agent 还是用单 Agent。

## 1.4 从 Demo 到规模运营：L1–L4 成熟度与操作系统视角

### 1.4.1 成熟度不看产品起名，看“管不管得住”

有的产品名字叫“全自动 AI 员工”，扒开代码看其实就是个单轮对话挂了个查询工具；有的系统虽然主打 Workflow 编排，却已经把状态持久化、权限拦截、全链路追踪和回归评估做到了位。**所以成熟度从来不由营销名词决定，只看四件事：任务循环闭环能力、时间跨度、环境操作风险以及生产治理有多硬。**

表 1-4 给出了判断单个应用成熟度的 L1—L4 四级标尺：

| 成熟度 | 典型长相 | 真正具备的能力 | 常见卡点 | 往上一级跨的门槛 |
| --- | --- | --- | --- | --- |
| **L1 辅助生成** | Chat、RAG、基础 Copilot | 查资料、生成文本、调个把只读工具 | 闭环还得靠人肉复制粘贴，系统基本不记任务状态 | 沉淀可复用的 Prompt、权限清晰的知识库和基础评测集 |
| **L2 受控自动化** | Workflow、在固定流程里局部嵌 Agent | 流程画死、结构化输出、局部节点动态判断、人工审批 | 一遇到没预料到的异常分支就卡死或转人工 | 明确能放权和不能放权的边界，引入 Harness 脚手架、工具策略与轨迹评估 |
| **L3 Agentic Execution** | Single / Long-Horizon / Multi-Agent 或混合形态 | 自主规划、真实操作工具与环境、多步状态持久化、局部失败自愈 | 单点 Demo 挺惊艳，一放量就撞上成本爆炸、越权风险、版本漂移 | 补齐独立的 Runtime、Sandbox、全链路可观测、安全护栏与回归验证 |
| **L4 规模运营与持续优化** | 多任务多租户并跑、统一治理、闭环自演进 | 跨应用策略控制、成本分摊、线上线下双评估、灰度发布与受控改进 | 整套体系很重，靠单个应用团队扛不住建设维护成本 | 用共享平台、组织级知识资产和自动化工具把治理边际成本打下来 |

表 1-4　Agentic Application 成熟度标尺（L1–L4）

看懂这张表有两个防踩坑原则：
1. **形态和成熟度是两张表，别混着对**。Single-Agent、Long-Horizon Agent 和 Multi-Agent 讲的是“怎么干活”，L1–L4 讲的是“跑得有多稳、管得有多严”。一个 Single-Agent 完全可以做到 L4；一个凑热闹拼起来的 Multi-Agent 如果连权限隔离和回归测试都没有，照样停在漏洞百出的早期 L3。
2. **L1 和 L2 不是低人一等，很多业务就该停在 L2**。低风险的内部百科助手停在 L1 省钱又好用；涉及资金清算、交易审批的核心系统选择 L2（用确定性 Workflow 兜底关键路径）反而是最负责任的架构选择。**永远追求“成本和风险可接受的最低充分架构”**——只有当现有级别确实啃不下业务价值、而新增收益明显大过工程代价时，才值得往上跨。

### 1.4.2 敲定成熟度后，动手前先答完这五个问题

在创建仓库和写第一行编排代码前，先把这五件事拍死：

1. **怎么定架构**：选 Workflow、Single-Agent 还是 Hybrid？真需要拉成长程或拆成多 Agent 吗？哪些步让模型动态想、哪些卡死在确定性代码或人工审批里？
2. **怎么搭 Harness**：Model、循环逻辑、Context 拼接策略、State 账本、Memory、Tool 和 Skill 怎么拆装？哪些高频套路该固化成 Skill 别每次让模型重猜？
3. **怎么跑稳底座**：长任务怎么排队调度、状态落哪张库、命令和文件放哪种隔离等级的 Sandbox 里跑、机器挂了从哪一步恢复？
4. **怎么立治理规矩**：Agent 用谁的身份干活、能碰哪些数据、预算上限怎么卡、出事了从哪条审计链追责？
5. **怎么验证并变好**：拿什么客观指标算“成功”、靠什么 Trace 和黄金评测集回归、怎么灰度放量以及改崩了怎么秒级回滚？

### 1.4.3 多个 Agent 并跑后：为什么 Kubernetes 兜不住，得看操作系统视角

当企业里只有一个两个 Agent 时，每个团队在自己的 Harness 或服务里顺手写点限流、重试、目录隔离和日志埋点也能凑合过。可一旦进入 L4，几百个租户、十几种框架开发的 Agent 在同一批集群里并发长跑，就会撞上一个躲不开的老问题：**这就像当年多个互不信任的程序抢同一台物理机，必须由操作系统统一管调度、隔离、授权、恢复和审计。**

有人会反问：“云平台和 Kubernetes 不是早就把调度、容器、配额和 IAM 全做了吗？”

还真不一样。**传统操作系统和 K8s 的所有机制，都建立在一个隐藏前提上：程序怎么跑，是程序员在写代码时就写死的。** 进程创建时一次领完权限、死了重启容器拉起、审计看系统调用就行。可 Agent 的执行路径是模型在运行时现决定、动态拼出来的——这就把传统系统管理的几乎每一条假设全掀翻了：

| 管理维度 | 传统软件 / 容器（路径写死） | Agentic Application（路径运行时生成） |
| --- | --- | --- |
| **跑的到底是什么** | 进程或容器 Pod，绑定具体代码入口 | 一次任务运行（Run），可跨多个进程、机器甚至休眠几天 |
| **状态在哪** | 跟着进程内存走，进程一退就释放 | 必须外置持久化，随时可挂起、换机恢复 |
| **怎么调外部能力** | 启动时定死的系统调用和设备接口 | 运行时按需发现并动态接入的工具与 MCP 端点 |
| **权限什么时候验** | 启动时一次性批完权限，越界直接拒绝 | 每次高危操作都得按上下文和策略现验，而且得随时能整串撤销 |
| **挂了怎么恢复** | 容器健康检查不过就杀掉重拉一个 | 重启进程不等于修好任务——可能已经发出了外部写请求且正在等人工审批 |
| **出事了查什么账** | 系统调用号、文件访问记录 | 得把用户意图、模型决策、工具调用、环境返回和最终后果串在同一条链上 |

表 1-5　传统软件与 Agent 在运行管理假设上的核心错位

最要命的是两点：**第一，授权不能只在启动时发一次**，模型随时可能受恶意网页或日志诱导去调原本不该碰的参数，拦截器必须卡在每次高危动作的必经之路上；**第二，恢复绝不是看容器死没死**，一个等待审批且已经扣了款的 Run，K8s 探针看它没死，或者重拉一个新容器从头再跑一遍，结果只会把钱扣两遍。

所以云和 K8s 只是底盘，不是替代品。在业务 Harness 和底层基础设施之间，必须长出一层管公共运行对象（Run、Workspace、预算租约、强制边界和独立证据）的新系统层——本书在 **第 30 章** 将它称为 **Agentic OS**。具体任务怎么推、什么时候算做完，这种业务语义永远留在应用侧 Harness；而轻量沙箱创建回收、绕不过去的出站卡控、跨任务的统一审计，迟早要沉到这层公共底座里去。

## 1.5 本章小结

- **看清主体**：**Agent = Model + Harness**。Model 负责认知和决定，Harness 脚手架负责拼上下文、管外置状态、接工具和做验收，生产落地再配齐管长跑的 Runtime、管隔离的 Sandbox 以及观测和安全治理。
- **选对形态**：Workflow、Single-Agent、Long-Horizon Agent 和 Multi-Agent 不是谁替代谁。能用确定性 Workflow 加局部 Agent 搞定的 Hybrid 方案就别上全自由调度；长程（时间跨度）和 Multi-Agent（角色协作）都带沉重工程代价，单 Agent 够用绝不硬拆。
- **克制选型**：别被产品名字忽悠，拿 L1–L4 成熟度对照真实风险和收益，选择**成本与风险可接受的最低充分架构**。架构边界必须在动工前定好。
- **看懂趋势**：多个 Agent 长期并发后，调度、隔离、授权、恢复和审计都会因为“运行时动态路径”重写规则，这正是第 02 章要划清责任域、第 30 章要收束为 Agentic OS 的原因。
